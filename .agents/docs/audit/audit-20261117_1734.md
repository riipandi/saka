# Architecture audit — layers, module maturity, data and concurrency, security delta

Audit date: 2026-11-17, branch `issues-remediation` at `af1f7929`, clean tree. The owner asked for an architecture audit and picked the focus in chat: layer and package boundaries, module consistency and maturity, data and concurrency, and the security delta since the six earlier audits. Scope is the Go backend plus the webapp and its sibling packages. The driver is maintainability. A second pass the same day read the implemented modules one by one (see "Module coverage"). Read-only: no production code changed, no test added, no file outside this one and the `index.md` row written.

## Verdict

The boundaries the docs promise hold where a tool enforces them, and the tooling baseline is green. The module pass found that the sharpest defects sit inside features, not between layers: the storage upload surface lets any signed-in account replace or delete other accounts' files and serve script from the application origin (F-15); OIDC tokens outlive the account standing that issued them (F-16); and two separate paths lead to account takeover (F-18, F-19).

## Boundaries that hold

Checked against the import graph, not the docs.

- `framework/**` imports nothing from `internal/`, `modules/`, `cmd/` or `web/`, and `pkg/**` imports nothing from `framework/`, `internal/` or `modules/`.
- `internal/transport` imports no module in non-test code. `internal/registry` is imported only by `cmd`.
- No module imports another area. `modules/identity`'s sub-features are the only intra-area edges.

## Checked and cleared

Claims I tested and dropped, so nobody re-opens them.

- **IPv4-mapped IPv6 bypass of the webhook destination check.** `netip.Addr.IsLoopback`, `IsPrivate` and `IsLinkLocalUnicast` unmap `::ffff:a.b.c.d`; run against `::ffff:127.0.0.1`, `::ffff:10.0.0.5` and `::ffff:169.254.169.254`, all three are refused. (The CGNAT gap in F-24 is real.)
- **Signup-token over-use.** `ConsumeSignupToken` carries `usage_count < usage_limit` and the expiry in the `UPDATE`'s `WHERE` (`modules/identity/signup/repository.go:243-262`).
- **Refresh-token rotation in `session`.** The row lock plus the `token_hash` compare serializes two renewals, and the reuse revocation commits (`modules/identity/session/service.go:483-509`).
- **Single-use codes** (password reset, email change, MFA recovery codes, TOTP step, device pairing, signup invitations) all spend through a guarded `UPDATE`/`DELETE`; the TOTP replay guard is a step compare-and-set.
- **Sort-key injection.** List sorts resolve through whitelists (`datastore.ListOrder`).
- **Webhook signing secrets and SCIM tokens** are sealed at rest and never read back.

### F-15 Any signed-in account can overwrite or delete any stored file and serve script from the app origin

The tus surface is guarded by `Authenticated` alone (`internal/guard/rules.go:536-539`), and `rules.md` accepts "any signed-in account may upload into any bucket". The code goes further than that sentence.

- **Overwrite.** `TusBegin` truncates the staging file and upserts the manifest row for the named `bucket/key` (`framework/storage/tus.go:81-85`, `manifest.go:221-232`). The upsert replaces `metadata`, resets `status` to pending and sets `is_private = false`. It never checks that the key is new or that the caller owns it.
- **Delete.** `DELETE /api/uploads/{bucket}/{key}` calls `TusDiscard`, which removes the manifest row and the staging file of any key (`tus.go:225-234`). It does not check that the row is a tus session. `/storage` answers 404 for a key with no manifest, so the file is gone to readers.
- **Private to public.** A private object is flipped public by the same `TusBegin`.
- **Hijack.** `HEAD` and `PATCH` act on any key's session without an owner check.
- **Script on the app origin.** The served `Content-Type` is the client-declared `filetype` (`tus_handler.go:139-160`, `internal/transport/handler/storage.go:104-108`). The default bucket is seeded with no size limit and no MIME list (`internal/database/seeders/default_bucket_factory.go:54-55`). The CSP is `script-src 'self'` (`framework/middleware/security.go`), which forbids inline script but admits a same-origin `<script src="/storage/…/x.js">`. An account uploads `x.js` as `application/javascript` and `x.html` as `text/html`, then sends a link to `x.html`. The script runs on the app origin, where the session tokens are JS-readable cookies by design (`rules.md`, webapp entry: "the script gate is the fence"). The fence has a hole.

Impact: file defacement and deletion across accounts, including profile pictures at the predictable key `pictures/<user-uuid>.<ext>` (`modules/identity/user/picture.go:64-71`), and token theft from any visitor of the link, administrators included. Self-signup (`access.mode` open) is enough to reach it.

Fix, smallest first: serve `/storage` with `Content-Disposition: attachment` and `Content-Security-Policy: sandbox` unless the manifest's type is on a safe list, or force `application/octet-stream` for non-image types; refuse `TusBegin` on an existing final object and `TusDiscard` on a row without the tus marker; record the owner in the manifest metadata at creation and require it on `HEAD`, `PATCH` and `DELETE`. The ownership rule is a product decision (it changes `rules.md`'s upload rule), so it is listed under "Decisions needed"; the serving headers are not.

### F-16 OIDC grants and refresh tokens survive ban, disable, deletion and group removal

The only code that deletes grant rows is `revokeGrants` (`modules/federation/oidc/consent.go:308-337`), reached from the user's own consent revocation and from RP-initiated logout (`consent.go:235,274`). The ban orchestration carries a session ender and a notifier and nothing for the protocol store (`modules/identity/user/service.go:230-240`). `oauth_sessions` has no foreign key to `users`; the subject sits in JSON. The token endpoint runs a grant handler that only stamps the refresh window (`protocol.go:195-197`), and the claim builders read the account without judging its state (`protocol.go:634-644`). The group-restriction and sign-in checks run at authorize time only (`protocol_policy.go:261-276`).

Scenario: an administrator bans or disables an account, or deletes it, or removes it from the group a client is restricted to. The relying party's refresh token keeps minting access and ID tokens for up to `oidc.refresh_token_hours` (default 336, 14 days) or `oidc.offline_refresh_token_hours` (default 720, 30 days), and `userinfo` keeps answering. The identity-session revocation the ban does perform does not reach these tokens.

Fix: a per-user revocation in the protocol store (the delete `revokeGrants` already writes, without the client filter), called from the ban, disable, delete and group-membership paths through the existing seam pattern; and a state check in the grant handler so a refresh for a restricted account answers `invalid_grant`. F-28's missing index makes the per-user delete a scan today.

### F-01 A restarted dispatcher races the previous generation's goroutines

`dispatcher.start` is guarded by `running.CompareAndSwap(false, true)` (`dispatcher.go:122`), and the fetcher's deferred cleanup clears the flag (`dispatcher.go:263`). That cleanup runs when the fetcher exits, which can be before the triggerer and the workers have exited. A second `Start` after a cancelled context therefore passes the guard and rewrites `d.ctx`, `d.shutdownCtx`, `d.tasks` and `d.ticker` (`dispatcher.go:126-138`) while the old triggerer still reads `d.shutdownCtx` and `d.ctx` (`dispatcher.go:250-252`). The comment at `dispatcher.go:162-166` states the opposite invariant: "stop must wait for them to exit before returning" so a restart cannot rebuild the fields under a live reader. That holds only when the caller calls `Stop` between the two starts.

Repro: `go test -race -count=3 -run TestTheSessionRetentionRunsTwiceWithoutDoingItAgain ./internal/jobs` reports `DATA RACE` on every run (10 reports over three runs). The test starts the client twice with a context it cancels on return and defers `Stop` to cleanup (`internal/jobs/session_cleanup_job_test.go:96-105`).

Impact: production starts the queue once per process, so a user is unlikely to hit it today. The cost is a red `-race` run and a false statement in the engine's contract. No task, workflow (`.github/workflows/test.yml`) or hook runs `go test -race`, which is why the suite stayed green.

Fix: have `start` join the previous generation (`d.workers.Wait()`, `d.engines.Wait()`) before it rebuilds, or clear `running` only after the join. Add a restart-after-cancel test in `framework/queue`. Add a `-race` pass over `framework/...` to the validation steps.

### F-02 `public.rate_limits` is never swept

The default driver is the database (`internal/config/defaults.go:382`). `fn_check_rate_limit` upserts one row per key, and the key is bucket plus client address (`framework/middleware/ratelimit.go:202-204`). A row is reset in place when its window lapses but never deleted. `entity.TableRateLimits` has no consumer outside the entity file, and `cleanupProcessor` (`internal/jobs/cleanup_job.go:70-120`) sweeps queue rows, WebAuthn tokens and signup tokens, not this table.

Scenario: every distinct source address that touches a counted route leaves a permanent row. An attacker rotating IPv6 addresses, or a busy public deployment, grows the table without bound; every check then runs against a larger index, and the check holds an advisory lock per key.

Fix: delete rows whose window ended more than one window ago inside `cleanupProcessor` (the table has `window_start` and `window_seconds`), in batches. The Valkey driver expires keys itself, so this concerns the default driver only.

### F-03 The limiter fails open, credential bucket included

When `Limiter.Allow` returns an error the middleware passes the request and counts it as `degraded` (`framework/middleware/ratelimit.go:160-167`); a failing global check does the same (`:150-154`). The database limiter runs on the shared application pool (`internal/transport/middleware/ratelimit_database.go:36-46`). Under pool exhaustion the limiter's own query fails first or alongside everything else, and the credential bucket (`guard.RateAuth`, ten requests per window) stops protecting sign-in and code procedures at the moment a brute-force run is also loading the database.

The converse also holds: the deployment-wide code budget (`rate_limit.code_global_limit`, default 300) is one shared key, so an attacker holding about thirty addresses (ten requests each per window) can exhaust it and make every legitimate reset, verification and one-time-access submission answer 429.

Recorded elsewhere: only the restriction lists' fail-open is written down (`architecture.md:301`). The limiter's posture is an undocumented decision.

Fix options: a per-class `FailClosed` flag set for the credential and code buckets (answer 503 or 429 on a limiter error); or a small dedicated pool for the limiter. The first is smaller. Needs the owner's call because it changes behaviour under a database fault.

### F-04 `internal/jobs` and `modules/*` import each other

`internal/jobs` imports eleven module packages for its processors (`apikey`, `devicelogin`, `multifactor`, `oauthsso`, `password`, `session`, `signin`, `user`, `webauthn`, `notification`, `webhook`). In the other direction, `modules/identity`, `modules/identity/verification`, `modules/identity/onetimeaccess` and `modules/federation` import `internal/jobs` for task types (`jobs.EmailVerificationTask`, `jobs.OneTimeAccessEmailTask`, `jobs.BackchannelLogoutTask`) and for eleven notifier constructors that `modules/identity/module.go` calls at lines 266, 302, 348, 377, 418, 479, 515, 522, 550, 661. This is the one place the layering runs both ways.

It compiles only because the importing packages differ. The next processor that needs `verification`, `onetimeaccess` or `federation` closes a cycle, and the way out then is a refactor under pressure. It also contradicts the consumer-shaped interface rule in `rules.md` ("Cross-feature gate").

Fix direction: move task payload types and the notifier constructors into a leaf package both sides import, or into each owning module, and leave only the processors in `internal/jobs`. This is a structural choice; see "Decisions needed".

### F-05 Modules take the whole `config.Config`

Five constructors take `config.Config` by value (`signin.NewService`, `webauthn.NewService`, `onetimeaccess.NewService`, `jwks.NewService`, `identity.Authenticate`) and `appconfig.NewModule` holds one. The nine `module.go` files call `do.MustInvoke` 205 times; `modules/identity/module.go` (840 lines) invokes `*config.Config` fourteen times and reads `c.Mailer.Notifications.*` flags inline. The framework side follows a different rule: a typed `Options` field, with `internal/config/adapters.go` translating (`rules.md`, "Framework boundary").

Cost: every service can read every secret, and a config rename touches module internals. The service tests must build a full `Config` to construct one service.

Fix: introduce small per-service options structs and fill them in `module.go`. Do it service by service when each is next touched; a bulk change would be large and low-value. The service-locator style in `module.go` is the documented design (area owns wiring), so the count of 205 is a size signal, not a violation.

### F-06 Transport hosts product features and resolves services itself

Three things in `internal/transport` are features rather than transport:

- The queue and scheduler admin procedures (`handler/admin_rpc.go`, 485 lines) hold the database and the audit recorder and write audit rows directly, with no service or repository and no `kernel.Module`. `rules.md` says every feature implements the kernel contract and `Deps` carries services.
- The tus uploads and the storage mount resolve `*storage.Manager` and `*storage.Signer` from the DI container inside `NewRouter` (`router/http.go:236-246,281-288`), driven by `Options.Injector`. A nil injector silently mounts no route, so a mis-wired container ships a smaller product instead of failing at boot. `Options` carries nine infrastructure fields for the same reason. F-15 lives in this unowned code: no module owns the upload authorization.
- The doc comment for `NewRouter` sits above `collectorOrigin` (`http.go:124-148`), and `NewRouter` itself has none.

Fix direction: make "system administration" and "uploads and storage serving" modules built by the registry, and pass the resolved manager and signer in `Options` so a missing one fails `Prewarm`. Owner decision.

### F-17 Email addresses are case-sensitive end to end

`users.email` is `TEXT NOT NULL UNIQUE` with only a case-insensitive regex check (`internal/database/migrations/00004_create_identity_tables.sql:11`); the `citext` extension is installed (`00001`) and unused. No layer folds case: the proto pattern accepts upper case (`api/connect/identity.proto:341`), signup stores the string as typed, sign-in compares `u.email = identity` (`modules/identity/signin/repository.go:81-83`), and the reset, email-change and SSO lookups compare `email = $1` (`password/recovery_repository.go:49`, `oauthsso/repository.go:374-379`). Only the blocklist lowercases (`blocklist/service.go:168`).

Consequences: `Alice@x.com` and `alice@x.com` become two accounts, which defeats the one-account-per-address rule and the strict-mode anti-enumeration decoy; a user who types a different case than the stored one cannot sign in or reset their password (the reset answers its generic success and sends nothing); and an SSO provider's lower-cased address never links to a mixed-case local account, so the JIT path creates a second account.

Fix: fold the address to lower case at the write and lookup boundaries, or move the column to `citext` through an additive migration that first reports existing case-colliding pairs. A migration is a schema decision; see "Decisions needed".

### F-18 SSO linking matches unverified local accounts

`ContinueSignIn` links a provider identity to the account `AccountIDByEmail` finds (`oauthsso/resolution.go:266-275`). That query is `SELECT id FROM users WHERE email = $1` with no condition on `email_verified_at` (`oauthsso/repository.go:374-379`). The linking toggle defaults on.

Scenario (pre-hijacking): with open sign-up, an attacker registers the victim's address with a password they know. The row stays unverified, so the attacker cannot sign in yet. The victim later signs in with Google, a verified address; the flow binds to the attacker's row and opens a session in it. The row's password still belongs to the attacker. The moment the victim confirms the verification code that arrived at sign-up, or any later step marks the address verified, the attacker's password signs in to the account the victim now uses.

Fix: link only to an account whose `email_verified_at` is set; for an unverified match, treat the provider's verified address as the proof and, in the same transaction, clear every credential the unverified row holds (password, MFA, API keys, sessions) before linking. Refusing alone does not close the vector: once the victim verifies the sign-up mail, the attacker's password is live.

### F-19 Email change and self-delete take API keys and no step-up

`RequestEmailChange` and `DeleteMyAccount` carry the `Authenticated` rule (`internal/guard/rules.go:80,243`). `Authenticated` refuses only an impersonated caller; `Session` is the rule that also refuses a machine credential (`internal/guard/guard.go:125-162`). `ConfirmEmailChange` is `Public` and spends the code alone. The step-up proof guards `AddPassword`, `RemovePassword` and four other credential procedures (seven `StepUp: true` entries) but not these two. `users.change_email_enabled` defaults to true; self-delete defaults off.

Scenario: an API key, or an access token stolen inside its lifetime, requests a change to an address the holder controls, confirms it with the code from that mailbox, then runs the public password reset to that address and owns the account for good. The old-address notice (`verification/service.go:491-499`) is best-effort and does not block it. A long-lived read-intended key thus escalates to account takeover.

Fix: make both procedures `Session` plus `StepUp`, like `RemovePassword`. This changes the contract for API-key callers; the key surface the guard documents ("API-key authentication is disabled on management routes") already points the same way.

### F-20 Every failure past the bound re-locks, re-mails and re-audits

`RegisterFailure` locks when `attempts >= p.max` (`restrictions/service.go:193`), not when the count first reaches it. `BumpFailures` keeps incrementing while the account is locked, because the sign-in counts every wrong password before it consults the restriction (`signin/service.go:221-233`). Each failure past the bound runs `ApplyLockout` (a plain insert; the index on open restrictions is not unique, `migration 00004:83-84`), writes a `user_locked` audit record and enqueues a locked-notice email (`restrictions/service.go:202-217`). The lockout expiry restarts each time.

Impact: with the default bound of 100, a distributed attacker who has driven one account to the bound can mail its owner once per further attempt, grow `account_restrictions` and `audit_logs` per attempt, and hold the account locked indefinitely. Only the per-address credential bucket (ten per window) limits the rate.

Fix: act on `attempts == p.max` only, or make the insert conditional on no open lockout and enqueue the notice only when a row landed. A regression test that drives twelve failures at a bound of five and counts rows and notices pins it.

### F-21 Wrong second-factor codes never count toward the lockout

A pending MFA bridge survives three wrong codes (`multifactor/service.go:77`). The failure ledger that locks an account counts only wrong passwords (`signin/service.go:227-231,559`; no other caller of `RegisterFailure`). A correct password mints a fresh bridge with three fresh attempts and also zeroes the password streak (`signin/service.go:236-240`). An attacker holding a leaked password therefore trades one sign-in for three code guesses, indefinitely, limited per address by the credential bucket and never per account. A six-digit code accepted in a ±window, matched against up to ten enrolled authenticators, is within reach of a distributed run.

Fix: count a wrong TOTP or recovery code against the same account streak (or a sibling counter) so the lockout applies, and keep the bridge's own cap.

### F-22 Every authenticated request reads the key table twice and decrypts the private signing key

`AccessVerifier.Verify` calls `SigningAlgorithm()` and then `SignKey(ctx)` on every request (`pkg/jwtutils/access.go:181-195`). `SigningAlgorithm` runs `signingPairs(context.Background())`, a database query with no request context (`jwks/service.go:328`). `SignKey` reads the active pairs again, unseals the first row's private key with AES-GCM, parses it and stamps it (`jwks/service.go:379-412`). Verification needs the public half; the private half is decrypted into memory per request. Nothing is cached. The OIDC provider's key function does the same read and decrypt per token request (`OIDCSigningKeys`, `jwks/service.go:523-585`).

Two consequences beyond cost. First, the verifier checks against `pairs[0]` only, ordered by `key_id` (`jwks/repository.go:94`), never against the token's `kid` or the key set. The `jwks:generate` help text says to "run the command again to stage a second key for rotation"; with two active rows the first by `key_id` signs and verifies everything, so the staged key is inert until the other is retired, and if the new key sorts first every in-flight access token fails its signature check at once. Second, the unbounded-context query can outlive a client that disconnected, holding a pool connection.

Fix: cache the opened signing key and the published set with a short TTL and invalidate on rotation; verify with the public key set by `kid`; pass the request context through `SigningAlgorithm`. Measure with a benchmark before and after; none was run here.

### F-23 A profile edit writes back stale `disabled` and `email`

`UpdateCurrentUser` reads the row with no lock (`user/service.go:577`), then writes the full row through `UpdateUser`, which sets `username`, `email`, names, metadata **and `disabled`** from the earlier read (`user/repository.go:225-233`). Between the read and the write an administrator can disable the account, or the email-change confirmation can commit. The write then re-enables the account or puts the old address back, while `email_verified_at` keeps the newer stamp.

The window is milliseconds, and the actor who wins it is the account's own holder. The fix is one line of scope: update the profile columns only, never `email` or `disabled`, or read the row `FOR UPDATE` inside the transaction. The administrator edit shares `UpdateUser` (`user/service.go:859`) and needs the same check.

### F-24 The webhook destination guard is a pre-resolution check with a CGNAT gap, on one of six outbound call sites

`checkDestination` resolves the host with `net.DefaultResolver` and refuses loopback, private, link-local and unspecified addresses (`webhook/service.go:733-767`); the fetcher then resolves again at dial time with no policy (`framework/fetcher` has no dial control). A name that answers public to the check and private to the dial passes (DNS rebinding); the code comment admits the residual risk. The range `100.64.0.0/10` is not refused: running the check's predicate on `100.100.100.200` (a cloud metadata address) returns "not blocked". Only the webhook sender applies the policy; SCIM sync (`scimsync/sync.go:280,432`), OAuth discovery and token calls (`oauthsso/discovery.go:64`, `providers.go:117,162`), CIMD fetches (`oidc/cimd.go:92`) and the back-channel logout job (`internal/jobs/backchannel_logout_job.go:57`) do not.

All the other URLs are administrator-configured, or sit behind the CIMD allowlist, so the exposure is administrator-level SSRF and the webhook rebinding case.

Fix: one dial-time guard in `framework/fetcher` (a `net.Dialer.Control` that refuses the ranges, including `100.64.0.0/10`, `192.0.0.0/24` and multicast) applied by default with an Options field to lift it, replacing the pre-check.

### F-25 The last-administrator guard covers deletion only

`refuseTheLastAdministrator` runs inside the two delete paths (`user/service.go:714,745`). `SetUserRoles` can replace an account's roles with none, including the last administrator's own (`authorization/service.go:440-552`); a ban or disable of the last administrator is likewise unguarded. `serve` warns about a lagging administrator grant at boot (`cmd/serve_grants.go`) but the repair is the CLI. Fix: run the same check in `SetUserRoles`, ban and disable.

### F-26 The wrong-device budget rolls back with its own refusal

The one-time-access exchange records a wrong device token with `RegisterWrongAttempt(ctx, tx, …)` and then returns `ErrDeviceMismatch` from the transaction closure (`onetimeaccess/service.go:185-201`). A returned error rolls the transaction back, so the increment and the token deletion never persist and the budget of five never fills. The doc comment names the budget as a compensating control for the single-factor exchange. The multifactor bridge handles the same situation by writing the strike on the pool, apart from the rolled-back proof (`multifactor/signin_bridge.go:181`). `ErrDeviceMismatch` also answers differently from an unknown code, which tells a caller the code exists. The device token is 256 bits, so the practical harm is small; the defect is a documented control that does nothing, and no test covers it (`onetimeaccess/service_test.go:342-348` asserts the error only).

### F-27 An unreadable setting mints never-expiring refresh tokens; rotation has no reuse detection

`refreshWindowHours` answers 0 when the setting read fails (`oidc/backchannel.go:113-129`), and `stampRefreshWindow` turns 0 into `RefreshTokenExpiresAt = 0`, which the catalog documents as "the token never expires" (`protocol.go:293-303`). A transient database error during a grant therefore issues a permanent token. Separately, rotation deletes the presented token's pointer before the compare-and-swap save (`protocol_storage.go:191-199`), so a replayed old token finds nothing and the grant is not revoked; a thief who refreshes first keeps the chain while the owner is merely refused (RFC 9700's refresh-token guidance asks for reuse detection on public clients). Fix: fail the grant on an unreadable window, and keep a tombstone for the retired pointer so a replay revokes the grant.

### F-28 `oauth_sessions` carries two unused indexes and a revoke with none

`save` writes `request_id = $1`, the row's own `kind` (`protocol_storage.go:64-70`), so every row of a kind shares one `request_id`; nothing reads the column, and `idx_oauth_sessions_kind_request` (`migration 00013:140`) is a no-op index paid for on every write. `idx_oauth_sessions_client_subject` indexes `request_data #>> '{session,subject}'` (`:142-143`), a path no query uses; the revoke reads `request_data->>'sub'` and `->>'grant_id'` (`consent.go:314-334`). The pointer delete filters on `grant_id` with no index, so it scans the table. The `active` column is never set false. Fix: drop the two indexes in an additive migration, add one on `(request_data->>'grant_id')` and one on `(client_id, (request_data->>'sub'))`, and stop writing `request_id` as the kind.

### F-29 The audit list counts and de-duplicates over the whole table

Every list page runs a separate `count(*)` (`auditlog/repository.go:126-144`), the filter controls run `SELECT DISTINCT` over the table and a join to `users` (`:168-229`), and pagination is offset-based. Retention is 90 days by default (`internal/config/defaults.go:249`), which bounds the table, but a busy deployment pays a full scan per page view of the administration screen. Unmeasured. Fix: cache the filter options, drop the exact total beyond a threshold or use keyset paging.

### F-30 Every API-key request writes `last_used_at`

`Validate` calls `TouchLastUsed` on the pool for each authenticated request (`apikey/service.go:307`, `repository.go:257-270`). A busy key serializes on its own row and bloats the table. Fix: write only when the stored instant is older than a minute.

### F-31 A watch stream outlives its credential and has no per-account cap

`WatchNotifications` authenticates once at open and then loops until the context ends (`notification/handler_rpc.go:264-308`), with its deadline lifted (`middleware.UnboundedFor`). After the access token expires, the session is revoked or the account is banned, the stream keeps delivering that account's notification titles and bodies. `Subscribe` accepts any number of streams per account, each holding a goroutine and a 32-slot channel (`notification/broker.go:33-50`). Fix: end the stream at the token's expiry, and cap streams per account.

### F-33 A SCIM endpoint change keeps the old token; a pass deletes every remote account it does not know

`Update` keeps the stored token when the request's token is empty (`scimsync/service.go:187-197`). An administrator can repoint the endpoint at a host they control and receive the sealed token on the next pass, which defeats "shown once". The reconcile pass deletes every remote user and group whose `externalId` is not in the local snapshot (`sync.go:140-168`), so pointing a provider at an application with its own accounts removes them on the first pass; there is no dry run. Fix: clear the token when the endpoint changes, and add a dry-run count that the first pass must confirm.

### F-34 The MFA bridge is minted before the ban and lockout check; the lockout default is 100 attempts

`SignIn` forks to the bridge before `IssueSession` applies the disabled, ban and lockout checks (`signin/service.go:259-287` against `:374-388`). A banned account with a confirmed factor and the right password is shown the code prompt and refused only at completion, while a banned account without one is refused at once. The difference is a ban oracle for a caller who already holds the password. Separately, `defaultLockoutMax` is 100 with a one-hour window (`restrictions/service.go:24-26`): a deliberately lax default, listed so the owner can confirm it.

### F-07 The step-up mirror is stale and unused

`STEP_UP_PROCEDURES` (`packages/webapp/src/libraries/reauth/reauth.ts:12-19`) lists six procedures. `internal/guard/rules.go` marks seven `StepUp: true`; `OAuthSSOService/UnlinkConnection` (`rules.go:190`) is missing from the set. Nothing in `src/` or `tests/` reads the constant. The connections view works anyway because it calls `useStepUp().run(...)` (`-connections-view.tsx:81`) and the guard's refusal maps to the dialog. `rules.md` tells the next editor to "change either side and re-check both"; no test enforces it, and it has already drifted.

Fix: delete the constant, or generate it from the rule table and test it. Deleting costs nothing today.

### F-08 Code departs from written rules

- **JSON v2.** Production code uses `encoding/json` v1 in `modules/identity/oauthsso/token_client.go:5`, `modules/identity/user/repository.go:5`, `modules/federation/oidc/protocol.go:7`, `modules/federation/scimsync/sync.go:5` and `internal/database/seeders/conformance_suite_factory.go:5`. 43 other files use v2. `tools/e2e-passkey` and `pkg/testutils/softauthn` are test tooling and not counted. The rule says v1 is test-only; v1 and v2 differ on case-insensitive field matching and unknown fields, which matters on the OAuth token response and the OIDC protocol document.
- **SQL in the service layer.** `modules/identity/usergroup/service.go:320` runs `SELECT 1 FROM users` through the pool from the service, reaching into a table another feature owns, with a hand-written `$1`. `modules/notification/repository.go:406` concatenates an `INSERT … SELECT` around builder output; that one may be the intended exception, but `rules.md` does not list it. `modules/federation/oidc/protocol_storage.go` writes five raw statements.
- **A handler checks a role.** `modules/appconfig/handler.go:31` calls `caller.HasRole(AdministratorRole)` to pick the published subset. The rule is "A handler never checks a role". The behaviour is documented (`rules.md` webapp entry), so this is a rule that needs an exception written down, or the split moved into the guard.
- **Check-then-delete without a lock.** `modules/storage/service.go:248-283` counts a bucket's objects and then deletes it; a concurrent `Stage` slips an object in between and the `ON DELETE RESTRICT` foreign key turns the race into an unmapped 500 (no data loss).

2. **F-16 scope.** (a) Revoke on ban, disable, delete and group removal; (b) on ban and delete only. Recommended: (a).

## Undeclared topology constraint

Not a numbered finding because the supported topology is the owner's to state. Four components assume one process: the tus per-upload locks (`framework/storage/tus_handler.go:47-52`, a `sync.Map` that serializes chunk appends), the in-process notification broker (`modules/notification/broker.go:14-20`; the durable record is the table, so a second instance's watchers wait for the next poll), the settings cache when the in-memory driver is on (`modules/appconfig/settings.go:538-605`; an update drops the local entry only, so the other instance serves the old value until the TTL, and the gates it caches include the access mode and the lockout policy), and local-disk storage as the default. The queue, scheduler and rate limiter are database-backed and safe across instances. Neither `.agents/docs/` nor `docs/` states a topology (`grep` for replica, horizontal, multi-instance finds nothing). Two tus chunks for one upload landing on different instances can interleave between the offset check and the write. Recommend one line in `docs/deployment.md` and `architecture.md`: either single instance, or sticky routing for `/api/uploads` and a shared cache driver.
