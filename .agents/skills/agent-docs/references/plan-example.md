# Land `key:rotate` — one command re-seals every surface the application secret encrypts

## Objective

`cmd/appkey.go:177` prints `not yet implemented` — the one open residue of
the 2026-10-14 reconciliation of the archived `partial` handovers
(issue-20261014_0949). This plan lands the command: rotate
`APP_SECRET_KEY` (the AES-256 application secret), re-seal every row and
payload sealed under the old key, write the new key to the deployment's
env file, and report what moved. No schema changes — the sealed format
(`enc:`-prefixed AES-GCM, `pkg/crypto/encryption.go`) stays as it is.

## Current state (verified in the tree, 2026-10-14)

- **The command exists as a stub.** `keyRotateCmd` (`cmd/appkey.go`)
  prints and returns; `key:generate` beside it carries the full UX the
  rotation should mirror (env-file creation, confirmation before
  overwrite, `--overwrite` to skip the prompt).
- **The cipher is one secret, no key ids.** `crypto.NewCipherFromHex(c.App.SecretKey)`
  builds the application cipher (`internal/registry/infrastructure.go:300-305`);
  the sealed wire format carries no key version — a row decrypts or it
  does not. Rotation is therefore decrypt-with-old, encrypt-with-new,
  all at once.
- **Six surfaces hold sealed material:**
  1. webhook endpoint signing secrets — `modules/webhook/service.go:857`
     (`secret_enc`, migration 00010, CHECK-constrained to `enc:%`);
  2. OAuth SSO upstream client secrets — `modules/identity/oauthsso/service.go:455`
     (the federation tables' sealed secrets, migration 00013);
  3. SCIM directory bearer tokens — `modules/federation/scimsync/service.go:160`
     (migration 00013's CHECK `token LIKE 'enc:%'`);
  4. TOTP enrollment secrets — `modules/identity/multifactor/service.go:316`
     (the factor's `secret` column);
  5. the JWKS private documents — `modules/identity/jwks/service.go:148`
     (migration 00012);
  6. appconfig's sealed setting values — `modules/appconfig/settings.go:961`
     (`def.Sealed`).
- **Queue payloads are optionally sealed at rest** (`queue.encrypt`,
  `internal/config/types.go:561`): every task payload carries
  `crypto.EncPrefix` and the archive keeps the sealed form
  (`framework/queue/client.go:65-68`) — rotation must keep the two
  consistent or a replayed task fails to open.
- **`AUTH_SECRET_KEY` is not a cipher key.** It is the HMAC/JWT signing
  secret; its rotation invalidates signed artifacts rather than sealing
  new ones, and the JWT key pair already rotates in the database
  (`jwks:generate`). Out of this plan's scope.

## Decisions

- **D1 (2026-10-14): the command rotates `APP_SECRET_KEY` only.**
  Re-encryption is possible only for sealed data; the HMAC signing
  secret has no sealed counterpart to migrate — rotating it is a mass
  invalidation, which is the deployment's own restart-and-reissue
  procedure, not this command. Rejected: a `--signing` mode — a second
  mechanism (sign-out enforcement) wearing a rotation name, with no
  data to re-seal.
- **D2 (2026-10-14): hybrid key supply, mirroring `key:generate`'s UX.**
  The old key comes from the loaded configuration (the env file the
  deployment already runs), the new key is generated by the command and
  written to `--env-file` with the same confirm/`--overwrite` dance —
  unless `--new-key` passes an explicit value for scripted runs. A
  `--dry-run` counts the sealed rows and verifies the old key decrypts
  them without writing. Rejected: passing the old key as a flag (it
  would sit in shell history — the secret-handling rule says a secret is
  listed in `secretKeys` and never printed); requiring both keys from
  the environment (breaks the interactive flow the other key commands
  set).
- **D3 (2026-10-14): queue payloads re-seal in the same pass.** When
  `queue.encrypt` is on, the rotation walks the queue's payload column
  and its archive and re-seals them with the new cipher, keeping the
  live and archived forms consistent. Rejected: a drained-queue
  requirement (an operational dance the operator will skip, with the
  failure mode — a replay that cannot open — discovered weeks later) and
  skipping the queue with a documented warning (`queue.encrypt`
  deployments would need a second rotation forever).
- **D4 (2026-10-14): all-or-nothing, abort on the first decrypt
  failure.** Every surface re-seals inside one transaction; a row that
  fails to open under the old key aborts the rotation with the row
  named — a wrong key or an already-rotated row is the operator's
  information, not a partial state. The `--dry-run` exists so the counts
  and the key check precede any write. Rejected: per-row best-effort
  (a half-rotated tree, unreadable by either key on rollback) and
  skip-and-report (the skipped row is unreachable data the operator must
  find again).

## Shape and enforcement points

| Surface | Where it seals today | What rotation does |
| --- | --- | --- |
| Webhook endpoint secrets | `modules/webhook/service.go:857`, `secret_enc` (00010) | decrypt → re-seal, in the pass |
| OAuth SSO client secrets | `modules/identity/oauthsso/service.go:455` | decrypt → re-seal, in the pass |
| SCIM directory tokens | `modules/federation/scimsync/service.go:160` | decrypt → re-seal, in the pass |
| TOTP enrollment secrets | `modules/identity/multifactor/service.go:316` | decrypt → re-seal, in the pass |
| JWKS private documents | `modules/identity/jwks/service.go:148` | decrypt → re-seal, in the pass |
| Sealed appconfig values | `modules/appconfig/settings.go:961` | decrypt → re-seal, in the pass |
| Queue payloads + archive | `framework/queue/client.go:65-68`, behind `queue.encrypt` | phase 2: re-seal both, same pass |
| The env file | `cmd/appkey.go` (`key:generate`'s writer) | phase 1: write the new `APP_SECRET_KEY`, confirm/`--overwrite` |

The engine is a `pkg/crypto` helper (`ReSeal(old, new *Cipher, sealed)`)
plus a small row-walker per surface — no module gains a dependency on the
command; the command owns the walk. The sealed modules are untouched:
their seal/decrypt paths keep working, only the key underneath changes.

## Explicitly out of scope

- **`AUTH_SECRET_KEY`** — D1: no sealed data migrates; mass invalidation
  is the deployment's own procedure.
- **A key-id / key-version column** — the sealed format stays
  versionless; the rotation is all-at-once (D4), so versioning buys
  nothing this plan needs.
- **JWT key-pair rotation** — already lives in the database
  (`jwks:generate`), a different mechanism.
- **`modules/**` seal paths** — untouched; only the key under them
  changes.
