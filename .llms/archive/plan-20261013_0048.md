# The last administrator's guard, and the singleton builtin provider picker

## Objective

Close two refusal gaps the owner named: an account deletion that would strip the
deployment of its last administrator is refused on the backend and gated on the
frontend, and the OAuth provider form stops offering a builtin provider that is
already configured (the Clerk model — one connection per builtin provider, read
from `clerk.com/docs/guides/configure/auth-strategies/social-connections/google`
on 2026-10-13). Flow reference: the owner's answers 2026-10-13 (Q1=1, Q2=1,
Q3=1, Q4=1).

## Current state

All claims verified in the tree at `ed3db3db` (2026-10-13):

- **The deletion paths.** `Service.DeleteUser` (`modules/identity/user/service.go:940`)
  refuses self-deletion (`ErrSelfDeletion`, mapped `FailedPrecondition` at
  `handler_rpc.go:389`) and nothing else about the target's standing.
  `Service.DeleteMyAccount` (`service.go:670`) gates on the self-delete setting
  and shares the deletion mechanics. Neither knows whether the target is the
  deployment's last administrator.
- **The administrator's standing lives in `user_roles`** (`00005_create_authorization_tables.sql:52`,
  live = `revoked_at IS NULL`, `uq_user_roles_active`), joined to `roles` where
  the seeded system role's name is `administrator` (`internal/authz/catalog.go:138`,
  `AdministratorRole`). Identity modules already import `internal/authz`
  (`modules/identity/session/impersonation.go:15`, aliased `appauthz`).
- **The wire `User` carries no roles** (`api/connect/identity.proto:384–448`,
  last field `password_updated_at = 18`) — the frontend list cannot tell which
  rows are administrators. The user detail view reads the target's roles from
  the authorization surface's `ListUserRoles` (`-user-detail-view.tsx:1129`).
  Deletion is triggered from one frontend surface: the detail view's danger zone
  (`-user-detail-view.tsx:298`); the list rows' dropdown carries no delete.
- **The provider uniqueness already binds.** `oauth_connections` is
  `UNIQUE (provider)` (`00015_create_oauthsso_tables.sql`, header comment: one
  connection per provider slug); a duplicate create is refused
  (`ErrProviderTaken` → `CodeAlreadyExists`, `handler_rpc.go:249`). Two builtin
  slugs ship: `google`, `github` (`modules/identity/oauthsso/builtin/builtin.go:47`).
  The form sheet (`-oauth-provider-sheet.tsx:275`) still offers every builtin
  slug regardless of what exists — the refusal surfaces only at submit.
- **The wire builder is shared.** `WireView` (`service.go:884`) writes every
  account's wire form; the view's groups are batch-filled by `withGroups`
  (`service.go:184`) — the same shape the roles fill will follow.

## Decisions

- **D1 (2026-10-13):** The backend refusal is service-level, inside the same
  transaction as the delete: when the target holds the live administrator role
  and no other live administrator exists, both `DeleteUser` and
  `DeleteMyAccount` refuse with the new `ErrLastAdministrator`
  (`FailedPrecondition`). Rejected: the DB-trigger guarantee (a service-level
  check the tests can read is the repo's refusal idiom; the owner chose it),
  and the delete-my-account-only reading (the admin-path refusal closes it).
- **D2 (2026-10-13):** The frontend gate is the Clerk model: the wire `User`
  gains `repeated string roles` (field 19, additive), and the detail view
  **hides** the delete danger zone for an administrator-row target — the note
  names the way out ("demote the role first"). Rejected: an
  `is_last_administrator` flag (a global fact a paginated list cannot compute),
  and leaving the refusal to the submit round trip (the gate the owner asked
  for is a gate, not a message). The backend's last-administrator word stays
  for the race a hidden button cannot prevent.
- **D3 (2026-10-13):** The provider picker is frontend-only: the sheet disables
  the builtin slugs a connection already uses, suffixing them "already added";
  the backend is untouched — `UNIQUE (provider)` is the binding, and relaxing
  it for custom connections (Clerk allows multiple custom OIDC) would delete a
  guarantee the deployment holds today. Rejected: a clearer backend refusal
  word only (the admin still discovers at submit).
- **D4 (2026-10-13):** The roles fill rides the existing batch-fill pattern
  (`withRoles` over `UserView`, `WireView` maps it) — one batched query per
  page, one per account read; the authorization module's `ListUserRoles` stays
  the roles-management surface and is not replaced.

## Phases

### Phase 1 — `feat(identity): the last administrator stands`

Add `roles` to the wire `User` (field 19); fill it with the account's live
role names through the batch fill. Add `ErrLastAdministrator` and the
transaction-scoped check in `DeleteUser` and `DeleteMyAccount`: refuse when
the target holds the live administrator role and no other account does.
Unit tests: the last admin's deletion refused on both paths, a deletable
admin (another exists) passes, a non-admin passes, the self-delete refusals
still stand. Validation: `go test ./...`, `task lint`, endpoint-reference
prose updated in the same commit.

### Phase 2 — `feat(webapp): the gates read the roles, the picker names what is taken`

The detail view reads `user.roles` off the wire and hides the delete danger
zone for an administrator target (the note says the role demotes first; the
grants card keeps its own management). The provider sheet receives the
existing connections (the view's list query already holds them) and disables
the taken builtin slugs with an "already added" suffix. Browser tests: the
danger zone's absence for an administrator row and presence for a plain one;
the picker's disabled state. Validation: `vp check`, webapp suite, full
Playwright E2E, release-build probe of the users surface.

## Explicitly out of scope

- A DB trigger or constraint enforcing the last administrator (D1 — the
  service check is the owner's pick).
- Banning or disabling the last administrator (the owner asked for deletion;
  a ban gap is its own question if the owner wants it closed).
- Multiple custom OAuth connections of one slug (D3 — the current global
  uniqueness stands).
- The login screen's provider buttons reading anything new — they already
  answer from `ListEnabledConnections`.
