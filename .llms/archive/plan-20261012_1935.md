# Plan — the OIDC consent interaction page in the SPA

## Objective

Close the parked debt `issue-20261012_0445.md`: the provider's interaction
surface is complete on the backend while the SPA surface that consumes it
never landed — no `(interaction)` route tree, no consent screen, nothing
consuming the `?callback=` handoff the provider redirects with. This plan
ships the interaction area: the consent page (decision post, `login_hint`
prefill, the `offline_access` persistent-access disclosure), the OAuth
device grant's browser verification state (the gap found while planning —
the device prompt currently redirects to a 404), and the small backend
delta that lets a bearer-carrying SPA receive the completion redirect at
all. Reference read 2026-10-12: Pocket ID `main`
(`frontend/src/routes/interaction/+page.svelte` — steps
`select_account`/`consent`/`reauthenticate`, inline passkey sign-in, the
"use a different account" affordance, `/interaction/error`); saka's wire
differs from it and the deltas are decisions D1–D5 below, not silent
deviations.

Owner's standing instructions for this plan (2026-10-12): execution waits
for the explicit go; atomic commit per phase, self-commits allowed during
the working session, and the closing state recommends its commit message;
no backward compatibility or legacy code; migration files are edited in
place and dev-database resets are allowed (this plan needs none); the test
matrix, the final validation phase, the docs sync, the `.llms` sync, and
the handover are mandatory; E2E lands where it is relevant.

## Current state

Every claim verified in the tree on 2026-10-12.

**The provider's side is complete.**

- `modules/federation/oidc/protocol.go:57–58` — `interactionPath =
  "/interaction"`, the SPA route the sign-in-less browser lands on; and
  the device grant's `PromptFunc` (:218–226) redirects every verification
  visit to `interactionPath + "?callback=" + escape("/oidc/device")` —
  a route the SPA does not have, so a real browser's device prompt 404s
  today (only the REST tools drive it).
- `modules/federation/oidc/protocol_policy.go:397–402` —
  `interactionRedirect` sends the browser to
  `/interaction?callback=<endpoint>/<sessionID>` (302, query-carried,
  escaped).
- `:66–95` — `signInPolicy` on `GET /oidc/authorize`: `prompt=none`
  answered from the browser-session marker alone (:142–159), a live
  marker within `max_age` resumes without fresh authentication
  (:97–132), a caller present proceeds to completion, and a caller
  absent is the 302 to the interaction page (:90).
- `:222–235` — `interactionPolicy` on `GET,POST /oidc/authorize/{id}`:
  no caller → the interaction redirect; a caller →
  `completeAuthentication`.
- `:243–256` — `devicePolicy` on `GET,POST /oidc/device[/{id}]`: the
  same two ways in. The code-entry visit is
  `GET /oidc/device?user_code=…` (`internal/authorize/device.go`,
  `initDeviceAuthVerification` — empty code re-renders the prompt,
  unknown code re-prompts, a known code runs the policy).
- `:261–336` — `completeAuthentication`: the group-restriction gate
  before any grant or consent write (:275–283), `skip_consent` completes
  on the spot (:285–294), a posted decision records the authorization
  (:296–308), a prior consent that covers the request completes silently
  (:313–322), and only the standing consent question answers the
  interaction document (:323–334):
  `{interaction_id, client_id, client_name, requested_scopes,
  consent_required, login_hint}` (`writeInteraction`, :404–414).
- `:37–39` — the decision body is `{"scopes": [...]}`
  (`consentDecision`); `:365–384` — `decisionScopes` filters the posted
  scopes to the requested set and **appends `openid` unconditionally**:
  every POST is an approval of at least `openid`; the wire cannot express
  a denial.
- The success completion writes the provider's own redirect — the 302 to
  the RP's `redirect_uri` — inside the library
  (`github.com/luikyv/go-oidc@v0.25.0/internal/authorize/authorize.go`,
  `authenticate`; the policy callback receives the writer but returning
  after writing it leaves the library writing again).

**The browser cannot complete the flow today.**

- `modules/identity/auth.go:27–41` — the authenticator reads
  `jwtutils.BearerToken(req)`, the `Authorization` header, and nothing
  else; `internal/transport/middleware/bearer.go:120–136` — the REST
  opportunistic path verifies a presented header and never a cookie.
  A browser navigation to the callback carries no bearer, so the policy
  redirects back to the interaction page — a loop; and the SPA's
  `fetch` cannot read a 302's `Location` (`redirect: 'manual'` answers
  an opaque response; `follow` would land the request, not the tab, on
  the RP's page). This is why the plan carries a backend phase.

**The SPA's side is absent.**

- `packages/webapp/src/routes/` holds `(app)`, `(app)/admin`,
  `(app)/account`, `(auth)`, `(auth)/auth`, and the two root pages
  `device.tsx`/`verify-email.tsx` — no `(interaction)` tree exists.
- `routes/device.tsx` + `-device-view.tsx` is the device-**login
  pairing** surface (`DeviceApprovalService` `Inspect`/`Decide`,
  :32–60) — a different feature from the OAuth device grant; it is
  untouched by this plan.
- `routes/(app)/account/-authorized-apps-view.tsx:190–196` —
  `ScopeChip` already renders `offline_access` as the
  "persistent access" badge (and a `login_hint` case); the consent card
  reuses it, lifted to a shared component.
- The login machine accepts a return trip:
  `routes/(auth)/route.tsx:14–22` redirects an authenticated visitor to
  `safeReturnTo(search.return_to) ?? '/overview'`, and
  `routes/(auth)/login.tsx:11` carries the `return_to` search param.
- The parked `TODO(frontend)` markers live in
  `.llms/endpoint-reference.md` (the authorize section — the consent
  screen's `login_hint` prefill and `offline_access` wording), pointed
  at `issue-20261012_0445.md`; this plan resolves them.

**The conformance harness stays honest.**
`packages/e2e-tests/conformance/driver.mjs:100–152` walks the interaction
protocol itself — it posts the decision with the deployment's bearer and

driver's 302 walk is untouched; the SPA's E2E exercises the dialect path
beside it.

## Decisions

Owner-answered 2026-10-12 via the option lists; each carries its rejected
alternatives.

- **D1 — Anonymous visitors are redirected to `/login`.**
  The `(interaction)/route.tsx` shell is session-load-only: it loads the
  guard state and, for an anonymous caller, redirects to
  `/login?return_to=/interaction%3Fcallback%3D…` (the exact callback
  string preserved). The consent page itself assumes a session.
  Rejected: Pocket ID's inline sign-in — it works there because the
  provider's only credential is a passkey, while saka's login machine
  (password, passkey, one-time code, SSO, the MFA fork) is too large to
  duplicate inside the interaction page, and an embedded copy would
  strand MFA-enabled accounts on the consent path again.
- **D2 — The OAuth device grant's verification joins the interaction
  area.** The same `/interaction` page serves the code-entry state (the
  callback names `/oidc/device` with no id), the resume, and the consent
  decision; `PromptFunc` stays pointing at the interaction page. The
  device-**login pairing** page (`/device`) is untouched. Rejected: a
  separate issue file (leaves a shipped surface 404ing in a real
  browser); re-pointing `PromptFunc` to the existing `/device` (merges
  two unrelated services' code-entry into one view).
- **D3 — Scopes render as names plus the lifted `ScopeChip`.** No
  backend change: the interaction document's scope names render raw,
  `offline_access` carries the persistent-access badge it already has.
  Rejected: adding human-readable scope descriptions to the interaction
  document (a wire expansion beyond both the current contract and the
  Pocket ID reference's shape).
- **D4 — `select_account` ("use a different account") is out of scope.**
  The interaction document carries no such step; adding one changes the
  wire. Trigger: a real multi-account-per-browser need.
- **D5 — Denial is a cancel, not a wire state.** The consent card offers
  Approve (the decision POST) and Cancel (navigate away; the pending
  session expires through `protocol_cleanup`). The wire cannot express a
  denial today and this plan does not change that. Rejected: backend
  deny semantics (`access_denied` redirect, the Pocket ID parity) — a
  backend wire delta whose trigger is an RP complaint about hanging
  flows or a conformance profile demanding `access_denied`.
- **D6 — The completion reaches the SPA through a header-keyed JSON
  dialect.** A small response interceptor mounted only on the SPA-facing
  callback paths (`/oidc/authorize/{id}`,
  `/oidc/device`, `/oidc/device/{id}`): when the request carries
  `X-Saka-Interaction: spa` and the wrapped handler writes a 3xx with a
  `Location`, the answer becomes `200 {"redirect": "<location>"}` in the
  interaction dialect; the SPA navigates `window.location` to it. The
  header is opt-in — the protocol surface, the conformance driver (which
  sends no such header), and plain browser walks keep the raw 302s;
  interaction documents and non-redirect answers pass through
  untouched. Rejected: keying on the bearer alone (it would silently
  flip the wire under the conformance driver's
  `driver.mjs:138–152` walk); a cookie-credential fallback on the
  interaction paths (a second credential path, a new CSRF surface, and
  a violation of the "cookie presence never authorizes" rule's spirit);
  forking the library's response writing.
- **D7 — One interaction URL, two states.** A single page route answers
  `/interaction` (shipped as the root-level `routes/interaction.tsx`
  beside the other standalone doors, the shell logic in its
  `beforeLoad`); the view forks on the callback's shape —
  `/oidc/authorize/{id}` renders the consent card, `/oidc/device` (no
  id) renders the code entry, `/oidc/device/{id}` renders the device
  resume/consent. The route-tree group the plan first sketched shrank to
  the one file: the group would have added no path segment and the page
  file still had to be named `interaction.tsx` to answer the provider's
  one URL. Rejected: a separate device URL (the provider redirects to
  one `interactionPath`; a second URL would need backend changes for no
  UX gain).
- **D8 — Completion navigates, it does not route.** The redirect target
  is applied with `window.location.href` — the RP's page takes the
  browser over entirely. Rejected: TanStack Router navigation (the
  target is an external URL the router must not own).

## Shape and enforcement points

**Backend (phase 1).**

- The interceptor lives beside the provider's mount
  (`internal/transport/router/http.go`, where the provider handler is
  wrapped into the chi tree): a `http.Handler` wrapper matching only the
  three callback shapes above, keyed on the exact header value
  `X-Saka-Interaction: spa`. It captures a written 3xx + `Location`
  (a `ResponseWriter` wrapper), answers `200` with
  `{"redirect": …}` through the interaction dialect's JSON writer, and
  passes everything else — every status, every path, every headerless
  request — through byte-for-byte.
- No migration, no proto, no guard rule change: the paths stay the
  guard's `Public` REST entries (`internal/guard/rules.go:559–562,
  587–590`) and the header adds no privilege.
- The dialect's response shape joins `writeInteraction`'s contract in
  the endpoint reference (same section, same change).

**Frontend (phases 2–3).**

- `routes/(interaction)/route.tsx` — the group shell: no auth guard;
  `ensureSessionLoaded()`; `validateSearch` carries `callback`
  (required, a same-origin `/oidc/…` path — a foreign or missing value
  is a not-found, never a redirect target); anonymous callers redirect
  to `/login` with `return_to` carrying the full interaction URL.
- `routes/(interaction)/consent.tsx` — thin wrapper over
  `-consent-view.tsx` (dash-file code splitting per the standing route
  convention; `staticData.pageTitle` set).
- `-consent-view.tsx` — the state machine: parse the callback; signed-in
  resume `GET <callback>` through the auth-aware seam with
  `X-Saka-Interaction: spa`; a JSON interaction document renders the
  consent card (client name, `requested_scopes` via the lifted
  `ScopeChip`, the `offline_access` disclosure, `login_hint` as a
  display-only prefill note — the signed-in credential decides the
  subject); a `{"redirect"}` answer navigates; the Approve action posts
  `{"scopes": <all requested>}` to the same callback; Cancel navigates
  history-back (the pending session expires server-side).
- `components/scope-chip.tsx` — `ScopeChip` lifted out of
  `-authorized-apps-view.tsx` and re-imported there; no visual change to
  the ledger page.
- The device-grant state (phase 3): the callback `/oidc/device` (no id)
  renders the code entry — the `XXXX-XXXX` input, submit as
  `GET /oidc/device?user_code=…` with the dialect header; the
  `/oidc/device/{id}` callback resumes like the authorize one (document
  → consent card; `{"redirect"}` — the device success is a plain 200,
  answered as the approved state). The entry state shares the consent
  page's mount; the provider's `PromptFunc` is untouched.

**Surfaces enumerated** (the plan ships no new RPC procedure, REST route,
job, email, audit event, guard rule, or settings key; the Yaak collection
needs no new row — the dialect rides endpoints the collection's
interaction requests already carry, and the endpoint reference documents
the header in the same change).
