## What the phases changed (the short map)

- **Phase 1** — PKCE `plain` dropped (S256 only); `claims_supported`
  completed (`at_hash` deliberately absent, D8); operator-supplied client
  secrets salted PHC (scrypt); `ListAllAuthorizedClients` paginated; the
  consent service handler codec fix (handlers must receive `opts...` or
  the wire leaks camelCase).
- **Phase 2** — the ID token mints `sid` = the grant's own ID; the logout
  policy passes the hint's `sid` into the delivery; `state` echo on
  registered `post_logout_redirect_uri` pinned; finding: `UpdateClient`
  is a full replace (omitted fields reset).
- **Phase 3** — the harness: compose-dev stack for the OIDF suite
  (prebuilt images, services named `server`/`mongodb`), the PKCS12
  truststore (`task cert:conformance`), the `ConformanceSuiteSeeder`
  fixture clients + account, the driver + runner in
  `packages/e2e-tests/conformance/`, tasks `conformance:up`/`conformance:run`.
- **Phase 4** — display + ACR values configured and advertised;
  `auth_time` stamped at completion and minted from the grant's store
  (watch the float64); the OP browser-session cookie (`saka_oidc_session`)
  with `prompt=none` / `max_age` resume / `prompt=login` semantics; JAR by
  value (none + ES256); the RS256 pair rides the seed; the runner gained
  the suite's long-poll wait-state, the cookie-clear, and the screenshot
  upload.
- **Phase 5** — logout expires the browser-session marker; the discovery
  decorator adds the back-channel members the engine never names; the
  logout profiles contradict on client registration — `suite-backchannel`
  carries the receiver alone, the runner maps plan → client pair; secrets
  ≥32 bytes; the fixture re-asserts `oidc.backchannel_logout_enabled=true`.
- **Phase 6** — this handover, the submission runbook (below), the product
  page `docs/oidc-provider/`, the audit dispositions, the
  `auth-design.md` federated-identity section.

## Running the harness

```sh
task cert:generate          # mkcert SANs incl. localhost.emobix.co.uk
task cert:conformance       # the suite JVM's truststore
task conformance:up         # suite stack (project `saka`)
task db:seed -- --env-file=.env.local   # fixtures: account + 4 clients
./build/release/saka --env-file=.env.local \
  --config-file=/tmp/saka-conformance.config.json serve
cd packages/e2e-tests
node conformance/run.mjs <plan-name> '<variant json>'
```

The four plans and their variants:

```sh
node conformance/run.mjs oidcc-basic-certification-test-plan '{"client_registration":"static_client","response_type":"code","request_authentication":"client_secret_basic"}'
node conformance/run.mjs oidcc-config-certification-test-plan
node conformance/run.mjs oidcc-rp-initiated-logout-certification-test-plan '{"client_registration":"static_client","response_type":"code"}'
node conformance/run.mjs oidcc-backchannel-rp-initiated-logout-certification-test-plan '{"client_registration":"static_client","response_type":"code"}'
```

Operational notes that bite:

- ONE running instance per alias — a killed runner leaves a ghost holding
  the alias until the suite restarts (`docker restart saka-server-1`).
- Never run two runners concurrently.
- The two throwaway configs share :3000 — the E2E's
  (`/tmp/saka-e2e.config.json`, issuer `http://localhost:3000`) and the
  harness's (`/tmp/saka-conformance.config.json`, issuer
  `https://saka.localhost.test:3443`). Restart the server with the right
  one when switching.
- `CONFORMANCE_MODULES=name1,name2` filters the plan (exact match wins).
- A DB reset mints a new admin password —
  `saka admin:reset-password admin@example.com --new-password ...` restores
  the runner's known credential.

## The hosted submission runbook

The hosted run happens on the OpenID Foundation's suite
(<https://www.certification.openid.net>) against a publicly reachable
issuer. What the owner does:

1. **Public deployment.** Deploy saka behind a public HTTPS front with a
   trusted certificate (Let's Encrypt or similar) — the certification
   program requires a TLS-terminating front and a stable issuer URL. Keep
   the deployment for the whole registration window.
2. **Register the clients on the deployment.** The hosted suite pre-registers
   static clients and prints the required registrations (client IDs,
   redirect URIs, post-logout and back-channel receivers, secrets) when a
   plan starts. Register each under its plan's alias; mirror the fixture
   shape the local seeder writes (`internal/database/seeders/conformance_suite_factory.go`).
3. **Turn the delivery switch on** —
   `oidc.backchannel_logout_enabled=true` — for the logout profiles.
4. **Run the four plans** on the hosted suite, same variant choices as the
   local rehearsal (Basic OP: `static_client` + `code` +
   `client_secret_basic`; Config OP: no variant; the two logout plans:
   `static_client` + `code`). The suite drives the browser; answer the
   consent/interaction steps as instructed (or use the submission
   deployment's consent-skip if the profile allows it).
5. **Gather the evidence**: each plan's results page (URL + the suite's
   exported log/`json`), the deployment's issuer URL, the software's
   repository link, and the public documentation page (`docs/oidc-provider/`).
6. **Submit**: mail <certification@oidf.org> per the
   [OP Test Guide](https://openid.net/certification/connect_op_testing/) —
   name the profiles (Basic OP, Config OP, RP-Initiated Logout OP,
   Back-Channel Logout OP), attach the plan URLs, state the implementation
   (Saka, <https://github.com/riipandi/saka>), and note the open-source
   project status ([the open-source policy](https://openid.net/certification/open-source-project-certification-policy/)
   waives the fee).
7. **Keep the deployment alive** until the certificate is issued; the
   certification team may re-run the plans against it.
