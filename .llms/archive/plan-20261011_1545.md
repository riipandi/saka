# Plan — Wave 3: the admin console core

## Objective

Close the Wave 3 rows of `.llms/roadmap/frontend-integration.md` (read 2026-10-11): the
admin shell and route guard with the impersonation banner, the user
management center, groups and the blocklist and signup tokens, the public
signup page decided by the public settings, the admin audit console, and the
`AuthorizationService` screens on the Wave 1.5 permission foundation. The
backend already serves every procedure this wave wires — no proto change, no
migration — so the wave is frontend integration with its contracts cited from
the protos and `internal/guard/rules.go`.

The flow reference is the Connect contracts themselves
(`api/connect/identity.proto`, `api/connect/authz.proto`,
`api/connect/auditlog.proto`, `api/connect/authn.proto`) and
`.llms/rules.md`'s Guard and Webapp frontend sections (read 2026-10-11). The
product flows follow the roadmap's Wave 3 acts as the roadmap records them.

## Decisions

- **D1 — the admin guard judges the claims snapshot, and the server stays
  the only authority.** `routes/(app)/admin/route.tsx` (a layout route
  wrapping the admin tree) runs `isAdministrator()` in `beforeLoad` and
  redirects a non-administrator to `/overview` with a notice — the same
  one-shot pattern the `loggedOut`/`unauthenticated` notices use. No new
  endpoint is minted to ask "am I an admin": the mint-time claims snapshot
  the Wave 1.5 custody already carries is the same fact the server's
  `Admin` rules will judge again on every call, and a stale snapshot
  degrades to the server's `not_found` word, never to a privilege. A
  dedicated 403 page was rejected — the guard's disclosure rule answers
  `not_found`, and a page that says "forbidden" would contradict it.
- **D2 — one shell, one sidebar, a gated section.** The admin pages mount
  inside the existing `(app)` layout; the sidebar gains an Administration
  section whose items render under `<Can permission="…">` (hiding, not
  disabling), judged by the catalog slugs each page actually consumes.
  A separate admin chrome with its own navigation was rejected — the
  impersonated session must see the same shell its actor would, because
  the banner's job is to say who is acting, not to build a second product.
- **D3 — the impersonation banner reads the token's own claims.**
  `auth-claims.ts` extends its zod schema with `actor_id`/`actor_username`
  (absent = not impersonating; malformed warns and never throws, as
  today). The banner renders above the content area whenever
  `actor_id` is present, naming the borrowed account and the actor
  (`actor_username` when the claim survives — the renewal's documented
  `ActorUsername` drop makes `actor_id` the stable fact), and its button
  calls `StopImpersonating` through the auth context: a fresh pair on the
  actor's own account, cache cleared, navigate to the overview. The
  banner state is the claims snapshot, not a store of its own — custody
  already owns the lifecycle.
- **D4 — the user center is a list page plus a detail route.**
  `admin/users.tsx` (the paginated, searchable, sortable table over
  `usePaginatedList` + `ListUsers`) and `admin/users/$id.tsx` (the
  detail: the full-replace `UpdateUser` form, the credential management
  sections, and the actions). The destructive actions (ban with its
  required reason, unban, unlock, delete, `AdminResetUserPassword`,
  `AdminDisableMfa`, the passkey roll) open AlertDialog confirmations —
  the pattern the account screens already keep — and the impersonation
  action navigates rather than confirms (the banner is its own evidence).
  A single-page modal-heavy variant was rejected: the detail route is
  shareable and the back button works, matching the pagination rule.
- **D5 — the signup page's shape is the public settings' answer, read
  fresh.** `signup.tsx` under `(auth)` gates every field by
  `usePublicSettings` (`auth.signup_username_enabled`,
  `auth.signup_password_enabled`, `auth.signup_email_enabled` is the
  address field itself), renders the invite-token field when
  `access.mode` reads invite (the `?token=` search param prefills), and
  submits `Signup` — unlike the recovery screens, this form surfaces the
  server's refusals verbatim (a duplicate account, a blocklisted address,
  a spent token are facts the applicant must see, and the endpoint is not
  an enumerator's shape). `auth.verify_email_at_signup` sends the
  applicant to the existing verify flow. Gating by the deployment
  document instead of the settings catalog was rejected — the roadmap
  settles this and the catalog is the live product surface.
- **D6 — the audit console is ListAll with facets from FilterOptions.**
  `admin/audit.tsx` reuses the account audit page's table shape with the
  admin procedure and the `FilterOptions`-fed event/user filters; the
  per-user view (`ListForUser`) is a tab on the user detail page, not a
  second console. A search with no matches renders the empty state.
- **D7 — the authorization screens are checkbox trees over
  ListPermissions, and their writes say when they land.** `admin/roles.tsx`
  (the role CRUD + `SetRolePermissions` as a checkbox group over the
  catalog listing), `admin/users/$id.tsx`'s grants tab (`ListUserRoles`/
  `SetUserRoles`, `ListUserPermissions`/`SetUserPermissions`), and the
  screens' copy carries the custody rule the roadmap names: the caller's
  own grants move at the next token, not in place. The admin cannot edit
  its own account's grants from these screens without that note — the
  server refuses nothing there, so the note is the UI's honesty.
- **D8 — the reset-procedure states render as the service answers them.**
  `AdminResetUserPassword`'s arms are `not_found`, no-password-credential,
  resend-cooldown, and mail-unavailable (`recovery_service.go:275-307`).
  The roadmap's "banned" arm belongs to the token spend, not the ask —
  the delta is recorded here and the UI copy names the four real states.
- **D9 — no backward compatibility, no legacy shims** (owner direction,
  2026-10-11): the admin screens compose the current uilibs components and
  hooks as they are; where an existing page's shape would tempt a
  compatibility layer (the audit table, the recovery dialog), the admin
  pages fork the composition rather than abstract it, and any migration
  this wave would need is an in-place edit with a dev-DB reset instead of
  an ALTER.

## Execution rules

- **Atomic commit per phase is authorized** for this plan; each phase's
  heading below names its suggested commit message, and the plan's
  closing report recommends the final message. Self-contained commits
  during the plan's session are allowed. The standing commit rule
  (recommend, do not commit unasked) resumes when the plan completes.
- **Execution waits for the owner's explicit instruction** — this plan
  runs only when the owner says go.
- **No backward compatibility and no legacy shims** (owner direction).
  **Migrations are edited in place** when one would be needed, and the
  development database may be reset during the plan's session; no ALTER
  columns.
- **Test matrix per phase**: the layers each phase's validation line
  names run before its commit. The full matrix runs once in the final
  phase.
- **Yaak rows ride the change**: a procedure whose row drifts from the
  contract is corrected in the same commit as the phase that noticed;
  every phase verifies the rows it touches (all exist today).
- **Docs sync is the closing phase's** (`architecture.md`, `rules.md`,
  `integration-roadmap.md` ticks, `docs/`, `.llms/index.md`, the
  handover) — but a phase that lands a contract the rules already
  describe may note it in the phase's own commit when the wording would
  otherwise go stale.
- **E2E runs when the wave's acts are reachable in a browser** — this
  wave ships two files (the guard/impersonation/ban act and the signup
  act); both run against a fresh release build via the Playwright
  webServer, never a hand-started one.
