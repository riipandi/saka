## What happened this session

### 1. The expiry scan queues its successor only after the pass succeeds (Medium 7, commit `6852fea`)

- `apiKeyExpiryScanProcessor` in `internal/jobs/apikey_expiry_job.go` used to enqueue its successor
  **before** `ListExpiring`. A failed scan still committed the successor, the queue's retry of the
  same attempt inserted another, and three attempts could leave three daily chains — two of which
  could both remind a key before either marked it.
- The enqueue now sits after the pass, and the pass itself moved into a new `apiKeyExpiryScan`
  function that returns the list failure instead of swallowing it. A failed scan leaves no successor;
  the queue's retry is the only run. Unmarked keys are still picked up by the next pass.
- The other three recurring jobs (`cleanup_job.go`, `audit_cleanup_job.go`, `storage_gc_job.go`)
  already kept this order — the user chose to leave them untouched rather than churn the pattern.
- `TestTheExpiryScanQueuesNoSuccessorWhenTheScanFails` drives the processor against a **second pool
  on the same DSN, shut down before the call**, so the list is genuinely refused while the client's
  own pool stays live for the assertion. The first draft shut down the only pool and could not read
  the pending count back.

### 2. A failed audit insert is contained in a savepoint (Medium 8, commit `fa7f99b`)

- New `datastore.WithSavepoint(ctx, q, fn)` in `internal/datastore/postgres.go`. It reads the surface
  it is handed: a `pgx.Tx` opens a nested transaction (pgx implements that as a savepoint) and rolls
  back to it on failure; a pool has no surrounding transaction to poison and runs `fn` directly.
  `fn`'s error is what the caller sees, not the savepoint's.
- `Recorder.Record` in `internal/audit/recorder.go` runs its insert through the helper. Postgres
  poisons a transaction on any statement error until rollback (`25P02`), so the old bare insert that
  ignored its own error would have taken the caller's change down with it — and the error the caller
  saw would not have named the audit insert. Now the record is lost, the change commits, and the
  recorder logs the event that went unrecorded.
- `internal/audit` still imports no pgx: the transaction vocabulary stays in `datastore`, which was
  the user's chosen shape (option A).
- Tests: `TestWithSavepointContainsAFailedStatement` and
  `TestWithSavepointOnThePoolRunsTheFunctionDirectly` in `internal/datastore/postgres_test.go`;
  `TestAFailedRecordDoesNotAbortTheCallersTransaction` and `TestAFailedRecordOnThePoolIsContained` in
  `internal/audit/recorder_test.go`. The audit tests use a `user_id` no account holds — the foreign

## Gotchas learned this session (durable)

- **Postgres poisons a transaction on any statement error until rollback (`25P02`).** A side effect
  that is allowed to fail without failing the caller cannot simply ignore its own error — it must run
  under a savepoint. This is the general rule the audit recorder now follows.
- **pgx implements a nested transaction as a savepoint.** `tx.Begin(ctx)` on a `pgx.Tx` is the
  savepoint, and its `Rollback` is `ROLLBACK TO SAVEPOINT`; no hand-written SQL is needed. A pool's
  `Begin` is a real transaction, which is why `WithSavepoint` branches on the surface type.
- **A recurring job's successor must be enqueued after its work succeeds.** Enqueuing first means a
  failed attempt still commits a successor, and the retry adds another — the schedule forks.
- A test that shuts down the pool it needs for assertions cannot read the assertion back; open a
  second pool on the same DSN when the failure must come from the database.
- The debug-build smoke commands make `task lint` red on a clean tree; it is not a regression.
