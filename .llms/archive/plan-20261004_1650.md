# Plan — OIDC IdP Standard Claims: `picture` and `updated_at`

Written 2026-10-04. The review of the issuance surface against OIDC Core §5.1
found the ID token and the userinfo endpoint answering every consumed Standard
Claim but two: `picture` — the account's avatar is stored and composed, never
issued — and `updated_at` — the account's change stamp is written by a trigger,
never read. The owner named both, with the claim carrying the standard name
`picture` rather than the internal `avatar_url` word.

## Objective

The OIDC provider's `profile` scope answers the Standard Claims §5.1 names the
account already holds: `picture` (the public URL of the account's stored
picture) and `updated_at` (the instant the account's information last changed),
on the ID token, the userinfo endpoint, and the operator's claim preview, so
all three name the same facts.

Design-doc rows touched: `.llms/architecture.md` § modules/federation (the
claims paragraph), `.llms/endpoint-reference.md` § OIDC (the userinfo and
preview rows). `.llms/auth-design.md` has no OIDC provider section — nothing to
tick there.

## Current state

Every claim verified in the code:

- The issuance claims live in one function: `subjectClaims`
  (`modules/federation/oidc/protocol.go:465-504`). Under scope `profile` it
  answers `given_name`, `family_name`, `name`, the nonstandard `display_name`,
  and `preferred_username`; under `email`, `email` and `email_verified`; under
  `groups`, the group names. **No `picture`. No `updated_at`.**
- The operator-defined custom claims merge under `profile` with
  `protectedClaimKeys` (`protocol.go:428-441`) guarding the protocol-minted
  names. The set protects `picture` already; **`updated_at` is not in it** — a
  custom claim row naming `updated_at` would shadow the protocol's own.
- The account read-model carries the picture but not the change stamp:
  `UserView.AvatarURL` (`modules/identity/user/service.go:400`) is composed at
  `view()` (`service.go:1003-1009`) from the joined `picture_bucket` /
  `picture_key` and the serving origin — empty when the account has no
  picture. `UserSchema` (`modules/identity/user/schema.go:17-45`) and
  `UserColumns` (`modules/identity/user/repository.go:36-44`) read **no
  `u.updated_at`**.
- The column exists: `users.updated_at TIMESTAMPTZ` with the trigger
  `trg_users_updated_at` stamping every update
  (`database/migrations/00004_create_identity_tables.sql:31,48`). Rows never
  updated since creation carry NULL.
- The preview duplicates the claim map: `preview.go:71-96` builds its own
  `profile` map (`sub`, `preferred_username`, `name`, `email`,
  `email_verified`, `groups`, the names) rather than calling `subjectClaims` —
  the two maps must not drift, and today both miss the same two claims.
- The tests pin the shape: `protocol_claims_test.go` drives `subjectClaims`
  directly over a `stubDirectory`; `service_test.go:353`
  (`TestPreviewBuildsTheClaimMapsForTheAccount`) drives the preview.
- E2E is not relevant: the federation surface has no ladder, and both probes
  the round needs are container tests over the claim maps.

## Decisions

1. **`picture` = the composed public URL the account read-model already
   answers, and the Go field carries the standard word** (`UserView.Picture`,
   renamed from `AvatarURL` 2026-10-04, owner's pick mid-execution — the field
   the claim reads should not carry two names). Emitted under scope `profile`,
   omitted when the account has no picture. The wire field saka's own REST API
   answers stays `avatar_url` — that surface is not an OIDC claim. Rejected: a
   nonstandard `avatar_url` claim; the raw bucket/key pair. **Superseded the
   same day (owner's word): the wire field too is `picture` now, and every
   `AvatarURL`/`avatar_url` remnant across the codebase is renamed — the
   saka-only REST surface included; no compatibility shim.**
2. **`updated_at` = the trigger's stamp, seconds since the Unix epoch** — a
   JSON number, the representation §5.1 names. A NULL stamp (the account never
   updated since creation) falls back to `created_at`: for an account whose
   information never changed, creation is when it was last updated, and
   omitting the claim would hand a relying party a profile section without the
   change anchor. Rejected: omitting when NULL; an RFC 3339 string (the spec
   pins the number); `email_verified_at` (wrong semantics — the address's
   proof, not the profile's age).
3. **The plumbing rides the one read-model**: `UserSchema.UpdatedAt
   *time.Time`, `UserColumns` gains `u.updated_at`, `view()` maps it into
   `UserView.UpdatedAt`. No second query, no migration — the column and its
   trigger exist; nothing is written by this round.
4. **`updated_at` joins `protectedClaimKeys`**: the protocol mints it, so an
   operator's custom claim row must not shadow it — the same rule `picture`,
   `sub`, and `email` already live under.
5. **The preview inherits the two claims**: `preview.go`'s map gains the same
   two entries under the same conditions, so the operator preview never names
   a claim shape the issuance would not mint.

## Shape and enforcement points

- `modules/identity/user/schema.go`: `UpdatedAt *time.Time \`db:"updated_at"\``
  beside `CreatedAt`; the read-model field `UserView.Picture` (renamed from
  `AvatarURL`, decision 1).
- `modules/identity/user/repository.go`: `UserColumns` gains `"u.updated_at"`
  (scan order decides the `ScanSchema` arg order — the field joins the schema
  in the same position).
- `modules/identity/user/service.go`: `UserView.UpdatedAt *time.Time`;
  `view()` maps it; the wire answer stays `AvatarUrl: user.Picture`.
- `modules/federation/oidc/protocol.go`: `subjectClaims` under `profile`
  answers `picture` (non-empty `view.Picture`) and `updated_at`
  (`UpdatedAt.Unix()`, falling back to `CreatedAt.Unix()` — `CreatedAt` is
  never zero on a read row);
  `protectedClaimKeys` gains `updated_at`.
- `modules/federation/oidc/preview.go`: the preview's `profile` map gains the
  same two entries (`account.Picture`).
- No migration, no new procedure, no new REST route, no audit event, no
  settings key — the surface is the two claim maps and the read-model columns
  behind them. The Yaak collection needs no row (the `/oidc/userinfo` row
  exists; the claims ride inside its answer).
