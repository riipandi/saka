# Handover — the sign-in completeness wave (plan-20261010_1830)

## What shipped

Eight phases, one commit each, every phase validated before its commit:

- **Phase 1 — the step-up machinery** (`640d53f4`): `libraries/reauth/` —
  `reauth.ts` (the guarded-procedure list mirroring `internal/guard/rules.go`,
  `createStepUpRunner`: challenge first, spend once, one retry on proof
  refusal, the `unauthenticated` backstop mapping, `StepUpCancelled`),
  `-reauthenticate-dialog.tsx` (password / passkey / email-code factors via
  `SendReauthenticationCode`), `use-step-up.ts`. The sessions center's
  per-row `RevokeSession` became the first consumer. The sessions browser
  tests were rewritten — the old "no per-row revoke" test was passing
  vacuously (it ran before the rows rendered).
- **Phase 2 — the login state machine** (`380ac937`): the engine answers a
  discriminated `SignInOutcome` (`signed-in` / `mfa-challenge` /
  `enrollment-required`); `completeSignIn` shares `finishSignIn` custody;
  the login view split into `-login-view.tsx`,
  `-mfa-challenge-view.tsx` (with the bridge countdown),
  `-mfa-enrollment-view.tsx` (QR via `uqr`, recovery codes shown once).
  The OAuth callback hands a forked bridge through
  `sign-in-handoff.ts` (one memory slot, take consumes).
- **Phase 3 — password management + MFA management** (`3af3ff67`): the wire
  gained `identity.v1.User.password_updated_at` (field 18, owner decision —
  no migration; the fill LEFT JOINs `user_passwords`). The security page
  (`account/security.tsx` over `-security-view.tsx`) composes the password
  card (gated on `passwordUpdatedAt`), the authenticators card
  (code-required-iff delete per `DeleteTotpEnrollmentRequest.code`),
  recovery regeneration, and Disable two-factor.
- **Phase 4 — passkeys end to end** (`8998a1db`):
  `libraries/webauthn/passkey.ts` `runPasskeyAssertion` — one ceremony
  shared by the login entry, the challenge's "Use a passkey instead", and
  the reauth dialog's passkey tab. The engine's `verifyPasskeyLogin` is
  custody (no MFA fork on `VerifyLoginResponse`). The security page gains
  the passkey card: enroll, rename (`UpdateCredential`, no proof), delete
  (step-up-guarded).
- **Phase 5 — password recovery routes** (`c09d4b13`): `forgot-password`
  wired (the always-success sentence; the `expose_reset_token` dev aid
  reads the response's own field, not a config flag), `reset-password.tsx`
  over `-reset-password-view.tsx` (the emailed **code to type**, `?token=`
  prefills; success navigates `/login?reset=1`, the login route renders
  the "Password reset" notice).
- **Phase 6 — one-time access** (`e76e604f`): the engine gained
  `requestOneTimeAccess` + `exchangeOneTimeToken` (the exchange answers the
  same fork; the worker op `exchange-one-time-token` writes the cookie only
  for a signed-in answer). The login card gains the toggle-gated "Email me
  a one-time sign-in code" entry and a `one-time-code` phase that spends
  the typed code with the in-memory device token. **Recorded delta from
  the plan's D6**: no `/login-code` route — the wire reserved the email's
  `redirect_path` away ("the login code is typed, never linked") and the
  email-path exchange demands the `device_token` back, which a URL cannot
  carry.
- **Phase 7 — E2E** (`03385064`): `workflow/sign-in-completeness.test.ts`

- **Phase 8 — docs sync** (this commit): `.llms/rules.md` carries the

## The decisions worth remembering (plan D1–D8)

- **D1** — step-up runs proactively at the guarded call site; the
  guard's `unauthenticated` is the backstop, no invented wire code (the
  rule table is not the UI's to disclose).
- **D2** — the proof rides per-call Connect options through the
  `callHints` channel; no `authFetch` change, no global reauth store.
- **D3** — the MFA fork is one mount's phases; the bridge never in a URL.
- **D4** — recovery codes shown once in an acknowledged dialog.
- **D5** — the reset route follows the verify-email pattern; the dev aid
  reads the response's field, not a config flag.
- **Delta on D6** — one-time access has no route; the code is typed into
  the login machine's own phase, the device token in that mount's memory.
- **D7** — E2E covers the token-bearing flows; passkeys keep the ladder.
- **D8** — the engine grows by named outcomes, not exceptions.
