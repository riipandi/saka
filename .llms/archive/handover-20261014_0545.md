# Handover — the session retention sweep

The backend session surface closes its retention gap. Found by the backend
auth audit (`.llms/audit/audit-20261014_0329.md`) and written up as
`issue-20261014_0330.md`, the sweep now runs on its own schedule with the
window the deployment names.

## What landed

- **Phase 1** (`257b5d04`): migration `00004` edited in place —
  `idx_sessions_expires_at` and the partial `idx_sessions_revoked_at`, the
  sweep's two user-less arms (the existing `(user_id, expires_at)` index
  cannot serve them). Proven with `EXPLAIN (ANALYZE, BUFFERS)` on 200k seeded
  rows: BitmapOr of the two arms at 0.75 ms / 40 buffers, against the
  17 ms / 3,467-buffer seq scan before. The dev database was reset and
  reseeded around the proof; the synthetic rows were deleted afterwards.
- **Phase 2** (`8e1f5c01`): `app.session_retention_days` — default 30,
  validated `> 0`, published as an administrative App row beside
  `audit_retention_days`. Three pins: the zero refusal, the default, the
  administrative-only publication.
- **Phase 3** (`2b000c9a`): the `session_cleanup` job (daily, the
  `audit_cleanup` shape — the window rides the task payload, so a config
  change takes effect at the next run) over the session repository's
  `DeleteRetentionExpired` (`revoked_at < cutoff OR expires_at < cutoff`,
  NULL-safe). Wired through `Register`, the `Seeder` (new `sessionDays`
  parameter), and `infrastructure.go`.
- **Phase 4**: docs sync — the endpoint reference's sessions section carries
  the retention paragraph; `rules.md`'s Job recipe records the retention-sweep
  shape; `architecture.md` records the reasoning in the jobs list and the
  session package's section; `docs/configuration.md`'s app row names the
  retention windows. `issue-20261014_0330.md` is resolved and archived; the
  backend audit's frontmatter flips to resolved with it.

## Traps worth keeping

- `public.sessions` carries `CHECK (expires_at > CURRENT_TIMESTAMP)`: a
  row whose expiry is in the past cannot be inserted, and an `UPDATE` that
  names `expires_at` re-evaluates the check. Tests work around it with
  future-dated rows and artificial cutoffs — the expired-never-stamped arm
  is proven at the repository level (`repository_retention_test.go`), the
  job-level tests carry only the shapes a fresh deployment can hold.
- The queue's `Register` panics on a duplicate queue name: the tests
  register once and run the processor repeatedly.
