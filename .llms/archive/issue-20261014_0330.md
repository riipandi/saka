# Session rows are never swept — the table grows without bound

- status: resolved
- plans: plan-20261014_0504.md (the session retention sweep; phases 1–4
  landed) · found by the backend auth audit, `.llms/audit/audit-20261014_0329.md`

## Finding

`internal/jobs/cleanup_job.go` sweeps the queue's expired completed rows, the
multifactor enrollments and bridges, the webauthn tokens, the signup tokens,
and the device-login requests. The `public.sessions` table is absent from the
sweep, so ended and expired session rows accumulate forever.

The retention shape is deliberate — `ListSessions` keeps ended rows listed
("the stamp is the fact a holder reads, not something to hide") — but the
stamp a holder reads stops being interesting long before the row stops
existing. Every sign-in adds a row; every account's `ListSessions` count
grows with its lifetime history; the table grows with the fleet.

## Resolution (2026-10-14, plan-20261014_0504)

- **Config key:** `app.session_retention_days`, default 30, validated `> 0`,
  published as an administrative App row beside `audit_retention_days`
  (plan phase 2).
- **Sweep:** dedicated `session_cleanup` recurring job (daily, the
  `audit_cleanup` shape) deleting rows whose end — `revoked_at` where
  stamped, `expires_at` where never revoked — is older than the window, via
  the session repository's `DeleteRetentionExpired` (plan phase 3).
- **Indexes:** `idx_sessions_expires_at` and the partial
  `idx_sessions_revoked_at` added to migration `00004` in place; proven with
  `EXPLAIN (ANALYZE, BUFFERS)` on 200k seeded rows — BitmapOr of the two
  arms, 0.75 ms / 40 buffers vs the 17 ms / 3,467-buffer seq scan
  (plan phase 1).
- Note: the remedy shape in this issue ("a retention sweep in the existing
  cleanup job") was refined to a dedicated job — the plan records the delta
  and its reason (D1).
