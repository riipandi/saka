# Passkey authentication plan: GitHub-style, backend first

Written 2026-09-30. Executed later; nothing in this plan is implemented yet except what the
"current state" section names. Every decision in the decisions table was confirmed with the
user in the same session; the few choices that remain are named in "Remaining decision
points" with a recommended answer, and the owning phase pauses rather than silently choosing.

## Objective

GitHub-like auth: email/password stays the primary sign-in, and passkeys flex across three
roles — passwordless first factor, second factor completing the MFA bridge, and step-up
reauthentication. Email stays required for every account, so the email reset path is always
the recovery anchor. One-time access tokens (email today, phone/SMS later) keep their place
in the ladder.

## Execution rules

- The agent is **authorized to create atomic commits during this plan**. Commit each
  validated step as it lands (the phase sections name the intended commit boundaries);
  stage explicit paths only, never push, never destructive Git commands.
- The agent is **authorized to reset the development database** during this plan:
  `task db:reset -- --force --up` followed by `task db:seed -- --force`. The reset applies
  to databases this plan's work created or owns — never to a database holding state the
  plan did not create. E2E artifacts (isolated databases, disposable config/env files,
  enrolled test credentials) are removed in the same session that created them, and the
  release server is stopped when a probe session ends.
- **Frontend is out of scope for Phases A and B.** Phase B's probe page is a test
  instrument, not a product surface. Where a feature needs a screen, the phase delivers the
  backend + contract and marks the UI work `TODO(frontend)` in the endpoint reference and
  in that phase's notes.
- Follow `AGENTS.md` and the identity sections of `.llms/architecture.md`. A phase that
  hits a fork the decisions table and "Remaining decision points" do not settle asks first
  rather than choosing silently.
- Reuse the established patterns: `modules/<area>/<feature>/` layout (`schema.go`,
  `repository.go`, `service.go`, `handler_rpc.go`, `module.go`), the identity area's
  `features()` list as the only registration, guard rules declared in `internal/guard`,
  audit events named in `internal/audit`, `pkg/testutils` containers for integration
  tests, Yaak requests for every shipped procedure, and the `clarity` skill before prose
  edits.
- Every new config-flavored key lands in the `modules/appconfig` catalog with a default and
  a `Validate` bound — never a process-level config key — because these are runtime product
  knobs an operator flips without a restart.
- RPC probing goes through `scripts/curl-rpc.sh`; the release binary under
  `build/release/tango serve --env-file=.env.local` is the E2E target, never a dev server
  guess.
- Each phase validates on its own (build, lint, focused suite, container tests where state
  is touched, `task rpc:stale` after any proto change) before it commits.

## Decisions (confirmed 2026-09-30)

| Decision | Pick |
|---|---|
| Sign-in passkey UX | Usernameless / discoverable credentials — `BeginLogin` takes no identifier; the account resolves from the credential ID. Matches upstream and GitHub. |
| Synced passkeys (iCloud, password managers) | Allowed; appconfig toggle `webauthn.allow_synced_passkeys`, default `true` (upstream parity). |
| Passkey assertion with user verification | Satisfies MFA fully — no TOTP demanded after a passkey sign-in, even on MFA-enabled accounts. |
| Step-up proof | Single-use reauthentication token (the `reauthentication` purpose `public.auth_tokens` already declares), consumed by the guarded procedure. No sudo-mode window. |
| One-time access vs MFA | Close the current bypass in this plan: `Exchange` on an MFA-enabled account mints the pending bridge instead of a session. UX change, accepted. |
| Email | Stays required (decided 2026-09-30). Passkey is never the only factor an account can hold. |
| Library | `github.com/go-webauthn/webauthn` — the library upstream v2.16.0 pins (v0.18.2), so ceremony shapes stay comparable. |
| RP identity | Derived from `app.base_url` (the public origin): RP ID is its hostname, RP origins is the origin itself. Same derivation upstream uses for its app URL. |
| Schema rework | Four changes folded inline into `00002`/`00003` (below), not stacked `ALTER`s — confirmed set. |
| AAGUID catalog (decided 2026-09-30) | The `aaguid.json` catalog from passkeydeveloper/passkey-authenticator-aaguids is **embedded**, the way Pocket ID embeds it: a manifest keyed by AAGUID UUID, loaded lazily, answering the authenticator's display name for the enrollment fallback and the credential view. Icons are upstream's second half — content-addressed SVGs behind a validated endpoint — and stay `TODO(passkey)` for Phase C. `scripts/get-aaguid.sh` fetches the catalog; its output moves from `storage/` to the embed location so the build picks it up. |
| Probe transport (decided 2026-09-30) | WebAuthn needs a secure context. Plain `http://localhost` works for most browsers, but HTTPS with a valid certificate is what cross-device (hybrid) and synced-passkey flows require — so the Phase B probe runs against the **nginx HTTPS proxy** in `docker/compose-dev.yaml`: `https://localhost:8443` → host `:3080`, self-signed pair from `task cert:generate` / `cert:trust`, with `app.base_url` pointed at the proxy origin so the RP identity matches. |

## Current state

- `public.webauthn_credentials` and `public.webauthn_sessions` exist (migration `00003`).
  As written they need the rework below: the credentials table carries `credential_id`,
  `public_key`, `attestation_type`, `transport`, `backup_eligible`, `backup_state`,
  `aaguid`, `last_used_at` (plus a `device_type` column nothing produces — dropped by the
  rework), and lacks a persisted signature counter. The sessions table carries a unique
  `challenge`, `challenge_type` (`registration|authentication`), `user_verification`,
  `credential_params`, `extensions`, `expires_at`, and a nullable `user_id` — the nullable
  side is what usernameless login needs.
- `modules/identity/webauthn/` is a stub: one-line files, no logic, not listed in the
  identity area's `features()`.
- `public.auth_tokens` already declares the `reauthentication` purpose (migration `00002`),
  hash-only rows, single use — with the `UNIQUE (user_id, purpose)` the rework relaxes for
  this purpose.
- `modules/identity/multifactor` owns the pending bridge (`user_mfa_pending`), the
  `mfaGate` interface wired after construction, and the constant `maxEnrollments = 10`
  (`service.go:62`) that the new settings replace.
- `modules/identity/signin` mints sessions (`IssueSession`, providers
  `ProviderOneTimeAccess` and friends) and is where the passkey provider lands.
- The ladder's hole: `modules/identity/onetimeaccess/service.go:235` — `Exchange` calls
  `signin.IssueSession` directly, so an MFA-enabled account signs in with an email link and
  no second factor.

## Auth ladder after this plan

| Path | Proof | MFA-enabled account |
|---|---|---|
| Password | knowledge | bridge → TOTP / recovery / passkey |
| One-time token, email | possession of email | bridge → TOTP / recovery / passkey (bypass closed) |
| One-time token, phone/SMS | possession of number | bridge → MFA, same shape — future work |
| Passkey + UV | possession + biometric/PIN | full session, one step |

`auth_tokens` stays channel-agnostic; delivery is transport only. The SMS future adds a
sender behind a dispatcher-style interface and a `signin.ProviderSmsOtp`, never a new token
shape.

## Schema rework

The migration set is not final yet (confirmed 2026-09-30), so the rework folds into the
existing `CREATE TABLE` statements instead of stacking `ALTER`s. Applying it means
`task db:reset -- --force --up` plus reseed — the dev database is disposable, no deployed
state exists. Migrations `00001`–`00011` keep their version numbers; the changes below edit
their files in place.

In `00003_create_multifactor_tables.sql`:

- `webauthn_credentials` gains `sign_count BIGINT NOT NULL DEFAULT 0`. Upstream does not
  persist the signature counter, which disables clone detection; tango persists it so
  go-webauthn's counter-regression refusal stays live.
- `webauthn_credentials.device_type` is dropped, with `idx_webauthn_credentials_device_type`
  and `idx_webauthn_credentials_user_device_type`. Upstream never carried the column, no
  tango code writes it, and the one-credential-three-roles design makes it obsolete. The
  `Down` section's index list shrinks to match.
- `webauthn_sessions` gains
  `CHECK ((challenge_type = 'registration' AND user_id IS NOT NULL) OR challenge_type =
  'authentication')` — a registration ceremony always names its account; an authentication
  session may stay userless because the account resolves from the credential.

In `00002_create_identity_tables.sql`:

- The `UNIQUE (user_id, purpose)` index on `auth_tokens` becomes a partial unique index,
  `WHERE purpose <> 'reauthentication'`. One live token per account remains the rule for
  email verification, one-time access, password reset, and email change (resend replaces);
  reauthentication allows several live tokens so a second tab's confirmation never kills
  the first's — the same several-live-rows rule `user_mfa_pending` already follows. The
  consumption is still a single-use `UPDATE ... RETURNING`, so a token is spendable once
  regardless of how many exist.

## Proto surface

New `api/connect/webauthn.proto`, service `tango.authn.v1.WebAuthnService`, mounted by the
identity area's new `webauthn` feature. Every procedure carries `buf.validate.field`
constraints where a shape exists (session id pattern, credential name length, base64url
credential payload non-empty).

Ceremony documents travel as opaque JSON: the requests carry the browser's
`PublicKeyCredential` JSON verbatim and the responses carry the go-webauthn options
document verbatim. The SPA passes both through untouched; the server never re-shapes what
the browser produced. Field sketch per procedure:

- `BeginRegistration` (authenticated, no body beyond validation floor) → `options` (the
  `PublicKeyCredentialCreationOptions` JSON), `session_id`.
- `VerifyRegistration` (authenticated) → `session_id`, `credential` (the registration
  response JSON), `name` (optional; the server derives a fallback from the AAGUID) → the
  credential view (id, name, aaguid, backup flags, transports, created at).
- `BeginLogin` (public, empty request) → `options` (the `PublicKeyCredentialRequestOptions`
  JSON, empty `allowCredentials`), `session_id`.
- `VerifyLogin` (public) → `session_id`, `credential` (the assertion JSON) → the sign-in
  envelope: session tokens and account view, same shape the password sign-in answers.
- `ListCredentials` (self) → the caller's credentials, minimal view.
- `UpdateCredential` (self) → `credential_id`, `name` → the updated view.
- `DeleteCredential` (self) → `credential_id` → empty success.
- `Reauthenticate` on `tango.authn.v1.AuthService` (authenticated) → either
  `password` or `credential` (an assertion over a freshly minted authentication session) →
  the reauthentication token (wire form, one-time, short TTL) and its expiry.

Guard rules in `internal/guard`: `BeginRegistration`, `VerifyRegistration`,
`ListCredentials`, `UpdateCredential`, `DeleteCredential`, `Reauthenticate` map to
`Self(user)`; `BeginLogin` and `VerifyLogin` are `Public`. A new `Reauthenticated` rule
consumes the token atomically (`UPDATE ... WHERE expires_at > now() AND purpose =
'reauthentication' ... RETURNING`) before the guarded handler runs, answering
`unauthenticated` when nothing returns — never `permission_denied`.

Audit events named in `internal/audit` (snake_case, what happened):
`webauthn_credential_registered`, `webauthn_credential_removed`,
`webauthn_credential_renamed`, `webauthn_sign_in`,
`webauthn_reauthentication_granted`, `webauthn_reauthentication_consumed`. The passkey
completion of an MFA bridge reuses the multifactor events the bridge already records; the
one-time fix rides `EventOneTimeAccessSignIn` unchanged.

## Service design

- **Enrollment** (`BeginRegistration` → `VerifyRegistration`): the ceremony session row
  stores what go-webauthn's `Session` carries (challenge, cred params, user verification,
  extensions, expiry) keyed by the row id; registration sessions always name the caller.
  Verification parses the attestation, enforces the `allow_synced_passkeys` toggle against
  `backup_eligible`, enforces `passkey.max_credentials` and (through the shared seam)
  `mfa.max_enrollments`, requires user verification, stores `public_key`, `sign_count`,
  `transports`, `aaguid`, and answers the view. The name falls back to the AAGUID-derived
  authenticator name when the caller sends none.
- **Sign-in** (`BeginLogin` → `VerifyLogin`): the authentication session row carries no
  user. Verification resolves the account by raw credential ID, checks the challenge and
  its expiry, verifies the signature, advances and persists `sign_count` (a regression is
  the clone refusal), updates `backup_state` / `last_used_at`, and issues the session in
  one step through `signin.IssueSession` with the new provider — passkey + UV is full
  authentication, so no bridge and no second factor. A disabled or banned account answers
  the same refusal shape the password path answers.
- **Second factor** (`multifactor`): `CompleteSignIn` gains the passkey verifier beside
  TOTP and recovery codes — the pending bridge is consumed by a valid assertion over an
  authentication session bound to the bridge's account. Wrong assertions spend the bridge's
  `wrong_attempts` budget; three wrong codes end the bridge, as today.
- **Step-up** (`Reauthenticate` + `Reauthenticated`): the RPC accepts password (the
  identity + password path the sign-in service already owns) or a passkey assertion, and
  mints a `reauthentication` token: hash stored, single use, several live per account,
  short TTL. The guard rule consumes it in one statement before the guarded handler runs,
  so the proof is spent exactly once even under concurrent calls.
- **One-time access fix** (`onetimeaccess`): `Exchange` consults the `mfaGate` before
  issuing; an account with confirmed MFA gets the pending bridge (5-minute TTL, same
  mechanism as the password path) instead of a session. Accounts without MFA keep today's
  one-step behavior.

## Settings (appconfig catalog)

- `webauthn.allow_synced_passkeys` — bool, default `true`. Enforced at registration: a
  `backup_eligible` attestation is refused when the toggle is off.
- `webauthn.user_verification` — enum `required|preferred|discouraged`, default `required`.
  Upstream exposes the same knob; MFA satisfaction holds only when it is `required`, so a
  lowered value narrows the ladder and the docs must say so.
- `mfa.max_enrollments` — int, default `10`, replaces the `maxEnrollments` constant. Read
  at enrollment time through `Settings`, never cached at startup; an unreadable value
  fails closed (the enrollment is refused, not waved through).
- `passkey.max_credentials` — int, default `10`. Counted separately from TOTP devices.
- Enforcement is enrollment-only: lowering a limit never unregisters existing devices.
- Each key lands in the catalog with a default, a `Validate` bound (ints 1–50), and an
  entry in the generated `config.schema.json`.

## Sensitivity set for step-up

Procedures that require `Reauthenticated`: password change, email change, MFA disable and
recovery regeneration, passkey enroll/delete (delete at minimum), session revocation,
impersonation start, grant and role changes, API-key management. The set lives in the guard
rules file; adding a procedure is one line. Each touched procedure's Yaak request gains the
header note in the same change.

## Phase B — browser probe, not UI

Phase B opens with the AAGUID catalog embedded, because the probe's enroll answers
are the first place a real authenticator's name shows up:

1. **AAGUID catalog** — `scripts/get-aaguid.sh` repointed at the embed location; the
   manifest embedded in `modules/identity/webauthn` and loaded lazily the way Pocket
   ID loads its manifest; the enrollment name fallback answers the catalog's name
   (`<name> Passkey`), and an unknown AAGUID keeps the plain fallback. Icons stay
   `TODO(passkey)` (Phase C).

Then the probe itself: a dev-only route in the embedded SPA (or a bare test page)
that runs a real enroll and sign-in against `build/release/tango serve
--env-file=.env.local` behind the nginx HTTPS proxy — `https://localhost:8443`,
self-signed pair trusted with `task cert:trust`, `app.base_url` set to the proxy
origin so the RP identity matches. Done means the ceremonies pass in Chrome and
Safari locally. Software authenticators cannot expose UV/UP quirks, resident-key
behavior, or transport surprises (hybrid/cross-device in particular); this phase
exists to catch them. Findings that require contract or schema changes come back to
the user before the change lands. The probe page and its test credentials are
removed in the same session.

## Phase D — final validation, comprehensive E2E, docs, and handover

Mandatory — the plan is not done until this phase passes. It mirrors the closing phase the
OIDC plan runs.

1. **Full suites**: `go test -count=1 -race ./...` on the touched packages plus the whole
   tree, `task check`, `task lint`, `task db:validate`, `task rpc:stale`.
2. **Wire-level E2E of the whole auth ladder** against a disposable server and database:
   build `build/release/tango serve --env-file=.env.local` over a freshly reset and seeded
   database, then drive the flows through the real HTTP surface. The ceremonies
   (`BeginRegistration`/`VerifyRegistration`/`BeginLogin`/`VerifyLogin`/`Reauthenticate`)
   cannot be driven with `curl` — the soft authenticator from Phase A doubles as the
   wire-level E2E driver, speaking ConnectRPC to the live server instead of calling the
   service in-process. Plain RPC and REST steps (`scripts/curl-rpc.sh`) cover the rest.
   The scenarios, in one session:
   - Signup → password sign-in → enroll a passkey on the authenticated session.
   - Passkey sign-in passwordless, on an MFA-enabled account — session in one step, no
     bridge, `amr`-shaped audit trail correct.
   - Password sign-in on an MFA-enabled account → passkey completes the bridge; then the
     same flow completed by TOTP, and once by a recovery code.
   - The `wrong_attempts` budget: three wrong assertions end the bridge; a fresh bridge
     costs a new password.
   - Step-up: `Reauthenticate` by password and by passkey; the guarded procedure consumes
     the token; the second call with the same token is refused; two live tokens are spent
     independently.
   - One-time access: an email code on an MFA-enabled account mints the bridge (not a
     session); on an account without MFA it issues the session directly.
   - Settings live: flip `webauthn.allow_synced_passkeys` off through the admin settings
     RPC and prove the next enrollment is refused without a restart; raise/lower both
     limits and prove enforcement at enrollment only.
   - Lifecycle: rename and delete a credential; delete the last credential on an account
     that still has a password (allowed) and the refusal shape on one that would strand.
   - Negative set: replayed assertion, expired ceremony session, unknown credential,
     disabled/banned account, counter regression (clone refusal).
   - The `webauthn_cleanup` job reaps expired ceremony sessions.
3. **Audit coverage**: for every flow above, the audit log carries the expected event with
   the account and resource named — read back through the audit-log RPC in the same
   session.
4. **Browser probe re-run** (Phase B instrument): the real Chrome and Safari enroll and
   sign-in against the release binary, so the E2E evidence includes a genuine
   authenticator. Findings route back to the user before any contract change.
5. **Cleanup in the same session**: the E2E accounts, credentials, ceremony sessions,
   reauthentication tokens, and audit rows the run created are deleted, and the server is
   stopped. The disposable database is reset or dropped — the execution rules cover it.
6. **Docs and collection**: `.llms/endpoint-reference.md`, `docs/api-endpoint.md`, and
   `.llms/architecture.md` (the identity/webauthn section) brought current; every new
   procedure has a Yaak request with `(unimplemented)` dropped; `config.schema.json`
   regenerated; superseded prose pruned.
7. **Front matter and handover**: this plan's `phases` entries stamped with status,
   commits, and notes as the work landed; a closing handover per the `handoff` skill.
8. **Report**: outcome, changed files, validation evidence, and the deferred list with the
   `TODO(passkey)` / `TODO(frontend)` markers collected in one place.

| Sign-in with unknown credential | the same refusal as any unknown login |
| Sign-in with counter regression | clone refusal, credential flagged in the audit entry |
| Disabled / banned account via passkey | the standard refusal shape |
| Bridge completion with passkey | bridge consumed once, session issued |
| Bridge completion with three wrong assertions | bridge dead |
| Reauthenticate with password / with passkey | token minted, hashed at rest |
| Guarded procedure with a valid token | consumed exactly once, handler ran |
| Guarded procedure with a spent or expired token | `unauthenticated` refusal |
| Two live tokens, both consumed independently | both work (no `UNIQUE(user_id, purpose)`) |
| One-time exchange, account with MFA | bridge minted, not a session |
| One-time exchange, account without MFA | session issued (today's behavior) |
| Ceremony session expiry | `unauthenticated`-shaped refusal, row reaped by cleanup |
| Delete last credential with no password set | refused (strand prevention) |

## Traps and risks

- **RP ID is load-bearing**: credentials are bound to the RP ID derived from
  `app.base_url`. Changing the deployment origin silently orphans every credential; the
  docs must say so, and the dev/prod gap (`localhost` vs the real host) is a data issue,
  not a bug to work around.
- **JSON codecs**: go-webauthn speaks `encoding/json` v1 internally. The ceremony documents
  are carried as opaque JSON, so tango's production `encoding/json/v2` never re-parses
  them — keep it that way; a typed re-marshal is where codec drift would bite.
- **Challenge uniqueness**: `webauthn_sessions.challenge` is `UNIQUE` across the table and
  single-use by consumption; the service deletes a spent session in the same transaction
  that acts on it, so a replayed challenge names no row.
- **BYTEA round trip**: `credential_id` and `public_key` are `BYTEA`; every read maps them
  through go-webauthn's byte slices — no stringly-typed copies.
- **ID conversion**: `jwtutils.Caller.UserID` is the wire form (`user_…`); convert with
  `user.UUIDFromWire` before any query, or the failure is a runtime 500.
- **The `mfaGate` seam stays**: the passkey verifier is defined in the consuming package
  and wired after construction; no import cycle back into `multifactor`.

## Out of scope, deliberately

- Phone/SMS delivery (the seam stays open; no column, no sender yet).
- Passkey-only accounts (no password) — contradicts the recovery anchor.
- Attestation verification beyond protocol parsing (`attestation_type` is stored, not
  policy-enforced; AAGUID is displayed, not trusted).
- LDAP, upstream's APIs entity — decided not planned.
