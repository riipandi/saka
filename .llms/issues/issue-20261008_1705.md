# Auth wiring — accepted risks and deferred findings

Findings from the frontend auth audit (2026-10-08). The fixable ones were fixed in the same
session (races: stale-verify resurrection, offline-≠-sign-out, RPC 401 retry; defects: profile
cookie crash, open-redirect backslash, query-cache leak; perf: main-thread token cache).
These are the ones that stay open by decision or need another surface.

- status: wontfix
  area: frontend/guard
  summary: The token pair and cached profile live in JS-readable cookies (`saka_token`,
    `saka_refresh`, `saka_user`, …). HttpOnly is impossible without the backend answering
    Set-Cookie, which the owner declined — the cookie copy is the chosen custody model.
  mitigation: The refresh token dies server-side on first rotation, so a stolen copy is
    replay-safe only until first use; `SameSite=Lax` + `Secure` on TLS.
  trigger: If the backend ever gains a Set-Cookie session mode, replace the cookie copy.

- status: wontfix
  area: frontend/guard
  summary: A tampered `saka_user` cookie renders a fake profile for one round trip until the
    background `GetSession` verify replaces it. Only matters under XSS, which already owns
    every JS-readable secret.
  trigger: If a hardening slice wants it, bind the profile cookie to a signature the worker
    can check — not before.

- status: considering
  area: frontend/guard
  summary: The engine (in the worker) and `api-client.ts` each build their own Connect
    transport — two fetch wrappers over the same origin. It is a consequence of the worker
    boundary, not drift: the worker cannot hold a main-thread transport instance.
  trigger: If the transport grows per-request logic that must not be duplicated, move the
    shared wrapper into a module both sides import.

- status: open
  area: backend/identity
  summary: The audit's scope was the frontend auth flow. The backend side — refresh-rotation
    queries, session-row indexes, the replay-revocation path's write pattern — was not
    audited. Owner asked about database structure/query performance; that is a separate pass.
  trigger: When the owner asks for the backend auth audit (`.llms/rules.md` plan flow).
