# Catalog drift leaves existing deployments with stale administrator grants

status: open
captured: 2026-10-11T22:05:00+07:00
updated: 2026-10-14T00:45:00+07:00

## Items

- Catalog additions (a new resource in `internal/authz/catalog.go`) reach an
  existing database only when a seeder runs: `migrate:seed` (development) or
  `initialize` (fresh installs). A deployment seeded before the addition
  keeps an administrator role whose `role_permissions` junction lacks the
  new slugs. The backend still answers — the guard judges `Rule: Admin`
  (role membership), not the slug set — but the access token's
  `permissions` claim is minted from `user.LoadGrants`, so the frontend
  permission gates (`<Can>`, sidebar entries) hide every surface the
  missing slugs protect. The user sees "some menus missing although I am
  admin"; nothing logs a warning.
  status: open
  trigger: any commit adding a resource/action to `internal/authz/catalog.go`;
  every existing local database and deployment must re-run `migrate:seed`
  (or the backend must self-heal — see the option below).
- Candidate remedies (not decided):
  1. Self-heal in the authorization seeder: report (or repair) the delta
     between the catalog's slug set and the administrator role's junction
     rows on every run — the seeder already reinserts junctions with
     `ON CONFLICT DO NOTHING`, so the repair is one extra report line; the
     real gap is that `serve` never invokes it.
  2. Have `serve` (or a startup check) verify the administrator junction
     count against the catalog and log a loud warning with the repair
     command when it lags.
  3. Document the "re-run `migrate:seed` after catalog changes" rule in
     `.llms/rules.md` and the release notes.
  status: open
  trigger: owner decision on the remedy shape.
