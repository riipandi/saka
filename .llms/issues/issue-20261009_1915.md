# Connect-go v2 migration — follow-ups the surface does not own today

Findings from the connect-go v1 → v2 migration (plan
`.llms/plans/plan-20261009_1826.md`, landed 2026-10-09, commits
`2a5fef28` P1 + `d489e62a` P2). None blocks the surface; each names the
trigger that reopens it.

- **status: open — `connectrpc.com/connect` v1 is still in `go.mod` as
  `buf`'s own indirect dependency.** Our code has zero v1 imports (the
  grep pass in P1 is the proof); the require line is what `go mod tidy`
  keeps while `buf.build/buf` links v1. Trigger: the next `buf` release
  that moves to connect v2 (or any dependency-graph cleanup) — re-run
  `go mod tidy` and the line drops. Nothing to do before that.
- **status: open — `validate` and `otelconnect` have no `/v2` modules
  yet; the v2 API rides their existing paths** (validate v0.9.0,
  otelconnect v0.12.0). When either tags a `/v2` module, adopt it in the
  same shape (the import path changes, nothing else). Trigger: a
  `go list -m -versions connectrpc.com/validate` run shows a v2 tag — or
  the next upgrade of either package.
- **status: open — the E2E harness boots one binary per invocation, and the
  two suites need different builds.** Release serves the SPA from the
  embedded manifest (`session-foundation` needs that); debug serves
  `/debug/passkey/*` (the ladder needs that) but the SPA document becomes
  the dev page proxying the Vite compiler at `127.0.0.1:5173` — with no
  `task dev` running, `session-foundation` hangs 30 s at "Loading"
  (502 on `/@vite/client`). The suites pass in their own tag
  (`session-foundation` 5/5 on release; ladder 3/3 on debug), so the wire
  contract is proven — one invocation just cannot prove both. The second
  trap: `reuseExistingServer: !CI` lets a lingering `saka serve` on :3000
  serve the suite with the wrong build. Trigger: the next "E2E hangs at
  Loading" or "passkey 404 envelope" report — check the tag and :3000
  first; a fix would boot the compiler for the debug run or embed assets
  in the debug binary.
- **status: wontfix (accepted D4) — an unknown method of a known service
  now answers in-protocol `unimplemented` (501) instead of v1's
  plain-text 404.** v2's `connecthttp.Mount` installs a per-service
  catch-all; a Connect client now reads a structured error where a
  browser once got bare text. Unknown *services* still fall to chi's
  NotFound and the in-protocol error writer. Recorded so a wire-diffing
  consumer does not read the 404→501 shift as a regression. Trigger:
  only if a client pins the old status.
- **status: open — v2 masks plain handler errors
  (`scrubHandlerError` → `unknown`, empty message; v1 published
  `err.Error()`).** The P2 audit found the surface already authors coded
  errors everywhere client text is intended, and
  `internal/transport/router.TestAPlainErrorIsMasked` pins the default.
  The open half is a convention, not a defect: any handler added later
  that wants a client-visible message must author a `*connect.Error` —
  a plain `return err` now silences it. Trigger: a bug report of a
  missing error message on the RPC surface (the first place to look is
  a bare `return err` in a handler/service tail).
