# Connect-go v2 migration — follow-ups the surface does not own today

Findings from the connect-go v1 → v2 migration (plan
`.llms/plans/plan-20261009_1826.md`, landed 2026-10-09, commits
`2a5fef28` P1 + `d489e62a` P2). None blocks the surface; each names the
trigger that reopens it. Re-verified 2026-10-14 against the tree.

- **status: open — `connectrpc.com/connect` v1 is still in `go.mod` as
  `buf`'s own indirect dependency.** Re-verified 2026-10-14: `go.mod:94`
  still carries `connectrpc.com/connect v1.21.0 // indirect` while the
  code imports only `/v2`. Our code has zero v1 imports (the grep pass in
  P1 is the proof); the require line is what `go mod tidy` keeps while
  `buf.build/buf` links v1. Trigger: the next `buf` release
  that moves to connect v2 (or any dependency-graph cleanup) — re-run
  `go mod tidy` and the line drops. Nothing to do before that.
- **status: open — `validate` and `otelconnect` have no `/v2` modules
  yet; the v2 API rides their existing paths.** Re-verified 2026-10-14:
  `go.mod:10–11` still pins `otelconnect v0.12.0` and `validate v0.9.0`.
  When either tags a `/v2` module, adopt it in the
  same shape (the import path changes, nothing else). Trigger: a
  `go list -m -versions connectrpc.com/validate` run shows a v2 tag — or
  the next upgrade of either package.
- **status: resolved — the E2E harness boots one binary per invocation, and the
  two suites need different builds.** Resolved 2026-10-14 (phase 5 of
  `.llms/plans/plan-20261014_0047.md`): the ladder's webServer is
  `boot-debug.mjs`, which boots the Vite compiler the debug build proxies
  (waiting for it to answer — its `/` is a 404 by design — then the
  binary) and the suite's server moved to the dedicated port `:4473`
  (`E2E_PORT` to override; :3000 stays the app server, :5173 the
  compiler); `reuseExistingServer` is now unconditionally false, so a
  lingering server can never serve the wrong build. The `E2E_BUILD_TAG`
  split stays: one invocation still proves one tag, but both invocations
  are self-sufficient and green in one pass (release 38 passed, ladder 3
  passed, 2026-10-14). Validation also surfaced and fixed two test-side
  defects: the consent-ledger expectation now reads protobuf JSON's
  omitted empty `entries` as the empty answer, and the MFA challenge
  test rides the `#mfa-challenge-form`-scoped OTP slots (the fork keeps
  the login form's textboxes alive for a beat, so an unscoped locator
  raced into the identity box). The harness's config also re-pins
  `app.assets_url` to its own port — the deployment's `PUBLIC_ASSETS_URL`
  pins :3000, and a picture URL pointing at a dead origin hides the
  avatar. Trigger: none — closed.
- **status: wontfix (accepted D4) — an unknown method of a known service
  now answers in-protocol `unimplemented` (501) instead of v1's
  plain-text 404.** v2's `connecthttp.Mount` installs a per-service
  catch-all; a Connect client now reads a structured error where a
  browser once got bare text. Unknown *services* still fall to chi's
  NotFound and the in-protocol error writer. Recorded so a wire-diffing
  consumer does not read the 404→501 shift as a regression. Trigger:
  only if a client pins the old status.
- **status: open — v2 masks plain handler errors
  (`scrubHandlerError` → `unknown`, empty message; v1 published
  `err.Error()`).** The P2 audit found the surface already authors coded
  errors everywhere client text is intended, and
  `internal/transport/router/rpc_test.go:310`
  (`TestAPlainErrorIsMasked`) pins the default.
  The open half is a convention, not a defect: any handler added later
  that wants a client-visible message must author a `*connect.Error` —
  a plain `return err` now silences it. Trigger: a bug report of a
  missing error message on the RPC surface (the first place to look is
  a bare `return err` in a handler/service tail). The convention's
  written record rides `.llms/rules.md` in
  `.llms/plans/plan-20261014_0047.md`'s closing phase.
