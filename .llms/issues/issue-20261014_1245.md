# The AUTH-cipher surfaces' rotation story beyond the command

## Background

Found while landing `key:rotate` (plan-20261014_0955): the plan's original
six-surface list assumed one cipher; the wiring shows two. Verified at the
composition wiring 2026-10-14:

- The **application cipher** (`NewCipherFromHex(APP_SECRET_KEY)`) seals the
  webhook signing secrets (`webhook/module.go:52-59`), the OAuth connection
  client secrets (`identity/module.go:622-632`), the SCIM provider tokens
  (`federation/module.go:161-167`), the sealed settings values
  (`appconfig/module.go:58-77`), and the queue payloads when
  `queue.encrypt` is on (`infrastructure.go:305`).
- The **auth cipher** (`NewAuthCipher(AUTH_SECRET_KEY)`) seals the TOTP
  enrollment secrets (`identity/module.go:458-462`) and the JWKS private
  documents (`identity/module.go:196-203`).

`key:rotate` (landed in plan-20261014_0955) re-seals both halves in one
pass — using it, nothing is lost. The gap is the manual path: hand-editing
`AUTH_SECRET_KEY` in the env file and restarting skips the re-seal, and
unlike the JWKS rows (which carry `seal_fp` and self-heal by retiring and
re-provisioning stale-seal pairs), `mfa_totp.secret` has no fingerprint
column and no recovery — every enrollment dies silently.

The stale comment this finding started from
(`multifactor/service.go:8`, "the one cipher the codebase has") was
corrected in the same pass.
