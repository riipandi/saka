# Session rows are never swept — the table grows without bound

- status: open
- plans: plan-20261014_0504.md (the session retention sweep, awaiting
  approval) · found by the backend auth audit,
  `.llms/audit/audit-20261014_0329.md`
- trigger: the next retention slice, or the first capacity report naming
  `public.sessions`

## Finding

`internal/jobs/cleanup_job.go` sweeps the queue's expired completed rows, the
multifactor enrollments and bridges, the webauthn tokens, the signup tokens,
and the device-login requests. The `public.sessions` table is absent from the
sweep, so ended and expired session rows accumulate forever.

The retention shape is deliberate — `ListSessions` keeps ended rows listed
("the stamp is the fact a holder reads, not something to hide") — but the
stamp a holder reads stops being interesting long before the row stops
existing. Every sign-in adds a row; every account's `ListSessions` count
grows with its lifetime history; the table grows with the fleet.

## Remedy shape

A retention sweep in the existing cleanup job: delete rows whose end is
older than a retention horizon — `revoked_at < now - retention` (and the
expired-but-never-stamped rows by `expires_at < now - retention`). The
horizon is a settings key the way the audit log's `audit_retention_days` is,
which makes the change a named surface (a config key + a job behavior + the
docs rows they owe), not a mechanical fix — hence the issue rather than a
drive-by.

The index work the sweep needs already exists: the expired arm rides
`(user_id, expires_at)`… the sweep's predicate is not user-scoped, so it
wants an `(expires_at)` / `(revoked_at)` index the way `idx_auth_tokens_expires_at`
serves its sweep. That rides the remedy, not this record.
