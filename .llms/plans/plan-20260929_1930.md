# OIDC industrialization plan: Tier 1–2 full, CIBA, inbound SCIM

## Objective

Carry Tango's federation surface from "parity with Pocket ID" to "meets the
industry standards an Okta/Entra-class deployment expects": close the Tier 1
gaps (JTI replay, token revocation, RFC 8414, logout propagation), complete
the Tier 2 surface the product actually wants (client credentials,
`offline_access`, session-management surface), deliver CIBA,
and make Tango a SCIM provisioning **target** for Okta/Entra. Runtime product
knobs move to the database-backed settings feature; the static JSON app
config keeps only what a restart legitimately owns.

**Explicitly out of scope:** fintech/open-banking profile work — DPoP, mTLS
token binding, JAR request objects (RFC 9101), and the FAPI 2.0 profile are
deferred until that market matters. **Future work (named, not planned):**
sign in with OAuth/social providers (Google, GitHub, custom OAuth) as an
identity surface.

## Execution rules

- The agent is **authorized to create atomic commits during this plan**. Commit
  each validated phase as it lands; stage explicit paths only, never push,
  never destructive Git commands.
- The agent is **authorized to reset the development database** during this
  plan: `task db:reset -- --force --up` followed by `task db:seed -- --force`.
  The reset applies to databases this plan's work created or owns — never to a
  database holding state the plan did not create. E2E artifacts (isolated
  databases, roles, disposable config/env files) are removed in the same
  session that created them.
- E2E of the OIDC/OAuth surface may use the **`oidc-test-tango`**
  container from `container/compose-dev.yaml` as the relying party: Tango runs
  on the host (dev `:3080` or the disposable E2E port), and the service's env
  carries the issuer (`TANGO_ISSUER`) and the client credentials
  (`TANGO_TEST_CLIENT_ID` / `TANGO_TEST_CLIENT_SECRET`) minted through
  Tango's admin RPC before the run, with the callback
  `http://localhost:9010/auth/callback` registered on that client — verify
  the callback path against the image at first use. Bring the container up
  only for the E2E session and take it down with the artifacts. The
  `ngauth-google` service in the same file stays pointed at itself — it
  belongs to the future social sign-in work; do not repoint it.
- Follow `AGENTS.md` and the federation sections of `.llms/architecture.md`.
  A phase that adds a schema, contract, grant, guard rule, or setting asks
  first when more than one option is viable — the decision points below name
  them with a recommended answer, and a phase pauses rather than silently
  choosing.
- **Settings vs app config:** a runtime product knob an operator may flip
  without a restart (a feature switch, a duration, a limit) becomes a
  `modules/appconfig` catalog setting — database-backed, hot-reloaded through
  the settings reads. A value that shapes process startup, security-critical
  keys, or transport (hosts, DSNs, secrets, cipher, JWKS sources) stays in
  the JSON app config. Every new setting key gets a catalog entry, a default,
  and audit coverage for free through the existing feature.
- **Frontend is out of scope for this plan.** Where a feature needs a screen
  or form, the phase delivers the backend + contract and marks the UI work
  `TODO(frontend)` in the endpoint reference and in that phase's notes.
- Reuse the established patterns: `protocolStore` pointer rows for protocol
  state, the `protocol_cleanup` job for sweeps, `guard.RestRules` for route
  classification, `pkg/testutils` containers for integration tests, Yaak for
  request documentation, and the `clarity` skill before prose edits.
- Each phase validates on its own (build, lint, focused suite, and container
  tests where state is touched) before it commits.

## Decision points (answer before the phase that owns them)

1. **Back-channel logout delivery** (phase 5) — *recommended:* queue-driven
   with bounded retries; a delivery the client does not acknowledge is
   logged, audited, and retried by the queue, never blocking end-session.
2. **Logout token scope** (phase 5) — *recommended:* end-session only for the
   first cut; extending to user-delete and admin session-kill is a follow-up.
3. **Per-client grant types** (phase 6) — *recommended:* add
   `allowed_grant_types` to the client record (migration), defaulting to the
   grants the client already uses, so client credentials and CIBA are opt-in
   per client rather than deployment-wide.
4. **Third-party initiated login** (phase 8) — *recommended:* implement the
   backend redirect now; `check_session_iframe` waits for the frontend
   (`TODO(frontend)`), because Tango's browser identity is the SPA's bearer
   session and an iframe session cookie is a design fork on its own.
5. **CIBA modes** (phase 9) — *recommended:* poll first; ping/push wait until
   a client actually needs them, since ping requires a client notification
   endpoint and a delivery contract.
6. **Inbound SCIM credentials** (phase 10) — *recommended:* one bearer token
   per inbound tenant row (hashed like every other secret), managed through
   an admin RPC surface; UI is `TODO(frontend)`.
7. **Inbound SCIM filtering** (phase 10) — *recommended:* `eq` filters on
   `userName` and `externalId` only — what Okta/Entra correlation actually
   sends — and a clear error for anything else.

## Phase 1 — JTI replay protection

1. Wire `provider.WithJTIConsumer` at the provider construction: the consumer
   claims one `jti` atomically (single-use state belongs in the statement's
   `WHERE`; zero rows affected means replay) against `public.oauth_jtis`,
   which migration 00004 already defines.
2. Store the JTI with its expiry as the token presents it; a replay within
   the lifetime is refused, an expired row is swept.
3. Extend the `protocol_cleanup` job (or add a bounded sweep alongside it) to
   reap expired `oauth_jtis` rows in batches.
4. Tests: first validation passes, an immediate replay is refused, an
   expired claim passes again, the sweep removes the rows; container-backed
   where the table is touched.
5. The startup warning `ConsumeJTIFunc is not configured` disappears.

## Phase 2 — Token revocation endpoint (RFC 7009)

1. Mount via `provider.WithTokenRevocation` at `/oidc/revoke`, client-scoped
   like introspection: a client may revoke only the tokens minted to it.
2. Declare the route in `internal/guard` (the credential bucket, matching
   `/oidc/token`), update the Yaak collection and the endpoint reference.
3. Tests: revoking an access/refresh token kills the grant-side rows the
   library touches; a foreign client's token is refused; the cascade matches
   what `RevokeMyAuthorizedClient` guarantees for the user-side path.

## Phase 3 — OAuth authorization-server metadata (RFC 8414)

1. Serve `GET /.well-known/oauth-authorization-server` alongside the
   existing discovery document: the library mounts only openid-configuration,
   so this handler is tango's — assembled from the same provider
   capabilities the OIDC metadata already names (grant types, scopes,
   endpoints, plus the revocation endpoint phase 2 delivered).
2. Both documents answer behind the `oidc.enabled` switch, 404 when off.
3. Tests assert the new document's fields against the live provider config;
   Yaak request + endpoint reference updated.

## Phase 4 — Settings groundwork and cleanup

1. Catalog the runtime knobs this plan introduces and the ones the config
   currently carries, moving what belongs in settings:
   - `oidc.end_session_revokes_consent` — migrate from app config to a
     setting (the config key is removed; a config value that still carries
     it is refused as an unknown key by the existing rules).
   - New keys this plan's phases need, declared by the phase that consumes
     them (client-credentials token duration, `offline_access` refresh
     duration, CIBA interval and lifetime, inbound SCIM switch, back-channel
     logout switch).
2. Decide the dead scaffolds: `oauth_jtis` becomes real in phase 1;
   `interaction_sessions` stays dead — record the decision (drop migration or
   documented keep) and execute it in phase 11's cleanup once every phase
   has landed and nothing claims the table.
3. Remove documentation that still describes shipped behavior as planned;
   verify the audit record and endpoint reference agree with the code.
4. Settings tests: a moved key answers its catalog default, an override
   hot-reloads without a restart, and the audit trail records the change.

## Phase 5 — Back-channel logout

1. Migration: `oidc_clients.backchannel_logout_uri` (nullable text, validated
   as an absolute URL) and `backchannel_logout_session_required` (boolean,
   default false). Both ride the existing client update contract with
   `buf.validate.field` constraints.
2. On a successful end-session for a client with a URI: mint a logout token —
   signed by the provider's signing keys, `events` carrying the
   back-channel-logout member, `aud` the client, `sub` the account, `sid`
   the ended session, no `nonce` — and deliver it by queue as a form POST
   (`logout_token=...`, `Content-Type: application/x-www-form-urlencoded`),
   expecting a 200.
3. Delivery is queue-driven with bounded retries (decision point 1); a
   failure logs, audits, and never blocks the end-session response.
4. Guard: the delivery is outbound — no route. Settings: a deployment-wide
   switch gates the whole feature (off by default).
5. Tests: token shape and signature, delivery form, retry on 5xx, the
   switch-off path; the client contract carries the new fields end to end.
6. `TODO(frontend)`: the client form needs fields for the URI and the
   session-required flag; the Yaak request documents them now.

## Phase 6 — Client credentials grant

1. Migration + contract: `allowed_grant_types` on the client record
   (decision point 3), seeded to the grants in use; the create/update
   procedures validate against the grant catalogue.
2. Enable `provider.WithClientCredentialsGrant`; the token endpoint answers
   `grant_type=client_credentials` for clients whose record allows it; the
   access token carries the client as subject, the client's configured
   scopes, and no user claims.
3. Duration is a setting (`oidc.client_credentials_token_minutes`, default
   60); guard reuses the client-authenticated token route.
4. Tests: allowed client mints a client-scoped token, a client without the
   grant type is refused, the token introspects back with the client as
   subject; the group-restriction rules do not apply (no account).
5. Yaak + endpoint reference; `TODO(frontend)`: grant-type editor in the
   client form.

## Phase 7 — The offline_access scope

1. Add `offline_access` to the scope catalogue and the consent surface's
   catalogue answer; a grant carrying it receives a refresh token with the
   long duration a setting defines
   (`oidc.offline_refresh_token_hours`, default 720) instead of the standard
   one.
2. Consent semantics follow OIDC: `offline_access` is only meaningful for
   the authorization code grant and is consent-gated — the SPA's consent
   question must name it distinctly.
3. Tests: a grant without the scope carries the standard refresh lifetime;
   with the scope, the long one; refresh rotation preserves it.
4. `TODO(frontend)`: the consent screen renders `offline_access` distinctly
   (persistent access wording).
5. Yaak + endpoint reference.

## Phase 8 — Session-management surface and third-party initiated login

1. **Third-party initiated login:** `GET /oidc/authorize` already accepts
   the standard parameters — add the documented entry point where an
   external page links to Tango with `client_id` (+ optional
   `login_hint`, `scope`), landing the browser in the existing
   authorize/interaction flow. This is mostly a documented contract over the
   shipped flow plus the request parameters the library already accepts;
   verify and pin with tests rather than building machinery.
2. **`check_session_iframe` + session management:** backend route and
   metadata fields are deferred behind `TODO(frontend)` — the SPA owns the
   browser session, and the iframe's postMessage session polling needs the
   frontend's session cookie story decided first. Record the fork in the
   endpoint reference so it is a decision someone makes, not an accident.
3. Tests cover the initiated-login entry point; docs name what is live and
   what waits.

## Phase 9 — CIBA (deferred — optional future work)

Deferred until a decoupled-authentication consumer exists: a
mobile-approval flow, a kiosk or call-center trigger, or a relying
party that needs to start a sign-in without a browser. The design
below stands; the poll mode (decision point 5) is the first slice
when it is picked up.

1. Storage: a `ciba` kind of `protocolStore` row (the pointer/document
   pattern the other nine kinds use) backs the `goidc.CIBAManager` — no new
   table, the expiry column drives the sweep.
2. Mount `provider.WithCIBAGrant` at `/oidc/bc-authorize` (poll mode,
   decision point 5), with `login_hint` (username or email) and
   `id_token_hint` both resolving the account.
3. The authentication walk rides the SPA: the pending CIBA session surfaces
   the approval question the way the device flow's verification does —
   the SPA notification/approval path is `TODO(frontend)` for its screen,
   while the backend exposes the session state the SPA needs.
4. Settings: `ciba.polling_interval_seconds` (default 5),
   `ciba.session_lifetime_minutes` (default 10), and a feature switch;
   `interval` in the token response honors the setting.
5. Guard: `/oidc/bc-authorize` is client-authenticated (the credential
   bucket); the poll is the token endpoint.
6. Tests: container-backed — auth request mints a pending session, approval
   completes it, the poll returns tokens, an unapproved poll answers
   `authorization_pending`, expiry answers `expired_token`, a wrong
   `login_hint` fails closed.
7. Yaak + endpoint reference + architecture notes.

## Phase 10 — Inbound SCIM server (deferred — optional future work)

Deferred until a provisioning source exists: a tenant that syncs users
from Okta or Entra ID, or the planned Google Workspace integration —
that Workspace plan is the named trigger. The design below stands;
revisit the decision points (6: one bearer per tenant, 7: `eq` filters
on userName/externalId) when it is picked up.

1. Migration: `scim_inbound_tenants` — display name, bearer token hash,
   active flag, timestamps. Tokens are hashed like every other secret;
   the raw value is shown once at creation.
2. Mount `/scim/v2` REST: `/ServiceProviderConfig`, `/Schemas`,
   `/Users`, `/Groups`, with the authn decision point 6 (one bearer per
   tenant, credential bucket rate limit). Guard classifies the tree
   explicitly; an undeclared path answers `not_found`.
3. Implement the resource surface against the identity area through the
   cross-feature interface pattern (the consuming package declares the
   interface; the area wires it): create/replace/delete users and groups,
   list with pagination (Okta/Entra send `startIndex`/`count`) and the
   `eq` filters of decision point 7.
4. Resource shapes follow RFC 7644/7643 for the attributes Okta/Entra
   synchronize (`userName`, `name`, `emails`, `active`, `externalId`,
   `groups` membership), mapping onto Tango's account fields; the group
   membership mapping respects the existing account/group model.
5. Settings: the feature switch (off by default) and nothing else —
   credentials are rows, not settings.
6. Tests: full CRUD round trip per resource, pagination correctness,
   filter behavior, auth refusal for a bad bearer, the switch-off 404;
   an Okta-shaped probe script proves the happy path the way Okta would
   drive it.
7. RPC admin surface for tenant/token lifecycle with audit events;
   `TODO(frontend)`: the admin screens.
8. Yaak + endpoint reference + architecture notes.
