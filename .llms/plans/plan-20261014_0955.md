# Land `key:rotate` — one command re-seals every surface the application secret encrypts

## Objective

`cmd/appkey.go:177` prints `not yet implemented` — the one open residue of
the 2026-10-14 reconciliation of the archived `partial` handovers
(issue-20261014_0949). This plan lands the command: rotate the application
and auth secrets, re-seal every row and payload sealed under the old ones,
write the new keys to the deployment's env file, and report what moved. No
schema changes — the sealed format (`enc:`-prefixed AES-GCM,
`pkg/crypto/encryption.go`) stays as it is.

**Amended 2026-10-14, phase 1 (owner pick "six"):** the plan originally
scoped the rotation to `APP_SECRET_KEY` alone; the wiring verification
showed two of the six surfaces seal under the **auth cipher**
(`AUTH_SECRET_KEY`) — the TOTP secrets and the JWKS private documents —
so D1 expanded: the command rotates **both secrets in one pass**, each
half re-sealing the rows its own cipher seals.

## Current state (verified in the tree, 2026-10-14)

- **The command exists as a stub.** `keyRotateCmd` (`cmd/appkey.go`)
  prints and returns; `key:generate` beside it carries the full UX the
  rotation should mirror (env-file creation, confirmation before
  overwrite, `--overwrite` to skip the prompt).
- **Two secrets, two ciphers, no key ids.** The application cipher
  (`crypto.NewCipherFromHex(c.App.SecretKey)`) and the auth cipher
  (`crypto.NewAuthCipher(c.Auth.SecretKey)` — the AES key derived from
  the HMAC secret) both live in `internal/registry`'s wiring; the sealed
  wire format carries no key version — a row decrypts or it does not.
  Rotation is therefore decrypt-with-old, encrypt-with-new, all at once,
  per cipher half.
- **Six surfaces hold sealed material** (the cipher named per line — the
  two auth-cipher lines are the phase-1 amendment):
  1. webhook endpoint signing secrets — `modules/webhook/service.go:857`
     (`secret_enc`, migration 00010, CHECK-constrained to `enc:%`) —
     application cipher;
  2. OAuth SSO upstream client secrets — `modules/identity/oauthsso/service.go:455`
     (the federation tables' sealed secrets, migration 00015) —
     application cipher;
  3. SCIM directory bearer tokens — `modules/federation/scimsync/service.go:160`
     (migration 00013's CHECK `token LIKE 'enc:%'`) — application cipher;
  4. TOTP enrollment secrets — `modules/identity/multifactor/service.go:316`
     (the factor's `secret` column) — **auth cipher**;
  5. the JWKS private documents — `modules/identity/jwks/service.go:148`
     (migration 00012) — **auth cipher**;
  6. appconfig's sealed setting values — `modules/appconfig/settings.go:961`
     (`def.Sealed`) — application cipher.
- **Queue payloads are optionally sealed at rest** (`queue.encrypt`,
  `internal/config/types.go:561`): every task payload carries
  `crypto.EncPrefix` and the archive keeps the sealed form
  (`framework/queue/client.go:65-68`) — rotation must keep the two
  consistent or a replayed task fails to open.
- **`AUTH_SECRET_KEY` is not a cipher key.** It is the HMAC/JWT signing
  secret; its rotation invalidates signed artifacts rather than sealing
  new ones, and the JWT key pair already rotates in the database
  (`jwks:generate`). Out of this plan's scope.

## Decisions

- **D1 (2026-10-14, amended phase 1): the command rotates both secrets.**
  The original scope — `APP_SECRET_KEY` only — came from the assumption
  that one cipher seals everything; the wiring shows the TOTP secrets and
  the JWKS private documents seal under the auth cipher, and the owner
  picked the full surface ("six"). The command loads both secrets, builds
  both old ciphers, and re-seals each surface with the pair its cipher
  names. Rejected: keeping the app-secret-only scope (the command would
  have reported success while the auth-cipher rows stayed sealed under
  the old secret — a half rotation wearing a full name).
  The AUTH half's amendment rides this plan; the manual-path gap (an
  env-file edit that skips the re-seal kills every TOTP enrollment, with
  no `seal_fp` recovery like the jwks rows have) is parked in
  `issue-20261014_1245.md`. Rejected: a `--signing` mode — a second
  mechanism (sign-out enforcement) wearing a rotation name.
- **D2 (2026-10-14): hybrid key supply, mirroring `key:generate`'s UX.**
  The old keys come from the loaded configuration (the env file the
  deployment already runs, loaded through the root `--env-file` flag),
  the new keys are generated by the command and written back to that
  same env file with the same confirm/`--overwrite` dance — unless
  `--new-key` / `--new-auth-key` pass explicit values for scripted runs.
  A `--dry-run` counts the sealed rows and verifies the old keys decrypt
  them without writing. (The command declares no `--env-file` of its
  own: a subcommand's flag shadows the root's, and the root's is what
  loads the configuration — one flag serves both the read and the
  write.) Rejected: passing the old keys as flags (they would sit in
  shell history — the secret-handling rule says a secret is listed in
  `secretKeys` and never printed); requiring both keys from the
  environment (breaks the interactive flow the other key commands
  set).
- **D3 (2026-10-14): queue payloads re-seal in the same pass.** When
  `queue.encrypt` is on, the rotation walks the queue's payload column
  and its archive and re-seals them with the new cipher, keeping the
  live and archived forms consistent. Rejected: a drained-queue
  requirement (an operational dance the operator will skip, with the
  failure mode — a replay that cannot open — discovered weeks later) and
  skipping the queue with a documented warning (`queue.encrypt`
  deployments would need a second rotation forever).
- **D4 (2026-10-14): all-or-nothing, abort on the first decrypt
  failure.** Every surface re-seals inside one transaction; a row that
  fails to open under the old key aborts the rotation with the row
  named — a wrong key or an already-rotated row is the operator's
  information, not a partial state. The `--dry-run` exists so the counts
  and the key check precede any write. Rejected: per-row best-effort
  (a half-rotated tree, unreadable by either key on rollback) and
  skip-and-report (the skipped row is unreachable data the operator must
  find again).

## Shape and enforcement points

| Surface | Where it seals today | Cipher | What rotation does |
| --- | --- | --- | --- |
| Webhook endpoint secrets | `modules/webhook/service.go:857`, `secret_enc` (00010) | application | decrypt → re-seal, in the pass |
| OAuth SSO client secrets | `modules/identity/oauthsso/service.go:455` | application (`identity/module.go:622`) | decrypt → re-seal, in the pass |
| SCIM directory tokens | `modules/federation/scimsync/service.go:160` | application (`federation/module.go:161`) | decrypt → re-seal, in the pass |
| TOTP enrollment secrets | `modules/identity/multifactor/service.go:316` | **auth** (`identity/module.go:458`) | decrypt → re-seal, in the pass |
| JWKS private documents | `modules/identity/jwks/service.go:148` | **auth** (`identity/module.go:196`) | decrypt → re-seal, `seal_fp` re-stamped, in the pass |
| Sealed appconfig values | `modules/appconfig/settings.go:961` | application (`appconfig/module.go:58`) | decrypt → re-seal, in the pass |
| Queue payloads + archive | `framework/queue/client.go:65-68`, behind `queue.encrypt` | application | phase 2: re-seal both, same pass |
| The env file | the root `--env-file` flag (`cmd/keyrotate.go`) | — | phase 1: write the new keys, confirm/`--overwrite` |

The engine is a `pkg/crypto` helper (`ReSeal(old, new *Cipher, sealed)`)
plus a small row-walker per surface — no module gains a dependency on the
command; the command owns the walk. The sealed modules are untouched:
their seal/decrypt paths keep working, only the key underneath changes.

## Explicitly out of scope

- **`AUTH_SECRET_KEY`** — D1: no sealed data migrates; mass invalidation
  is the deployment's own procedure.
- **A key-id / key-version column** — the sealed format stays
  versionless; the rotation is all-at-once (D4), so versioning buys
  nothing this plan needs.
- **JWT key-pair rotation** — already lives in the database
  (`jwks:generate`), a different mechanism.
- **`modules/**` seal paths** — untouched; only the key under them
  changes.
