# Plan — Wave 5: platform administration

## Objective

Deliver the complete Wave 5 surfaces defined in [.llms/integration-roadmap.md](file:///Users/ariss/Developer/github.com/riipandi/saka/.llms/integration-roadmap.md) (read 2026-10-11):

1. **Platform settings & configuration** — Database-backed application settings (`SettingsService/List`, `Update`, `Reset`), mailer health verification (`AppConfigService/TestEmail`), and administrator view of the deployment document (`GET /api/configuration`). Handle sealed items with clear `enc:` visual masking and confirmation.
2. **Notification administration & live streaming probe** — Admin announcement publishing (`NotificationService/CreateNotification`, `GetNotification`, `ListAllNotifications`, `CancelNotification`). Formally validate the armed D4 server-streaming clause by exercising `NotificationService/WatchNotifications` over ConnectRPC and `authFetch` / `rpcTransport` in the webapp environment.
3. **User notification inbox & notification center** — Authenticated caller's inbox (`ListNotifications`, `MarkNotificationRead`, `MarkAllNotificationsRead`, `UnreadCount`), live stream consumer via `WatchNotifications` updating the unread bell indicator and triggering toasts, with proper reconnect and `ListNotifications` catch-up semantics.
4. **Outbound webhooks administration** — Complete ten-procedure administrative surface (`WebhookService/List`, `Create`, `Get`, `Update`, `Delete`, `RotateSecret`, `Test`, `ListDeliveries`, `ListAllDeliveries`, `ListEventTypes`). Reuse the show-once secret modal pattern (`components/dialogs/-show-once-secret-dialog.tsx`) for creation and rotation; show delivery logs with redacted response metadata and retry history.
5. **API keys lifecycle** — Account self-service personal access tokens (`ApiKeyService/CreateAPIKey`, `ListAPIKeys`, `RenewAPIKey`, `RevokeAPIKey`) under `/account/api-keys`, and administrator system-wide overview (`ApiKeyService/ListAllAPIKeys`) under `/admin/api-keys`. Raw tokens presented via show-once dialog upon creation and renewal.
6. **Final validation, docs sync, and handover** — Run full validation suite (`task check:all`, `task build`, composition probe over local runner), synchronize roadmap, endpoint reference, architecture records, Yaak workspace, and produce handover documentation.

The backend already serves every procedure this wave integrates — no backend schema `ALTER` needed. In-place migration editing and development database reset are authorized if any schema alignment is required.

The references for screen semantics, UX, and copy are **.llms/auth-design.md** (settings taxonomy, authentication policies, session lifetimes, security rules, NIST 800-63B posture), **Pocket ID** (audit vocabulary and UI inspiration), and **Saka's own records** (`.llms/endpoint-reference.md`, `internal/authz/catalog.go`, `modules/appconfig/settings.go`).

## Decisions

### D1: Route layout for Wave 5 platform surfaces
- **Decision**:
  - Admin routes under `routes/(app)/admin/`:
    - `/admin/settings.tsx` over `-settings-view.tsx` (product settings catalog overrides + configuration viewer + TestEmail modal).
    - `/admin/notifications.tsx` over `-notifications-view.tsx` and `-notification-dialog.tsx` (announcement broadcasting and administrative list).
    - `/admin/webhooks/index.tsx` over `-webhooks-view.tsx` (endpoints table + create dialog).
    - `/admin/webhooks/$id.tsx` over `-webhook-detail-view.tsx` (endpoint config, rotate secret, test delivery, and delivery attempts table).
    - `/admin/api-keys.tsx` over `-api-keys-view.tsx` (system-wide active and revoked API keys audit).
  - Account routes under `routes/(app)/account/`:
    - `/account/notifications.tsx` over `-notifications-view.tsx` (user inbox with category tabs, read/unread filters, mark all read).
    - `/account/api-keys.tsx` over `-api-keys-view.tsx` (self-service token list, create modal, renew/revoke actions).
  - Global header / shell:
    - Mount unread notifications popover trigger in the app layout header / top navbar beside user menu.
- **Rationale**: Cleanly mirrors existing route organization in `(app)/admin/` and `(app)/account/` with TanStack Router code splitting (`-`-prefixed view files).
- **Alternatives rejected**: Creating a single multi-tab catch-all admin route (bloats file size and degrades navigation routing).

### D2: Streaming consumer validation & D4 fallback clause settlement
- **Decision**: Validate `WatchNotifications` server-streaming with `createConnectTransport` over `authFetch`. Connect-web uses the standard Web Streams API (`ReadableStream`). `authFetch` passes through the underlying `fetch` `Response` object.
  - Phase 2 conducts an explicit wire probe in the webapp environment to verify that chunks stream smoothly without being buffered by `ofetch.raw` or middleware.
  - If `ofetch` buffers the stream (the D4 fallback clause), isolate streaming calls to use native `fetch` with authorization header injection specifically for the streaming client while keeping `ofetch` for unary calls.
  - Keep reconnect logic resilient: exponential backoff with jitter on disconnect, automatic refetch of unread count and active inbox upon reconnect (since `WatchNotifications` has no cursor/replay history).
- **Rationale**: Directly honors the recorded D4 architecture contract in `integration-roadmap.md` and `plan-20261009_0025.md`.

### D3: Settings presentation structured by auth-design.md taxonomy
- **Decision**: The settings UI (`/admin/settings`) groups catalog items into tabbed/sectioned categories mirroring [.llms/auth-design.md](file:///Users/ariss/Developer/github.com/riipandi/saka/.llms/auth-design.md):
  1. **User & Authentication**:
     - *Email*: `auth.signup_email_enabled`, `auth.require_email`, `auth.verify_email_at_signup`, `auth.signin_email_enabled`, `auth.signin_email_code_enabled`.
     - *Username*: `auth.signup_username_enabled`, `auth.require_username`.
     - *Password & NIST 800-63B*: `auth.signup_password_enabled`, `password.min_length` (default: 8), `password.reject_compromised` (HaveIBeenPwned breach corpus), complex character rules (`password.rule_lowercase`, `password.rule_uppercase`, `password.rule_number`, `password.rule_special`).
     - *Passkeys & WebAuthn*: `webauthn.allow_synced_passkeys`, `webauthn.user_verification` (required / preferred / discouraged), `passkey.max_credentials`.
     - *User Model Self-Service*: `users.self_delete_enabled`, `users.change_email_enabled`, `users.change_username_enabled`.
  2. **Access Mode & Sign-up Rules**:
     - `access.mode` (open vs invite-only token required).
     - `access.allowlist_enabled` & `access.allowlist` (comma/newline separated accepted addresses or `@domain`).
     - `access.blocklist_enabled` & `access.blocklist_applies_to_signins`.
     - `access.block_email_subaddresses` (blocking `+tag` variants when base address is already registered).
  3. **Multi-Factor (MFA)**:
     - `mfa.required` (enforces second-factor setup upon sign-in/sign-up).
     - `mfa.max_enrollments` (caps total active TOTP + passkey second factors).
  4. **Sessions**:
     - `session.lifetime` (standard unremembered session window).
     - `session.max_lifetime` (maximum lifetime for remembered sessions, between 5 minutes and 10 years).
     - `session.inactivity_timeout` (idle session expiration).
     - `session.reverification_window` (step-up validity window, default 30 minutes).
  5. **Advanced Rules & Protection**:
     - *Lockout Policy*: `lockout.enabled`, `lockout.max_attempts` (default 100, floor 5), `lockout.duration` (indefinite vs time limit, e.g. `1h`).
     - *User Enumeration Protection*: `auth.user_enumeration_protection` (`bulk` rate-limited honest vs `strict` decoy responses).
  6. **Federation & OIDC**:
     - `oidc.end_session_revokes_consent`, `oidc.backchannel_logout_enabled`, `oidc.refresh_token_hours`, `oidc.offline_refresh_token_hours`, `oauth.account_linking_enabled`.
  7. **Deployment & Mailer Test**:
     - Admin view of immutable runtime configuration (`GET /api/configuration`) with redacted secrets, plus the synchronous `TestEmail` action.
- **Form Controls & Behavior**:
  - Boolean settings render as clean Switches.
  - Duration/number settings render with clear units (seconds, hours, days, characters) and bounds validation.
  - Sealed items (`sealed: true`) are masked with clear encryption indicators (`enc:…`).
  - "Reset to default" button invokes `SettingsService/Reset` with confirmation, reverting to catalog default.
- **Rationale**: Replaces ad-hoc string tables with an authoritative, product-aligned administration console following the exact specification of `auth-design.md`.
- **Alternatives rejected**: A flat alphabetical table of 30+ raw keys with no category context.

### D4: Webhook signing secret presentation and rotation
- **Decision**: Use `ShowOnceSecretDialog` when registering a new webhook endpoint (`WebhookService/Create`) and when rotating an existing signing secret (`WebhookService/RotateSecret`).
  - Signing secret is displayed in plaintext with copy button and warning that it cannot be retrieved again.
  - Rotation confirmation dialog explicitly informs that older deliveries in-flight will still be verified by prior signatures, but new deliveries immediately use the new secret.
- **Rationale**: Eliminates security risks while providing a cohesive UX matching OIDC client secrets and SCIM tokens.

### D5: API keys lifecycle and machine credential guards
- **Decision**:
  - Creation modal asks for `name` and optional expiration window (`expires_in_days` or timestamp).
  - Shows raw key `<prefix>.<secret>` once via `ShowOnceSecretDialog`.
  - Self-service table lists user's keys with status badges (Active, Expired, Revoked).
  - Renewal button enabled only for expired keys (as unexpired keys are rejected with `failed_precondition` per proto).
  - Revocation is soft with confirmation dialog.
  - Admin view `/admin/api-keys` displays owner username/email alongside the key metadata, with filtering by status.
- **Rationale**: Completely enforces the invariants defined in `api_key.proto` and `endpoint-reference.md`.
