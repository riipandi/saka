## Decisions

### D1: Route layout and placement for Federation Admin
- **Decision**: Admin federation surfaces live under `routes/(app)/admin/`:
  - `/admin/oidc-clients/index.tsx` (list), `/admin/oidc-clients/new.tsx` (create), `/admin/oidc-clients/$id.tsx` (detail, secrets, allowed groups, SCIM, preview).
  - `/admin/oauth-providers.tsx` (OAuth SSO admin connections table & modal configuration).
  - `/admin/claims.tsx` (Custom claims table for user and group claims).
  - `/admin/consents.tsx` (Admin authorized clients audit ledger).
- **Rationale**: Keeps clear separation of federation sub-domains matching `federation.proto` and `authn.proto`, following TanStack Router dash-file code splitting (`-oidc-clients-view.tsx`, `-oauth-providers-view.tsx`, etc.).
- **Alternatives rejected**: Bundling all federation features into a single gigantic settings view (unmanageable file size and violates TanStack code splitting).

### D2: Account-side linked connections and authorized applications
- **Decision**: Place self-service federation surfaces under `routes/(app)/account/`:
  - `/account/connections.tsx` over `-connections-view.tsx` for linked OAuth providers (`ListLinkedConnections`, unlinking with step-up confirmation, token drawer via `GetLinkedAccountTokens`).
  - `/account/authorized-apps.tsx` over `-authorized-apps-view.tsx` for authorized OIDC apps (`ListMyAuthorizedClients`, `RevokeMyAuthorizedClient`).
- **Rationale**: Follows the existing account layout (`/account/sessions`, `/account/security`, `/account/email`, `/account/audit`).
- **Alternatives rejected**: Cramming linked connections into `/account/security` (security is already heavily packed with password, MFA, passkeys, and recovery codes).

### D3: Show-once secret dialog pattern
- **Decision**: Create a shared show-once credential presentation modal (`components/dialogs/-show-once-secret-dialog.tsx`) that renders the minted secret or raw token with a copy-to-clipboard button, a warning that it will never be displayed again, and an explicit acknowledgement button to dismiss.
- **Rationale**: Satisfies the shared machinery requirement for Wave 4 (OIDC client secrets, SCIM tokens), and will be reused by Wave 5 (API keys, webhooks).
- **Alternatives rejected**: Displaying secrets inline in table rows or notifications (security hazard and easily missed on rerender).

### D4: Logo upload mechanism
- **Decision**: Use `OidcClientService/UploadLogo` ConnectRPC procedure with base64/bytes payload or REST seam upload matching the proto specification `UploadOidcClientLogoRequest` (`bytes logo = 2`).
- **Rationale**: `UploadLogo` is an existing Connect RPC on `OidcClientService`.
