# Wave 1 — the account works on real data

## Objective

Land `.llms/integration-roadmap.md` Wave 1 (the four checklist items: profile &
preferences, the session center, email verification & change, the account's own audit
trail) and the shared machinery it carries: the pagination hook, the Connect-code
error mapping, and the public-settings read the danger zone and email-change gates
need. The wave ends with the settings page free of its DummyJSON demo stub and the
account navigating real pages — the self-service slice the admin console will later
link back to.

## Current state

Verified in the tree 2026-10-10:

- **The wire is ready; nothing is consumed yet.** `UserService/GetCurrentUser` and
  `UpdateCurrentUser` are done (`api/connect/identity.proto:894`, `:913`;
  `UpdateCurrentUserRequest` carries `first_name`/`last_name`/`display_name` with
  `buf.validate` bounds, `locale` (empty clears), `timezone` (IANA, empty resets to
  UTC, 64 chars), and `username` (3–32 ASCII, case-insensitive unique, absent keeps —
  the service judges the toggle); `identity.proto:913–947`). The response carries the
  updated `User` (`identity.proto:985–987`), and `User` carries `email_verified`
  (`identity.proto:409`) and the preferences block (`locale`, `timezone`;
  `identity.proto:424–455`). `DeleteMyAccount` takes nothing and answers
  status+message (`identity.proto:949–956`).
- **The picture routes ride `/me`.** `PUT/DELETE /api/users/me/profile-picture` are
  `Authenticated` and need no identifier; `/api/users/{id}/profile-picture` is
  `Self("id")` (`internal/guard/rules.go:514–526`). The public read is
  `GET /api/users/{id}/profile-picture.png` (`rules.go:504`) — redirecting to the
  bundled default when the account has none. Upload: magic-byte sniff PNG/JPEG/WebP,
  2 MiB cap; the endpoint reference lists only the `{id}` forms — the `/me` rows are a
  docs-sync item.
- **The session surface is complete on the wire.** `ListSessions` carries `page`/
  `limit` and answers `Session` views (id `sess_…`, `provider`, `remember`,
  `user_agent`, `ip_address`, timestamps) newest-first, ended included, paginated by
  `saka.common.v1.ListMetadata` (`api/connect/authn.proto:464–489`); `RevokeSession`
  takes the TypeID (`:492–495`); `SignOutOtherSessions`/`SignOutAllSessions` answer
  `revoked_count` (`:511–541`). The engine already owns `GetSession`/`SignOut` and the
  `unauthenticated`-on-ended-session restore signal
  (`packages/webapp/src/libraries/guard/auth-engine.ts:104`, `:343`).
- **The email flows are code-entry, not link flows.** The verification email renders
  `verificationCode` and the change request renders `confirmCode` — the templates
  carry codes, no URL
  (`packages/email/templates/email-verification.tsx`,
  `email-change-request.tsx:11`). `VerifyEmail` and `ConfirmEmailChange` take the raw
  `token` (`api/connect/identity.proto:276–280`, `:313–317`); both are guard-`Public`
  (`internal/guard/rules.go:81`) and consume-on-success. `RequestEmailChange` takes
  `new_email` and refuses a taken address there (`identity.proto:293–299`).
  `SendEmail` refuses an already-verified account (`identity.proto:224–232`).
  `ConfirmEmailChange` is shipped but absent from the endpoint reference
  (`issue-20261010_0017.md` ISS-001).
- **The account's own audit list paginates.** `AuditLogService/List` is
  guard-`Authenticated` (an impersonated caller is refused), takes `page`/`limit` and
  a `sort_by` whitelist (`event`, `username`, `ip_address`, `created_at`) with
  `sort_order` asc/desc (`api/connect/auditlog.proto:138–166`), and answers the
  `AuditLog` view — event, trigger type, action status, ip, user agent, device
  fingerprint, country/city, actor fields, payload map (`auditlog.proto:59–136`).
  `ListMetadata` carries page/limit/total_pages/total_items/first_item_index as
  optionals (`api/connect/common.proto:18–32`).
- **The gates are settings, and none of the three the account pages need is public.**
  `users.self_delete_enabled` (default false), `users.change_email_enabled` (default
  true), `users.change_username_enabled` (default true) are catalog entries without
  `Public: true` (`modules/appconfig/settings.go:472–484`), so
  `SettingsService/ListPublic` — the anonymous surface — does not answer them. The
  self-delete refusal is `not_found`-shaped while off
  (`modules/identity/user/service.go:254` names the key; the override column
  `users.self_delete_override` turns the decision either way,
  `modules/identity/user/schema.go:54`).
- **The settings page is the demo stub.** `routes/(app)/settings.tsx` renders the
  DummyJSON warning ("Authentication runs against the DummyJSON demo API"), a
  read-only profile card fed from the guard's profile, a theme card, and a sign-out
  danger row — 144 lines, zero RPC calls. The guard's store carries the profile
  (`UserProfile` flattened from the sign-in's `AuthenticatedUser`); nothing in the
  tree calls `GetCurrentUser`/`UpdateCurrentUser` today.
- **The shell carries template residue.** The sidebar logo reads "ReactiVite" with

  Messages; `routes/(app)/-sidebar.tsx:12–24`); the landing hero says "Vite React

- **The machinery does not exist yet.** No pagination hook (grep for `ListMetadata`
  in `packages/webapp/src` is empty); `guard/auth-utils.ts` exports
  `getErrorMessage`/`safeReturnTo` only (lines 9, 28) with no Connect-code mapping.

## Decisions

- **D1 (2026-10-10, owner direction to prepare) — the three user toggles become
  public settings.** `users.self_delete_enabled`, `users.change_email_enabled`, and
  `users.change_username_enabled` gain `Public: true` in the catalog
  (`modules/appconfig/settings.go`), joining the nine public items the catalog test
  pins. Code-only: the catalog is code, `public.app_settings` stores overrides alone,
  and no migration or guard change is involved. Rejected: keeping them non-public
  (the account pages cannot gate their own actions and would ship buttons that
  always fail — self-delete defaults to false); rendering the actions ungated and
  surfacing the server's `not_found` (honest but hostile UX for the default
  deployment); adding a new RPC to expose them (a round trip for facts a public
  listing already carries).
- **D2 (2026-10-10) — profile updates patch the store from the response; no forced
  token refresh.** A successful `UpdateCurrentUser` writes the answered `User` into
  the guard's profile store and invalidates the `GetCurrentUser` query. The access
  token's `display_name` claim stays stale until the next mint — cosmetic: the
  backend writes its records from the account row, not the claims, and the refresh
  re-reads the account at renewal anyway. Rejected: forcing a silent refresh after
  every save (an extra round trip per edit to fix a display string); re-deriving the
  profile from the form state (the response is the authority).
- **D3 (2026-10-10) — the page rides the route's search params.** The pagination
  hook takes `page` (and the sort keys where the surface offers them) from the
  route's `validateSearch` state, so a page two URL is shareable and the back button
  works; the hook wraps Connect-Query's `useQuery` with the page inputs as query-key
  members. Rejected: component-local state (unshareable, back-button hostile);
  cursor pagination (the wire is page-based).
- **D4 (2026-10-10) — the picture rides `/me` through the REST seam.** The upload is
  `PUT /api/users/me/profile-picture` over `fetcher` with the raw file body (the seam
  is the raw-body path D3 of the foundation plan built), not a multipart
  re-encoding; the delete is the sibling `DELETE`. After a change, the avatar's URL
  is re-derived with a cache-busting query param from the account view's updated
  state. Rejected: the `{id}` routes (they exist for self-service-by-id parity; `/me`
  is simpler and needs no identifier round trip); a tus session (2 MiB whole-file
  staging is in-request by design).
- **D5 (2026-10-10) — code entry, with `?code=` prefill.** The verification and
  change-confirm UIs render an input (the `otp-field` component) for the code the
  email carries, prefilled from a `?code=` search param so a future link-based email
  or a pasted URL both work; the flows stay `Public`-callable, so the root
  `verify-email.tsx` route works signed-in or not. Rejected: link-only consumption
  (the shipped templates carry codes, no URLs — inventing a link format would change
  the email templates, which this plan does not touch); session-gating the verify
  route (the token identifies the account by design).
- **D6 (2026-10-10, amended 2026-10-10 by owner decision) — the session center is
  read-heavy, write-explicit.** The view renders the uilibs `Item` composition (one
  item per session: the device it names, where and when it was opened, its state
  badge) rather than a grid. The wire's `current` flag marks the caller's own row.
  Sign-out-others/all are distinct destructive actions behind their own
  confirmations, and sign-out-all drops the token pair client-side too (the
  statelessness the backend records). **The per-row revoke deferred to Wave 2:**
  `RevokeSession` is step-up-guarded (`internal/guard/rules.go` marks it
  `StepUp: true`; the interceptor answers a missing proof `unauthenticated`), so the
  button ships the moment the step-up modal exists — the roadmap's Wave 2 records
  the handoff. Rejected: one blended "sign out everywhere" button (the count and
  the self-inclusion differ); shipping the revoke button against the step-up
  refusal (an action that always fails is not a UI).
- **D7 (2026-10-10) — the audit page is display-only in this wave.** It renders the
  caller's own records with the pagination hook and the `sort_by` whitelist; the
  admin facets and filters are Wave 3's surface. Rejected: building
  `FilterOptions`-driven filters now (an admin surface, out of scope).

feature-local wrappers only); the demo stub's DummyJSON copy leaves with phase 3 and
never returns.

decode, the query-key wiring Connect-Query expects) and extend
`guard/auth-utils.ts`'s `getErrorMessage` with the Connect codes this wave's surfaces
