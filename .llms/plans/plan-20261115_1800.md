# The overview says something true — a working dashboard for the account, a second one for the administrator

## Objective

`/overview` is a placeholder today: three static marketing cards ("One Account", "Passkey First", "Self-hosted"), a quick-links card whose sign-out row still reads "End the current DummyJSON session", and the same page for every caller. The owner picked on 2026-11-15: build the dashboard from the RPC list calls that already exist (no new backend surface), and show each audience what it can act on — an account view for everyone, an administration view on top for the administrator, cards the caller cannot read hidden rather than disabled. No token, color, or component is added to `packages/uilibs`.

## Current state (verified in the tree, 2026-11-15)

- **The page** (`packages/webapp/src/routes/(app)/overview.tsx`, 169 lines): `STATS` is a constant array of three strings; the quick links are Settings, a GitHub link, and a sign-out row; the only dynamic fact is the greeting and the one-shot `?notice=admin` alert the admin guard's redirect carries. Page layout styles live in `styles/pages/page.stylex.ts` (`cardsGrid*`, `quickCard`, `statLabel`).
- **No aggregate RPC exists.** Counts come from list responses: every list carries `ListMetadata.total_items` (`api/connect/common.proto`, optional), so a list with `limit = 1` answers a total in one call.
- **The server judges administration by role, not by slug.** `internal/guard/rules.go` has 114 `Rule: Admin` entries and 4 permission-bearing ones; every administration list the dashboard would read — `UserService.ListUsers` (`:258`), `UserGroupService.ListUserGroups` (`:269`), `AuditLogService.ListAll` (`:213`), `QueueService.ListQueues` (`:389`), `SchedulerService.ListJobs` (`:397`) — is `Admin`. The sidebar's slug gate (`-sidebar.tsx`, `admitsAdminNav`) is a UI nicety on top of that; a caller below the administrator role is refused by the server whatever slugs the snapshot lists.
- **The caller's own facts are `Session` or `Authenticated`:** `SessionService.ListSessions` (`:320`, ended sessions included, `revoked_at` absent while live), `MultifactorService.ListTotpEnrollments` (`:110`), `WebAuthnService.ListCredentials` (`:134`), `ApiKeyService.ListAPIKeys` (`:307`), `NotificationService.ListNotifications` (`:346`, with `unread_only`), the caller's own audit `List` (`auditlog.proto:39`).
- **`QueueSummary` carries `pending` and `dead`** per queue (`system.proto`), so the operations signal needs no per-task call.
- **The frontend pattern:** `useQuery(Service.method.x, input)` from connect-query (`hooks/use-pagination.ts:144` wraps it for tables); `usePermissions()` answers `isAdministrator` and `can(slug)` (`libraries/guard/use-permissions.ts`). The `(app)` admin routes already redirect a non-admin to `/overview?notice=admin` (`admin/route.tsx`).
- **uilibs already has the pieces:** `card`, `text`, `item`, `badge`, `skeleton`, `empty`, `description-list`, `alert`. A skeleton is the loading state.
- **Tests that touch the page:** E2E workflows land on `/overview` after sign-in (`account-sessions.test.ts` and others); there is no browser test for the overview itself.

## Decisions

- **D1 (owner pick 2026-11-15): the dashboard is composed from the existing list RPCs.** Tiles read `total_items` with `limit = 1`; nothing is added to the wire. Rejected: a `DashboardService.GetSummary` RPC (a new proto, handler, guard rows, tests, endpoint reference, and Yaak rows for numbers the lists already answer) and a static page.
- **D2 (owner pick 2026-11-15): one route, content by audience.** `/overview` renders the account view for every caller and, above it, the administration view when `isAdministrator`. Rejected: a second `/admin/overview` route (a new destination for sign-in and the guard's redirect).
- **D3 (agent finding, confirm at approval): two audiences, not one per slug.** Because every administration list is `Rule: Admin`, a caller below the administrator role could never read an administration tile whatever slug it holds; per-slug cards would render empty or refused. The gate is therefore `isAdministrator` for the administration view and nothing for the account view; a tile whose own query fails is hidden (an error is not a count of zero). Rejected: slug-gated cards (they promise what the server refuses).
- **D4: the account view** — a greeting; **Sessions** (live sessions counted from the first page: `revoked_at` absent and `expires_at` in the future; the current one named); **Sign-in methods** (passkeys, authenticator apps — the two counts, with a nudge to Security when both are zero); **Unread notifications** (`unread_only`, `total_items`); **API keys** (own, total); **Recent account activity** (the five newest rows of the caller's own audit log); and quick links to Settings, Security, and Notifications. The placeholder cards and the "DummyJSON" row go. Sign-out stays in the user menu, which already carries it.
- **D5: the administration view** — **People** (users, groups: `total_items`), **Operations** (dead tasks summed over `ListQueues`' `dead`, with the pending sum beside it; scheduler jobs counted), **Integrations** (webhooks, OIDC clients, OAuth providers: `total_items`), and **Recent activity** (the five newest rows of `AuditLog.ListAll`), each tile linking to its console screen. A tile with a nonzero dead-task count reads as a warning (the existing `Badge` critical variant), nothing else is color-coded. Rejected: charts and time series (no backend series exists; a count is the honest unit) and login-rate metrics (not derivable from a list).
- **D6: the guard's notice stays.** `?notice=admin` still renders its one-shot alert above everything, unchanged.
- **D7: loading and failure are per tile.** Each tile shows a `Skeleton` while its query runs and disappears on error; one slow list never blocks the page. Queries run in parallel and carry the connect-query defaults (no polling): the dashboard reads at mount and on focus.
