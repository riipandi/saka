# Plan — Framework extraction: the reusable layer and owned migration sets

Written 2026-10-04. The owner wants the project to grow toward multiple
binaries (sidecars). The tree is modular but the reusable engines still live
beside the application composition, so a second binary would either import the
whole app or copy code. This plan extracts the reusable, independent packages
into `framework/`, moves `database/` under `internal/`, and gives schema-carrying
framework packages their own goose migration sets.

## Objective

**Composability is the binding criterion.** A `framework/` layer holds the
engines any binary composes from; `internal/` keeps only the Saka composition
and the schema-bound code; each binary declares which framework pieces and
which migration sets it runs. No behavior change on the wire — every endpoint,
job, and command answers exactly as before.

Composable means, concretely (decision 16): every framework package is
constructible in isolation from its declared dependencies and options alone —
no package-level state, no singletons, no implicit config reads, no init-time
wiring; a package must work in any subset a binary selects, degrade by
contract (Noop/off) rather than by nil-checks at the call site, and accept
what varies (identity, namespaces, paths) as options rather than reading it
from the environment or the app.

Design-doc rows touched: `.llms/architecture.md` (new `framework` section,
rewrites of the sections of every moved package), `.llms/rules.md` (the
framework boundary rule and the migration-set contract), `.llms/index.md`
(the plan row and the map).

## Decisions

1. **`framework/` stays a directory of the main module**
   (`github.com/riipandi/saka/framework/...`). Dated 2026-10-04, owner's pick.
   The boundary framework-does-not-import-internal is enforced mechanically,
   not by convention: a `depguard` rule in `.golangci.yml` denies
   `saka/internal/**` and `saka/modules/**` imports from files under
   `framework/**`, added in phase 2 so every later move is checked by
   `task lint`. Rejected: a separate go.mod (needs go.work/replace machinery
   now; revisit when a second binary actually ships); a separate repository
   (heaviest: versioning and release cycle for one consumer); an unenforced
   convention.
2. **`internal/config` splits**: the generic engine moves to
   `framework/config`; the Saka schema (`Config`, its sections, defaults,
   schema validation, `config:generate`'s published file) stays in
   `internal/config` wrapping the engine. Dated 2026-10-04, owner's pick.
   Rejected: moving the whole package (framework would carry the Saka schema);
   every framework package defining its own Options with no engine (more glue,
   and rejected below in decision 9's direction — the engine serves the app
   schema, not the framework packages).
3. **Scope**: Tier A (`kernel`, `authz`, `datastore`, `health`), Tier B
   (`observer`, `logger`, `fetcher`, `cache`), the mailer engine, the storage
   engine, and `queue` + `scheduler` + `audit` move now. The audit deferral
   was retracted when the examination showed its `entity` usage is the one
   table-name constant (`recorder.go:161`) — the same treatment as queue and
   scheduler; the owner named the storage engine and the migrator toolkit
   mid-discussion. Dated 2026-10-04.
4. **`database/entity` stays internal.** Queue, scheduler, and audit declare
   their table-name constants locally (`framework/queue`,
   `framework/scheduler`, `framework/audit` — `TableQueueTasks`,
   `TableQueueTasksCompleted`, `TableSchedulerJobs`, `TableAuditLogs`); the
   duplicated constants in `entity` are deleted. Dated 2026-10-04, owner's
   pick; the audit half retracted the earlier deferral (decision 3). Rejected:
   moving `entity` into framework (it is the app's row model); contract
   interfaces over entity (four string constants need no contract).
5. **`database/` moves wholesale to `internal/database`** (entity, migrations,
   seeders, migrator, dump/backup/restore, seed factories). Import paths
   retyped everywhere. Dated 2026-10-04, owner's pick. Rejected: phased move
   (entity first) — two waves for one mechanical rename.
6. **`pkg/` stays** as the small-utility layer; `framework/` holds engines.
   Dated 2026-10-04, owner's pick. Rejected: merging `pkg/` into `framework/`
   (churn without a boundary gain today).
7. **Migration toolkit — composed runner, goose-native, full toolkit.**
   `framework/migration` carries the generalized runner (version table and
   advisory lock key as options), `Set{Name, FS, VersionTable, LockKey}`,
   `Compose` (refuses duplicate names, version tables, lock keys), and the
   already-generic developer tools: `ValidateFS` (schema checks over any
   `fs.FS`, no DSN needed) and `CreateMigration` (skeleton writer with
   duplicate-name refusal). Each schema-carrying framework package embeds its
   own SQL files and exports a `migration.Set` (`framework/queue.Schema()`,
   `framework/scheduler.Schema()`, `framework/audit.Schema()`). The binary's
   migration commands compose the sets (`migration.Compose(app set, queue,
   scheduler, audit, …)`) and one `migrate:up/down/status` runs them in order
   with a unified report; each set is its own goose `Provider` with its own
   version table (`queue_migrations`, `scheduler_migrations`,
   `audit_migrations`). Dated 2026-10-04, owner's pick ("seamless and aligned
   with internal migration in each binary; the project uses goose"; the
   toolkit's full depth is the owner's pick of option 2). Rejected: full
   River-style self-migration (each package runs its own Migrate — the
   operational report fragments); injecting SQL into the single app sequence
   (framework releases would fight for version numbers; shared-DB binaries
   must agree on the whole sequence); the minimal engine (runner + Set +
   Compose only — a second binary could not validate or create migrations
   without copying code).
8. **Framework packages take typed `Options`, not `config.Config`.**
   `observer.Options`, `logger.Options`, `fetcher.Options`, `cache.Options`
   carry what the constructor consumes; the vocabulary types
   (`LogTransport*`, `LogFormat`, `OTELSampler*`, `OTELCompression*`,
   `OTELTracing`) move into their owner package, since they are domain
   vocabulary, not schema — `internal/config` imports them from there. The
   Saka-isms become options: `cache.Options.KeyPrefix`, `logger.Options.
   FilePath` (the `storage.local_path/logs/saka.log` derivation moves to the
   caller), `fetcher.Options.UserAgent` and an instrumentation-name parameter.
   The rule is uniform across the framework: **every metric instrument name
   is composed from an options namespace** (`fetcher`, `queue`, `scheduler`,
   `storage` all carry `saka.<domain>.*` prefixes today), defaulting to the
   package's own domain word, with the app passing `"saka"`; and **the app
   identity constants** (`config/meta.go`'s `AppName`, `AppIdentifier`,
   `AppVersion`, read directly by `logger/otlp.go` and `observer/telemetry.go`
   for the OTel resource) arrive as `Options` fields, never as package
   constants the framework reads. Dated 2026-10-04. Rejected: framework
   packages reading `config.Config` (drags the schema in); hardcoding a
   neutral prefix in the framework (the deployment owns its telemetry
   identity).
9. **No config builder** — plain struct literals over the `Options`, and the
   schema→options mapping lives in `internal/config` as small adapter
   functions. Dated 2026-10-04, owner's pick of option 1. Rejected: fluent
   builders (ceremony over data); self-configuring packages declaring their
   keys to the engine (the cross-section validation — e.g. valkey cache driver
   requires `kvstore.enable` — and `config:print`'s single surface would have
   to be re-assembled from fragments). A declarative key-metadata hybrid is
   noted for the day duplication hurts, not built now.
10. **Early-stage, no backward compatibility.** No shims, no legacy import
    paths, no `ALTER` migrations — migration files are edited in place and the
    development database is reset during the work. Dated 2026-10-04, owner's
    word.
11. **The mailer engine moves; templates are injected, not owned.**
    `framework/mailer` carries `Mailer`, `Message`, `Request`, `Service`, the
    `Templates` renderer, `View`/`Body`/`Sender`, and `NewTemplatesFS` — built
    from `Options` (the `cfg.Mailer` fields), never from `config.Config`. The
    template mechanism is the already-FS-generic renderer: each binary embeds
    its own compiled template set (the Vite build's `<name>_html.tmpl` /
    `<name>_text.tmpl` layout, whose contract `framework/mailer` documents and
    validates at parse time) and hands the `fs.FS` to `NewTemplatesFS`; the
    framework never imports `web`. The Saka side stays in `internal/mailer`:
    the `web.EmailTemplates` binding, `SenderFrom` (the product name and logo
    URL), and the 21-name template catalog in `data.go`. The MIME boundary
    prefix `"saka-"` (`envelope.go:330`) is dropped on the move — a boundary
    needs uniqueness, not a brand. Dated 2026-10-04,
    owner's word ("mailer juga sepertinya bisa dijadikan reusable … perlu
    mekanisme untuk handle template"). Rejected: framework owning a template
    registry or the embed (couples the framework to the app's build output);
    moving the catalog constants (they name the app's emails, not a generic
    contract); a second template engine beside the compiled React Email
    output.
12. **The storage engine moves; the serving surface and bucket catalog stay
    app-side.** `framework/storage` carries the `Store` contract with the FS
    and S3 drivers, `Manager`, manifests, the buckets registry, the tus
    protocol handler (`net/http` — it mounts anywhere), and the signed-link
    `Signer` — built from `Options` (driver, local path, the S3 settings,
    metric namespace, link path prefix), never from `config.Config`. The
    Saka-isms become options: `Options.LinkPathPrefix` replaces the hardcoded
    `/storage` (`signed_url.go:20`), the metric instruments take a namespace
    option instead of the `saka.storage.*` prefix (decision 8's uniform rule),
    and `linkDomain` becomes the neutral constant `signed-link` — it
    separates HMAC purposes, not apps, and the `"saka-storage-signed-link"`
    spelling embedded the app's name (changing it invalidates links already
    issued; no backward compatibility this round). The app side
    stays where it is: `internal/transport/storage` serves `/storage`, and
    the app's bucket catalog is registered from `modules/storage`. Dated
    2026-10-04, owner's word ("sekalian naikan juga storage engine ke
    framework"). Rejected: keeping the whole package internal (the engine is
    dependency-clean; only the route path and the metric prefix were
    Saka-isms); moving the tus HTTP surface into `internal/transport` (the
    handler is protocol-generic and mounts like any other).
13. **The request kit, not a Gin-style Context.** `framework/webutil` gives the
    REST handlers per-request helpers over the stdlib signatures — handlers
    keep `func(w http.ResponseWriter, r *http.Request)`, chi middleware and
    every stdlib-mounting surface (tus, health, Prometheus) stay untouched.
    The kit absorbs `pkg/responder` (the envelope, pagination, request IDs —
    56 production users) and `pkg/validate` (decode + ozzo), and exposes
    `PathParam`, `Query`, `Decode` (decode + validate + envelope error in one
    call), and `Principal` (the guard identity read from the typed request
    context). The ConnectRPC surface is deliberately outside the kit: its
    procedures answer `connect.Request[T]` and its cross-cutting concerns are
    interceptors — a request-scoped object cannot wrap it, which is the
    reason a Gin/Echo-style `*Context` was refused. Dated 2026-10-04, owner's
    pick of the request kit over the Context. Rejected: a Gin-style Context
    (the RPC asymmetry, the stdlib/middleware break, `c.Set`/`c.Get`
    duplicating `context.Context` as hidden state); leaving responder and
    validate in `pkg/` while the kit wraps them (two names for one contract).
14. **The `pkg/` line.** `responder` and `validate` rise into
    `framework/webutil` (decision 13). `jwtutils`, `crypto`, `envfile`,
    `printext`, `strutils` stay: pure utilities, no wiring, correctly imported
    by both framework and internal packages (framework → pkg is the allowed
    direction). `pkg/testutils` splits: the container starters (Postgres,
    Mailpit, MinIO, VictoriaLogs) stay in `pkg/testutils`; `MigratedPostgres`
    moves to `internal/testutils` — it composes the app's migration sets
    (decision 7), which is application wiring, not a utility, and its current
    imports (`database` migrator, `datastore`) already reach past the pkg
    line. Dated 2026-10-04. Rejected: moving the whole of `pkg/` into
    framework (decision 6 stands); moving `jwtutils`/`crypto` (they are
    vocabulary and primitives, not engines).
15. **`authz` splits: the engine moves, the catalog stays.** `framework/authz`
    carries the grant semantics — `Wildcard`, the `Permission`/`Resource`
    types, `Slug()`, `Match()`, `Grants()` — plus a `Catalog` value the
    caller constructs from resources (`NewCatalog(resources)`), with
    `ValidSlug`/`Catalog` lookups becoming methods over it. The Saka
    vocabulary stays in `internal/authz`: the `resources` list
    (`authz.go:85-140`), `AdministratorRole`, `SystemRoles`, and the
    construction of the catalog from them. `guard`, the seeders, and
    `modules/identity/authorization` read the catalog from the binding; the
    engine from framework. Dated 2026-10-04, from the sweep the owner
    ordered ("cek ulang apakah masih ada yang terikat"). Rejected: moving
    `authz` unchanged (it would carry the app's permission catalog and role
    names — the exact coupling this plan exists to remove); splitting
    `Resource`/`Permission` types from the matching functions (one engine,
    one package).
16. **Composability is the framework's binding criterion.** Every framework
    package is constructible in isolation from its declared dependencies and
    `Options` alone; nothing is read from the environment, the app config, or
    package-level globals at construction; a package works in any subset a
    binary selects. The degradation contract is explicit construction, not
    hidden nil: a disabled signal builds the no-op (`observer` with every
    signal off, `cache` handing out Noop, an unconfigured `mailer` answering
    `ErrNotConfigured`), so a caller never branches on nil. Where a package
    needs to vary, the variation is an option — identity, namespaces, paths,
    prefixes (decisions 8, 11, 12) — because an option composes and a
    constant couples. Dated 2026-10-04, owner's word ("kunci atau objective
    untuk framework adalah composable"). Rejected: a framework-owned
    container/locator that packages fetch dependencies from (that is
    `internal/registry`'s job, inverted); optional interfaces assembled at
    init time.
17. **The frontend bundler integration moves as `framework/bundler`; the
    assets stay app-side.** The shell (the HTML document and its trusted
    head), the Vite build-manifest integration (config, manifest, the entry
    fragment), and the static mounting move into `framework/bundler` —
    parameterized by `fs.FS` (the build output) and options (the dev-server
    URL), never by an embed, because an embed is compile-time and the assets
    are a binary's own. The debug/release pairing that today rides build
    tags (`static_debug.go` / `static_release.go`) becomes two constructors;
    the build tag moves to the app binding. `web/` stays as that binding:
    `embed.go` (`EmailTemplates`, the SPA `output/`), the generated asset
    directories, and the passkey devtool probes — the app's frontend is the
    app's; the bundler never imports `web`. The name is `bundler` rather
    than `vite` because the role is "bind a frontend bundler's build output
    into a Go binary" (and `framework/webutil` is already the request kit).
    Composability holds by construction: a bundler builds from an `fs.FS`
    alone, serves whatever it is handed, and degrades loudly when the
    manifest is absent rather than reading the environment. Dated
    2026-10-04, owner's word ("Jadikan framework/bundler. Pastikan
    composable juga"). Rejected: moving `web/` whole (the framework would
    carry Saka's SPA and its 21 email templates — assets, not abstractions);
    the name `framework/vite` (collides conceptually with the request kit
    and names the tool, not the role); keeping the build tags in framework
    (a compile-time fork is a binary's decision).
18. **The generic request middleware moves as `framework/middleware`, each
    piece configurable, and the policy middleware stays app-side.** Moving:
    `requestid`, `logger`, `recoverer`, `timeout`, `security`, `unbounded`,
    `cors`, and the rate-limit engine with its kvstore driver — every one is
    stdlib plus the request kit, constructible from its arguments alone. The
    configuration coupling goes: `cors` today imports `internal/config` for
    the default method/header lists — the middleware takes them as explicit
    options and the app passes its schema values; the rate-limit metrics drop
    the `saka.http.ratelimit.*` prefix for a namespace option (decision 8's
    uniform rule). The `Limiter` is an interface the composition injects, so
    a driver is a caller's choice. Staying in
    `internal/transport/middleware`: `guard`, `bearer`, and `apikey` (policy
    and authentication over this application's tables and claims),
    `clientinfo` (the seam that builds `audit.ClientInfo` for the request),
    and `ratelimit_database` (the driver over Saka's own `fn_check_rate_limit`
    SQL function — the function is the app migration's, so the driver that
    calls it is the app's). Dated 2026-10-04, owner's word ("beberapa
    middleware … juga sepertinya bisa naik ke framework/middleware, tapi
    tetap composable/configurable"). Rejected: moving the whole middleware
    directory (half of it is policy over Saka's tables — exactly the coupling
    the boundary forbids); a middleware registry or global chain (a chain is
    the composition root's list, not a package's).

## Shape and enforcement points

Target structure after the plan:

Enforcement points:

- `framework/migration` — the only new cross-package contract: `Set`,
  `Compose` (refuses duplicate names, version tables, and lock keys), the
  runner, `ValidateFS`, and `CreateMigration`.
- `internal/database` migrator becomes a `framework/migration` client carrying
  the app set; `cmd/migration.go` composes and reports.
- `internal/config` adapter functions are the only place schema meets options.
- Import direction: `framework/**` must not import `internal/**` or
  `modules/**` — enforced by the `depguard` rule in `.golangci.yml` from
  phase 2 on, and pinned in `.llms/rules.md`.
- `00009_create_scheduler_tables.sql` leaves the app sequence; queue,
  scheduler, and audit each gain `00001_*` files in their own package; the
  table DDL is edited in place (no ALTER; dev-DB reset authorized).
- No new endpoint, job, email, audit event, guard rule, or settings key — the
  Yaak collection needs no row.

## Execution rules

- Atomic commit per phase is authorized; each phase's heading names its
  suggested commit message; the standing commit rule resumes when the plan
  completes. Every commit is limited to that phase's files.
- Migration rule this round: no `ALTER` — migration files are edited in place;
  resetting the development database (`migrate:reset --up`) is authorized and
  expected in phase 10. No backward compatibility: no shim, no alias, no
  legacy path.
- Yaak updates ride the same change as the contract — this round names none
  (no wire surface changes; verified).
- Per-phase validation runs before each commit: `go test ./...`, `task lint`;
  phase 10 additionally runs the migration commands against the dev database;
  phase 11 runs the full closing battery.
- E2E is not relevant — nothing on the wire changes; the serve probe in phase
  10 covers the composed binary.
- Comments say what the code cannot: the framework boundary rule and the
  per-set version-table/lock-key invariant are stated at their write sites.

## Phases

### Phase 1 — `database/` into `internal/database` (`refactor(database): move database into internal/database`)

- `git mv database internal/database`; retype every importer's path
  (`cmd/`, `internal/{audit,jobs,queue,registry,scheduler,storage,transport}`,
  `modules/**`, `pkg/testutils`).
- `migrate:create` default `--dir` becomes `internal/database/migrations`;
  scripts and references follow.
- Docs mentions of `database/migrations` corrected in the same commit where
  the diff stales them (full docs sync rides phase 11).
- Validation: `go test ./...`, `task lint`, `task db:validate`.

### Phase 2 — Tier A into `framework/` (`refactor(framework): extract kernel, authz, datastore, health`)

- `kernel`, `datastore`, `health` move unchanged to `framework/`; `authz`
  splits per decision 15 — the engine (`Wildcard`, `Permission`/`Resource`,
  `Match`, `Grants`, the constructed `Catalog`) moves, the Saka resources
  list, `AdministratorRole`, and `SystemRoles` stay in `internal/authz` as
  the binding; importers retyped
  (`internal/{guard,registry,transport,storage,cache,logger,jobs,mailer,audit}`,
  `modules/**` where applicable, `cmd/`).
- The `depguard` rule lands in `.golangci.yml`: files under `framework/**`
  deny `saka/internal/**` and `saka/modules/**` — the boundary is lint-checked
  from here on (decision 1).
- `health`'s doc example (`helper.go:251`) loses the `saka` name; `health`
  keeps its interface-based checks.
- Validation: `go test ./...`, `task lint`.

### Phase 3 — Config split (`refactor(config): split the engine into framework/config`)

- Engine pieces with no knowledge of the Saka schema move to
  `framework/config`: loader/precedence, env interpolation, `EnvName`,
  duration keys, flags binding, `meta`, `predicates`, the generic redaction
  machinery.
- `internal/config` keeps the `Config` struct, its sections, defaults, schema
  validation, `publish` (`config:generate`'s file), the secret keys list, and
  wraps the engine.
- The vocabulary enums (`LogTransport*`, `LogFormat`, `OTELSampler*`,
  `OTELCompression*`, `OTELTracing`) stay in `internal/config` this phase and
  move in phase 4 with their owner packages.
- Validation: `go test ./...`, `task lint`, plus a `config:generate` /
  `config:print` probe against `.env.local`.

### Phase 4 — Tier B behind Options (`refactor(framework): extract observer, logger, fetcher, cache behind Options`)

- `observer`, `fetcher`, `cache`, `logger` move to `framework/` with typed
  `Options` (decision 8); the vocabulary types move with their owner package;
  `framework/logger` imports `framework/observer`; `framework/cache` imports
  `framework/datastore`.
- Saka-isms become options/parameters: `KeyPrefix`, `FilePath`,
  `UserAgent` + instrumentation name.
- `internal/config` gains the adapter functions and retypes its schema fields
  to the framework vocabulary; `internal/registry` and `cmd/` wiring updated.
- The file-sink path derivation (`storage.local_path/logs/saka.log`) moves to
  the internal caller.
- Validation: `go test ./...`, `task lint`, `logger:smoke` and `otel:smoke`
  probes against `.env.local`.

### Phase 5 — Request kit into `framework/webutil` (`refactor(framework): build the request kit over responder and validate`)

- `pkg/responder` and `pkg/validate` move into `framework/webutil` unchanged in
  behavior — the envelope, pagination, request IDs, decode + ozzo validation;
  the 56 importers retype.
- The kit's helpers land over stdlib signatures: `PathParam`, `Query`,
  `Decode` (decode + validate + envelope error in one call), `Principal`
  (the guard identity from the typed request context). No handler signature
  changes; the RPC surface is untouched (decision 13).
- `pkg/testutils` splits (decision 14): `MigratedPostgres` moves to
  `internal/testutils`; the container starters stay.
- Validation: `go test ./...`, `task lint`; the REST route tests (the 21
  mounted routes) answer byte-identically.

### Phase 6 — Request middleware into `framework/middleware` (`refactor(framework): extract the request middleware, configurable`)

- `framework/middleware` gains `requestid`, `logger`, `recoverer`, `timeout`,
  `security`, `unbounded`, `cors`, and the rate-limit engine with its kvstore
  driver — every piece constructible from its arguments alone (decision 16).
- The configuration coupling goes: `cors` takes the allowed methods, headers,
  and origins as explicit options (the app passes its schema values; the
  middleware stops importing `internal/config`), and the rate-limit metrics
  take a namespace option instead of the `saka.http.ratelimit.*` prefix.
- `internal/transport/middleware` keeps the policy half: `guard`, `bearer`,
  `apikey`, `clientinfo` (the audit seam), and `ratelimit_database` (the
  driver over the app's own SQL function). `internal/transport` retypes its
  chain to the framework pieces and keeps the policy ones.
- Validation: `go test ./...`, `task lint`; the transport middleware tests
  answer unchanged.
### Phase 7 — Mailer engine into `framework/` (`refactor(framework): extract the mailer engine behind Options`)

- `framework/mailer` gains `Mailer`, `Message`, `Request`, `Service`,
  `Templates`/`View`/`Body`/`Sender`, `NewTemplatesFS` — built from
  `Options` (the `cfg.Mailer` fields: host, port, credentials, TLS,
  timeouts), never from `config.Config`.
- The template layout contract (`<name>_html.tmpl` / `<name>_text.tmpl`, the
  html+text pair required, parse failure = construction failure) is stated in
  the package docs and pinned by tests over fixtures.
- `internal/mailer` becomes the app binding: the `web.EmailTemplates` embed
  wiring, `SenderFrom` (product name, logo URL), the 21-name catalog, and the
  `cfg.MailerOptions()` adapter. The MIME boundary loses its `"saka-"`
  prefix (`envelope.go:330`); `messageID` already takes the sender's domain.
- Validation: `go test ./...`, `task lint`, `mailer:smoke` against
  `.env.local` (the wiring probe renders and sends through the moved engine).

### Phase 8 — Storage engine into `framework/` (`refactor(framework): extract the storage engine behind Options`)

- `framework/storage` gains the `Store` contract, the FS and S3 drivers,
  `Manager`, manifests, the buckets registry, the tus protocol handler, and
  the signed-link `Signer` — built from `Options` (driver, local path, S3
  settings, metric namespace, `LinkPathPrefix`), never from `config.Config`.
- The Saka-isms become options: the hardcoded `/storage` link prefix
  (`signed_url.go:20`) and the `saka.storage.*` metric prefix; `linkDomain`
  becomes the neutral `signed-link` constant (decision 12).
- Importers retyped (`internal/{jobs,registry,transport}`,
  `modules/{federation,identity,storage}`); `internal/transport/storage`
  mounts the tus handler and serves `/storage` over the framework engine; the
  bucket catalog stays registered from `modules/storage`.
- `cfg.StorageOptions()` joins the adapter set in `internal/config`.
- Validation: `go test ./...`, `task lint`; the storage checks of the health
  endpoint and the `/storage` tus round-trip are covered by the existing
  suite.

### Phase 9 — Frontend bundler into `framework/bundler` (`refactor(framework): extract the frontend bundler integration`)

- `framework/bundler` gains the shell, the Vite manifest integration, the
  entry fragment, and the static mounting — every function takes the build
  output as `fs.FS` and its options; no `go:embed` crosses the boundary, so
  the framework carries no asset.
- The debug/release pairing (`static_debug.go` / `static_release.go`, build
  tags today) becomes two constructors; `web/` keeps the build-tagged
  binding file that picks one.
- `web/` stays the app binding: `embed.go` (`EmailTemplates`, the SPA
  `output/` embeds), the generated directories, the passkey devtool probes.
  `internal/mailer`'s `web.EmailTemplates` binding is untouched; `internal/
  transport` retypes to the framework API plus the binding.
- Composability (decision 16): a construction test builds the bundler from a
  fixture `fs.FS` alone and asserts the missing-manifest failure names
  itself.
- Validation: `go test ./...`, `task lint`, plus the release build + serve
  probe proving the SPA and the shell still answer (the bundler is on the
  serving path).

### Phase 10 — Migration toolkit; queue, scheduler, audit (`refactor(framework): extract queue, scheduler, audit with owned migration sets`)

- The migrator engine generalizes into `framework/migration` — the full
  toolkit (decision 7): runner (`Set`, `Compose`, version table + lock key as
  options), `ValidateFS`, and `CreateMigration`; `internal/database`
  migrator becomes its client for the app set.
- `queue`, `scheduler`, and `audit` move to `framework/`, declaring their
  table-name constants locally (`TableQueueTasks`, `TableQueueTasksCompleted`,
  `TableSchedulerJobs`, `TableAuditLogs`); the now-unused `entity` constants
  are deleted. `framework/audit` carries the recorder engine (`Recorder`,
  `Entry`, `Sink`, `ClientInfo`); the event catalog and its call sites stay
  in `internal/audit`. The `saka.queue.*`/`saka.scheduler.*` metric prefixes
  become namespace options (decision 8), and the package docs lose the
  "saka's" openings (`queue.go:1`, `scheduler.go:1`).
- `00009` is split in place: queue DDL → `framework/queue/migrations/
  00001_create_queue_tables.sql`, scheduler DDL →
  `framework/scheduler/migrations/00001_create_scheduler_tables.sql`; audit's
  `audit_logs` DDL is extracted from `00004_create_identity_tables.sql` in
  place into `framework/audit/migrations/00001_create_audit_logs.sql` (no
  ALTER; edit in place; the app sequence drops both fragments).
- `cmd/migration.go` composes app + queue + scheduler + audit sets; one
  report, each row naming its set; `migrate:status` lists every set.
- `pkg/testutils.MigratedPostgres` learns the composed sets — it migrates
  the same list the binary composes (or takes it as a parameter), so every
  feature's integration test sees the schema it touches.
- Seamless existing dev DB: the package DDL keeps `CREATE TABLE IF NOT
  EXISTS`, so the first run over a database that already holds the tables
  records the version without touching data; the stale `00009` row in
  `app_migration` remains as history. A `migrate:reset --up` rebuilds from
  scratch to prove the fresh path.
- Validation: `go test ./...`, `task lint`, `task db:validate`,
  `migrate:up`/`migrate:status`/`migrate:down --count 1`/`migrate:reset --up`
  against the dev database, and a probe of the freshly built release binary
  serving `/healthz`.

### Phase 11 — Final validation, docs sync, handover (`docs(architecture): framework extraction docs and handover`)

- Full closing battery: `go test -race ./...`, `task lint`, `task rpc:stale`,
  `task db:validate`, release build + serve probe, `config:print` review.
- Docs sync: `.llms/architecture.md` gains the `framework` section and the
  moved packages' sections are retitled/rewritten to the new paths (database →
  internal/database, the config split, the Options pattern, the migration
  toolkit and sets); `.llms/rules.md` gains the framework boundary rule
  (depguard) and the migration-set rules; `.llms/index.md` gains this plan's
  row.
- Handover document (`.llms/handover/handover-*.md`): the extraction map, the
  decisions D1–D18 with their rejected alternatives, the migration-set
  adoption story, what was deliberately deferred (module split, the key-
  metadata config hybrid, the first sidecar binary).
- Plan status closes; the closing commit is recommended, not made.
