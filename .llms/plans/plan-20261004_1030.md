# Plan — OAuth SSO refinement: full attribute mapping, custom attributes, sign-in refresh

Written 2026-10-04. This plan refines the shipped OAuth SSO feature
(`.llms/plans/plan-20261003_0258.md`, all six phases landed) to match the Clerk
custom-provider attribute-mapping shape while keeping this repo's own vocabulary.

## Objective

Close the attribute-mapping gap between the shipped custom OIDC connection and
Clerk's social-connections custom provider: map the provider's user-ID, verified
flag, username, and avatar claims; let an operator define custom attributes that
land on the user; and re-apply the mapping on every sign-in, the way Clerk does.
The design row this plan closes is `.llms/auth-design.md` § SSO Connections —
it gains the **Custom attribute mapping** row, ticked when the work lands.

Flow references (read 2026-10-04):

- Clerk, "Add a custom OAuth provider as a social connection" — the attribute
  mapping section: defaults for missing claims, empty-mapping semantics, the
  userinfo URL's priority over the id_token, the proxy escape hatch.
- Clerk, "Account linking for OAuth" — linking by verified email (already
  implemented; no change this round).
- Clerk, "Custom Attribute Mapping" (enterprise connections) — read for the
  custom-attribute idea only; its SAML/SCIM surface is out of scope.

## Decisions

Confirmed with the owner, 2026-10-04 (UTC+7). Each carries its rejected
alternatives.

1. **Scope — extended mapping + custom attributes.** The plan ships the extended
   claim mapping (subject, verified flag, username, avatar), the operator-defined
   custom attributes, and the every-sign-in refresh. Rejected: the provider-token
   retrieval API (owner refusal this round; stays a handover follow-up), new
   builtin providers (Google + GitHub suffice; an adapter per provider would
   widen the plan without touching the gap).
2. **Empty mapping field = the default claim name.** The shipped semantics stay.
   Clerk's "leave the mapping field empty to not set it" is a recorded delta: an
   unset field falls back to `sub` / `email` / `email_verified` /
   `given_name` / `family_name` / `preferred_username` / `picture` defaults.
   Rejected: adopting Clerk's unset semantics (a behavior break for stored
   connections that would need an explicit reset sentinel on the wire).
3. **The mapping applies on every successful resolution.** Names, avatar, and
   custom attributes refresh on the linked account's user at each sign-in —
   Clerk's behavior. Username is the exception: it is written once at JIT
   creation (mapped claim, then the existing derivation from the address) and
   never overwritten — the UNIQUE constraint and format check on `users.username`
   make an every-sign-in overwrite a churn risk. Rejected: refreshing username
   every sign-in with a collision fallback (churn without a use the owner asked
   for).
4. **Custom attributes live in `users.custom_attributes`.** A new nullable JSONB
   column on `users`, read and written through a seam the user module owns —
   the closest analog to Clerk's `publicMetadata`, and the home SCIM inbound can
   share when that round comes. Rejected: a column on
   `oauthsso_linked_accounts` (provider-scoped, invisible to the rest of the
   user surface) and `users.metadata` (the closed preferences document — its own
   comment forbids exactly this).
5. **Attribute values keep the shape they arrived in.** A scalar stores as a
   scalar, an array of scalars stores as an array — Clerk's multi-value semantics
   come from the claim's own shape, not a toggle. Blank and null values are
   dropped; an object or a nested structure refuses the write. Rejected: an
   explicit "allow multiple values" toggle (OIDC claims already carry their
   shape; the toggle would duplicate it).
6. **Avatar downloads into storage.** The mapped avatar claim is fetched over
   the outbound fetcher, stored through the storage engine, and set as the
   account's `picture_file_id` on each refresh. Rejected: keeping the URL as a
   custom attribute (`picture_file_id` is a storage object; a URL would never
   render through the existing surface) and skipping avatar mapping entirely
   (the owner asked for Clerk parity).
7. **No "don't set" sentinel, no proxy seam.** The empty field means the default
   claim (decision 2); a provider needing transformations points its userinfo
   URL at a transforming proxy — Clerk's own escape hatch, which needs no code
   from this plan.

## Shape and enforcement points

- `users.custom_attributes JSONB DEFAULT NULL` — an in-place edit of the
  users `CREATE TABLE` in `00004_create_identity_tables.sql` (the plan's
  own DDL, edited in place while it lands; the dev database resets to
  reconcile). No trigger, no index: the document is read and written
  whole.
- `AttributeMapping` (schema) and `OAuthAttributeMapping` (wire) gain:
  `Subject`, `EmailVerified`, `EmailVerifiedDefault` (a `bool` the resolution
  answers when the verified claim is absent — the Clerk tip's "default values
  for missing claims"), `Username`, `AvatarURL`. `mergeMapping` and `wireMapping`
  extend with them; the empty-string-means-default rule covers every name field.
- The connection row's `attribute_mapping` JSONB gains `custom_attributes` —
  an array of `{key, claim}` definitions, validated at write time (key is a
  non-empty identifier, claim a non-empty name, no duplicate keys) beside the
  existing discovery validation.
- Resolution (`custom/custom.go`) reads the extended names through the same
  raw-document readers; arrays pass through untouched for custom attributes.
- The profile refresh runs inside the resolution transaction through a seam the
  user module owns: a profile writer that updates `first_name`, `last_name`,
  `display_name`, and `picture_file_id`, and a custom-attribute writer that
  merges the mapped document onto `users.custom_attributes`. The oauthsso
  feature never opens the users table directly.
- Avatar download rides the existing outbound fetcher seam; a failed or
  non-image download is not a sign-in failure — the refresh continues without
  the picture, and the previous one stays.
- No new procedures, REST routes, jobs, emails, audit events, or guard rules.
  The Create/Update Connection requests carry the widened mapping; their Yaak
  rows are updated in the same change (`yaak update --json`) — no new request is
  added, none carries `(unimplemented)`.

## Execution rules

- **Atomic commit per phase is authorized** — one commit per validated phase,
  each phase's heading names its suggested commit message, staged by explicit
  path, never pushed, never destructive Git commands. The standing commit rule
  resumes when the plan completes; the closing state is not committed on the

- Each phase validates on its own before it commits: build, `task lint`,
  focused suite, `task rpc:stale` after any proto change, `task db:validate`
  after any migration change.

## Phases

### Phase 1 — Contract, schema, Yaak (`feat(oauthsso): extended attribute mapping contract`)

- `users.custom_attributes` edited in place into the users `CREATE TABLE`
  in `00004_create_identity_tables.sql`; `task db:validate` and a dev
  reset cover it.
- Proto: `OAuthAttributeMapping` gains `subject`, `email_verified`,
  `email_verified_default`, `username`, `avatar_url`; a new
  `OAuthCustomAttribute` message (`key`, `claim`) rides
  `OAuthConnection.custom_attributes`, the Create and Update requests, with
  `buf.validate.field` constraints on both fields of each entry.
- Schema, repository, `mergeMapping`, `wireMapping`, and the connection
  validation extend for the new fields; the custom-attribute definitions
  validate at write time (unique keys, non-empty claims).
- Yaak: the Create/Update Connection requests gain the new fields.
- Validation: build, `task lint`, `task rpc:stale`, `task db:validate`, the
  oauthsso service tests.

### Phase 2 — Custom adapter: extended mapping (`feat(oauthsso): read the extended claim mapping`)

- `custom/custom.go`: `mappedSubject` (default `sub`), `mappedEmailVerified`
  (default `email_verified`, answering `EmailVerifiedDefault` when the claim is
  absent), `mappedUsername` (default `preferred_username`), `mappedAvatarURL`
  (default `picture`); the raw-document readers accept array values for the
  custom attributes instead of dropping them.
- The bindability judge keeps reading the mapped email; the subject joins it in
  the "no bindable identity" refusal.
- Builtin adapters untouched.
- Validation: build, `task lint`, the adapter tests against the local fake OIDC
  server — every new mapping field proven in both directions (claim present,
  claim absent → default).

### Phase 3 — Apply-on-sign-in profile refresh (`feat(oauthsso): refresh the profile on every sign-in`)

- The user module gains the profile and custom-attribute writer seam the
  oauthsso resolution calls inside its transaction: names and avatar refresh
  every sign-in; username is written only on the JIT insert (the existing
  derivation keeps its conflict suffix); custom attributes merge onto
  `users.custom_attributes` (scalar or array of scalars stored as arrived,
  blank/null dropped, an object refused).
- Avatar: the mapped URL downloads over the outbound fetcher, stores through
  the storage engine, and sets `picture_file_id`; a failed download leaves the
  previous picture and never fails the sign-in.
- The continue stage's `require_names` pause keeps its shape: a refresh that
  names nobody does not re-open the pause on an account that already carries
  names.
- Container tests: refresh on a second sign-in (names, avatar, custom
  attributes change; username does not), the JIT username conflict suffix, the
  blank-value drop, the object refusal, the avatar-download failure path.
- Validation: build, `task lint`, the container suite.

### Phase 4 — Validation, E2E, docs sync, handover (`feat(oauthsso): mapping refinement validation and docs`)

- Full suite `-race`, `task lint`, `task rpc:stale`, `task db:validate`.
- E2E (relevant — the mock providers exist): `tools/e2e-oauthsso/ladder.py`
  gains checks for the extended mapping — a subject-mapped sign-in binding, the
  verified-default value steering the unverified gate, custom attributes
  landing on the user and refreshing on a second sign-in, the avatar download
  setting the picture (the nginx-fronted mock serves an image), and the
  username surviving a second sign-in unchanged. Rows the ladder creates are
  removed in the same turn; the server is stopped.
- Docs sync: `.llms/architecture.md` gains the mapping-decision records;
  `.llms/rules.md` the custom-attributes contract and the seam;
  `.llms/endpoint-reference.md` and `docs/api-endpoint.md` note the widened
  requests; `.llms/auth-design.md` § SSO Connections gains and ticks the
  **Custom attribute mapping** row (status marks only, never prose); the Yaak
  collection audited one last time.
- Handover document (`.llms/handover/handover-*.md`): the decisions and deltas
  from Clerk this round recorded, the remaining follow-ups named (token
  retrieval, provider logos, SPA screens, SCIM inbound sharing
  `users.custom_attributes`).
