# Close the login-toggles decision (`issue-20261009_0127`) — the deployment document keeps them

## Objective

Settle the question the owner parked on 2026-10-09: the three toggles the
login screen gates on (`oidc.enabled`,
`auth.one_time_access_email_as_admin_enabled`,
`auth.one_time_access_email_as_unauthenticated_enabled`) stay where they
are — deployment-file keys published only through the configuration
document — and the boundary between "what the deployment offers" and
"what the administrator can change at runtime" is recorded where the next
reader will look. The issue closes `wontfix`; no code moves.

## Current state (verified in the tree, 2026-10-14)

- **The three keys are deployment-file keys published through the
  document.** `internal/config/publish.go:41` (`PublishedOIDC` — "the
  enable switch is public") and `:82-83` (the two one-time-access
  switches) are fields of the published document; their values come from
  the config file's `oidc` and `auth` sections, never from the database.
- **The settings catalog carries none of them.**
  `modules/appconfig/settings.go`'s `Catalog()` holds twelve `Public`
  keys (`SettingAccessMode`, the signup/sign-in toggles, the users'
  self-service three, the MFA/passkey caps, the OIDC lifetime keys) —
  `oidc.enabled` and the two one-time-access switches are absent, and
  that absence is what the frontend's REST read works around.
- **The frontend reads the document through a hand-shaped zod schema.**
  `packages/webapp/src/libraries/app-config.ts:28-33` —
  `one_time_access_email_as_*_enabled`, `oauth.enabled`, `oidc.enabled`
  with `false` defaults — validated against `GET /api/configuration` and
  served through TanStack Query (`readAppConfig`).
- **The origin decision anticipated this.** plan-20261009_0025 (archived)
  D7 chose the deployment document as the boot/capability source and
  rejected `SettingsService/ListPublic` as "the DB-backed product
  settings catalog, a different surface"; the issue's 2026-10-09 note
  parked the backend move on the owner's word. This plan re-opens and
  settles it with the owner's pick.
- **The two surfaces differ in who owns the truth.** The settings
  catalog is the administrator's runtime-mutable store (the admin
  console edits it through the settings RPCs); the deployment document
  is the operator's word, immutable for the process. A toggle that an
  administrator could flip against the deployment's file would make two
  masters for one login-screen gate.

## Decisions

- **D1 (2026-10-14, owner): the deployment document owns the capability
  toggles.** The login-screen gates stay exactly where they are — config
  file to publish layer to `GET /api/configuration` to the frontend's
  zod-validated read. The settings catalog stays what it is for: the
  product settings an administrator changes at runtime, with defaults the
  seeder writes and the catalog's own keys can express. The distinction
  is ownership, not plumbing: a capability the deployment offers is the
  operator's word and cannot be voted past the deployment by an
  administrator at runtime.
  Rejected: **moving the three keys into the catalog** — an
  administrator could enable OIDC or the one-time-access email against
  the deployment's file, two sources of truth for one gate, and the
  deployment's own answer (`/api/configuration`) would still say the
  opposite unless a read-only-mirror mechanism was built for it.
  Rejected: **a read-only mirror in the catalog** — the same truth kept
  twice, a boot-time projection that can drift, paid forever so one
  fetch seam could be reused.
  Rejected: **moving only the one-time-access keys** — they are as much
  deployment facts as `oidc.enabled` (the switches live in the same file
  section); a split that buys one key buys nothing and blurs the
  boundary it claims to draw.
- **D2 (2026-10-14): the hand-shaped zod schema is the contract, not
  debt.** `app-config.ts`'s shape is the typed view of the document the
  frontend consumes; it changes only when the published document does,
  and the document's Go side is tested (`internal/config` publish tests).
  No parity machinery is built for a shape this stable. Rejected: a
  generated-from-Go schema (a build seam for a ten-line shape) and
  re-publishing the document as a proto (a wire change for the same
  bytes).
