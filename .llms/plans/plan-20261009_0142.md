# OAuth SSO: one store for every provider, the enabled-provider listing, the SPA flow

## Objective

Make the login screen offer exactly the providers the deployment configured —
builtin (Google, GitHub) and custom OIDC alike — driven by one management
store, and wire the sign-in flow the buttons point at. The store question the
owner resolved 2026-10-09: **every provider's credentials and enablement live
in `public.oauth_connections`** (the Clerk shape — one dashboard surface over
all connections, runtime-mutable, secrets sealed at rest); the JSON config
file's only SSO fact is the `oauth.enabled` master switch. The configuration
layer is immutable per process (a change takes a restart) and stays out of
the provider-credentials business; the settings are mutable and live in the
database.

This plan also gives the frontend the **actual** public configuration shape
(today it parses a hand-picked subset) and lands the SPA's missing
`/oauth/callback` route — the redirect target the backend already sends the
resolved browser to.

Flow reference: `.llms/auth-design.md` and `docs/auth.md` (the OAuth SSO
rows) — read 2026-10-09. The Clerk model studied the same day
(`clerk.com/docs` — the SSO-connections dashboard pages, the custom-provider
guide, the `clerk config patch` config-as-code note: config-as-code writes
the same instance store the dashboard does, it is not a process config file).
Deltas from that reference are D1–D8.

## Current state

Every claim read in the code 2026-10-09:

- `modules/identity/oauthsso/builtin/builtin.go` — exactly two builtin
  providers ship: `google` (OIDC id_token verified) and `github` (OAuth2,
  identity from the user API). The definitions map is closed over these;
  the endpoints are the code's own, never stored.
- `modules/identity/oauthsso/custom/custom.go` — the generic OIDC adapter
  for operator-configured connections: endpoints from the row (discovery
  resolution or the operator's manual set), claims from the id_token (the
  userinfo response taking priority when the row names one), the attribute
  mapping naming which claim answers each account field.
- `internal/database/migrations/00015_create_oauthsso_tables.sql:12` —
  `oauth_connections.kind IN ('builtin','custom')`, `client_id`/`client_secret`
  `NOT NULL` (the secret sealed `enc:`), **`UNIQUE(provider)`** — one
  connection per provider slug, so multiple custom providers already rest in
  the table as distinct rows.
- `modules/identity/oauthsso/flow.go:62` (`Begin`) and :137 (`Callback`)
  resolve the connection row by slug and unseal the secret; a missing or
  disabled row answers `ErrConnectionUnavailable`. The connection CRUD
  (`handler_rpc.go:236` `CreateConnection`) already accepts builtin-kind
  connections that carry only their credentials and custom-kind ones with
  discovery or manual endpoints — the CRUD is the management surface
  Clerk's dashboard corresponds to; only its UI is unbuilt.
- The proto carries the split honestly: `OAuthConnection.kind`
  (authn.proto:1240) and `CreateOAuthConnectionRequest.kind` (:1391).
- Guard: `internal/guard/rules.go:180` `OAuthSSOServiceBeginSignInProcedure`
  Public; :602–603 `/oauth/{provider}/start` and `/oauth/{provider}/callback`
  Public.
- `modules/identity/oauthsso/flow.go:26` — `spaCallbackPath = "/oauth/callback"`;
  `FlowRedirect` (:227) sends the resolved browser to
  `/oauth/callback?flow_token=…`. **The SPA has no such route** —
  `routes/(auth)/` holds only `login.tsx` and `forgot-password.tsx`; the
  redirect lands on the SPA's 404 today.
- `ContinueOAuthSignInResponse` (authn.proto:1147) — the token pair when the
  sign-in completes, or the MFA bridge; the same fork the password sign-in
  pauses with. The frontend refuses the MFA half (`unimplemented`)
  deliberately.
- `internal/config/publish.go:303` — `Published(full bool)`: the public
  subset is field-selected (app, the two one-time-access toggles, oidc,
  mailer announcement); secrets cross only through the redaction path. No
  `oauth` section exists. The loader resolves whole-value `env:NAME`
  directives (`framework/config`) — irrelevant under the DB decision, noted
  because the owner's earlier `env:GITHUB_CLIENT_ID` shape rode on it.
- `packages/webapp/src/libraries/app-config.ts` — types a hand-picked
  subset of the public document, not the document itself.
- `packages/webapp/src/routes/(auth)/login.tsx` — the SSO buttons are static
  Google/GitHub placeholders gated by `config?.oidc.enabled` — the wrong
  section (`oidc.enabled` answers whether the deployment federates **as an
  IdP**, publish.go:224; it has nothing to do with signing in through
  Google). No button drives any flow.
- No seeder writes connection rows; no RPC lists the providers an
  unauthenticated caller may see.

## Decisions

- **D1 (2026-10-09, owner) — one store for every provider.** The
  `oauth_connections` table is the credentials-and-enablement store for
  builtin **and** custom connections alike; the connection CRUD is the
  single management surface (the SPA's admin UI is a later phase). The
  config JSON carries only the `oauth.enabled` master switch. This is the
  owner's pick among hybrid / DB-store / config-store, studied against
  Clerk's SSO-connections dashboard. Rejected: hybrid (builtin credentials
  in config, custom in rows — two places to learn, and the immutable
  config's restart semantics are the wrong contract for an operator
  experiment); all-declarative config (buries the working CRUD, sealing,
  and discovery-validation machinery and makes adding a provider a file
  edit plus a restart). The earlier `env:`-interpolated config credentials
  are dropped with this decision — credentials are runtime data; a
  bootstrap/IaC seeding path is future work if a deployment asks.
- **D2 (2026-10-09) — the master switch.** `oauth.enabled` (default `true`)
  joins the config schema and the published public subset. `Begin` refuses
  with `ErrConnectionUnavailable` while the switch is off, whatever the
  rows say — the config gates the surface, the rows decide the providers.
  The switch is immutable per process: turning SSO off for real takes the
  restart the configuration model already prescribes.
- **D3 (2026-10-09) — the enabled-provider listing.** A new public
  procedure `OAuthSSOService/ListEnabledConnections` answers, for an
  unauthenticated caller, the `slug` and `display_name` of every connection
  whose `enabled` is true — the exact facts a login screen renders, one
  button per row. Rejected: baking the provider list into the
  configuration document (the document is resolved once at startup, so a
  runtime enable would need a restart to show up — the wrong store's
  semantics); reusing `ListConnections` (the operator's view carries
  sealed-secret metadata and administrative fields an anonymous caller
  must never see).
- **D4 (2026-10-09) — the SPA drives the flow by navigation.** The login
  button navigates to `/oauth/{provider}/start` — the server's 302 chain is
  the flow's transport (the routes are already Public). The new
  `/oauth/callback` route consumes `flow_token` (→ `ContinueSignIn` through
  the worker engine, custody semantics identical to the password sign-in)
  and `error` codes (→ the login alerts). Rejected: driving `BeginSignIn`
  RPC from the SPA (the REST start is the redirect surface; the RPC stays
  for non-browser callers).
- **D5 (2026-10-09) — the right toggle, corrected.** The login screen no
  longer reads `oidc.enabled`; that key keeps its meaning untouched (the
  OP/federation side) and stays published.
- **D6 (2026-10-09) — the frontend's configuration type mirrors the
  document.** `app-config.ts` types and validates the **actual public
  subset** (app, auth, oauth, oidc, mailer). The configuration is immutable
  per process: the refetch on account flip widens the **scope** (the
  administrator's fuller document), it does not observe a changed
  configuration. Rejected: typing the full document including the
  administrative half (the anonymous login screen never holds it).
- **D7 (2026-10-09) — the builtin slugs stay reserved.** A custom
  connection may not take the slug `google` or `github` (the existing
  collision rule, service.go:27); the two builtin rows are the only rows
  that ride the code's own endpoints. No migration changes this plan — the
  table already fits the decision; the dev database reset stays authorized
  for the test data alone.
- **D8 (2026-10-09) — no backward compatibility.** The static
  placeholder buttons die; the `useAppConfig`'s `oidc`-gated SSO block dies
  with them. The `ContinueOAuthSignInResponse`'s MFA bridge stays refused
  in the frontend (the challenge UI ships later, the standing posture).
- **D9 (2026-10-09, owner) — the settings prefix normalizes to `oauth.`.**
  The settings-catalog key `oauthsso.account_linking_enabled`
  (`modules/appconfig/settings.go:109`, read by
  `modules/identity/oauthsso/resolution.go:34`) renames to
  `oauth.account_linking_enabled`, matching the `oauth.*` family the
  master switch starts. Early-stage: the rename is in-place (the constant
  and the catalog entry), any override row under the old key dies with the
  authorized dev-DB reset — no migration, no alias. Rejected: keeping the
  `oauthsso.` prefix (two prefixes for one feature family is the drift the
  rename exists to end).

## Shape and enforcement points

Config key (`internal/config/schema.go`, `publish.go`, `sample.go`):

| Key | Default | Public |
| --- | --- | --- |
| `oauth.enabled` | `true` | yes |

New procedure (authn.proto, `OAuthSSOService`):

- `ListEnabledConnections(ListEnabledConnectionsRequest{}) →
  ListEnabledConnectionsResponse{ connections: [EnabledConnection] }`,
  `EnabledConnection { slug, display_name }` — guard rule `Public`
  (`rules.go`), answered from `repo` over the enabled rows.

Backend enforcement:

- `modules/identity/oauthsso/flow.go` — `Begin` checks the master switch
  (a config seam beside `WithBaseURL`) before touching the rows.
- `modules/identity/oauthsso/handler_rpc.go` — the new procedure rides the
  existing mount; no rule changes beyond the new Public row.

Frontend surfaces:

- `libraries/app-config.ts` — the actual public shape (D6) + the envelope.
- `hooks/use-oauth-providers.ts` (new) — Connect-Query hook over
  `ListEnabledConnections`, the login screen's provider source.
- `routes/(auth)/login.tsx` — one button per listed provider (display_name
  as the label, the icon by slug for the two builtins, a generic glyph for
  customs), each navigating to `/oauth/{provider}/start`.
- `routes/(auth)/oauth-callback.tsx` (new, public) — `flow_token` → the
  worker engine's `continueSignIn` → the signed-in shell; `error` codes →
  the login alerts; the `verify_email` stage → the surface the flow names.
- `libraries/guard/auth-engine.ts` — `continueSignIn(flowToken)` riding the
  same custody path as `login` (the token pair into the worker, the cookie
  copy, the store), MFA fork refused as today.

Yaak rows: the new `ListEnabledConnections` request/response pair; the
`/api/configuration` body gains the `oauth` section. No contract is removed.
