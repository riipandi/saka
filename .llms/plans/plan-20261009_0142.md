# OAuth SSO by configuration: the `oauth` section, config-backed builtin providers, the SPA flow

## Objective

Close the gap between what the login screen offers and what the deployment
actually configured. The sign-in-with-a-provider buttons are hardcoded
placeholders gated by the wrong toggle, the frontend's configuration types
cover a hand-picked subset instead of the document the backend serves, and
the builtin providers' credentials rest in mutable database rows when the
owner has decided they belong to the deployment configuration. This plan
lands: the `oauth` section in the JSON config (immutable — a change takes a
server restart), the builtin providers (Google, GitHub — the only ones the
code ships) reading their credentials from that section with `env:`
interpolation, the actual configuration shape typed in the frontend, and the
SPA's OAuth SSO sign-in flow wired end to end.

Flow reference: `.llms/auth-design.md` and `docs/auth.md` (the OAuth SSO
rows) — read 2026-10-09. The deltas this plan records are D1–D8.

## Current state

Every claim read in the code 2026-10-09:

- `internal/config/publish.go:303` — `Published(full bool)` builds the
  public subset by field selection: `app.{mode,base_url,timezone}`,
  `auth.one_time_access_email_as_{admin,unauthenticated}_enabled`,
  `oidc.enabled`, `mailer.notifications.announcement_email_enabled`. The
  full scope adds the rest, secrets crossing only through the redaction
  path (`withSecrets` + `publishedSecretRender`, publish.go:332).
- `internal/config/schema.go` — no `oauth` section exists. `OIDC.Enabled`
  (publish.go:224) is the **OP/federation side**: whether this deployment
  acts as an identity provider for relying parties. It has nothing to do
  with signing in through Google or GitHub.
- The config loader resolves whole-value `env:NAME` directives in the file
  (`framework/config`; a directive naming a missing variable is deferred,
  the key keeps its default — `internal/config/config.go:15` onward). This
  is the interpolation mechanism the owner's `env:GITHUB_CLIENT_ID` shape
  rides on; nothing new is needed in the loader.
- `modules/identity/oauthsso/builtin/builtin.go` — exactly two builtin
  providers ship: `google` (OIDC id_token verified) and `github` (OAuth2,
  identity from the user API). The definitions map is closed over these.
- `modules/identity/oauthsso/flow.go:62` (`Begin`) and :137 (`Callback`)
  resolve the connection from `repo.ByProvider` and unseal
  `conn.ClientSecret` — **the credentials live in `public.oauth_connections`
  rows**, created by the operator CRUD (`handler_rpc.go:236`
  `CreateConnection`, secret sealed `enc:`). No seeder writes connection
  rows, so out of the box no provider works until an operator creates one
  through the admin surface.
- `internal/database/migrations/00015_create_oauthsso_tables.sql:12` —
  `oauth_connections.kind IN ('builtin','custom')`, `client_id`/`client_secret`
  `NOT NULL`.
- `api/connect/authn.proto:1240` (`OAuthConnection.kind`) and :1391
  (`CreateOAuthConnectionRequest.kind`) — the contract carries the builtin
  kind; `CreateConnection` (:1072) accepts builtin connections whose
  credentials the operator typed into the admin surface.
- Guard: `internal/guard/rules.go:180` `OAuthSSOServiceBeginSignInProcedure`
  Public; :602–603 `/oauth/{provider}/start` and `/oauth/{provider}/callback`
  Public.
- `modules/identity/oauthsso/flow.go:26` — `spaCallbackPath = "/oauth/callback"`;
  `FlowRedirect` sends the resolved browser to `/?flow_token=…` on that path

  only `login.tsx` and `forgot-password.tsx`; the redirect lands on the SPA's

- `packages/webapp/src/libraries/app-config.ts` — parses a hand-picked
  subset of the public document, not the document itself; the `oidc.enabled`
  key it reads is the one the login screen misuses.

## Decisions

- **D1 (2026-10-09) — the configuration owns the builtin providers.** A
  builtin provider's enablement and credentials come from the JSON config
  file (`oauth.google.*`, `oauth.github.*`), never from a database row. The
  `oauth_connections` table and the connection CRUD become **custom-only**;
  the builtin kind dies — from the table (migration edited in place, dev DB
  reset authorized), from the proto (`OAuthConnection.kind`,
  `CreateOAuthConnectionRequest.kind`), and from the CRUD's rules. Rejected:
  config seeds connection rows at boot (an immutable source copied into a
  mutable store invites drift and a second admin surface to keep honest);
  config values overriding row values by precedence (two sources of one
  truth, resolved silently at request time).
- **D2 (2026-10-09) — key shape.** `oauth.enabled` (master switch, default
  `true`) + `oauth.google.{enabled,client_id,client_secret}` and
  `oauth.github.{enabled,client_id,client_secret}`. Per-provider `enabled`
  defaults to `false`. A provider enabled without both credentials set is a
  loud misconfiguration: `Validate` refuses it at load — an `env:` variable
  left unset stays empty and would otherwise silently disable a toggle the
  operator believed on. Rejected: silent unavailability (the deployment
  restarts to change config; a silent no-op at the login screen is the
  hardest kind to debug).
- **D3 (2026-10-09) — `env:` interpolation defaults.** The code defaults
  for `client_id`/`client_secret` are empty; the sample file
  (`internal/config/sample.go`) carries `env:GOOGLE_CLIENT_ID`,
  `env:GOOGLE_CLIENT_SECRET`, `env:GITHUB_CLIENT_ID`,
  `env:GITHUB_CLIENT_SECRET` — the loader's own directive form, deferred
  when the variable is unset. The two secrets join `secretKeys` (redaction
  path, never printed); `client_id` is administrative, published plain in
  the full scope only.
- **D4 (2026-10-09) — the published `oauth` section.** Public subset gains
  `oauth: {enabled, google: {enabled}, github: {enabled}}` — the exact facts
  a login screen renders. The full scope adds each provider's `client_id`
  (plain) and `client_secret` (redacted). Rejected: publishing `client_id`
  publicly (the browser needs nothing of it), publishing a display-name list
  (the SPA knows the two builtins it ships).
- **D5 (2026-10-09) — the SPA drives the flow by navigation.** The login
  button navigates to `/oauth/{provider}/start` — the server's 302 chain is
  the flow's transport (the routes are already Public, rules.go:602). The
  new `/oauth/callback` route consumes `flow_token` (→ `ContinueSignIn`
  through the worker engine, custody semantics identical to the password
  sign-in) and `error` codes (→ the login alerts). Rejected: driving
  `BeginSignIn` RPC from the SPA (the REST start is the redirect surface;
  the RPC stays for non-browser callers).
- **D6 (2026-10-09) — the right toggle.** `login.tsx` gates the SSO options
  on the `oauth` section, not `oidc.enabled`. The OIDC section stays
  published untouched: it answers whether the deployment federates **as an
  IdP**, a different feature's switch.
- **D7 (2026-10-09) — the frontend's configuration type mirrors the
  document.** `app-config.ts` types and validates the **actual public
  subset** (app, auth, oauth, oidc, mailer) — one shape, kept in step with
  `publish.go` by the contract tests. The configuration is immutable per
  process (a change takes a restart): the refetch on account flip widens the
  **scope** (the administrator's fuller document), it does not observe a
  changed configuration. Rejected: typing the full document including the
  administrative half (the anonymous login screen never holds it).
- **D8 (2026-10-09) — no backward compatibility.** The builtin-kind
  connection rows, the `kind` column, and the proto fields die outright;
  migration `00015` is edited in place and the dev database reset. The
  `ContinueOAuthSignInResponse`'s MFA bridge stays refused in the frontend
  (the challenge UI ships later, the standing posture).

## Shape and enforcement points

Config keys (all new, `internal/config/schema.go`):

| Key | Default | Public |
| --- | --- | --- |
| `oauth.enabled` | `true` | yes |
| `oauth.google.enabled` | `false` | yes |
| `oauth.google.client_id` | empty; sample `env:GOOGLE_CLIENT_ID` | admin |
| `oauth.google.client_secret` | empty; sample `env:GOOGLE_CLIENT_SECRET` | admin, redacted |
| `oauth.github.enabled` | `false` | yes |
| `oauth.github.client_id` | empty; sample `env:GITHUB_CLIENT_ID` | admin |
| `oauth.github.client_secret` | empty; sample `env:GITHUB_CLIENT_SECRET` | admin, redacted |

Published document (`internal/config/publish.go`): `PublishedOAuth` with
`Enabled bool`, `Google PublishedOAuthProvider{Enabled bool}`,
`GitHub PublishedOAuthProvider{Enabled bool}` public; `client_id`/`client_secret`
fill in the full scope. `app-config.ts` mirrors this exactly (D7).

Backend seams:

- `modules/identity/oauthsso` — the `Service` gains the config through a
  constructor-time seam (the way `WithBaseURL` rides today, flow.go:46);
  `Begin`/`Callback` resolve a **builtin** provider into an in-memory
  connection (definition from `builtin.BySlug`, credentials from the config)
  and a **custom** provider from `repo.ByProvider` as today. An
  unavailable builtin (master off, provider off, or credentials empty at
  runtime) answers the existing `ErrConnectionUnavailable`.
- `oauth_connections` — migration `00015` edited in place: the `kind`
  column and the `('builtin','custom')` check die; the table is custom-only.
  The soft-delete triggers and the `oauth_accounts` half stay as they are.
- The CRUD (`handler_rpc.go`) — builtin slugs stay refused for custom
  connections (the existing collision rule, service.go:27); the proto drops
  the `kind` field; `ListConnections`/`GetConnection` answer custom rows
  only.
- Guard rules — no change (the surfaces are already declared).

Frontend surfaces:

- `libraries/app-config.ts` — the actual public shape (D7) + the envelope.
- `routes/(auth)/login.tsx` — one button per `oauth.<provider>.enabled`
  under the `oauth.enabled` master; each navigates to
  `/oauth/{provider}/start`.
- `routes/(auth)/oauth-callback.tsx` (new, public) — `flow_token` → the
  worker engine's `continueSignIn` → the signed-in shell; `error` codes →
  the login alerts; `verify_email` stage → the verify surface the flow
  names.
- `libraries/guard/auth-engine.ts` — `continueSignIn(flowToken)` riding the
  same custody path as `login` (the token pair into the worker, the cookie
  copy, the store), MFA fork refused as today.

Yaak rows: the connection CRUD's request bodies lose the `kind` field
(update the collection rows in the same change); the `/api/configuration`
body gains the `oauth` section. No new endpoint ships — the plan's surface
is one section, one contract slimming, and two SPA routes.

## Execution rules

- Atomic commit per phase is authorized; each phase commits when its
  validation passes, and the commit is limited to that phase's files.
  Self-commits during this plan's working session are allowed; the closing
  state still waits for the owner.
- No backward compatibility, no legacy shims. Migration files are edited in
  place — never `ALTER` — and the development database reset is authorized
  (`task run -- migrate:reset --force --up`, then `migrate:seed --force`).
- Yaak collection updates ride the same commit as the contract change they
  describe.
- Per-phase validation runs before each commit; `task rpc:generate` after
  any proto edit; `task rpc:stale` stays green.
- The standing commit rule resumes when the plan completes; the closing
  phase recommends the final commit messages.

## Explicitly out of scope

- Any additional builtin provider (the definitions map stays Google +
  GitHub — the owner named the support surface as-is).
- Per-provider `scopes` overrides in the config (the builtin definitions'
  default scopes stand; an override is a feature request, not a foundation).
- The SPA's admin surface for custom connections (the CRUD is backend-only
  until a phase builds the UI).
- The OIDC OP/federation side: `oidc.enabled` and the CIMD allowlist keep
  their meaning untouched.
- The settings-catalog migration for the login toggles
  (`issues/issue-20261009_0127.md` stays parked; the backend moves only on
  the owner's explicit instruction).
- An E2E of the full provider round-trip (the builtin endpoints are the
  code's own — pointing them at the mock-oauth2 container would need an
  endpoint-override seam this plan does not add).
- The MFA bridge UI for the SSO flow (the fork stays refused, the standing
  posture).
- HttpOnly cookies (the recorded custody posture).
