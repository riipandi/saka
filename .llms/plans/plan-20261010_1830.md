# Plan — Wave 2: sign-in completeness

## Objective

Close the Wave 2 rows of `.llms/integration-roadmap.md` (read 2026-10-10): the
MFA challenge and enrollment fork, password recovery, one-time access, and
passkeys with the step-up machinery as shared infrastructure. Every account the
backend already serves — MFA-enabled, password-recovering, one-time-accessing,
passkey-holding — becomes one the SPA can carry. The roadmap's flow reference is
the Connect contracts themselves (`api/connect/authn.proto`,
`api/connect/webauthn.proto`, `api/connect/one_time_access.proto`) and
`.llms/rules.md`'s Multifactor and guard sections; the product flows follow
Pocket ID's behavior as the roadmap records it.

## Current state (verified 2026-10-10)

**The backend surface is complete and served.** No proto change, no migration,
and no new procedure is in scope — every procedure the wave consumes exists:

- `api/connect/authn.proto:35` `SignIn`; `:60` `ForgotPassword`; `:68`
  `ResetPassword` (`terminate_sessions` at `:119-124`); `:170`/`:176`

  `ListTotpEnrollments`/`DeleteTotpEnrollment`; `:192` `CompleteSignIn`;

**The step-up machinery exists end to end on the backend, unused by the SPA.**

**The SPA refuses the forks loudly today.** `signIn` throws
`Unimplemented` on `mfaRequired || mfaEnrollmentRequired`
(`packages/webapp/src/libraries/guard/auth-engine.ts:282-291`); `continueSignIn`
does the same for the OAuth path (`:309-325`). No `reset-password` or
`login-code` route exists (the `(auth)` directory holds only `route.tsx`,
`login.tsx`, `forgot-password.tsx`); no `account/security.tsx` exists. The
per-row revoke is deliberately absent with a comment naming this wave
(`-sessions-view.tsx:66`).

**`forgot-password.tsx` is a rendered stub** — the card, the form, and the
copy exist; no backend call is wired.

**The raw materials are in place.** `@simplewebauthn/browser` `^14.0.0` is a
webapp dependency (`packages/webapp/package.json:27`, unused in `src/` yet).
`useAppConfig` already parses the two one-time-access public toggles

published at `internal/config/publish.go:61`). The per-call header channel the
step-up proof rides already exists: the engine's `callHints`/`withHints`

devtool pages) exists and runs under `E2E_BUILD_TAG=debug`.

## Decisions

- **D1 — step-up is proactive at the guarded call sites (2026-10-10).** The
  SPA names the procedures it calls that the rule table guards; the UI opens
  the Reauthenticate modal *before* the guarded call, and the modal's answer
  feeds that one call. The wire's `unauthenticated` for a missing proof stays
  the backstop: the shared error mapping treats `CodeUnauthenticated` on a
  known-guarded procedure as "open the modal", not as a session expiry —
  one mapping site, in `guard/auth-utils`. Rejected: a distinct
  `reauth_required` wire code — it publishes the rule table's shape and
  contradicts the guard's disclosure rule; a global "current reauth token"
  store — mutable state two concurrent guarded calls can race, the same
  reasoning that put the worker's traceparent in per-call headers (Wave 1.6
  D4).
- **D2 — the proof rides the per-call Connect options.** `withStepUp(run)`
  resolves the modal to a token held in the runner's closure, then attaches
  `{ headers: { 'x-saka-reauthentication': token } }` to the guarded call —
  the same channel `callHints` established. No `authFetch` change is needed:
  every StepUp-guarded procedure is a Connect RPC, so the roadmap's "plumbing
  in `authFetch`" lands as Connect call options instead — a recorded delta,
  smaller and true to the seam.
- **D3 — the challenge and the forced enrollment are phases of the login
  flow, never URLs.** `login.tsx`'s view becomes a small state machine
  (credentials → challenge → enrollment → done); the pending bridge
  (`mfa_pending_token`, 5-minute, hashed; the enrollment fork's
  `pending_token`) never appears in the address bar, and back navigation
  restarts the sign-in. Rejected: a dedicated `/mfa` route — a URL that
  carries or implies a live bridge invites refresh-and-replay confusion and
  contradicts the `(auth)` anonymous-only guard, which would bounce a
  half-signed-in caller to `/login` anyway.
- **D4 — the recovery codes are shown once, in a dialog, at the moment the
  backend answers.** `ConfirmTotpEnrollment` and `RegenerateRecoveryCodes`
  render the one-time set in an AlertDialog the user must acknowledge; the
  component state is the only copy. No clipboard convenience, no re-display.
- **D5 — the reset route follows the verify-email pattern.**
  `reset-password.tsx` consumes `?token=` from the search params the emailed
  link carries, spends it with `ResetPassword`, and lands the user on
  `/login` with a success notice — `terminate_sessions` defaults to true, so
  the old session is dead anyway and the custody path must not pretend
  otherwise. The `expose_reset_token` development aid surfaces in the
  forgot-password success state (token + a prefilled link) when the public
  document carries it.
- **D6 — one-time access enters from the login page and lands in the
  existing custody path.** The login flow gains a "sign in with an email
  code" entry (gated by `one_time_access_email_as_unauthenticated_enabled`);
  `/login-code` consumes `?code=` through `ExchangeToken`, whose token pair
  enters custody exactly as a sign-in's does (`persistTokens`), then routes
  to the overview. The admin toggle
  (`one_time_access_email_as_admin_enabled`) does nothing here — admin
  issuance is Wave 3.
- **D7 — E2E covers the three token-bearing flows; passkeys stay on the
  ladder.** One new workflow file (`sign-in-completeness.test.ts`) drives the
  MFA challenge (with `otpauth` as an `e2e-tests` devDependency, as the
  roadmap's Adopt row already plans), the password reset, and one-time
  access. Passkeys need a virtual authenticator the CI suite does not
  manage; they keep the debug-build ladder and gain browser-mode unit
  coverage instead. Rejected: a CI passkey flow — the WebAuthn ceremony
  needs CDP virtual-authenticator plumbing that belongs to the ladder, not
  the suite.
- **D8 — the engine's API grows by named outcomes, not exceptions for
  control flow.** `signIn` returns a discriminated result
  (`{ kind: 'signed-in' } | { kind: 'mfa-challenge', ... } |
  { kind: 'enrollment-required', ... }`); the same shape serves
  `continueSignIn`. The worker gains the matching ops (`auth complete-sign-in`,
  `auth begin-totp-enrollment`, `auth confirm-totp-enrollment`,
  `auth exchange-one-time-token`) — user-caused, span-wrapped by the facade.
  `accessToken`/`authorization` and the anonymous ceremony calls
  (`ForgotPassword`, `RequestEmail`) stay uninstrumented or facade-free per
  the Wave 1.6 seams.

## Execution rules

- **Atomic commit per phase is authorized** for this plan; each phase's
  heading below names its suggested commit message, and the plan's
  frontmatter `status`/`note` rides the same commit. Self-contained commits
  during the plan session are allowed.
- **Execution waits for the owner's explicit instruction** — the plan does
  not start because it exists.
- **No migration and no backend schema change are in scope.** The dev
  database may be reset if a phase's validation needs a clean state; no
  `ALTER` is written.
- **No backward compatibility, no legacy shims** — the loud
  `Unimplemented` refusals in the engine are replaced outright.
- **Per-phase validation runs before each commit** (see the matrix). The
  standing commit rule resumes when the plan completes; the closing phase
  recommends the final commit message and stops for the owner.
- **Yaak**: no new procedures ship, so no new rows are owed; phase 8
  verifies the existing rows for the procedures the SPA newly covers instead.
- **Comments** carry invariants and traps only; test fixtures follow the
  Dan Brown / Harry Potter convention; test names stay behavioral.

## Phases

### Phase 1 — fix(auth): the step-up machinery and its first consumer

`#/libraries/reauth` (the guarded-procedure list, `withStepUp(run)`, the
`unauthenticated`-on-guarded mapping in `guard/auth-utils`), the
Reauthenticate dialog (three factors; `SendReauthenticationCode` behind the
email-code factor), and the sessions center's per-row revoke: the row action
opens the modal, spends the proof on `RevokeSession`, and the row's revocation
lands without a page reload. Browser tests cover the modal's password factor
and the revoke wiring; unit tests cover the runner and the mapping.

prove the untouched backend stays green.

### Phase 2 — feat(auth): the sign-in fork — challenge and enrollment

The engine's `signIn`/`continueSignIn` discriminated outcomes (D8) and the
`completeSignIn`/enrollment methods; the login flow's state machine renders
the TOTP challenge (the countdown from `mfa_pending_expires_at`), the
recovery-code factor, and the forced-enrollment phase (begin → QR → confirm →
recovery codes shown once per D4 → the sign-in completes). The worker gains
the new ops. The loud refusals die.

Validation: webapp `unit` + `browser`, `tsc`, `task lint`.

### Phase 3 — feat(webapp): the security page — MFA and password management

`account/security.tsx` + `-security-view.tsx`: the TOTP device list with

recovery-code view-once dialog and regeneration, `DisableMfa`, and
`AddPassword`/`RemovePassword` — every destructive action behind D1's modal.

Validation: webapp `unit` + `browser`, `tsc`, `task lint`.

### Phase 4 — feat(auth): passkeys — sign-in, enrollment, credentials

The login flow's passkey entry (`BeginLogin`/`VerifyLogin` via
`@simplewebauthn/browser`'s `startAuthentication`), enrollment
(`BeginRegistration`/`VerifyRegistration`), and the credential roll on the
security page (list, rename, delete with the strand rule) — plus

cover the request/response shaping; browser tests cover the enrollment
dialog against the browser-mock pattern established in Wave 1.6.

Validation: webapp `unit` + `browser`, `tsc`, `task lint`.

### Phase 5 — feat(auth): password recovery routes

`forgot-password.tsx` wired to `ForgotPassword` (the always-success contract,

### Phase 6 — feat(auth): one-time access
