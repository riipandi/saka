# Auth alignment plan: auth-design.md vs the shipped surface

Written 2026-10-01. Executed later; nothing in this plan is implemented yet except what the
gap matrix names as already present. The audit ran against the tree at `522855b`. Every
decision in the decisions table was confirmed with the user in the same session; the two
choices still open are named in "Remaining decision points" and the owning phase pauses
rather than silently choosing.

## Objective

Bring the shipped authentication surface in line with `.llms/auth-design.md`, backend
first, for the owner's focus areas only: user & authentication, passkeys, user model,
multi-factor, access mode, sessions. The spec's deferred sections (phone, waitlist,
multi-session, advanced rules, blocklist, email templates) and SMS MFA and native
biometrics are skipped throughout. SSO account linking is out of scope here.

## Decisions (confirmed 2026-10-01)

| Fork | Decision |
|---|---|
| Where new auth policy items live | **Settings DB** (`public.settings` via `modules/appconfig`), not the JSON config — the catalog pattern `oidc.*` / `webauthn.*` already established; runtime-editable, audited, `Public` flag for the SPA |
| Session lifetimes | **Move to settings DB** as `session.max_lifetime` / `session.inactivity_timeout` / `session.reverification_window`; `auth.refresh_short_ttl` + `auth.refresh_long_ttl` are deleted without a shim (repo rule: no compatibility shims). Confirmed 2026-10-01: the refresh keys die in Phase 1 with the reader rewired; `auth.access_ttl` stays in internal/config (Phase 5: the access-token TTL remains a deployment concern). Durations rest as integer seconds; bounds: max lifetime 5 min–10 years, inactivity 5 min–1 year. |
| Breached-password check | **Implement it flat over `internal/fetcher`** (confirmed 2026-10-01, corrected 2026-10-01 17:10: not an adopted dependency — the client's full surface is not needed and the Resty client fits this architecture): the Pwned Passwords k-anonymity range API — SHA-1 prefix of 5 on the wire, padded answer, suffix scan. The deployment config gains a secret key (`auth.hibp_api_key`, default empty, resolved through the env table as `env:HIBP_API_KEY`, listed in `secretKeys` + `.env.example`). The feature is optional: an empty key (or an API error) skips the check — sign-up, change, and sign-in proceed unchecked, one warning logged, no refusal path depends on the service. |
| Strength meter + bot protection | **Deferred** (confirmed 2026-10-01): no zxcvbn port this round — `password.min_strength` stays a catalog key with no enforcement until the meter lands (`TODO(strength)`); captcha/Turnstile stays out with bot protection. |
| Access mode scope | **Two modes**: `open` and `invite` (today's token path), allowlist as a toggle on open; waitlist deferred |

## Execution rules

- The agent is **authorized to create atomic commits during this plan** — one commit per
  validated phase (or finer where a phase names a boundary); stage explicit paths, never
  push, never destructive Git commands. An atomic commit ships complete: code, its tests,
  its contract (proto + Yaak), and its docs land together or the commit waits.
- **Rework debt is marked, never silent.** Work a phase defers to a later rework — a
  shortcut, a partial implementation, a known-better design not shipped — gets a
  `TODO(<scope>)` or `FIXME(<scope>)` marker in the code where the debt lives, stating
  what and why (repo comment rules apply: what the code cannot say, no phase markers).
  The phase's frontmatter note and the handover list every marker it left behind.
- **Flow reference duty — Clerk shapes the flow, Pocket ID owns the technology.**
  `.llms/auth-design.md` follows Clerk's flow semantics, not Clerk's implementation;
  the project's basis is Pocket ID. Before implementing any flow (Phases 2–5), the
  owning phase reads, for every flow it touches, the matching Clerk documentation —
  the agent index at <https://clerk.com/docs/llms.txt>, entry points
  <https://clerk.com/docs/nextjs/getting-started/quickstart> and
  <https://clerk.com/docs/guides/development/custom-flows/overview>, plus each flow's
  page from that index (sign-up, sign-in, sessions, MFA, users) — and the matching
  Pocket ID surface: `.llms/pocket-id-api-reference.md`, the identity sections of
  `.llms/architecture.md`, and the upstream source when the reference is thin.
  Where the two disagree, the flow's shape follows Clerk and the mechanism follows
  Pocket ID; a deviation is named in the phase's note, never absorbed silently.
- **Every design item is a setting.** Each actionable item in `.llms/auth-design.md`
  maps to a configurable key in the `modules/appconfig` `Catalog()` — global behavior
  becomes a global setting, account-scoped behavior (self-delete opt-in, MFA
  enrollment) becomes a per-user preference column — so an operator flips the behavior
  without a deploy. Phase 1 seeds the catalog from the design doc; Phases 2–5 wire
  their behavior to their keys and never hardcode a toggle the doc lists; Phase 6's
  audit ends with a coverage pass — a design item with no setting behind it fails.
  The auth settings are **admin-only**: the management surface rides the existing
  `Admin` guard rules on the Settings procedures, and a public read answers only the
  `Public: true` family — every other auth key is invisible before sign-in.
- **Frontend stays out of scope.** Where a behavior needs a screen, the phase delivers
  the backend + contract and marks the UI work `TODO(frontend)` in the endpoint reference.
- A phase that touches a proto procedure updates the matching Yaak request
  (`api/specs/`, `yaak update --json`, id inside the payload) in the same change,
  dropping `(unimplemented)` when a procedure ships. A shipped procedure without a
  matching request entry is an incomplete phase. The reference surfaces are
  `docs/api-endpoint.md` (people-facing), `.llms/endpoint-reference.md` (agent-facing),
  and the `api/specs/` sync mirror (the checklist) — all three read before a contract
  edit, all three brought current by the phase that moved the contract, and Phase 6
  audits them against the shipped surface.
- New setting keys land in the `modules/appconfig` `Catalog()` with a default and a
  validate rule at the reader — never a process-level config key. The deleted JSON keys
  leave `types.go`, `defaults.go`, `validate.go`, `keys.go`, the sample, and the schema
  tests in the same commit that rewires their last reader.
- Migrations edit the identity DDL in place (repo rule: no `ALTER` history — the
  migration file that created the table is edited directly); table modifications and
  a development-database reset are permitted during this plan (`task db:reset --
  --force --up`, then `task db:seed -- --force`), and a reset is allowed only for
  state this plan created. Deletion flows
  reuse the schema's soft-delete capture — `fn_soft_delete()` +
  `public.deleted_records` (migration `00001`) — by attaching
  `CREATE TRIGGER trg_<table>_soft_delete BEFORE DELETE ... EXECUTE FUNCTION fn_soft_delete()`
  to the tables a flow deletes from (in-place, alongside the table's DDL); a flow must
  not invent a parallel archive mechanism, and `deleted_records` rows are never
  queried by product features without an owner decision.
- **Comments carry no vendor names.** Code, comments, and identifiers never mention
  Clerk or Pocket ID — the flow research lives in the plan and `.llms/` prose; the
  codebase speaks only its own vocabulary. Audit-event names, setting keys, and
  endpoint descriptions follow the same rule.
- **No magic links, no verification links.** Every email-delivered artifact is a

  invitation. No phase builds a link-based channel, not even as a fallback; the
  `onetimeaccess` code path is the only email sign-in channel. The removed
  "Email link" items in `.llms/auth-design.md` stay removed.
- Guard rules go in `internal/guard` (new procedures stay `Public`/`Self` as the phase
  names), audit events named in `internal/audit` inside the causing transaction.
- Each phase validates on its own before it commits: build, `task lint`, focused suite,

## Phase 2 — Access mode + open sign-up

- `Signup` branches on `access.mode`: `invite` = today's token path; `open` = no token.
  `SignupRequest.token` loses its `min_len`; proto alone cannot express the mode, so
  the service owns the conditional check.
- Allowlist filters sign-up identities when open mode is on; the refusal is
  `not_found`-shaped per guard semantics (no account-existence leak).
- Username becomes conditional: `auth.signup_username_enabled` off → field optional
  (empty stored per column semantics, pattern applies only when present);
  `auth.require_username` forces it when the toggle is on.
- Email verification at sign-up: when `auth.verify_email_at_signup` is on, the account
  is created unverified, a verification code is issued in the same transaction, and
  sign-in refuses unverified accounts with a distinct error the SPA can route to the
  verification screen. The existing token machinery (`PurposeEmailVerification`) is
  reused; the sign-in read checks `users.verified` beside the password hash.

## Phase 3 — Password policy

- `password.Validate` reads `password.min_length` and the four char-rule toggles from
  settings (call sites: signup, password change, recovery, admin create).
- Breached-password check rides the Pwned Passwords range API — **implemented
  flat over `internal/fetcher`** (the Resty client, the circuit breaker the
  dead upstream needs), not as an adopted dependency: k-anonymity is one GET,
  `range/{prefix}` — the SHA-1's five hex characters — and a padded
  `SUFFIX:COUNT` answer to scan. The deployment config carries the secret
  `auth.hibp_api_key` (default empty, env-table interpolation `env:HIBP_API_KEY`,
  listed in `secretKeys` and `.env.example`, schema entry from `config:generate`).
  **The feature is optional and fails open**: the range API needs no key, so an
  empty key or an API error skips the check with one warning (the password is
  never logged — the fetcher owns that rule), and no refusal path depends on
  the service answering. On a positive count: refused at sign-up and password
  reset, flagged at sign-in (the deviation below still stands until the owner
  says otherwise).
- Strength meter **deferred** (confirmed 2026-10-01): no zxcvbn this round.
  `password.min_length` and the char rules are the whole sign-up gate;
  `password.min_strength` rests in the catalog unenforced, marked
  `TODO(strength)` at the validate site, until the meter lands.
- Spec deviation to confirm at implementation: the spec rejects compromised passwords
  at sign-in too. The plan implements verify-then-flag — a verified-but-breached
  password opens the session flagged and forces a password change — because a full
  rejection hands attackers an oracle.

## Phase 4 — User model completion

- Self-service delete behind `users.self_delete_enabled` plus a per-user override
  column (in-place DDL edit). Procedure `DeleteMyAccount` (guard `Self`) runs a real
  `DELETE` on `users` with the schema's `fn_soft_delete()` trigger attached, so the
  whole row is captured as JSONB in `public.deleted_records` (migration `00001`) —
  the recovery record — while the operational side effects stay the admin delete's:
  sessions ended, audit recorded inside the same transaction (the audit names the
  account in `resource_type`/`resource_id` per the `ON DELETE SET NULL` convention),
  and dependent rows resolved by their own table rules. The trigger is attached to
  the identity tables a delete cascades through, so the capture is complete.
- Username change: `ProfileParams` grows `Username` behind
  `users.change_username_enabled`; uniqueness comes from the existing column; audit
  event `user_username_changed`.
- Email change wraps the existing flow in `users.change_email_enabled` (off = the
  procedure refuses `not_found` per guard semantics).

## Phase 5 — Require-MFA + session semantics

- `mfa.required`: at sign-in and after sign-up, an account with zero confirmed factors
  is routed to enrollment — a pending state that mints no access token until a factor
  is confirmed (the existing bridge fork is the per-account case; this is the global
  gate above it). Admin accounts are not exempt unless a later decision says otherwise.
- `session.max_lifetime` replaces `refresh_long_ttl` (deleted with its sibling in
  Phase 1, where the mint was rewired) as the remembered session bound; the
  non-remembered path collapses into the same maximum. Token minting reads the
  cached getter, so a change lands at the next mint.
- `session.inactivity_timeout`: the session store compares the row's last activity
  against the timeout on every refresh/mint; an idle-expired session is refused and
  rotated out. The access-token TTL stays a deployment concern (it bounds a stolen
  token's blast radius, not user experience).
- `session.reverification_window`: `reauthTTL = 5 * time.Minute` in
  `modules/identity/webauthn/service.go` is replaced by the setting (default 30 m),
  read through the cached getter.

## Phase 6 — Final validation, comprehensive E2E, docs, handover

- Full suite: `go test ./... -count=1 -race`, `task lint`, `task rpc:stale`,
  `task db:validate`, frontend typecheck. Every matrix row below must trace to a test
  that ran in this phase's commit.
- Wire-level E2E ladder against `build/release/tango serve --env-file=.env.local` over
  a disposable database (reset in the same session), one concern per probe, mirroring
  the `tools/e2e-passkey` pattern:
  1. open-mode sign-up (no token) → verification code issued → sign-in refused until
     verified → verify → sign-in → session pair minted;
  2. invite-mode sign-up with a valid token, and the negative set (expired, spent,
     unknown token);
  3. allowlist on → refused address, allowed address passes;
  4. username toggles: optional-off (sign-up without username), require-on (missing
     username refused);
  5. password policy: each char rule, min length from settings, breached password
     (HIBP fixture or stubbed fetcher), strength floor;
  6. `mfa.required`: factor-less sign-in routes to enrollment, no token minted,
     TOTP confirmed → sign-in completes; recovery code spends once;
  7. sessions: max lifetime honored, inactivity timeout expires an idle session,
     reverification window gates a step-up procedure and expires on schedule;
  8. user model: username change, email change, self-delete off (refused) and on
     (account gone, sessions ended, audit names the resource, the row readable from
     `deleted_records`).
- Docs brought current in the same phase: `api/specs/` Yaak collection (every shipped
  procedure, `(unimplemented)` dropped), `.llms/pocket-id-api-reference.md`,
  `.llms/endpoint-reference.md`, the auth sections of `.llms/architecture.md`,
  `docs/api-endpoint.md`; README only if a setup step changed. The audit closes with a
  three-way pass over the surfaces the execution rules name — `docs/api-endpoint.md`,
  `.llms/endpoint-reference.md`, `api/specs/` — where each of the 212 mirror files
  either matches a shipped procedure or names a scaffold one, and a procedure shipped
  without its mirror entry fails the phase. The same pass covers the settings rule:
  every item in `.llms/auth-design.md` traces to a catalog key or a per-user

- Handover: a fresh `.llms/handover-<date>_<time>.md` via the `handoff` skill — state,
