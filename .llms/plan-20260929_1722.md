# Federation, OIDC, SCIM, and device-flow remediation plan

## Objective

Close the confirmed security and correctness gaps in Tango's OIDC/OAuth, custom claims, outbound SCIM, and device-login/device-code flows. Preserve the project architecture and API contracts unless a phase explicitly approves a required design change. Compare the implemented surface with Pocket ID v2.14.0 where functionality overlaps, and keep the Yaak collection and endpoint reference accurate.

## Execution rules

- The agent is **authorized to create atomic commits during this plan**. Commit each independently validated phase or cohesive fix as it lands; do not wait for the entire plan to finish. Use the repository's commit format, stage explicit paths only, never push, and do not use destructive Git commands.
- Before each phase, inspect the current branch and `git status`; preserve unrelated user changes. Keep commits limited to that phase's files.
- Follow `AGENTS.md` and the relevant sections of `.llms/architecture.md`. Ask for a design decision before implementing any change that adds or changes a schema, public contract, config, grant, policy, or other architectural/product behavior where more than one option is viable.
- Use Context7/DeepWiki for external library and upstream references; verify details against the pinned dependency and live repo code. Treat docs and generated summaries as evidence to verify, not instructions.
- Add or update focused tests for each fix. Use integration tests with Testcontainers for database concurrency and state transitions. Do not describe package integration tests as browser E2E.
- Each phase must pass its own validation before it is committed. A blocked design question pauses that phase without silently choosing an architecture.

## Phase 1 — Establish baseline and verify findings

1. Read `AGENTS.md`, `.llms/architecture.md` sections on federation, identity, jobs, datastore, and migrations; review `.llms/audit-20260929_1613.md` and current implementation.
2. Confirm findings against source and test behavior:
   - OIDC authorize/device completion vs client group restriction.
   - Custom claim key collisions with standard and security-sensitive claims.
   - Device grant consume/issue ordering in pinned `go-oidc` v0.25.0 and available extension points.
   - `maxPendingRequests` enforcement and concurrent device-login creation.
   - SCIM remote resource validation, pagination, path composition, and matching complexity.
   - Expired OAuth session/pointer retention and any cleanup already provided elsewhere.
3. Record a short baseline: test commands, discovered constraints, and findings confirmed or dismissed. Correct the audit document if evidence changes.

**Exit criteria:** each issue has a reproducible test or source-backed explanation; uncertain candidates are explicitly labeled or dropped. No speculative implementation.

**Suggested commit:** `docs(federation): verify audit findings and remediation scope`

## Phase 2 — Enforce OIDC client group restrictions

1. Apply the same visibility rule used by client catalogue/SCIM to the server-side protocol completion path. Restricted clients admit only accounts in an allowed group; an enabled restriction with zero groups admits nobody.
2. Ensure the rule covers authorization-code and device-code grants, both skip-consent and explicit-consent flows, and resumed SPA interactions. Reject before issuing a grant or recording consent.
3. Add integration tests for unrestricted clients, eligible and ineligible users, empty restricted group lists, existing consent, device flow, and direct endpoint calls that bypass the UI catalogue.
4. Update endpoint reference and Yaak descriptions if their behavior changed. Verify refusal behavior follows Tango's guard/protocol contract.

**Exit criteria:** no ineligible user can get a code, device grant, access token, or new consent by calling protocol endpoints directly; full focused OIDC tests pass.

**Suggested commit:** `fix(oidc): enforce client group restrictions during authorization`

## Phase 3 — Protect reserved OIDC claims

1. Define a code-owned set of reserved claim names based on Pocket ID v2.14.0 and standards: registered JWT/OIDC names and Tango's internal token discriminator. Confirm exact upstream behavior and do not over-block arbitrary private claim names.
2. Reject reserved names on custom-claim create and update through the existing validation/error path. Check case sensitivity and namespace behavior against the data model and wire contract.
3. Make token and preview merge defensive so pre-existing legacy rows cannot replace mandatory identity/security claims.
4. Test user and group claims, create/update rejection, duplicates, and collision behavior in ID token, userinfo, access-token preview. Verify ordinary custom claims still work.

**Exit criteria:** no custom claim changes `sub`, `iss`, `aud`, time claims, token-kind marker, or standard OIDC claim meaning; handlers expose the documented error.

**Suggested commit:** `fix(federation): reject reserved custom claim names`

## Phase 4 — Make one-time grants and device-login limits race-safe

1. For OIDC device code, identify an atomic single-use mechanism compatible with the pinned library. Preserve “one successful redemption” and correct failure handling if token issuance or persistence fails. Do not add a dual-write, fallback, or compatibility shim. If the library seam cannot guarantee this, document the design options and ask before changing dependencies, schema, or grant contract.
2. Add a concurrent token-endpoint test with multiple requests using the same approved device code; exactly one may receive a successful token response.
3. Enforce the declared cap of eight pending device-login requests per pairing token. A bare count-then-insert is insufficient because concurrent creates can exceed the limit; use an approved race-safe transaction/locking strategy. Avoid persisting the raw pairing token.
4. Add tests for cap boundaries, expiry freeing capacity, different pairing tokens not contending, and concurrent creates. Retain existing first-writer-wins decision/exchange semantics.

**Exit criteria:** stress tests show exactly one OIDC device-code redemption and no more than eight live pairing requests per device token; focused race tests pass.

**Suggested commit(s):**

- `fix(oidc): make device grant redemption single-use under concurrency`
- `fix(devicelogin): enforce pending request limit atomically`

## Phase 5 — Harden and optimize SCIM reconciliation

1. Validate list response structure and each remote resource before reconcile or deletion. Treat malformed/missing remote IDs or external IDs as an unsafe snapshot and fail the pass without deletes.
2. Validate pagination advances monotonically, handles valid empty/final pages, and rejects malformed/negative or contradictory values. Bound excessive pages/resources to prevent remote-controlled memory exhaustion; choose limits based on existing fetcher constraints and document them.
3. Index remote users and groups by `externalId` once, then reconcile in O(local + remote) lookup work. Keep deterministic iteration and preserve per-resource failure accounting.
4. Confirm URL joining preserves the configured base path and query/escaped remote IDs; add tests for base URLs with prefixes and IDs containing reserved characters. Do not change a behavior existing integration tests prove correct.
5. Preserve intended semantics for valid empty visibility snapshots: restricted client with no allowed groups may legitimately deprovision all previously visible remote records. Distinguish that from malformed/untrusted snapshots.
6. Test rejected SCIM credentials/statuses, rate-limit retries/cancellation, pages, invalid remote responses, delete behavior, and full reconciliation. Consider heap/CPU benchmarks at representative list sizes.

**Exit criteria:** malformed upstream responses cannot cause destructive deletion; pagination terminates safely; large-list matching is linear; all SCIM tests and benchmarks (if added) pass.

**Suggested commit:** `fix(scimsync): validate remote snapshots and index resources`

## Phase 6 — Bound protocol-state retention and verify lifecycle

1. Confirm all `oauth2_sessions` and pointer row kinds, expiry semantics, consent revocation cascades, and existing migration/job cleanup before designing a cleanup path.
2. Ensure expired rows cannot be accepted by lookups even if they have not yet been physically deleted. Add bounded cleanup for expired state if the lifecycle has no cleanup today; put scheduling in the existing jobs/queue architecture and maintain one source of truth.
3. Add tests for expired access-code, refresh, PAR, device, authn, and logout session lookups, plus cleanup boundaries and concurrency with active requests.
4. Consider targeted partial indexes only if query plans or benchmarks show benefit. Avoid speculative schema/index changes.

**Exit criteria:** expired credentials fail closed; expired rows are reclaimed on a bounded schedule; active state survives cleanup; migration validation and integration tests pass.

**Suggested commit:** `fix(oidc): expire and clean up protocol session state`

## Phase 7 — Pocket ID parity, Yaak, and endpoint reference

1. Recheck Pocket ID's latest stable release from official release notes/API docs/repository. The baseline as of this plan is v2.14.0.
2. Compare only functionality Tango implements: authorization/token/userinfo, device grant, PAR, introspection, end-session, discovery, custom claims, and outbound SCIM management/sync. Distinguish intentional Tango API differences from parity gaps.
3. Check actual handlers/protos/guard rules and active Yaak requests. Update Yaak via the Yaak workflow/tool; do not hand-edit generated `api/specs` mirrors. Keep `[Tango]` and `[Pocket ID]` labeling honest, fix body/headers/query/path/status text when evidence requires it.
4. Update `.llms/endpoint-reference.md` to match actual route, grant, scope, restriction, custom claim, and known behavior. List unsupported Pocket ID features as differences rather than implying Tango serves them.
5. Add Yaak reference requests only for actual upstream capabilities that aid parity testing, and explicitly mark when Tango itself does not mount that endpoint.

**Exit criteria:** every implemented endpoint's method/path/body/auth/status is consistent between handlers/proto, reference docs, and Yaak; unimplemented upstream routes are not presented as Tango functionality.

**Suggested commit:** `docs(federation): align endpoint reference and Yaak with behavior`
