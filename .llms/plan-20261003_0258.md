# Plan — OAuth SSO sign-in: Google, GitHub, custom OIDC

Written 2026-10-03. Phases 1–3 have landed; the resolution, the account
surfaces, and the closing validation remain. The plan opens when the
owner approves it; the five decision points in "Remaining decision points" pause their
owning phases rather than being chosen silently.

## Objective

Sign in with external identity providers — builtin Google and GitHub, plus
operator-configured custom OIDC connections — as first-class citizens of the existing
authentication surface. The flow follows Clerk's semantics; the mechanism is this
repo's own. Every resolved identity opens its session through `signin.IssueSession`,
honours the MFA fork, links accounts by verified email, and stores provider tokens
sealed.

## Scope

- **In**: builtin `google` and `github` connections, custom OIDC connections (discovery
  or manual endpoints), the outbound authorization-code flow with PKCE, account
  linking by verified email, JIT sign-up (per decision point 1), the missing-requirements
  continue step for names, provider token storage (sealed, no retrieval API yet),
  user-facing linked-connection management (list, unlink), admin connection CRUD.
- **Out**: SAML and enterprise SSO, directory sync, provider logos (the
  `oidc-logos` key pattern stays the federation feature's), social login on the SPA
  screens beyond `TODO(frontend)` markers, a provider-token retrieval API, webhooks.
- `.llms/auth-design.md` § SSO Connections ("Account linking", default true) is the
  design row this plan closes; the row is ticked in Phase 6.

## Decisions (confirmed with the owner, 2026-10-03)

| Fork | Decision |
|---|---|
| Client libraries | **`golang.org/x/oauth2` + `github.com/coreos/go-oidc/v3`** (locked). `luikyv/go-oidc` is the OP engine and has no client package; `markbates/goth` rejected (framework session model); `zitadel/oidc` rejected (RP certification not a target — GitHub is OAuth2-only anyway, so no single library covers every provider). |
| Package layout | `modules/identity/oauthsso/` root holds the feature (schema, repository, service, module, the provider interface) with `builtin/` (google, github adapters) and `custom/` (the generic OIDC adapter) beneath it. The root is the only thing the area imports; the adapters satisfy the interface. |
| Account linking | A user may hold several linked connections. The linking path depends on how the account came to be — an OAuth-created account and a password/passkey-created account are distinct cases the resolution phase separates. |
| Verified email mandatory | Clerk semantics: automatic linking and JIT sign-up proceed only on a **provider-verified** email. An unverified provider email routes through an email-code verification step (the existing `email_verification` shape — a code, never a link) before the link or creation completes. |
| Required names | The **continue step**, not auto-fill: when the provider supplies no given/family names and the account needs them, the flow pauses with its missing requirements and the client collects them. |
| Provider tokens | Access/refresh tokens are stored **sealed with the application cipher** (`crypto.NewCipherFromHex(c.App.SecretKey)` — the SCIM-token half of the two-cipher rule; the auth cipher stays for account-authentication material). Retrieval endpoints are out of scope this round. |
| Flow authority | Where Clerk's flow and this repo's mechanism disagree, Clerk's shape wins and the deviation is named in the phase's note, never absorbed silently. |

## Decision points (settled with the owner, 2026-10-03 03:20 UTC+7)

1. **JIT provisioning — follows the access mode.** A provider identity matching no
   account creates the account when `access.mode = open` (allowlist and blocklist
   still gate the identity); `invite` mode answers the standard sign-up refusal.
   Clerk's sign-in-or-up shape; no second toggle.
2. **MFA after OAuth — enforced like the password path.** A resolved account keeping
   a confirmed TOTP factor mints the pending bridge through the `mfaGate`; the answer
   carries the challenge, not a session. OAuth is a first factor, never a replacement
   for the second.
3. **Unlink stranding — allowed, password demanded first.** Unlinking proceeds
   freely while the account keeps another credential (a second linked connection, a
   passkey). Unlinking the **last** connection on an account with no password and no
   passkey is refused with `failed_precondition` until the holder sets a password —
   the owner's pick, softer than the webauthn refusal: the way back in is one
   procedure away, and the refusal names it.
4. **Connection configuration — settings database.** Client ids, secrets, discovery
   and manual endpoints, and scopes live in `public.settings` through
   `modules/appconfig`, secrets sealed `enc:` with the app cipher — the `oidc.*`
   catalog pattern, runtime-editable, audited.
5. **Contract shape — one service.** `tango.authn.v1.OAuthSSOService` in
   `api/connect/authn.proto` carries start, continue, complete, linked-account
   list/unlink, and admin connection CRUD; the guard table splits
   `Public`/`Session`/`Admin`, the way `MultifactorService` and `WebAuthnService`
   already mix rules on one service.

## Execution rules

- The agent is **authorized to create atomic commits during this plan** — one commit
  per validated phase (or finer where a phase names a boundary); stage explicit paths,
  never push, never destructive Git commands. An atomic commit ships complete: code,
  its tests, its contract (proto + Yaak), and its docs land together or the commit
  waits. **The closing state is not committed on the agent's own hand**: when every
  phase has landed, the agent stops, reports the outcome, and recommends the commit
  message and paths for the owner's approval. Starting this plan also waits for the
  owner's explicit instruction.
- **Migrations edit the new DDL in place** (the plan's own migration files are edited
  directly, never `ALTER` history); a development-database reset is permitted
  (`task db:reset -- --force --up`, then `task db:seed -- --force`) for state this
  plan created. Deletion flows attach the `fn_soft_delete` trigger beside the table's
  DDL — connections and linked accounts join `public.deleted_records`.
- **Comments carry no vendor names.** Code, comments, identifiers, setting keys, and
  audit-event names never mention Clerk or the client libraries' marketing names; the
  codebase speaks its own vocabulary (`oauthsso`). Flow research lives in this plan.
- **Every toggle is a catalog setting.** Behavior switches (JIT, linking, the
  feature's enablement) land in `modules/appconfig` `Catalog()` with defaults and
  reader bounds, admin-only, never hardcoded.
- **Guard rules go in `internal/guard`.** Every REST route this feature mounts under
  `/api` gets a `RestRules` entry — an undeclared route answers `not_found`, so the
  start and callback paths must be declared. Audit events are named in
  `internal/audit` and recorded inside the causing transaction.
- **Single-use consumption lives in the `UPDATE`'s `WHERE`.** Flow-state rows are
  consumed by a guarded conditional, never a read-then-write pair; no
  `UNIQUE(user_id)`-shaped constraint on the flows table — several live flows per
  account are legitimate.
- A phase that touches a proto procedure updates the matching Yaak request
  (`api/specs/`, `yaak update --json`) in the same change, dropping `(unimplemented)`
  when a procedure ships.
- **`.llms/auth-design.md` stays lean.** The design document is the spec, not the
  record: a phase that closes a design row flips that row's status (and the
  frontmatter's `updated`), and writes nothing else there — prose, decisions,
  findings, and corrections live in the plan and the other `.llms/` documents.
- Each phase validates on its own before it commits: build, `task lint`, focused
  suite, container tests where state is touched, `task rpc:stale` after any proto
  change, `task db:validate` after any migration change.

### Phase 2 — Connections administration

`feat(oauthsso): connections administration`

- Admin CRUD over connections: create/update/delete, enable/disable, the custom
  provider's discovery URL (fetched and validated at save — the OIDC discovery
  document must parse) or manual endpoints (authorization/token/userinfo), scopes,
  attribute mapping for the custom provider (Clerk's shape: the userinfo response is
  the claim source, mapping fields with defaults for missing claims).
- Builtin definitions: `google` (`endpoints.Google`, OIDC, `openid email profile`
  default scopes) and `github` (`endpoints.GitHub`, OAuth2-only — identity reads
  `GET api.github.com/user` + `/user/emails`, the primary **verified** email decides
  linking) shipped as code constants the rows reference by slug, not as seed rows to
  re-create. Seeding is idempotent (`ON CONFLICT DO NOTHING`, skipped rows reported)
  where a seeder is the right home.
- Secrets sealed with the app cipher at write; `Redacted`-style answers never carry
  one. A nil cipher answers at the call site.
- Container tests over the CRUD; the discovery-validation test runs against a local
  fake discovery document.

### Phase 3 — Outbound authorization flow

`feat(oauthsso): outbound authorization flow`

- The provider interface in the feature root: `Begin(ctx, connection, flow)` returns
  the authorize URL; `Resolve(ctx, connection, code, verifier)` returns the verified
  external identity (provider account id, email, verified flag, names, raw claims,
  tokens). `builtin/google` and `builtin/github` and `custom` implement it —
  google and custom verify the `id_token` through `go-oidc` (issuer, audience, nonce,
  JWK set); github reads the userinfo API over `x/oauth2`.
- The REST surface: start redirects the browser (302) after writing the flow row;
  the callback consumes `code` + `state` — the state comparison is constant-time, the
  flow row is consumed by the guarded `UPDATE`. PKCE S256 on every provider that
  accepts it. Errors render as redirects to the SPA's error surface, never a JSON
  envelope (the caller here is a browser mid-redirect).
- The flow sweep job expires stale rows (the `webauthn_cleanup` pattern).
- Provider tokens sealed and stored on the linked row at resolution time.
- Wire-level tests against a local mock authorization server (container) for the
  custom path; httptest fakes for the builtin adapters' endpoints.

### Phase 4 — Identity resolution: sign-in, linking, JIT sign-up

`feat(oauthsso): identity resolution, linking, JIT sign-up`

- The resolution order at the callback, per Clerk's transfer semantics:
  1. A linked account row exists for (connection, provider account id) → sign in
     through `signin.IssueSession` (`ProviderOAuthSSO`, `audit.EventOAuthSsoSignIn`),
     honouring the MFA fork per decision point 2.
  2. No link, the provider email is **verified**, and an account holds that address →
     link (audit `oauthsso_account_linked`) inside the transaction, then sign in. The
     password question never arises: the verified email is the proof Clerk accepts.
  3. No link, the provider email is **unverified** → the flow enters the
     email-verification stage; the email code (the existing single-use-code shape)
     must be spent before any link or creation.
  4. No account at all → JIT per decision point 1; the created account skips email
     verification (the provider verified it), and a missing given/family name sends
     the flow to the **continue** stage (`ContinueSignIn` completes it) before the
     session opens.
- Blocklist and allowlist gate the identity at creation (the signup feature's
  helpers), access mode gates it per decision point 1, and the `users` table's
  uniqueness answers the race the way signup's does.
- The continue and verify stages answer through the flow token; the token is the
  credential, the guard rule is `Public`, and the flow row's stage machine forbids
  skipping stages.
- Container tests per branch of the resolution order, including the race (two
  callbacks, one flow row) and the unverified-email gate.
