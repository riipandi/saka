## What this session settled

Five threads, all closed. The reasoning lives in the artifacts; do not restate
it here.

1. **DI/lifecycle analysis → implemented.** Warm-up and runner ordering moved
   from `cmd/serve.go` into `internal/registry` (`Prewarm`, `Runner`,
   `Runners`); route-conflict detection added to `kernel.Mount`/`MountRPC`.
   Rationale in `.llms/architecture.md` → "internal/registry" and
   "internal/kernel".
2. **Response contract → implemented.** `ResponseMetadata` trimmed to the
   pagination-only `ListMetadata`; `CheckResponse` carries no metadata;
   correlation id is written once by the request middleware. A duplicate
   `X-Request-Id` in RPC responses (an interceptor and, before it, an error
   `Meta().Set` writing the header a second time; connect merges handler-set
   headers by appending) was found and fixed — the single-writer rule is
   pinned by tests. `docs/api-response.md` rewritten as the per-transport
   mapping (one contract, each idiom).
3. **Rate limiter made consistent across transports → implemented.** The
   throttled surface is two chi groups, each refusing in its caller's
   protocol (`restRefuse` envelope / `rpcRefuse` connect
   `resource_exhausted`); exclusion lists are per transport
   (`httpRateLimitExclusions` / `rpcRateLimitExclusions`), and both health
   endpoints are excluded — the RPC readiness used to be throttled while its
   REST twin was not. Rationale in `.llms/architecture.md` →
   "internal/transport".
4. **Protocol and auth decisions → recorded.** ConnectRPC is the primary
   protocol (internal/backoffice); REST serves external integrations and the
   planned OAuth2/OIDC surface; authentication is stateless (Bearer JWT +
   `X-API-Key`, no auth sessions). One correction was made mid-session: the
   JWT signing stack is a **config decision** (`auth.jwt_algorithm`, derived
   from the material when unset), not an audience decision — the audience
   only constrains verifiability. All of it is recorded in
   `.llms/architecture.md` → "Protocol and authentication (settled
   2026-09-24)" and mirrored in agent memory.
5. **OTEL/LGTM + Perses → implemented.** The Prometheus bridge now registers
   the Go runtime and process collectors deliberately (`internal/observer`,
   `newRegistry`); the transport is instrumented (`otelconnect` interceptor in
   `rpcHandlerOptions`, `otelhttp` wrapper in `NewServer`); the Perses MCP
   server is enabled in compose; the four Grafana-migrated dashboards
   (placeholder queries) were replaced with five working ones plus an
   application-monitoring dashboard. The provisioning traps and the verified
   plugin kinds are recorded in `.llms/architecture.md` → "observability
   stack (docker)" and in agent memory.

## Notes for the next session

- **Stack port map (host side)**: Perses `3380`, Perses MCP `3880`,
  VictoriaLogs `33801`, VictoriaMetrics `33802`, VictoriaTraces `33803`; the
  OTLP fan-out (Vector, replacing the OpenTelemetry Collector) keeps
  `4317`/`4318`, and Vector's own pipeline is scraped on job `vector` at
  `:9598`. Container-internal traffic uses the backends' own ports — only the
  host-side curls in `scripts/task-metrics.yml` carry the mapped ones; the Perses
  datasources go through the Perses proxy and name the container URLs.
- **Vector is pinned to a dated nightly** (`VECTOR_VERSION` in
  `docker/compose-sre.yaml`) because the `otlp` codec and
  `use_otlp_decoding` are not in a stable release; the accepted trade-off and
  its review trigger are documented in the architecture's observability
  section. A config edit needs a Vector recreate (`--force-recreate`).
- **Metrics ingestion is pull-first**: the Prometheus bridge (`/metrics`) is
  the primary route and keeps flowing while Vector is down; `otel.metrics.push`
  (default off) adds the OTLP push leg for deployments without a scraper. The
  dashboards read the scraped side (`job="tango"`), not the pushed labels.
- **Quantitative vs qualitative split** (user decision): Application Monitoring
  stays metrics-only; logs and traces share one `logs-traces` dashboard keyed
  by the `service` variable (the resource attribute both signals carry).
  Dashboard file names carry no `-cr` suffix; Perses provisioning reads every
  file in `docker/perses/dashboards/`.
- **Instrumentation pattern for subsystem metrics**: each package defines its
  own `metrics.go` (`internal/queue`, `internal/scheduler`, `internal/storage`,
  `internal/fetcher`, `internal/transport/middleware`), building its OTel
  instruments in the owner's **constructor** from `otel.Meter(<package scope>)`
  — real when the observer is up, the SDK's no-op when metrics are off. A
  process-level `sync.Once` was tried and rejected: instruments built before
  `SetGlobals` stay no-op forever and cannot be unit-tested. Outcome labels
  mirror each subsystem's own contract (queue settle branches, scheduler claim
  outcomes, fetcher `errors.Is` classes, limiter surface/outcome). The
  `application-internals` dashboard reads them scraped from `job="tango"`.
- **ListVariable needs a defaultValue or panels render empty**: an unselected
  list variable interpolates `instance=~""` and matches nothing — the
  "nginx dashboard shows no data" report. Every instance/datname variable now
  carries `defaultValue` + `customAllValue: ".*"`.
- **Edge status codes come from access logs**: nginx writes one JSON line per
  request (`log_format json_edge`) to a shared `../.storage/nginx_logs` bind
  mount; Vector's `file` source + remap transform ships it to VictoriaLogs'
  `insert/jsonline?_stream_fields=service.name` via a plain `http` sink — the
  `opentelemetry` sink with `codec: otlp` only accepts raw OTLP envelopes, so
  non-OTel logs need the jsonline path, and `_stream_fields` in the URI is
  what makes `{service.name=...}` match.
- **SLO & Error Budget dashboard** (targets are defaults: 99.9% availability,
  99% under 300ms, 30d window; burn-rate panels are the future vmalert
  surface; ConnectRPC not covered — rpc series carry no status label).
- **The nginx config is a compose `configs:` template** (`$$` escapes a
  literal `$`); adding a `location` there means recreating the nginx container,
  not restarting it. Its `stub_status` is read by Vector's `nginx_metrics`
  source and exposed on `:9599` (job `nginx`); the collector self-metrics live
  on Vector's `:9598` (job `vector`).
- **VictoriaMetrics reads its scrape config once at process start** — after
  editing the scrape jobs, `--force-recreate` the VM container; a restart of
  another service or waiting is not enough, and stale samples from the old
  config keep showing up in range queries for a few minutes.
- **The `redis-db` scrape job pins its target in `params`**
  (`target: ['valkey:6379']`), not in a `__param_target` relabel — an
  `__address__`-derived relabel pointed the exporter at itself and silently
  emptied the valkey dashboard. A panel guarded by `or vector(0)` shows a flat
  zero in that state; confirm series exist before trusting a zero.
- **Perses provisioning never overwrites**: after editing a dashboard or
  datasource file, `DELETE` the object over the API (`/api/v1/projects/tango/dashboards/<name>`
  or `/api/v1/globaldatasources/<name>`) and restart Perses — a restart alone
  re-applies nothing. The same applies to the VictoriaMetrics scrape config:
  it is a compose config mounted into the VM container, so a scrape-job edit
  needs a VM recreate.
- `pkg/responder` remains the single enforcement point for pagination and
  envelope rules on both transports; do not re-implement its rules in a
  handler.
- `kernel.Mount`'s conflict detection reads routes back from a scratch
  router before registering them; Mount implementations must stay
  registration-only for this to hold (documented in the kernel section).
- The queue's construction seeds its jobs, so any test that resolves the
  queue needs a migrated database — see `internal/registry/lifecycle_test.go`
  for the idiom.
- **Perses provisioning speaks native kinds only** (`Dashboard`, `Project`,
  `GlobalDatasource`); a `PersesDashboard` CR file is skipped silently, and
  dashboards are project-scoped — the full trap list lives in
  `.llms/architecture.md` → "observability stack (docker)".
- Documentation lookups go through MCP Context7 / DeepWiki / official docs
  first — the user requires it.
