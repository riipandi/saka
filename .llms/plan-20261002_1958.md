# Plan — Access restrictions: Blocklist + Block email subaddresses

Closes three rows of `.llms/auth-design.md`:

- § Block email subaddresses — subaddressed variants of a registered address are
  blocked from signing up or being added to an existing account.
- § Blocklist — block specific account identifiers from signing up (default: false).
- § Apply allowlist and blocklist to sign-ins — the lists also apply at sign-in
  (default: false).

Clerk's model, read from `clerk.com/docs/guides/secure/restricting-access.md` and
the 2025-08-08 changelog, is the reference: lists apply to sign-ups by default,
the allowlist wins where both name the same identifier, a blocked exact address
also blocks its subaddressed variants, and the subaddress blocker compares base
addresses (first subaddressed sign-up for a base is allowed, later ones are not).

## Decisions the owner made (2026-10-02, binding)

1. **Storage: a `blocklist_entries` table plus admin RPC CRUD** — not the settings
   catalog. The enable toggles stay settings; the entries are rows.
2. **Blocklist grammar: exact address + `@domain` suffix + subaddress
   normalization** — the allowlist's grammar plus Clerk's carry-over: a blocked
   exact address also blocks `foo+tag@`, `foo=tag@`, `foo#tag@`. No wildcards
   (`*@domain`, `*@*.domain`) — rejected as machinery this deployment has no use
   for yet; the matcher can grow them later.
3. **Sign-in refusal is ban-aligned**: evaluated where the account's credential
   has already been verified, answered `permission_denied` like
   `account is banned`. An anonymous caller learns nothing; only the holder of
   the correct credential sees the block. (Rejected: `not_found`-shaped —
   strongest anti-enumeration, but inconsistent with the ban mechanism the owner
   asked to align with.)
4. **Block email subaddresses ships too**, as a standalone toggle with Clerk's
   provider rules — including its "added to an existing account" side, which
   lands on `RequestEmailChange` (the only path that attaches a new email to a
   live account).

## Shape

- **Toggles (settings catalog, `modules/appconfig/settings.go`)**:
  - `access.blocklist_enabled` (bool, default `false`) — off, the table is dead.
  - `access.block_email_subaddresses` (bool, default `false`) — off, subaddressed
    addresses behave as plain addresses.
  - `access.blocklist_applies_to_signins` (bool, default `false`) — applies both
    lists at sign-in. Dead while both lists are off (the design note's
    precondition). The subaddress blocker has no sign-in side: accounts that
    already hold a subaddressed address keep signing in (Clerk's rule).
  - Admin edits them through the existing `tango.appconfig.v1.SettingsService`
    (guard `Admin`) — no new write surface for the toggles.
- **Entries (table)**: `blocklist_entries` — `id uuidv7`, `pattern text not null`
  (lowercased exact address or `@domain`), `created_by uuid null` (→ `users.id`,
  `ON DELETE SET NULL`), `created_at timestamptz not null`. `UNIQUE(pattern)`.
- **Feature package `modules/identity/blocklist/`**: `schema.go`, `repository.go`,
  `service.go` (CRUD + the matcher + the email base-normalization helpers),
  `handler_rpc.go`, `module.go`. The address-shape helpers live here once;
  signup and signin consume the feature through seams, and the pure helpers are
  imported directly (no service dependency, no cycle).
- **Proto `tango.identity.v1.BlocklistService`** (`api/connect/identity.proto`):
  `ListBlocklistEntries` (paged like the other admin lists), `AddBlocklistEntry`
  (pattern; grammar-validated; idempotent on duplicate — answers the existing
  row), `RemoveBlocklistEntry` (by id). All three guard `Admin`
  (`internal/guard/rules.go`), mirroring the other admin surfaces.
- **Cross-feature seams** (the established pattern — interface defined in the
  consuming package, wired in the identity area `Package` after construction,
  never an import back):
  - `signup` gains `WithBlocklist(checker)`; its `signupPolicy` reads
    `access.blocklist_enabled` and `access.block_email_subaddresses` from the
    settings it already reads.
  - `signin` gains `WithBlocklist(checker)`; reads
    `access.blocklist_applies_to_signins` through its `sessionSettings` reader.
  - `verification` (owner of `RequestEmailChange`) gains the same seam for the
    email-change guard.
- **Precedence**: the allowlist wins. At sign-up, an address the allowlist accepts
  passes even when the blocklist names it. At sign-in with the toggle on:
  blocklisted → refuse; allowlist on and the account's address is not
  allowlisted → refuse the same way.
- **Failure stance: fail-open with a warn log**, matching the allowlist's
  "unreadable key keeps its default" behavior — a broken settings read or a
  failed query never locks the deployment out of its own sign-up.

## Address helpers (one place: `blocklist` package, pure functions)

- `SubaddressBase(address)` — lowercases, splits the last `@`, strips the
  subaddress from the local part at the provider's separators:
  - Gmail (`gmail.com`, `googlemail.com`): `+`, `=`, `#`, and dots removed from
    the local part (`j.smith@gmail.com` → `jsmith@gmail.com`).
  - Yahoo (`yahoo.com`, `ymail.com`, `rocketmail.com`, `y7mail.com`, and the
    country set `yahoo.co.uk`, `yahoo.fr`, `yahoo.co.jp`, `yahoo.com.br` — exact
    domain match, not a `yahoo*` prefix): `+`, `=`, `#`, `-`.
  - Every other domain: `+`, `=`, `#`.
- `BlocklistMatch(address, patterns)` — exact match, `@domain` suffix match, or
  the address's base matching a blocked exact entry (the carry-over).
- Gilded edge cases pinned by tests: a domain that merely starts with `yahoo`
  (`yahoo.dev`) is NOT Yahoo; a local part containing `+` in the middle of a
  registered domain is still a subaddress; the strip takes the FIRST separator
  (`foo+tag=more@` → base `foo@`).

## Enforcement points

- **Sign-up** (`signup.Service.SignUp`, beside the existing allowlist check):
  1. Allowlist precedence — accepted addresses pass everything below.
  2. Blocklist (`access.blocklist_enabled` on): `BlocklistMatch` → refuse.
  3. Subaddress collision (`access.block_email_subaddresses` on): the candidate's
     base collides with an existing email identity's base → refuse. The first
     sign-up for a base passes even when subaddressed (Clerk's rule). The query:
     indexed exact probes on the candidate and its base, plus one prefix probe
     (`lower(email) LIKE base_local-escaped || '%@' || domain`, verified in Go by
     recomputing each hit's base) so a stored subaddressed twin
     (`user+tag@x.com` already registered, `user+other@x.com` signs up) is
     caught; sign-up QPS makes the bounded scan a non-issue.
  - Refusal reuses the allowlist's answer — `not_found` "sign-up is not
    available" — so a blocked sign-up is indistinguishable from a closed one, an
    allowlist refusal, or a collision (no oracle about which rule fired).
- **Email change** (`verification.Service`, `RequestEmailChange`): when
  `access.block_email_subaddresses` is on and the new address's base collides
  with an existing account's address base → refuse. The caller is authenticated
  here, but the refusal still must not confirm the other account: a generic
  `failed_precondition` "email address cannot be used". Blocklist does not apply
  here (owner-settled scope).
- **Sign-in** (`signin.Service.IssueSession`, inside the state switch beside
  `Disabled` / `bannedAt` — the choke point every session-opening path shares,
  including one-time access and the MFA bridge): only when
  `access.blocklist_applies_to_signins` is on, match the account's primary email
  identity — blocklisted → refuse; allowlist on and the address not allowlisted
  → refuse the same way. Refusal is a new `ErrSigninRestricted` answered as
  `permission_denied` "sign-in is not permitted" — the ban's wire shape at the
  ban's position (after credential verification). Accounts without an email
  identity cannot match email-shaped entries and pass. Existing subaddressed
  accounts are unaffected (the subaddress blocker has no sign-in side).
- **Audit**: the public-surface refusals are not recorded (consistent with the
  ban refusal — a refusal log on a public surface is an enumeration oracle).
  CRUD is: `blocklist_entry_added` and `blocklist_entry_removed`, named in
  `internal/audit/audit.go`, described in `internal/audit/catalog.go`, mirrored
  in `modules/webhook/events.go` (`blocklist.entry_added` /
  `blocklist.entry_removed` — `TestTheCatalogCoversEveryAuditEvent` demands the
  mapping), recorded by the service inside the causing transaction.
