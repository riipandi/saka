# Auth completion plan: add password + waitlist

Written 2026-10-02. Covers the remaining actionable items of `.llms/auth-design.md` the
owner named: **Add password to account** and **Waitlist**. Deferred by the owner this
round: sign-in with mobile biometrics (needs the native API), SMS verification code
(behind phone-number support). Every decision below was confirmed with the user in the
same session; the user's answers are recorded in the decisions table. The plan runs
against the tree at `d84c889`.

## Objective

Two features, backend first:

1. A passwordless account can set its first password through a proof-shaped flow —
   the Clerk reverification semantics the owner picked ("pelajar Clerk"): the action
   rides a fresh reverification proof, and an account with no proof material verifies
   by an email code. This unlocks the `Add password to account` item and retires its
   open gate in the design doc.
2. The third access mode: `access.mode = waitlist`. Sign-ups are disabled; anyone can
   join the waitlist; the administrator reviews the queue and invites entries through
   the existing signup-token machinery. This unlocks the `Waitlist` item and the two
   waitlist email templates.

The strength meter is **frontend-owned** (owner: zxcvbn lands in the SPA). The backend
keeps `password.min_strength` in the catalog unenforced and the existing
`TODO(strength)` marker untouched; the plan only documents the split.

## Decisions (confirmed 2026-10-02)

| Fork | Decision |
|---|---|
| AddPassword proof | **Clerk-shaped reverification.** The proof is the existing `Reauthenticated` machinery — a passkey assertion or password when the account holds one, and a **fresh email code** when it does not. Mirrors Clerk's "sensitive actions require reverification" with the email-code reverification factor. No account is stranded; a stolen session cannot complete the flow (it cannot read the email). |
| Waitlist join contract | **Separate `JoinWaitlist` procedure** on `SignupService`. `Signup` refuses in waitlist mode with the same not-found refusal shape today's invite refusal answers. The SPA reads the public `access.mode` and renders the matching form. |
| Waitlist admin surface | **Extend `SignupService`** with three admin procedures reusing the signup-token machinery — no separate proto service. |
| Strength meter (zxcvbn) | **Frontend-owned.** Backend policy (min length, char rules, HIBP) unchanged; `password.min_strength` rests unenforced. |
| Mobile biometrics, SMS | **Deferred** with the owner. SMS waits for phone-number support; the auth ladder's SMS seam stays as the 20260930 plan left it. |

- The agent is **authorized to create atomic commits during this plan** — one commit per
  validated phase, each phase's files only. Stage explicit paths, never push, never
  destructive Git commands.
- **Yaak sync is part of every contract change.** When a phase ships or changes a
  procedure, the same change updates the matching request in `api/specs/` via
  `yaak update --json '{"id":"rq_…", ...}'` (create with `yaak request create <ws>` when
  the procedure is new), drops `(unimplemented)` markers, and brings
  `.llms/pocket-id-api-reference.md`, `.llms/endpoint-reference.md`, and
  `docs/api-endpoint.md` current. `task rpc:stale` runs before each commit.
- Migrations: new tables get a **new migration file** (next version above the last;
  `-- +goose Up`/`Down` mandatory). The `auth_tokens` purpose CHECK constraint is
  **edited in place** in `00002_create_identity_tables.sql` — the established pattern;
  that edit authorizes a dev database reset (`task db:reset -- --force --up`, then
  `task db:seed -- --force`) for state this plan created.
- Guard rules land in `internal/guard`; audit events are named in `internal/audit` and
  recorded inside the causing transaction. New public procedures are declared there the
  moment they ship — an undeclared procedure answers `not_found`.
- Every email artifact is a **single-use code**; no links, no redirects. The waitlist
  invitation email carries the signup token as code text, never a URL.
- Refusal semantics follow the guard contract: `unauthenticated` or `not_found`, never
  `permission_denied`. Anti-enumeration: the waitlist join answers the same success for
  a duplicate entry and for an address that already holds an account.
- Frontend stays out of scope (the SPA is still a placeholder); the
  `password.min_strength` frontend split is marked in the endpoint reference, not
  implemented here.
- Each phase validates before it commits: build, `task lint`, the focused suite with
  `-race -count=1`, container tests where state is touched, `task rpc:stale` after any
  proto change.
- Comments carry no vendor names (Clerk, HIBP, Pocket ID); the research lives here.

## Phase 1 — Email-code reverification

The generic reverification factor every sensitive procedure can spend — AddPassword is
only its first consumer.

- `api/connect/authn.proto` (or the proto the `Reauthenticate` procedure already lives
  in): the proof oneof grows an `email_code` field.
- New procedure `SendReauthenticationCode` — guard `Self`, rate-limited under the
  credential bucket the sign-in path uses. It issues a single-use code (the unambiguous
  alphabet at twelve characters, per the no-link rule) as an `auth_tokens` row and
  delivers it through the existing email job queue.
- The `auth_tokens` purpose CHECK constraint (`00002_create_identity_tables.sql:152`)
  gains `reauthentication_code` — in-place edit, dev reset authorized. The new purpose
  follows the several-live-rows rule only where the bridge needs it: one live code per
  account (resend replaces) is the rule here, matching `email_verification`.
- `Reauthenticate` with `email_code`: verifies the code against the caller's account,
  consumes it single-use, and mints the **standard** reauthentication token (hashed,
  several live, short TTL) the `Reauthenticated` guard rule already consumes. Wrong
  codes ride the same rate budget the password proof answers to.
- Audit: `reauthentication_granted` carries the factor used (`password`, `passkey`,
  `email_code`) in the entry payload — one event name, no new event per factor.
- Yaak: `SendReauthenticationCode` added, `Reauthenticate` updated with the oneof.

## Phase 2 — Add password to account

- New procedure `AddPassword` on `UserService` (self-service account management, the
  service `UpdateCurrentUser` and `DeleteMyAccount` already answer) — request carries
  the new password only; the proof is the `Reauthenticated` header the guard rule
  consumes. The procedure refuses when a password row already exists (`failed_precondition`
  — the change flow is a different procedure), and runs the settings-driven policy:
  `password.min_length`, the four char rules, and the HIBP breach check (fail-open,
  per the settled fault-tolerance contract).
- The write is one transaction in `modules/identity/password`: insert the
  `user_passwords` row (PHC hash via the shared hasher), record
  `user_password_added` inside it. No session changes; the next sign-in uses the
  password path, and an account at `mfa.required` meets the bridge it always would.
- The sign-in fork needs no change: `FindAccountByIdentity` matches the credential the
  moment the row exists.
- Email notice: the account receives the existing `password-changed-notice` template
  (a password was added is a password set), no new template.
- Yaak: `AddPassword` added; the reference notes the strength meter is enforced by the
  frontend (`password.min_strength` stays a catalog key the backend reads and does not
  enforce — `TODO(strength)` untouched).

## Phase 3 — Waitlist mode + join

- New migration `00015_create_waitlist_tables.sql` (version checked against the last at
  execution): `waitlist_entries` — `id` (uuid v7), `email` (the same shape the
  `users.email` column carries), `status` (`pending` → `invited`), `created_at`,
  `invited_at` nullable, `UNIQUE (email)` so an address holds one row; a soft-delete
  trigger (`fn_soft_delete`) rides the table's DDL per the schema rule.
- `access.mode` gains `waitlist`: the appconfig catalog's validate rule and description
  widen to `open|invite|waitlist` (public key — the SPA must read the mode before
  authentication). The signup service's policy reader learns the third value.
- `JoinWaitlist` on `SignupService` — guard `Public`, rate-limited (the same database
  limiter the sign-in bucket rides; the exact limit named in the phase note). The
  handler records the entry and queues the waitlist confirmation email in one
  transaction. Idempotent and anti-enumeration by contract: an address already on the
  list or already holding an account gets the same success and the same silence.
- `Signup` under `access.mode = waitlist` refuses with the existing `ErrSignupNotAllowed`
  → `not_found` shape; the token path refuses the same way in waitlist mode (a waitlist
  address is invited by the admin flow, not by spending a raw token — see Phase 4).
- Email template `waitlist-confirmation.tsx` under `email/templates/` plus its struct in
  `internal/mailer/data.go` (`TemplateProps` shape); proves via Mailpit.
- Yaak: `JoinWaitlist` added; `Signup`'s description names the refusal.

## Phase 4 — Waitlist admin surface

- Three procedures on `SignupService`, guard `Admin`:
  - `ListWaitlistEntries(page, limit, search, sort)` — pagination clamps through
    `responder.NormalizePage`; the search **escapes `%`/`_`** (the escape gap the
    audit named; this surface gets it right on day one).
  - `InviteWaitlistEntry(id)` — mints a signup token through the existing machinery,
    sends the waitlist invitation email carrying the token as a single-use code (no
    link), marks the row `invited` with `invited_at`. Re-inviting a pending entry
    replaces the live token (the resend rule `UNIQUE(user_id, purpose)` already
    follows for signup tokens).
  - `DeleteWaitlistEntry(id)` — removes the row; the soft-delete trigger captures it.
- Audit events: `waitlist_joined` (user trigger, Phase 3's join), `waitlist_entry_invited`,
  `waitlist_entry_deleted` — recorded inside the causing transaction.
- Email template `waitlist-invitation.tsx` plus its `internal/mailer/data.go` struct;
  proves via Mailpit (`task mailer:smoke` path).
- Yaak: three requests added; `(unimplemented)` dropped as each ships.

## Phase 5 — Final validation, E2E, docs sync, handover

- Full suite: `go test ./... -count=1 -race`, `task lint`, `task rpc:stale`,
  `task db:validate`, `config.schema.json` regenerated (`task config:generate`).
- Wire-level E2E over `build/release/tango serve --env-file=.local` on a disposable
  database (created, seeded, dropped in-session; server stopped at the end):
  1. A passwordless account (created by one-time access) signs in →
     `SendReauthenticationCode` (code read from Mailpit) → `Reauthenticate` with the
     code → `AddPassword` → password sign-in completes; a second `AddPassword` is
     refused.
  2. Passkey-held account: `Reauthenticate` by passkey still mints the token
     (regression); `Reauthenticate` with a wrong/expired email code refuses.
  3. `access.mode = waitlist`: `Signup` refuses; `JoinWaitlist` succeeds; a duplicate
     join and a join by an address holding an account answer the same success; the
     confirmation email is in Mailpit.
  4. Admin: list (search escaped — a `%` query returns literal matches only), invite
     (token lands in the invitation email, entry flips to `invited`), delete; every
     action carries its audit event read back through the audit-log RPC.
  5. The invited address signs up with the token from the email; the spent token
     refuses again.
  6. Guard negatives: each new procedure anonymous → 401; non-admin on admin
     procedures → `not_found`.
- Docs: the three-way pass (`docs/api-endpoint.md`, `.llms/endpoint-reference.md`,
  `api/specs/`) — every shipped procedure mirrored; `.llms/architecture.md` auth
  sections; `config.schema.json` regenerates with the widened `access.mode` enum.
- `.llms/auth-design.md` status update (checkboxes only, per the established rule):
  `Add password to account` → done; `Waitlist` → done; the two waitlist email-template
  rows → done; the waitlist/invitation template notice stays.
- Handover: a fresh `.llms/handover-<date>_<time>.md` via the `handoff` skill — state,
  decisions, deferred items (mobile biometrics, SMS, zxcvbn-frontend), the test
  matrix's final state.
