# Handover: JWKS single signing authority — config key pair removed

## Objective

The decision recorded in this session's chat: the database (`public.jwks`)
is now the application's **only** asymmetric signing authority. The
configured `auth.private_key` / `auth.public_key` pair is gone from the
configuration, `key:generate` emits only the two environment secrets, and
`saka initialize` provisions the first signing key pair. Branch
`refine-architecture`, **nothing committed** — the work sits uncommitted in
the working tree (37 paths) and the commit message is at the bottom of this
file.

## State

- **Config** (`internal/config`): `Auth.PrivateKey` / `Auth.PublicKey`
  removed from `types.go`, `publish.go`, `redact.go`, `sample.go`
  (secretKeys), `validate.go`. `JWTAlgorithmMaterialError` now takes
  `(algorithm, secretKey)` — an asymmetric algorithm names no config
  material, so only the HMAC leg is refused there; a config with no signing
  material at all validates clean. `public/config.schema.json` carries the
  same removal. `.env.example` lists only `APP_SECRET_KEY` and
  `AUTH_SECRET_KEY`.
- **pkg/crypto** (`keygen.go`): `KeyGenerator` emits `APP_SECRET_KEY` +
  `AUTH_SECRET_KEY` only; an asymmetric `--algorithm` is refused with a
  message that names the database. `GenerateKeyPair(algorithm)` is the new
  standalone generator the jwks rows are stored from — both halves base64
  JWK JSON sharing one `jwk_` TypeID kid (the public half copies the
  private half's kid; two independent mints would mismatch).
- **jwks.Service** (`modules/identity/jwks/service.go`): the config-pair
  parse is gone. `SignKey` unseals the first active row (`ORDER BY
  key_id`, stable) and adopts the row's `kid`; `SigningAlgorithm` derives
  from the row's `algorithm` column when `auth.jwt_algorithm` is unset,
  falling back to the HMAC secret's length. `VerifyKeySet` fails the call
  when the source cannot be read (no more degrade-to-configured-key).
  `ErrNoSigningKey` / `ErrNoStoredKeys` messages name `saka initialize`.
  `parseKeyPair`, `keyPairAgrees`, `stampGeneratedKid`, and the legacy-kid
  rename are deleted. The module provider (`modules/identity/module.go`)
  tolerates `ErrNoSigningKey`/`ErrNoStoredKeys` at construction with a
  warn log — a fresh database still serves; sign-in answers the missing
  key per call.
- **initialize** (`cmd/initialize.go`): provisions the signing pair in the
  seed transaction through `seeders.System(cipher, algorithm)` and writes
  the `jwks_provisioned` audit event (`internal/audit.EventJwksProvisioned`).
  Refuses without `APP_SECRET_KEY` (nothing to seal with). Idempotency is
  unchanged — the account refusal covers re-runs, and the seeder skips
  when any row exists.
- **jwks:generate** (`cmd/jwksgen.go`): stays for manual rotation, now
  built on `seeders.GenerateJWKSKeyPair` + `seeders.InsertJWKSRow`, so both
  paths write the same shape. The local raw-key generation and JSON
  helpers were deleted.
- **key:generate** (`cmd/appkey.go`): two secrets only; the description
  points at `initialize` for the key pair.
- **migrate:seed** (`cmd/migrate_debug.go`): `developmentSeeders(cfg)`
  appends the JWKS seeder when `APP_SECRET_KEY` seals (`seeders.SeedJWKS`),
  so a development seed also provisions.
- **Docs**: `.llms/architecture.md` (crypto + jwks sections rewritten),
  `AGENTS.md` (JWKS bullet), `README.md` (setup step 9: initialize),
  `scripts/task-database.yml` (new `db:initialize` task).
- **Dev DB**: reset, initialized (`admin` / `@dmin123`), seeded, and
  E2E-verified on port 3099 — JWKS publishes one `jwk_` key with `alg`
  ES256 and no private fields; sign-in returns an access token whose JOSE
  header names that kid; `jwks:generate` adds a second key and the set
  publishes both; a second initialize answers `refused`. The server was
  stopped and temp files removed.

## Bugs the E2E run caught

1. **The jwks columns store JWK JSON documents, not the base64 envelope.**
   `GenerateJWKSKeyPair` first stored `crypto.GenerateKeyPair`'s base64
   output; `parseStoredKey` / `openSealedKey` parse the column value
   directly, so the published set came back empty with
   `invalid character 'e'` skip-logs. The seeder now `DecodeJWK`s both
   halves and re-marshals them before sealing/storing.
2. **`do.MustInvoke` turns provider errors into panics.** The identity
   `Mount` chain resolves the key provider eagerly; a provider error
   (nil-logger warn, database-unreadable) surfaces as a nil-pointer panic
   at the call site. The nil-pool area test also needs a real
   `*slog.Logger` and the composition-root guard that passes a nil source
   when the pool is nil (`modules/identity/module.go`).
3. **Typed-nil gotcha**: a nil `*datastore.Postgres` wrapped as a
   `Querier` interface is non-nil, so `r.db == nil` guards in the
   repository do not catch it — `p.pool` dereferences and panics. The
   guard lives at the Package provider (pass no source for a nil pool),
   and the registry compose test overrides `*jwks.Service` with a
   nil-source service over the stub pool.

## Migration notes for existing deployments

- Old env files keep `AUTH_PRIVATE_KEY`/`AUTH_PUBLIC_KEY`: the keys are
  unread by the new binary and can be deleted at leisure.
- Tokens minted before the upgrade name the old configured kid, which no
  row explains; they fail verification until they expire (access TTL is
  minutes). Run `saka initialize` — it is refused if accounts exist, so
  an existing deployment provisions via `jwks:generate` instead (one row
  is enough) or re-runs the seeder on an empty jwks table.

## Addendum (same session, later): the two secret halves

A follow-up directive split the sealing across the two secrets: auth material
is now sealed with `AUTH_SECRET_KEY` (via `crypto.NewAuthCipher`, a SHA-256
derivation so any HMAC length seals), everything else keeps `APP_SECRET_KEY`.

- `pkg/crypto/encryption.go`: `Fingerprint()` (16-hex non-secret key id),
  `AuthSealKey` (SHA-256 derive), `NewAuthCipher` (`ParseHMACKeyHex` input).
- `modules/identity/module.go`: jwks and multifactor providers build the
  auth cipher; appconfig/scimsync/queue keep `c.App.SecretKey`.
- `database/migrations/00004` (edited in place): `seal_fp TEXT NOT NULL
  DEFAULT ''` on `public.jwks` — the fingerprint of the sealing key.
- Auto-invalidation: `jwks.Service.WithSealer(repo, repo.GeneratePair,
  algorithm, recorder)`; a stale fingerprint on the signing read retires the
  rows (`RetireStaleSeals`) and provisions a replacement pair, then records
  `jwks_invalidated` (audit). One sign-in-shaped call pays for the rotation;
  tokens under the retired key expire naturally.
- `auth.secret_key` validation: hex, even-length, ≥ 64 chars (`isHexSecret`).
- The unified provisioning path: `jwks.GeneratePairWith(algorithm, cipher)`
  (free) and `Repository.GeneratePair` (method) — seeders, `jwks:generate`,
  and the auto-invalidation all write the same row shape.
- E2E proven on the release binary: two `AUTH_SECRET_KEY` rotations each
  retired the stale rows, re-provisioned, and both sign-in and the full OIDC
  authorization-code + PKCE + consent + token-exchange + refresh-rotation +
  replay-refusal flow worked against the new kid; an `APP_SECRET_KEY`
  rotation left the jwks rows untouched; the old refresh token stayed valid.
- Migration note: rows provisioned before this change carry `seal_fp = ''`
  and are retired on the first signing read after the upgrade (the empty
  fingerprint never matches) — run `saka jwks:generate` first on a live
  deployment if zero-downtime matters, or accept one failed signing window.
