## The owner decisions the plan records

1. **Normalized restriction storage.** One `account_restrictions` table for ban and
   lockout — both answer since/until/why, so one schema, one expiry rule, one read.
   `failed_attempts` stays on `users` (the hot path's counter). No backfill, no shim.
2. **Session revocation follows the kind.** A ban ends the account's live sessions
   (through the existing `WithBanSideEffects` seam, in the ban's own transaction); a
   lockout does not — ending a legitimate holder's session serves only the attacker
   who guessed the password.
3. **The counter is a streak, never a tally.** Success zeroes, lift zeroes, an
   expired lockout's read zeroes. A lifetime count would lock accounts for history.
4. **`lockout.max_attempts` keeps 100.** The design doc named it; Clerk's July 2026
   drop to 10 is a consumer-platform posture — a self-hosted operator tunes the knob.
5. **No manual `LockUser`.** The ban covers manual restriction; the lockout is
   automated only. No zxcvbn. No sign-in-attempt notices for non-existent accounts
   (no email-code sign-in strategy to ride).

## What the ladders caught

- **The unmounted procedure.** Phase 4's ladder answered `unknown procedure
  "/saka.identity.v1.UserService/UnlockUser"` — the handler existed, the guard rule
  named it, but the module's `MountRPC` never claimed the path. `RemovePassword`'s
  mount line landed with phase 5's implementation. This is the trap AGENTS.md's
  forwarding test exists for: a hand-built `Deps` passes while the wiring is broken.
- **The rate limit hides the lockout.** The lockout leg (100 wrong passwords) outruns
  the default `rate_limit.auth_limit` — the E2E variant config
  (`/tmp/e2e_p4.config.json`, derived from the OAuth ladder's, both limits at 10000)
  is the ladder's precondition, exactly as the plan's test matrix predicted.
- **The wire's revocation is row-level.** The ban revoked the session rows but the
  access token kept answering `GetCurrentUser` — the access token is a stateless JWT
  (900-second TTL, no per-request session lookup, by design). The revocation's wire
  evidence is the paths that read the row: `GetSession` and `Refresh` answer
  `unauthenticated "the session has ended"`, and the stateless token dies at its TTL.
  The ladder had to prove the revocation in those terms, not the token's.

## The mail-probe pattern that works

The real trigger for the passkey receipts is a browser ceremony, so the probe seeds
the queue rows the ceremony would enqueue (`INSERT INTO public.queue_tasks (id,
queue, task) SELECT uuidv7(), 'passkey_added_notice', convert_to('{…}','utf8')`) and
lets the running binary's dispatcher process them — proving the processor, the
template, and the delivery. The dispatcher's fallback poll is a full minute; wait for
it or seed a task whose queue the notify path wakes. The password-removed notice is
proven end to end — the reauthentication proof is a password RPC, no browser needed:
`Reauthenticate` (oneof `password`, a **string**, not a nested message) answers
`{"token": …}` and `RemovePassword` spends it through `X-Saka-Reauthentication`.

The wire fixes worth remembering: a raw UUID is not an id on this surface — admin
procedures want the TypeID form (`user_…`), and a bare uuid answers `user not found`
(which made the first ladder run lie about the ban and the unlock).
