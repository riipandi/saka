## Part 1 — Vite root / Go toolchain (committed)

Committed as `ecb7bc0 fix(vite): keep the go toolchain working from the project root`. Changed
`vite.config.ts`, `plugins/plugin-golang.ts`, `plugins/plugin-email.ts`. See the commit diff rather
than a restatement here.

Root cause in one line: `config.root` is **Vite's** root (`web/`), not the project root; the plugin
used it as `cwd` for `go build` and for spawning the dev binary, so `app.config.json` and `go.mod`
were never found.

Two things worth not re-litigating:

1. **`root: resolve('web')` cannot be removed** while `index.html` lives in `web/`. Vite derives the
   emitted HTML name from `path.relative(config.root, htmlFile)` and ignores the alias key in
   `rolldownOptions.input`; there is no config option for the HTML output path. Without `root`, the
   build lands at `web/output/web/index.html` and `web/static_release.go` breaks. Confirmed via
   DeepWiki on `vitejs/vite` and Context7 `/vitejs/vite`.
2. **`binArgs` now carries `--env-file=.env.local`** (`vite.config.ts:56`). Without it the dev
   binary starts with no `DATABASE_URL` and exits. `pkg/envfile.Load` tolerates a missing file, so
   this is safe on a fresh checkout.

Also added: `server.watcher.add(projectRoot)` in both plugins, because Vite only watches its own
root and `cmd/` + `email/templates/` sit above it.

Verification done: `pnpm exec vite build` emits `web/output/index.html` with `favicon.*` + `images/`;
dev server starts clean; editing `cmd/serve.go` and `email/templates/*.tsx` both trigger rebuilds;
release binary serves `GET /` → 200 HTML and `GET /api/healthz` → 200; `oxfmt --check`, `oxlint`,
`tsc -b --noEmit`, `go build ./...` all clean.

## Part 2 — `internal/**` wiring audit (NOT started, NOT committed)

Scope: 15 packages under `internal/`, 137 Go files. Verdict: the wiring is mostly solid — the
`kernel.Module` contract is clean, `internal/registry` is the only composition root, and the
shutdown ordering in `cmd/serve.go` (scheduler → listener → container) is correct. Six defects
follow, all verified empirically (temporary tests, `curl` against a release binary, or reading the
`samber/do` source). **All temporary test files were removed; working tree is clean.**

### High

**1. `datastore.Postgres.Close()` / `datastore.Valkey.Close()` are never called.**
`cmd/serve.go:196` closes the container with `injector.ShutdownWithContext`. `samber/do` v2.1.0
calls only four interfaces — `Shutdowner`, `ShutdownerWithError`, `ShutdownerWithContext`,
`ShutdownerWithContextAndError` — and **does not know `io.Closer`** (`service_lazy.go:183-209`).
Both types expose only `Close()` (`internal/datastore/postgres.go:176`, `internal/datastore/valkey.go:90`).
Verified with a throwaway test against `do`: `Close() called: false`, report `Succeed=true`. The
comment at `cmd/serve.go:178` claims the pool is closed after the drain; it is not, and the report
is a false green. Fix: give both a `Shutdown(ctx)` delegating to `Close()`, or register them as
values and close explicitly in `serve.go`.

**2. The task queue is cancelled mid-flight by the signal instead of draining.**
`cmd/serve.go:108` passes the signal context (`cmd/main.go:16`, `signal.NotifyContext`) to
`queueClient.Start`. `internal/queue/dispatcher.go:79` stores it as `d.ctx`, the parent of every
task execution (`dispatcher.go:291`). On SIGTERM `ctx.Done()` closes **before**
`client.Shutdown(shutdownCtx)` runs, so workers exit and in-flight tasks see a cancelled context.
Verified with a test mirroring `serve.go`'s order: `TASK CTX CANCELLED: context canceled`, task
abandoned. Practical impact: a `ChunkUploadTask` (30-minute timeout) is cut mid-upload on every
deploy. `TestStopDrainsInFlightTasks` misses it because it cancels the context *after* `Stop`. Fix:
build `d.ctx` from `context.WithoutCancel(ctx)` so only `shutdownCtx` stops the dispatcher.

**3. The rate limiter is bypassed by every module route under `/api`.**
`internal/transport/handler.go:70-80`: `api.Use(middleware.RateLimit(...))` binds to the `/api`
subrouter, while `kernel.Mount(r, opts.Modules...)` mounts modules on the **root** router. Verified
with a probe module: `module route status=200 limiter.calls=0`. Every module endpoint — auth,
webhook, the whole application API — is unthrottled; the configured limit only covers `/api/` and
`/api/healthz`. Fix: mount the limiter on the root router behind a `/api` prefix predicate, or mount
modules inside the `/api` subrouter.

### Medium

**4. `/api/healthz` publishes the database target.** `internal/registry/registry.go:74` passes
`config.RedactDSN(...)` as `DatabaseCheck`'s target, and `internal/health/helper.go:64` tags it
`json:"target,omitempty"`. Verified unauthenticated: `"target": "localhost:5432/postgres"` in the
response body. This contradicts `AGENTS.md` ("no DSN, no URL … in the published form").
`StorageCheck` already does it right (no target); `cmd/healthcheck.go:117` shows the CLI pattern
(`StorageCheckWithTarget`). Fix: pass `""` in `registry.go`.

**5. `queue.release_after` (600s) is below the longest task timeout (1800s).**
`internal/config/defaults.go:138-142` states the invariant in a comment ("ReleaseAfter must stay
above the longest queue Timeout"), and `internal/config/types.go:388` repeats it, but
`internal/config/validate.go:278` only checks `> 0`. `ChunkUploadTask.Timeout = 30 * time.Minute`
(`internal/jobs/storage_upload_job.go:34`). A 10-minute upload is re-claimed by a second worker
(`internal/queue/store.go:80-91`) while the first still holds it. Fix: raise the default above 30
minutes, or cross-validate against the registered queue timeouts.

### Low

**6. `/static` is never mounted but `app.assets_url` points at it.**
`internal/config/defaults.go:184` sets `DefaultAssetsURL = "http://localhost:3080/static"`; no route
serves it (`curl /static/app.js` → 404 JSON). Not currently harmful: `mailer.SenderFrom`
(`internal/mailer/templates.go:58`) prefers `app.base_url`, so the email logo resolves through
`/images/logoEmail.svg` (verified 200). The `assets_url` fallback would produce a dead link.

### Checked and clean

`dispatcher.worker()`'s `break` inside `select` looks like a bug but is not — `shutdownCtx` is
already done when `d.tasks` closes, so the loop exits through that branch; no goroutine leak
(measured delta 0). Middleware chain order and the panic path (panic → 500 + request line, verified).
`responder` reads `X-RateLimit-*` off `w.Header()`, so the headers reach real responses.
`web/static_release.go` SPA fallback, deep links, and API prefix rejection all correct. No `init()`
or global singletons outside `registry.startTime`. Scheduler seeding and transactional fire are
correct. `jobs.Register` seeding is idempotent. `do.Provide` panics on a duplicate interface
registration, so `cache.Cache`, `storage.Store`, and `middleware.Limiter` are safe from ambiguity.
`go test ./...` green.
