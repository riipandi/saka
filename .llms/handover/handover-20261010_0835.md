# Handover — the authz foundation (plan-20261010_0610)

## What shipped

All five phases of the plan executed and committed. The frontend now judges
by the same rule the server judges with — and the server never changed:

- **Phase 1** (`ba994504`) — `libraries/guard/auth-claims.ts` decodes the
  access token's `roles`/`permissions` claims (base64url, zod over the
  untrusted boundary, no new dependency). The decode rides `persistTokens`
  (`auth-worker-client.ts`) — the one custody site both the worker path and
  the main-thread fallback wire — so sign-in, refresh, restore, and drop all
  replace the snapshot at the same tick; `authStore.state.grants` carries
  them beside the profile, and `clearAuth` drops them with it. Absent claims
  are the empty snapshot the backend's omission contract defines; a
  malformed payload warns and never throws.
- **Phase 2** (`44067524`) — `libraries/guard/permissions.ts`:
  `matchRequirement`/`grantsSatisfy`, the segment-exact TS port of
  `framework/authz/grants.go`. The unit table is
  `framework/authz/authz_test.go` transcribed pair for pair — the two
  matchers must answer identically, and a pair added on either side rides
  here too.
- **Phase 3** (`0a888752`) — `permissions-store.ts` (`can(requirement)` and
  `isAdministrator()` as synchronous store reads, deliberate: route guards
  and interceptors ask outside React), `use-permissions.ts`
  (`usePermissions()` → `{ can, isAdministrator }` subscribed via
  `useSelector`), and `can.tsx` (`<Can permission fallback>` — hides rather
  than disables; warns at the render when the slug is not three segments,
  because the matcher's silent false would make a surface vanish for the one
  account that should see it).
- **Phase 4** (`08506f34`) — the refusal-words pin: the guard answers
  `unauthenticated`/`not_found` (the disclosure rule,
  `internal/transport/middleware/guard.go`), no permission code ever reaches
  the client, and `getErrorMessage` passes the server's sentence through.
  The roadmap's refusal-mapping bullet is corrected in place, not extended
  with codes the server never sends.
- **Phase 5** (this commit) — the docs rollup, the validation matrix, and one
  flake fix the matrix shook out: the profile E2E's settle signal.

## The decisions worth remembering (plan D1–D5)

- The claims are mint-time truth (`pkg/jwtutils/access.go:22-26`): the UI
  never refetches grants — the refresh is the refetch. Anything that wants
  fresher grants asks the backend to mint, not a new endpoint.
- The snapshot changes hands at custody alone; there is exactly one decode
  in either realm. A second decode site is a defect, not a convenience.
- `isAdministrator` is `roles.includes('administrator')` — the value the
  backend seeds (`internal/authz/catalog.go:103`); the frontend spells the
  string once, in `permissions-store.ts`.
- A malformed claim must not break the sign-in that just succeeded — the
  decoder degrades, never throws.

## What the next wave inherits

- **Wave 3's admin console** is the first consumer: the admin route guard
  answers `isAdministrator()`, the pages gate their actions with `can('...')`
  requirements written exactly as the guard's rules spell them (the wildcard
  is the instance position's alone), and `ListPermissions`' screens land
  there. `Wave 2`'s step-up modal can compose on top of `<Can>` — the
  namespace stays generic per D10.
- The matcher's cross-check contract: change `framework/authz/grants.go` or
  `libraries/guard/permissions.ts` and re-check both — the unit table is the
  bridge.
- The custody wiring is additive: a future custody surface (the step-up
  bridge, the MFA fork) rides the same listener and inherits the grants
  decode for free.

- Webapp `unit` 142 + `browser` 44 green; `tsc -p packages/webapp` clean;

- E2E: 19/19 over the five release-build files. One real flake was hunted to
  its root during this phase: the profile save's second `toBeEnabled` is not
  a settle signal — it passes before React has rendered the pending state,
  so a reload firing in that window aborts the save mid-body (the server
  answers `context canceled`, the old name survives the reload). The test
  now waits for the real settle — the button going disabled again, which
  only happens once the mutation answered, the answer re-seeded the draft,
  and the refetched view agrees. Ten consecutive profile-file runs went 4/4

  `datastore: commit transaction: failed to deallocate cached statement(s):
  conn closed` under the statement-cache exec mode — pgx's invalidated-
  statement deallocate pipeline on a connection the canceled request closed
  (the jackc/pgx#2100 shape); switching the pool to `DescribeExec` unmasks
  the honest `context canceled` but costs a second round trip per query, and
  the poisoned connection was the aborted request's own, so the default exec
  mode stands and the test's settle signal is the fix.
