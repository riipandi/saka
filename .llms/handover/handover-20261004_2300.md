# Handover — Framework extraction: the composable engine layer (2026-10-04 23:00 UTC+7)

Plan `.llms/plans/plan-20261004_1800.md` — all eleven phases shipped. The round extracted every reusable engine out of the
application into `framework/`, made the layer composable behind typed Options,
moved `database/` into `internal/`, and gave the packages that own tables their
own goose migration sets. After this round a second binary can compose the
engines it wants without inheriting the application's identity, schema, or
event catalog.

## The decisions (D1–D18), their rejected alternatives

Each decision below names what was rejected and why; the plan file holds the
full alternatives list per phase.

- **D1 — framework/ is a directory of the main module**, boundary enforced by a
  `depguard` rule in `.golangci.yml` refusing `internal/**` and `modules/**`
  imports — framework `_test.go` files included (phase 8 proved the need: the
  storage manager test had reached for `internal/database`'s migrations).
  Rejected: a separate Go module now (premature — one version vector to keep in
  step, no second consumer yet), a `pkg/` merge (pkg/ stays the small utility
  layer: `crypto`, `printext`, `envfile`, `jwtutils`, `strutils`, `testutils`).
- **D2/D9 — the config engine knows no keys.** `framework/config` owns the
  sources, precedence, normalization, and resolution; `internal/config` is the
  schema (struct, defaults, validation, vocabularies) and wraps the engine.
  Rejected: moving the whole schema (no composability), key injection into the
  engine (a `map[string]any` engine is no engine).
- **D3/D15 — scope.** Tier A (kernel, datastore, health, config, authz engine) +
  Tier B (observer, fetcher, cache, logger, webutil, middleware) + mailer +
  storage + bundler + queue/scheduler/audit engine splits. Rejected: also
  moving guard/transport/registry (they are the application's composition).
- **D4 — tables belong to their engine.** A framework package owning a table
  declares the constant locally (`TableQueueTasks`, `TableSchedulerJobs`,
  `TableAuditLogs`) and carries the DDL in its own set. `database/entity` keeps
  only application tables. Rejected: keeping everything in `entity` (the engine
  would import the app), constants-per-column (never the style).
- **D7 — the migration toolkit.** `framework/migration`: `Set{Name, FS,
  VersionTable, LockKey}`, `Compose` (refuses duplicate names, version tables,
  lock keys), the `Runner` (up in composition order, down in reverse with one
  shared count budget), `ValidateFS`, `CreateMigration` (directory required).
  Each set its own goose `Provider`, its own session locker, its own version
  table (`app_migration`, `queue_migrations`, `scheduler_migrations`,
  `audit_migrations`) and lock key. Rejected: River-style self-migration per
  engine (an engine migrating at construction is a boot-order hazard), a single
  injected app sequence (sets stop being composable), a minimal runner only
  (validation and creation are what goose's API does not give).
- **D8 — the identity rule.** An engine's names are bare domain words by
  default (`queue.tasks.enqueued`, scope `queue`; `cache:`, `ratelimit:` key
  prefixes; `fetcher` scope); the application widens them through typed Options
  (`TelemetryNamespace`, `Scope`, `KeyPrefix`, `LinkPathPrefix`, `Surface`) via
  the `Config.*Options()` adapters. Rejected: hardcoding `saka` (the old bug,
  just moved), a global identity registry (hidden state).
- **D10 — no back-compat shim.** Importers were rewritten in full each phase;
  the tree is one binary, the callers all in-repo. Rejected: alias files (they
  would live forever).
- **D11/D12 — mailer and storage move on typed Options.** `mailer.Options`
  (host, port, credentials, TLS, timeout), templates as caller's `fs.FS`;
  `storage.Options{Driver, LocalPath, S3, Scope, TelemetryNamespace,
  LinkPathPrefix}`. The Saka-isms became fields. Rejected: keeping the engines
  internal (the round's whole point).
- **D13/D14 — webutil has no Gin-style Context** (stdlib `http` types through
  and through), and `pkg/testutils` split: containers stay, the migrated-
  database helpers moved to `internal/testutils` (they compose the app's sets).
- **D16 — composability is a test.** Every moved package builds from declared
  dependencies and Options alone, with a construction test; framework tests
  stand their own fixtures up (fixture DDL schemas, `fstest.MapFS`). This is
  the rule the depguard rule exists to protect.
- **D17 — the bundler** mounts from an `fs.FS` plus a `Page` (the shell
  document): `MountDev`/`MountRelease` replace the app's `go:embed`; `web/`
  keeps the embeds and the page. Rejected: embedding in the framework (an
  engine cannot embed the app's assets), a framework-owned index.html.
- **D18 — middleware engine vs policy.** requestid, logger, recoverer, timeout,
  security, cors, ratelimit (engine + kvstore driver), clientip are framework;
  guard, bearer, apikey, clientinfo, ratelimit-database are the application's
  policy and stay internal.
- **Deltas worth knowing.** The audit set's `user_id` carries **no foreign
  key** (the original fragment had `ON DELETE SET NULL`): an audit record must
  survive its subject's deletion with the identifier intact, and the set must
  stand alone. The metric namespaces went bare (`queue.tasks.enqueued`, not
  `saka.queue.tasks.enqueued`) with the app passing its identifier. The queue's
  kvstore key prefix is `ratelimit:`, not `saka:ratelimit:` — existing dev
  windows restart, nothing else. The app set was renumbered (old
  `00010–00016` → `00009–00015`) because the set validator demands consecutive
  versions after `00009`'s scheduler DDL moved out; the stale `app_migration`
  row stays as history and the first run over an existing database records the
  framework sets without touching data (`CREATE TABLE IF NOT EXISTS`).

## What was deliberately deferred

- **The module split.** framework/ stays a directory of the main module until a
  second binary actually consumes it; depguard is the boundary until go.mod is.
- **The key-metadata config hybrid.** The sealed-key machinery (`seal_fp`,
  rotation) is unchanged this round.
- **The first sidecar binary.** Nothing consumes the framework yet besides the
  application itself; the composability tests are the proof, the consumer is
  the next round's work.
