## E2E-only catches (worth knowing next time)

- Mailpit in `container/compose-dev.yaml` **requires SMTP auth** (`MP_SMTP_AUTH`):
  `maileruser1`/`mailerpass1` are in the compose file. Without
  `MAILER_SMTP_USERNAME`/`MAILER_SMTP_PASSWORD` every send fails with smtp 530 and the
  queue retries.
- A new email template needs `task email:build` before the Go binary embeds it — a
  `go build` alone ships the stale set and the send fails with
  `unknown template "reauthentication-code"`.
- The text render of a code **doubles the inline code** in the text body
  (`4QaJmy4QaJmy` for the code `4QaJmy`) — pre-existing rendering artifact of the text
  templates, cosmetic, but it will confuse anyone scraping codes from Mailpit in E2E.
- Admin `CreateUser` leaves the account **unverified**: with
  `auth.verify_email_at_signup` on, the account cannot sign in until its verification
  code is confirmed. Flagged as pre-existing intended behavior; the operator triggers
  the verification email through `EmailVerificationService/SendEmail`.

## Known flakes

- Resolved during this session: `TestForgotPasswordIssuesOneTokenPerAccount` was not a
  flake — `crypto.AlphabetUnambiguous` carried `0` and `1` against its own design
  comment ("drops 0/O, 1/l/I"), so ~a third of minted codes tripped the test's
  `[2-9]` regex at random. The alphabet now ships `23456789`; the failure pattern that
  looked like container-load flakiness is gone. The `identity/verification` load flake
  (from the earlier session) keeps its "fails in parallel batches, passes alone"
  behavior — still unexplained, still not reproduced in isolation.
