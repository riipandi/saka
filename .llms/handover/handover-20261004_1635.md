## The decisions, and the rejected alternatives

1. **Offboard action = a permanent ban** (owner's pick): the restrictions row
   with no expiry, every session revoked through `RevokeAllForUser` in the same
   transaction, and the existing `user_banned` audit event carrying the
   offboarding reason with the provider's slug inside it. Rejected: a
   `disabled`-flag write (a second access-withdrawal concept with no audit
   vocabulary of its own); unlink-only (the account keeps signing in by its
   other credentials); account deletion (irreversible, for an automated
   judgement).
2. **The probe is the refresh-token grant**: `invalid_grant` is the provider's
   own word for "this identity is gone". Rejected: a userinfo check against the
   stored access token (an expired access token is normal after an hour — the
   probe would offboard every holder whose access token aged out); an
   admin-driven sweep (the hole this plan closes is precisely the one nobody is
   watching).
3. **A binding with no refresh token is uncheckable and skipped, fail-open.**
   The provider that answered no tokens cannot be judged dead; failing closed
   would offboard those holders on the first pass. The skip is logged with a
   count, not silent.
4. **Retrieval is holder-only, guard `Session`** (owner's pick): a foreign or
   unknown binding answers the same `not_found`. Rejected: a step-up (the read
   mutates nothing); an admin variant (no consumer named).
5. **Refresh on read, with rotation stored**: an expired access token (or one
   inside a 60-second grace window, or one whose age is unknown) refreshes
   first; the rotation persists. **Any refresh failure answers the stored
   tokens** — the read does not fail because maintenance did, and the
   `invalid_grant` judgement belongs to the offboarding job.
6. **Every sign-in refreshes the binding's tokens too** (the resolution's own
   transaction), replacing the write-once-at-first-bind shape — otherwise a
   second sign-in after a provider-side rotation would store nothing new and
   the probe would judge month-old material.
7. **No new audit event vocabulary**: the offboard records as `user_banned`.
8. **Migration is an in-place edit of `00016`** (owner's standing rule):
   `oauth_linked_accounts.access_expires_at TIMESTAMPTZ`, NULL when the
   provider named no expiry.

## What the E2E round found (the ladder earned its keep)

- **The fetcher's classification ate the protocol.** The shared fetcher marks
  a 4xx as its own error; the first `FormPostAdapter` dropped the response on
  `err != nil`, so the mock's `invalid_grant` body never reached the token
  client — the offboarding probe classified a refused grant as a transport
  failure and skipped the binding. Fix: the adapter hands the classified
  response back (`res != nil` wins over the verdict; only a call that never
  answered is transport). The container tests never caught it because the
  `recordingPoster` stub bypasses the fetcher — the wire probe is the only
  test that exercises the real adapter stack.
- **Revocation bites at renewal, not at the access token.** The guard reads
  the signed claims — no per-request session-row check — so a revoked
  session's access JWT answers until it dies. The probe's honest check is
  `AuthService/Refresh` with the holder's refresh token answering `401`.
- The mock (navikt `mock-oauth2-server` 6.0) rejects unknown refresh tokens
  with `400 invalid_grant` (strict since 4.0). The ladder stages a dead
  refresh token the honest way: the connection's client secret is re-sealed
  around a string the mock never minted (`UpdateConnection`), the sealed form
  is read from the database and copied onto the binding's refresh column, and
  the secret is restored — the presented token is a well-sealed bogus. The
  pending pass is nudged with `UPDATE queue_tasks SET wait_until = now()`; the
  dispatcher's fallback poll (one minute) picks it up.
