# Load test report — the HTTP surface under k6

Audit date: 2026-10-05. The comprehensive run over the release binary
(`task start`, `build/release/saka serve`): the smoke, load, and stress
profiles from `scripts/loadtest/` (committed `240cc3c7`, fixes `416aaaa6`,
`96488cbc`). This report is the load-test record; the code audit of the same
tree is `audit-20261005_0940.md`.

## The setup

- **Target:** the release build serving on `localhost:3000`, a seeded
  database, the storage engine live — the fixture object uploaded by setup().
- **Rate limits raised for the measurement** in the untracked local
  `app.config.json`: `rate_limit.limit` 60000/min (≈1000 req/s per client)
  and `auth_limit` 6000/min, from the defaults of 60 and 10 per minute. The
  defaults are the security posture and stay in place for production; the
  raised values exist so the run measures the server rather than the guard
  (the first load run, at 6000/min, showed exactly that: 429 refusals, not
  server behavior).
- **The scenarios:** ten, one per crucial endpoint — health, JWKS, sign-in,
  session reads, notifications, the audit log's faceted list, the queue
  admin's reads, the storage GET, and a serial refresh (one VU rotating its
  own pair, because a concurrent refresh is a reuse the session revokes).

## Smoke (1 VU, 20 iterations per scenario)

A correctness pass: all ten scenarios answered success, zero failures, and
the latencies read idle — health 0.2 ms, JWKS 0.3 ms, the DB-backed reads
2–3 ms, sign-in 152 ms (the scrypt hasher's deliberate cost), refresh 15 ms.

## Load (ramping to 250 VUs across the surface, 4½ minutes)

The unbounded shape: each VU loops flat out, so the run arrives at
~34,700 requests/second aggregate — deliberately unrealistic, the point
being whether the server survives, not what a user feels.

| Question | Answer |
| --- | --- |
| Volume | 9,368,579 requests, 0.00% failed — not one error, not one refusal |
| Health / JWKS | p95 5.1 ms / 4.6 ms — untouched by the storm |
| The DB-backed reads | answered, but slowed: p95 539–673 ms (get-session, list-sessions, notifications, audit log) |
| The heaviest | `admin-queues` p95 8.4 s; `signin` p95 10.4 s — the scrypt hasher holds a core per call |
| Memory | grew 150 → 521 MB, stable, no leak signature |

**Read:** under an extreme-and-unrealistic hammering the server degrades
gracefully — slower, never down, never wrong, no 5xx — and the fast paths
(health, JWKS) keep their speed throughout.

## Stress (arrival-rate ramps to ~450 req/s aggregate, 11 minutes)

The representative shape: traffic at a controlled rate, rising to a sustained
~450 requests/second across the surface.

| Question | Answer |
| --- | --- |
| Volume | 293,609 requests at 444.5 req/s |
| Outcome | checks 100.00% succeeded; every threshold met; exit 0 |
| Latencies | health p95 0.46 ms · JWKS 0.37 ms · get-session 4.4 ms · notifications 5.2 ms · audit log 6.9 ms · list-sessions 8.2 ms · admin-queues 31.4 ms · sign-in 171.4 ms · storage 4.0 ms |
| Memory | 311–445 MB while under load, settling after |

**Read:** at a sustained 450 req/s the server is comfortable — its slowest
endpoint sits 10× inside its budget, and the ceiling was not reached. The
load profile above was the harsher test; the server passed both.

## What the runs surfaced (and fixed)

- **ConnectRPC answers without an envelope** — the response body is the
  protojson message itself; refusals are `{code, message}`. The first client
  assumed the REST envelope and read every procedure as a failure.
- **The procedure services**: GetSession/ListSessions/Refresh live on
  `saka.authn.v1.SessionService`, ListQueues/ListTasks on
  `saka.system.v1.QueueService` — the first draft had named
  `AuthService`/`SystemService` and collected `unimplemented` refusals.
- **k6 mechanics**: threshold durations are plain milliseconds (v2.3 rejects
  `"300ms"`); an executor's `exec` name must be a valid JS export (the dashed
  scenario keys map to camelCase exec functions); stage targets in the
  arrival-rate executor must be integers; and a duration-based single-VU
  scenario loops flat out — the smoke profile is per-VU iterations for that
  reason. `k6 inspect` does not inherit the process environment; pass `-e`.

## Observations left standing (not defects)

- **The rate limiter's `database` driver touches the database on every
  counted request.** Under the load profile's 34k req/s this is part of why
  the DB-backed reads slow together; a deployment with high sustained traffic
  can name the `kvstore` driver and move that write off the SQL pool. The
  database driver is the right default for a single-instance deployment.
- **`admin-queues` degrades furthest** under the unbounded shape (p95 8.4 s):
  the queue admin's reads count live and dead rows per call. Worth
  re-measuring only if the admin surface becomes a hot page in practice.
- **The stress ceiling was not found** — 450 req/s is inside the server's
  comfort zone on this machine. A run with the stage targets at 600–1000/s
  would locate the actual bend; the profile takes it as `K6_VUS` today only
  for the load shape, so a higher stress run is one number away.
