# Backend auth audit — sessions, refresh rotation, revocation

Audit date: 2026-10-14. The backend half of the frontend auth audit's open
item (issue-20261008_1705): the session surface's refresh-rotation queries,
the session-row indexes, and the replay-revocation write pattern, reviewed

## Findings fixed in this phase

### 1. The inactivity gate's revocation rolled back with the refusal (defect)

`Service.Refresh` runs inside one `WithTx`, which rolls back on any error.
The inactivity gate called `repo.Revoke(ctx, tx, …)` and then returned
`ErrSessionEnded` — the sentinel error rolled the revocation back with it,
so the "revoked on the spot" the comment promised never happened: the idle
row stayed unstamped until `expires_at` closed on its own, and the session
center kept listing it as live. The replay branch had the right shape (set a
flag, return nil, let the transaction commit, carry the sentinel out of it);
the gate now does the same (`idledOut` rides beside `reused`). Proven with a
negative check: the corrected test fails against the old shape and passes
against the new one.

### 2. The gate's own test never reached the gate (test defect)

`TestAnIdleSessionIsRefusedAndRotatedOut` presented the token the previous
renewal had already spent — the second `Refresh` took the replay branch
(`rotated_token_hash` match), revoked the session as compromised, and
committed, so the assertion on `revoked_at` passed without the inactivity
gate ever firing. The test now presents the renewal's replacement token, so
it exercises the gate it names. The replay-vs-gate confusion is why finding 1
survived: the suite was green while the gate's revocation was rolled back on
every fire.

## Findings that stand (no change)

- **The replay-revocation write pattern is sound.** `LockByRefreshHash`
  takes the row lock before any read, so two in-flight renewals of one token
  serialize; a presented hash matching `rotated_token_hash` is the reuse
  signal; the revocation and the audit record write in the caller's
  transaction, the audit insert inside its own savepoint
  (`datastore.WithSavepoint`), so an audit failure cannot roll the
  revocation back and an aborted statement cannot poison the caller's write.
  The commit is what carries both out — a replay that rolled back would
  leave the leaked session live, and it does not.
- **The indexes serve every shape.** `token_hash UNIQUE` answers the
  current-secret arm, `idx_sessions_rotated_token_hash` (partial) the
  spent-secret arm, and the renewal's OR composes them as a BitmapOr;
  `(user_id, expires_at)` serves the bulk revoke's lock read and its write
  predicate; the session center's page sorts over one account's rows only —
  a top-N heapsort of tens of rows, no index change warranted. The seq scans
  a naive probe shows are artifacts of volatile function arguments and the
  dev table's size, not the bound-parameter shape the code sends.
- **The token custody chain is coherent.** The refresh secret is 32 random
  bytes, base64url; the stored form is its SHA-256 hex, so a row read is not
  a credential; both issuers (`pkg/crypto.NewRefreshTokenPair`) hash the
  same way, and rotation rewrites `token_hash` while keeping the spent hash
  beside the row for exactly one window — the reuse signal.
- **`FindActiveByTokenHash` is a test-only reader.** No production caller
  (the renewal locks; the sign-in inserts; the access token verifies
  statelessly). It stays as the tests' read helper — it is index-served and
  harmless; noted so a future pass does not mistake it for a live path.

## Finding opened as an issue

- **Session rows are never swept.** `internal/jobs/cleanup_job.go` purges
  queue rows, MFA enrollments and bridges, webauthn tokens, signup tokens,
  and device-login requests — the sessions table is absent. Ended rows are
  deliberately kept listed ("the stamp is the fact a holder reads"), but
  nothing prunes them after any horizon, so the table and every account's
  `ListSessions` count grow without bound. A retention sweep (ended or
  expired past N days) fits the job's existing pattern; it implies a
  retention key and a named surface, so it opens as
  `issue-20261014_0330.md` rather than landing here.
  → resolved 2026-10-14: `plan-20261014_0504.md` landed the key, the two
  retention indexes, and the daily `session_cleanup` sweep.
