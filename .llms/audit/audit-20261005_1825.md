# OIDC provider audit — deep pass, E2E, certification readiness

Audit date: 2026-10-05. The OIDC/OAuth provider surface (`modules/federation/oidc`,
the protocol mounts, the guard rules, the `oauth_sessions`/`oauth_jtis` storage,
the sweeps) reviewed against the goal of OpenID Connect certification. The prior
audit (`audit-20261005_0940.md`) covered the framework extraction and
concurrency at large; this one is the provider's own pass: the grant lifecycle,
the client surface, the metadata contract, the database shape, and a live E2E
exercise of every grant the discovery document names.

## Findings fixed

### 1. The discovery document advertised a dead `jwks_uri` (cert-failing)

The metadata renders `jwks_uri: {issuer}/oidc/.well-known/jwks.json` — the
library joins the path prefix — while `Protocol.Mount` never registered that
path: the only JWKS face was the identity module's root
`/.well-known/jwks.json`. A relying party that fetched the metadata and then
the advertised URI met a 404; every token verification would have failed in
the field. Fixed by mounting the provider's handler at
`protocolPrefix+protocolJWKSEndpoint` with its guard rule, and pinned by the
metadata test, which now fetches every advertised URL and refuses a 404.

### 2. The metadata advertised an unreachable registration endpoint

`WithDCR` is what resolves clients (and materializes CIMD identifiers on
first sight), and the library advertises `registration_endpoint` whenever a
DCR manager exists — with no way to suppress the member. The route stayed
unmounted, so the metadata pointed at a 404. Registration is the management
surface's job by design, so the fix mounts the endpoint and lets the store's
refusal answer: a POST receives the RFC 7591 `invalid_client_metadata` 400,
never a bare 404. The metadata is now honest about where a registration
request lands, and dynamic registration stays closed. Pinned by the metadata
test.

### 3. A lost compare-and-swap answered 500

Under the race probe, the requests that lost the one-time grant's
compare-and-swap answered **500** — the library turns any store error it does
not recognize into `internal error`. A lost race is the normal outcome of
concurrent redemption, not a server fault, and RFC 9700 names the refusal:
`invalid_grant`. `grantStore.SaveGrant` now wraps
`ErrGrantConcurrentlyModified` in the goidc error the token endpoint maps
onto the OAuth error body. After the fix the probe answers exactly one 200
and seven 400s per round. `errors.Is` still matches, so the CAS tests hold.

### 4. The consent-revocation deletes scanned the whole table

`revokeGrants` (the end-session and consent-withdrawal path) deletes the code
and refresh pointer rows with
`request_data->>'grant_id' IN (...) AND kind IN ('authcode','refresh')` — no
index answered the JSONB expression, so at 200k seeded rows the delete
sequential-scanned the table (28 ms here; the cost grows with the
deployment's whole token population, not with the consent being withdrawn).
Migration `00016_oauth_session_grant_indexes` adds the partial expression
index for the two pointer kinds and a `(client_id, request_data->>'sub')`
partial index for the grant rows the same delete names by subject (the
existing client-subject index serves the authn session's document shape, not
the grant's). Both deletes are index-backed after the migration: sub-millisecond
at 200k rows.

## Reviewed and found sound

**The compare-and-swap itself.** The live race probe and the store's own
`-race` tests agree: of the requests racing on one code or one refresh token
exactly one wins, and a replayed refresh token answers not-found because the
rotation deletes the retired pointer row in the same save that mints the
replacement.

**Code replay.** A replayed authorization code is refused, and — per RFC 9700
— the grant the code issued is revoked with it: the previously minted access
token stops answering userinfo. Verified live (E2E pins both halves).

**OWASP posture of the provider surface:**

- *Open redirects / redirect_uri tampering* — the callback matcher
  (`urlmatch.go`) requires an exact pattern match with query-count equality,
  refuses `javascript:`/`data:` schemes, implements the RFC 8252 loopback
  port rule, and an unregistered `redirect_uri` answers 400 (pinned in E2E).
- *SSRF via CIMD* — the allowlist is judged before any fetch, an empty
  allowlist is the feature off, the fetch runs through the shared fetcher
  (per-host circuit breaker, size-capped body, sensitive-header-stripping
  redirects), the document is capped at 1 MB and 15 s.
- *Client secret storage* — SHA-256 hex of the value, constant-time compare,
  several live secrets per client for rotation. (See observations: a
  carried-over low-entropy secret hashed with unsalted SHA-256 is the weak
  shape; the random mint is the intended path.)
- *Rate limiting* — the token, revoke, PAR, and device-authorization
  endpoints ride the auth bucket; authorize and userinfo are exempt by
  design (the redirect is free, the bearer already paid).
- *SQL injection* — every query is parameterized through the sqlbuilder
  helpers; the two raw fragments interpolate bound parameters only.
- *JWT handling* — signing algorithms come from the database's key rows
  (no `none`), the JTI consumer claims every client-presented JWT's ID
  against a unique index (replay refused without a read-then-write window),
  and the logout policy refuses an `at+jwt` hint.
- *Secrets in responses* — a client secret exists in exactly one response;
  the list views carry prefixes and windows only.

**Memory and lifecycle.** The per-request CAS context objects are bounded by
the request lifetime; the JTI table is bounded by the 15-minute replay
window and the hourly sweep; `oauth_sessions` is bounded by expiry plus the
sweep's grace, with the NULL-expiry carve-out pinned by tests. No unbounded
map or ticker leak in the provider's own code (the framework-level tus lock
leak was fixed in the prior audit).

**Resource hygiene in the CIMD path** — the fetcher owns the body, the
cap is enforced both by the transport and the caller.

## Observations left standing (not defects, owner's call)

Dispositions follow each item — the certification-readiness phases
(`.llms/plans/plan-20261005_1845.md`) resolved most of them.

- **PKCE `plain` is still supported.** RFC 9700 discourages it; the metadata
  advertises `["S256","plain"]` and the provider accepts both. Certification
  only requires S256, so this is a posture choice: dropping `plain` from
  `WithPKCE` would harden the profile but break any client that chose it.
  → **Addressed (phase 1):** `plain` dropped — S256 only, discovery names
  `["S256"]`; no backward-compatibility burden (D7).
- **`id_token` carries no `at_hash`** on the code flow — optional in OIDC
  Core §3.1.3.6 (required only for implicit); the conformance suite's Basic
  OP profile does not demand it.
  → **Accepted (D8):** the engine's code-flow issuance passes no access
  token into ID-token minting; the deviation is recorded, not forked.
- **Client credentials secrets**: an operator-supplied secret is hashed with
  unsalted SHA-256 (the right shape for the 32-char random mint the service
  draws, weaker for a human-chosen carried-over value).
  → **Addressed (phase 1):** operator-supplied secrets now salted PHC
  (scrypt) via `crypto.NewPasswordHasher()`; machine-minted secrets stay
  SHA-256.
- **`AllAuthorizedClients` (the deployment-wide consent ledger read) is
  unbounded** — an administrative read with no pagination. Fine at current
  scale; worth a page size if the surface becomes a hot admin page.
  → **Addressed (phase 1):** paginated (proto page/limit, shared metadata
  block).
- **The rate limits in the dev `app.config.json` are raised** (60000/min)
  from the security defaults for load measurement; the posture that ships
  should keep the defaults (60/min, auth 10/min) — the E2E scripts need the
  raised values only because they drive hundreds of requests in seconds.
  → **Addressed (phase 1):** the tracked config rests at the security
  defaults; the E2E drives a throwaway config via `serve --config-file`.
- **`.llms/index.md` named `docs/oidc-provider/`**, which does not exist —
  removed in this pass.
  → **Addressed (phase 6):** the product page now exists at
  `docs/oidc-provider/`.

## Certification readiness (Basic OP profile)

What the live server answers today, verified by the E2E script:

- Discovery (OIDC Discovery + RFC 8414 alias), JWKS at the advertised URI,
  issuer, endpoint set, scope/claim lists — conformant, all advertised URLs
  answer.
- Authorization code flow with mandatory PKCE (S256), RFC 9207 `iss`
  parameter, PAR, response mode `query`/`fragment`, one-time codes with
  replay-revocation per RFC 9700.
- ID token: ES256, `nonce` echo, `sub` stability (the raw UUID the grant
  stores), `iss`/`aud`/`exp` from the library's mint.
- Userinfo: bearer authentication, scope-gated Standard Claims.
- Refresh: rotation with replay refusal; `offline_access` rides the
  long-window setting.
- Introspection (RFC 7662, client-scoped) and revocation (RFC 7009, grant
  revocation on access-token hint).
- Device grant (RFC 8628) with hashed pointer rows; end-session (RP-initiated
  logout) with hint verification; back-channel logout delivery.
- Client credentials for machine-to-machine, per-client allowlist.

What stands between this and a certification run:

1. **The OpenID conformance suite itself** — the profiles (Basic OP with
   `code` flow, optionally Form/PAR/Dev profiles) run against a
   publicly reachable issuer; the local run here is the rehearsal. The
   scripts under `scripts/` are the harness seed, not the suite.
   → **Resolved (phases 3–5):** the suite runs locally in Docker; Basic OP
   35/35, Config OP 1/1, RP-Initiated Logout 11/11, Back-Channel Logout 2/2.
2. **A decision on `plain` PKCE** (above) — recommend dropping it.
   → **Resolved (phase 1):** dropped.
3. **HTTPS issuer** — certification requires a TLS-terminating front; the
   local issuer is plain HTTP.
   → **Resolved (phase 3):** the rehearsal issuer terminates TLS at
   `https://saka.localhost.test:3443` (mkcert material, suite-side nginx).
4. **`claims_supported` could name `sub` and the Standard Claims' common
   siblings** — cosmetic; the suite does not verify the list's contents.
   → **Resolved (phase 1):** the list names the registered claims the
   tokens mint beside the scope-gated profile claims.
5. The stale `.llms/index.md` product-doc reference is fixed; the product
   docs for the OIDC surface (`docs/`) do not exist yet — if the
   certification submission includes public documentation, that page is
   still to be written.
   → **Resolved (phase 6):** `docs/oidc-provider/` written.
