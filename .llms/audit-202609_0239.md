## Change already in the tree

`internal/queue/dispatcher.go` waits on a one-slot `workerIdle` signal when every worker is busy, and returns when the start context or the shutdown context is done. The signal carries no token. The fetcher recounts free workers, and it is the only receiver of those tokens.

The old loop slept 100ms and did not watch shutdown. A worker that leaves because its context ended never returns a token, so that loop could run until the process exited.

Tests: `TestFetchWaitsUntilAWorkerIsFree`, `TestFetchReturnsWhenTheRunStops`, `TestWatcherSettlesConcurrentWriters`. `go test -race -count=1 ./internal/queue/ ./internal/storage/` passed.

The queue section of `.llms/architecture.md` records the same wait.

## Medium

Each item has its own tests and its own rule. Land them separately.

### 1. Refresh rotation does not compare the hash it replaces

`Rotate` in `modules/identity/session/repository.go` updates `WHERE id AND revoked_at IS NULL`. `Refresh` in `modules/identity/session/service.go` reads the token, then writes.

Two in-flight refreshes of the same token can both pass `FindActiveByTokenHash` and both commit. Both store the original hash in `rotated_token_hash`. The loser's new secret is never stored, so presenting it returns `ErrSessionEnded` and does not call `revokeCompromised`. The winner keeps a live session. Reuse detection fires when a token that was already rotated is presented later. It does not fire when two first uses overlap.

Fix: `SELECT … FOR UPDATE` the session row, and include the hash being replaced in the `WHERE`. If the row is still live under a different hash, treat that as reuse and revoke the session.

### 2. Email-change confirm can apply a stale payload

`UpsertEmailChangeToken` keeps the row id and replaces `token_hash` and `payload`. `ConfirmEmailChange` copies the payload into memory, writes that address, then `DeleteToken` deletes `WHERE id` and ignores `RowsAffected`.

Under READ COMMITTED, a confirm that read the row before a re-request committed can set the old address and delete the new token. Password reset already deletes `WHERE id AND token_hash`. This path should too, and a zero-row delete must abort the transaction.

### 3. A superseded one-time-access code can delete its replacement

`Exchange` finds by hash, then `DeleteToken` deletes `WHERE id`. `UpsertToken` keeps the id. An exchange that read the old row before a re-issue committed still opens a session for that same account and removes the new code.

Same fix as item 2: `WHERE id AND token_hash`, and fail the transaction when no row is removed.

### 4. An impersonated refresh can sign a token with no actor

When `ImpersonatedBy` is set and `ReadAccount` fails, `Refresh` ignores the error and still signs. `IsImpersonating` reads `ActorID` only. The token is for the target account with no actor, so `Session` and `Authenticated` treat the caller as that account. The comment above the read says a delegation that cannot name its actor is worse than the query. The code signs anyway.

Fix: if the row is a delegation and the actor cannot be read, return `ErrSessionEnded` and do not sign. Read the actor before `Rotate`, so a failed read does not burn the refresh token first.

### 5. Re-stage can keep a content hash of the previous bytes

`Stage` in `internal/storage/manifest.go`, on conflict, updates the staging fingerprint and sets `pending`. It leaves `content_hash` as it was. `Sync` in `internal/storage/manager.go` reuses that hash when status is `pending`, the hash is non-empty, and size and mtime match.

After `Stage`, the stored fingerprint is the new file's. A match means Stage just wrote this stat. It does not mean the stored hash was computed from these bytes. `Sync` skips hashing, uploads the new bytes, and records the old SHA-256.

Whether mtime matches depends on what survives a round trip through `timestamptz` (microseconds). On a coarse volume this is the normal re-stage path. On APFS, a sub-microsecond residue can make a local test pass while the bug remains. The other direction is the same comparison: a retry of an unchanged file on a nanosecond filesystem almost always hashes again.

Fix: clear `content_hash` on re-stage. Compare mtimes after truncating both sides to microseconds, so an honest retry still takes the fast path.

### 6. The upload deadline does not stop the hash or the local write

The upload task times out at 30 minutes so it stays under `queue.release_after` (default one hour). `Register` refuses a timeout that is not strictly shorter, so two workers do not run one task.

The hash in `Sync` is `io.Copy` with no context check. `FS.Put` in `internal/storage/storage_fs.go` discards its context and copies the same way. The S3 `Put` uses the context.

If hashing plus the local write outlasts `release_after`, the row stays claimed while the first worker is still inside `io.Copy`. The next claim takes the same key. Two renames and two manifest writes can overlap, and staging cleanup can unlink a file the other worker still has open.

This shows up for a file whose work exceeds the release window, not for an ordinary upload. Fix: a reader that returns when the context ends, in the hash and in `FS.Put`.

### 7. The API-key reminder schedule duplicates itself when the scan fails

`apiKeyExpiryScanProcessor` in `internal/jobs/apikey_expiry_job.go` saves its successor before `ListExpiring`. The cleanup job saves its successor only after the work succeeds (`cleanup_job.go`).

When `ListExpiring` fails, the successor is already committed and the attempt is retried, which inserts another successor. Three attempts can leave three daily chains. Two overlapping chains can both send a reminder before either marks the email sent.

Fix: enqueue the successor only after the scan returns nil. Unmarked keys are still picked up on the next pass. A crash between the scan and the enqueue loses one day, and does not leave a second permanent schedule.

### 8. A failed audit insert aborts the caller's transaction

`Record` in `internal/audit/recorder.go` logs the error and returns. Its comment says the caller is not failed. On Postgres any statement error aborts the transaction until rollback (`25P02`). Later statements, or the commit in `WithTx`, fail, and the change that was supposed to survive an audit miss rolls back with them. The caller sees an error that does not name the audit insert.

`user_id` and `resource_id` are UUIDs with a foreign key, and `trigger_type` is an enum. A bad id or trigger is enough.

Fix: run the insert under a savepoint and roll back to it on failure, so the outer transaction can still commit.

## Low

### 9. API-key renew does not repeat the check the read just made

`Renew` refuses a missing, foreign, or unexpired key on the read. `RenewKey` then updates `WHERE id` only. A concurrent revoke, or two renews, can still change the hash. A revoked row stays revoked, and only the last hash is stored, so this is not an authorization bypass. The caller who lost the race is handed a raw secret that will not authenticate.

Fix: put `user_id`, `revoked_at IS NULL`, and `expires_at <= now()` in the `UPDATE`, and map zero rows to the same errors as the read.

### 10. Creating a staging directory enqueues an upload of the directory

In `internal/storage/watcher.go`, a `Create` for a directory is added to the watch and then falls through to `resetTimer`. `stageKey` accepts `avatar/usr_1`. After the debounce, that key is enqueued as a file. `Sync` opens it as a file, the read fails, and the task retries until it is dead. Every new directory on a nested key does this.

Fix: `continue` after `watch.Add` when `info.IsDir()`.

### 11. A cache entry larger than one 64 KiB chunk is corrupted once the shard is full

`write` in `internal/cache/cache_memory.go` calls `nextChunk` when the entry does not fit. At the budget, `nextChunk` clears the index and rewinds to chunk 0 before the entry is finished. The tail overwrites the start of the key. The index still names the offset captured before that overwrite, so `Get` misses.

No production caller uses `Set` yet. When one does, reject an entry larger than a chunk, or do not reset the ring in the middle of one `write`.

### 12. Logger shutdown can write an async sink from two goroutines

`SendToLogger` in `internal/logger/async.go` drops its read lock before the send. `Close` sets `closed` and then closes `done`. A producer that already observed `closed == false` can still take the `done` branch and call `inner.SendToLogger` while the worker drains the queue through the same writer. `bufio.Writer` is not safe for two concurrent `Write` calls. The comment on `work` says the closed flag makes this impossible. The check and the send are not atomic.

The window is shutdown only. Fix: hold the lock across the closed check and the enqueue, and have the `done` branch wait until `exited` before it touches `inner`.

## MFA is a product choice

`DeleteTotpEnrollment` skips `verifyProof` when more than one confirmed device remains. `BeginTotpEnrollment` does not ask for a factor the account already holds. That matches the comment and the written rule: proof is required for disable, regenerate, and delete-last.

A stolen session can enroll a new device and then delete the victim's device with no code. The remaining factor is the attacker's. The next sign-in uses it. Requiring proof on enroll while a factor exists, and on every confirmed delete, inside one transaction with `FOR UPDATE`, is a product decision. It is not a drift from the comment.

## Rejected

| Claim | What the code does |
| --- | --- |
| Watcher timer map is a data race | The map is touched only on the `Start` goroutine. The `AfterFunc` callback only sends on a channel. `TestWatcherSettlesConcurrentWriters` pins that path. |
| `runDue` leaks goroutines | Results use a channel buffered to `len(due)`, and the caller reads that many. A check that ignores its context is left running so the aggregate can return. |
| `closeSink` needs a second 5s timeout | The caller already bounds the wait. `closeLogger` uses 5s. A second timer cannot force a blocked `Close` to return. |
| Queue claim logs leak schema to clients | `err.Error()` is an operator log, the logger contract. It is not a response body. |
| Cache `string([]byte) == string` allocates | That comparison does not allocate. `bytes.Equal` through a string-to-bytes copy does. |
| Pool size cannot be configured | `database.max_conns`, `min_conns`, `max_conn_lifetime`, and `max_conn_idle_time` already exist. |
| `ready` / `trigger` buffers are too small | A full buffer drops a wakeup an earlier signal already covers. |
| TOTP decrypt is an N+1 query | One `ListTotp`, then at most 10 in-memory unseals. Migration `00003` indexes `user_id`. Do not cache unsealed secrets. |
| Postgres and Valkey are never closed | Both implement `Shutdown`. `serve` calls `injector.ShutdownWithContext` after the listener drain. |
| `CHECK (expires_at > CURRENT_TIMESTAMP)` rejects a later update | On local Postgres, an expired row still accepted `UPDATE … SET revoked_at` (`UPDATE 1` on a temporary table). Do not drop those checks on this claim. |
| Shadowed names in `WithTx` callbacks | The transaction pattern used throughout the tree. |
| SQL injection in dump and restore | Table and column names go through `pgx.Identifier.Sanitize`. |
| Rate limit fails open | Intentional. The client address comes from `server.trusted_proxy_headers` when that list is non-empty. Committed `app.config.json` leaves it empty, which is right for a process reached directly. A deployment that only sees nginx sets the header there. Do not trust `X-Forwarded-For` by default. |
| A procedure missing from the guard tables | Falls through to `Admin`. |

## Left unchanged on purpose

This pass does not add a watcher mutex, an `errgroup` around health checks, a second logger-close timeout, redacted queue-claim logs, `bytes.Equal` on the cache hot path, new config keys for the pool or the channel buffers, a cache of unsealed TOTP secrets, or a cap on the queue encode `sync.Pool`.

`pgxpool.Stat` exists and is not exported as a metric. That is optional observability. The queue has no depth gauge on purpose.
