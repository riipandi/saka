# Federation and device-flow audit

Audit date: 2026-09-29. Reviewed OIDC/OAuth protocol and management, custom claims, outbound SCIM, OIDC device grant, and Tango device-login pairing. Focused package tests were run; no production fixes were applied in this audit.

## Findings requiring fixes

### High: OIDC authorization does not enforce the client group restriction

`modules/federation/oidc/protocol_policy.go:100-143` resolves the client and sets the subject after sign-in/consent, but does not check that the account belongs to an allowed group. `modules/federation/oidc/consent.go:153-169` filters the user-facing client catalogue only; direct `/oidc/authorize` and device-flow requests bypass that catalogue. The authorization policy must check membership before granting a code/device grant, including the restricted-empty-group case (which should admit nobody). The SCIM-specific view has separate restriction logic and does not protect tokens.

### High: custom claim keys can override standard OIDC claims

`modules/federation/oidc/protocol.go:352-363` merges administrator claims into the emitted claim map after standard email/groups/profile values. `modules/federation/oidc/preview.go:140-146` does the same for previews. `modules/federation/customclaim/service.go` has no key-reservation validation. A key such as `sub`, `aud`, `iss`, `exp`, `email`, `groups`, or `preferred_username` can conflict with a protocol claim. Pocket ID v2.14.0's implementation rejects reserved OIDC claim names (DeepWiki details: `backend/internal/service/custom_claim_service.go:isReservedClaim`). Implement a reserved-name policy at create and update, with tests, and ensure legacy rows cannot overwrite protected claims at issuance.

### High: OIDC device grant can be redeemed concurrently more than once

The pinned `go-oidc` v0.25.0 token handler reads the grant, checks `DeviceCodeConsumedAt`, saves the consumed grant, then issues tokens. These operations are not atomic. The Tango adapter (`modules/federation/oidc/protocol_storage.go:119-159,170-188`) reads grant pointers and writes the state in separate pool operations. Parallel token endpoint requests can both see an unconsumed grant and both pass the check. Context7 documentation for `/luikyv/go-oidc` corroborated the library's sequence. Fix needs to make exactly-one redemption atomic without introducing false token issuance if later token work fails; inspect the pinned module source and its extension points before deciding design. Add an integration concurrency test that asserts one success only.

### Medium: device-login creation limit is declared but not enforced

`modules/devicelogin/schema.go:21` declares `maxPendingRequests = 8`; `modules/devicelogin/repository.go:139-150` provides `CountLiveForToken`, but `Service.Create` (`service.go:65-85`) does not use either. Repeated create calls can fill `device_login_requests` with pending rows until expiry. Implement a race-safe per-device cap (count-then-insert alone races; use an advisory lock or transactional locking strategy consistent with repo SQL rules) and test concurrent requests.

### Medium: SCIM upstream response validation / pagination / cost

`modules/federation/scimsync/sync.go:79-88,112-169,314-336` trusts remote SCIM list items. Missing/empty IDs can lead to unsafe delete paths; absent/malformed `itemsPerPage` can stop pagination or make progress unreliable; `findByExternalID` is repeated for each local record, causing O(local × remote) matching. Validate list records and pagination before any writes/deletes; build one externalId index per resource kind. Use bounded-memory paging or explicitly enforce remote/list limits if practical.

## Race, memory, and database notes

- Device-login pairing state uses status predicates in its `UPDATE` queries to make decision and consume single-use; tests cover sequential outcomes, but a concurrent two-exchange integration test would be useful.
- SCIM is deliberately sequential per provider. `SyncAll` reads all providers, then each `Sync` materializes full visible local snapshots and full remote user/group lists into memory. This can become a memory/latency hotspot at larger tenant sizes; pagination is remote-read but all pages are accumulated. Incremental or streaming reconcile is a future optimization, but must retain deletion safety.
- `modules/federation/oidc/protocol_storage.go:63-69,80-92` stores protocol rows with expiry but does not filter expired rows on reads; expired records remain active. A dedicated cleanup job for `oauth2_sessions` was not found in the reviewed packages. Verify migrations/current job registration before adding bounded cleanup; the table already has an `expires_at` index. Consider partial indexes only if measurements show need.
- Database state is JSONB for grant/session payloads with indexed `(kind,key)`, `expires_at`, and client/subject expressions. Consent revocation currently reads grant IDs then deletes pointers and grants. Benchmark before denormalizing further; any redesign must preserve the secret-hash pointer invariant.
- No confirmed goroutine leak was found in audited paths. SCIM request/retry flow is context-bound through the shared fetcher; device login long poll exits on request context cancellation. Retry uses `time.After`, at most two retry timers per SCIM HTTP call.

## Pocket ID parity comparison

The latest stable release found on the audit date is Pocket ID v2.14.0 (release notes: <https://github.com/pocket-id/pocket-id/releases/tag/v2.14.0>). Its release highlights multiple client secrets, RFC 8414 metadata at `/.well-known/oauth-authorization-server`, CIMD auto-grant support, and SCIM actor migration. Official SCIM docs: <https://pocket-id.org/docs/configuration/scim>. Device protocol reference: <https://datatracker.ietf.org/doc/html/rfc8628>.

Pocket ID SCIM documentation specifies all users/groups for unrestricted clients and only assigned groups/members for restricted clients, hourly sync, five-minute debounce after changes, and manual sync. Tango implements outbound SCIM with a Tango-specific ConnectRPC contract and one-time token response; its differences from Pocket ID's REST service-provider CRUD are intentional and documented in Yaak.

Tango currently exposes `/.well-known/openid-configuration`, not the RFC 8414 alias added by Pocket ID v2.14.0. It supports authorization code, refresh token, and device-code grants; scopes are `openid profile email groups`; it does not support client credentials or `offline_access`. These are feature differences, not request-shape drift.

Tango's device grant routes are `/oidc/device_authorization`, `/oidc/device`, and `/oidc/token`; user interaction must validate the user code per RFC 8628. The current Yaak device authorization, verification, and poll examples use those Tango paths and form fields. The separate Tango pairing device-login surface (`/api/device-login/...`) is not OAuth device flow.

## Phase 1 verification (2026-09-29)

Every finding was re-checked against the source on `refine-architecture` at
`1c6301c`. None was dismissed; two gained sharper evidence than the original
text. Baseline tests: `go test ./modules/federation/oidc/... ./modules/federation/customclaim/... ./modules/federation/scimsync/... ./modules/devicelogin/... -count=1` — all four packages pass (6.3s / 3.3s / 3.7s / 4.1s, testcontainers).

### Finding 1 — client group restriction (confirmed)

`completeAuthentication` (`modules/federation/oidc/protocol_policy.go:100-143`)
never consults `oidc_clients_allowed_user_groups`; all three branches
(skip-consent, explicit consent, the already-consented shortcut at line 136)
set `session.Subject` without a membership check. The device approval walks
the same function through `devicePolicy` — the device flow inherits the gap.
The only restriction query in the package is the catalogue filter in
`consent.go:MyClients` (lines 162-170).

### Finding 2 — custom claim collisions (confirmed, sharper than first written)

The override reaches further than the profile claims. `MakeIDToken` in the
pinned library ends with `maps.Copy(claims, opts.Claims)` (`go-oidc@v0.25.0`
`internal/token/token.go:190`), so the map `subjectClaims` returns overwrites
the library-built `sub`, `iss`, `aud`, `iat`, `exp`, and `nonce` too — a row
keyed `sub` replaces the token's subject, not merely a profile field.
`modules/federation/customclaim/service.go` validates nothing about `key`
(create, update, no reserved-name set anywhere in the package).

### Finding 3 — device grant race (confirmed, with an extra constraint)

`go-oidc@v0.25.0/internal/token/device.go:68-95` reads the grant, checks
`DeviceCodeConsumedAt`, sets it, calls `ctx.SaveGrant`, then issues tokens —
no atomicity, no hook to make the check-and-set atomic from the adapter. Two
facts that shape the fix: `SaveGrant` runs *before* `Issue`, so a CAS in the
`grantStore.SaveGrant` adapter (`protocol_storage.go:119`) can reject a
second redemption before any token is minted; and on an issuance error the
library revokes the grant in the same closure, so a failed issuance never
leaves a redeemable code. `GrantByDeviceCode` resolves through the hashed
pointer row (`sessionKindDeviceCod`) in a separate pool read.

### Finding 4 — device-login cap (confirmed)

`maxPendingRequests = 8` (`modules/devicelogin/schema.go:21`) and
`CountLiveForToken` (`repository.go:142`) have no caller: `Service.Create`
(`service.go:65-85`) inserts without reading the count. The row already
stores only the SHA-256 of the pairing token (`device_token_hash`), so no
raw token is persisted — the cap is the whole gap.

### Finding 5 — SCIM snapshot safety (confirmed, sharper than first written)

The destructive case is worse than a malformed row: `listRemote` decodes each
page into a zero-valued `remoteList[T]` when the body is not a SCIM list, so
a single malformed answer yields an empty snapshot, and `reconcile`
(`sync.go:96-170`) then deletes *every* remote user and group whose
`externalId` is not local — an unauthenticated-looking page wipes the
provider. The pagination loop (`sync.go:315-336`) advances
`startIndex += page.ItemsPerPage` and stops only on
`len(all) >= TotalResults` or an empty page; a remote reporting a large
`TotalResults` with one row per page accumulates without bound (bounded only
by request context). Matching is still O(local × remote): the
`remoteUserID` map at line 112 maps ids for group members, but the
create-or-update lookup is `findByExternalID` per local record (lines 124,
153). `scimURL` (`sync.go:264-274`) joins with `path.Join` over the parsed
base path and `pathEscape`s resource ids, so base-path prefixes and escaped
ids are preserved — existing behaviour to keep, not fix.

### Finding 6 — expired protocol state (confirmed)

`protocolStore.load` (`protocol_storage.go:80-92`) filters on `active`
alone; `expires_at` is written but never read. No job in `internal/jobs`
touches `oauth2_sessions` — the registered cleanups are the queue-record
`cleanup`, `audit_cleanup`, the storage GC, and apikey expiry. The library
checks expiry in-band from the stored payloads (auth code
`internal/token/auth_code.go:52`, refresh `refresh_token.go:43`, device
`device.go:78`, authn and PAR `internal/authorize/validation.go:36`, logout
via `LogoutSessionTimeoutSecs`), so an expired row fails closed at the
protocol level but is reclaimed by nothing.

### Baseline constraints carried into the fixes

- `oauth2_sessions` is JSONB documents over hashed pointer rows; the secret
  hash invariant and the `(kind, key)` upsert in `save` (line 48) must
  survive any atomicity work.
- The repo SQL rules apply to any cap enforcement: single-use state belongs
  in the UPDATE's WHERE; zero rows affected is `ErrNoRows`.
- The scope of the OIDC restriction fix is the server-side completion path
  plus the device approval; the SCIM visibility roll already shares the
  catalogue rule and needs no change for finding 1.

## Remediation record (2026-09-29, phases 1–8 of plan-20260929_1722.md)

Every finding above was fixed and committed on `refine-architecture`. One
new gap surfaced during the phase 8 end-to-end probes and is recorded below
with its evidence.

### Findings fixed

1. **Client group restriction** — enforced at protocol completion
   (`completeAuthentication`) under the fail-closed rule the user chose:
   restricted = `is_group_restricted` flag **or** allowed-groups roll
   carries rows; flag with an empty roll admits nobody. Catalogue and SCIM
   share the rule; SCIM no longer provisions accounts the sign-in would
   refuse. `cf96fb2`.
2. **Reserved custom claim keys** — create and update refuse the set
   Pocket ID v2.14.0 reserves (verified from the tag source) plus
   `tango:token_type`, exact case, `invalid_argument`; the issuance merge
   drops protected keys a legacy row may carry. `4a11973`.
3. **Device grant redemption race** — a per-request snapshot cache
   (middleware on the token and introspection routes; the library
   delegates context values to the request context) arms a compare-and-
   swap in `grantStore.SaveGrant`: the save lands only while the row still
   holds the document the request read. Covers device redemption, the
   authorization code's consumption, and the refresh rotation's rewrite.
   A loser's save is refused before issuance; a losing request that never
   saved cannot clobber the winner's document. `b8f644f`.
4. **Device-login cap** — `CreateWithinLimit` takes
   `pg_advisory_xact_lock(hashtextextended(token_hash, 0))`, counts, and
   inserts inside one transaction; the handler answers 429. `270137b`.
5. **SCIM snapshot safety** — presence-detecting list decode, per-page
   count validation, 100-page/100k-resource bounds, per-row identifier
   validation before any write, `externalId` indexing, and a rewritten
   `scimURL` that no longer double-encodes escaped ids. A malformed body
   fails the pass without deletes. `108bee4`.
6. **Expired protocol state** — `loadDocument` refuses rows the
   `expires_at` column judges dead (2-minute skew allowance, NULL expiry
   exempt); the hourly `protocol_cleanup` job reaps rows past a one-hour
   grace in batches of ten thousand. `cf21065`.

### New finding from the E2E probes — fixed in the follow-up pass

7. **`/oidc/end-session` was broken.** The endpoint was mounted but every
   request answered `invalid_request`: the provider registered
   `WithLogout` without `WithLogoutPolicies`, and the library refuses to
   open a logout session without a policy. Now wired: one policy whose
   setup requires an `id_token_hint` (the provider holds no browser
   session, so a hint-less request names no subject), whose logout
   verifies the hint is not an access token — the JOSE type member, not a
   claim, carries the distinction — and revokes the subject's grants and
   tokens for the client in one transaction, recording
   `oidc_session_ended`. The revoke scope is the new config key
   `oidc.end_session_revokes_consent` (off by default: the grants and
   tokens die, the authorized-client ledger survives). A registered
   `post_logout_redirect_uri` receives the redirect with `state`; an
   unregistered one is refused `invalid_request`; without one the browser
   lands on the SPA root. E2E-verified end to end after the fix. One
   subtlety the tests now pin: the ID token's `sub` claim carries the raw
   UUID form the grant rows store, so the policy accepts both that form
   and the wire form.

### Rejected approaches (kept out of the code)

- Timestamp-based CAS on the consumed transition (same-second collisions
  keep the race alive).
- Pre-consuming the device code at read time (an unauthenticated request
  holding only the code could burn the legitimate redemption).
- Post-consumption saves allowed unconditionally (the loser's revocation
  would clobber the winner's grant document).
- Rolling back the catalogue's roll-only rule (the hybrid rule preserves
  seeded flag rows fail-closed).
