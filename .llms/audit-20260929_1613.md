# Federation and device-flow audit

Audit date: 2026-09-29. Reviewed OIDC/OAuth protocol and management, custom claims, outbound SCIM, OIDC device grant, and Tango device-login pairing. Focused package tests were run; no production fixes were applied in this audit.

## Findings requiring fixes

### High: OIDC authorization does not enforce the client group restriction

`modules/federation/oidc/protocol_policy.go:100-143` resolves the client and sets the subject after sign-in/consent, but does not check that the account belongs to an allowed group. `modules/federation/oidc/consent.go:153-169` filters the user-facing client catalogue only; direct `/oidc/authorize` and device-flow requests bypass that catalogue. The authorization policy must check membership before granting a code/device grant, including the restricted-empty-group case (which should admit nobody). The SCIM-specific view has separate restriction logic and does not protect tokens.

### High: custom claim keys can override standard OIDC claims

`modules/federation/oidc/protocol.go:352-363` merges administrator claims into the emitted claim map after standard email/groups/profile values. `modules/federation/oidc/preview.go:140-146` does the same for previews. `modules/federation/customclaim/service.go` has no key-reservation validation. A key such as `sub`, `aud`, `iss`, `exp`, `email`, `groups`, or `preferred_username` can conflict with a protocol claim. Pocket ID v2.14.0's implementation rejects reserved OIDC claim names (DeepWiki details: `backend/internal/service/custom_claim_service.go:isReservedClaim`). Implement a reserved-name policy at create and update, with tests, and ensure legacy rows cannot overwrite protected claims at issuance.

### High: OIDC device grant can be redeemed concurrently more than once

The pinned `go-oidc` v0.25.0 token handler reads the grant, checks `DeviceCodeConsumedAt`, saves the consumed grant, then issues tokens. These operations are not atomic. The Tango adapter (`modules/federation/oidc/protocol_storage.go:119-159,170-188`) reads grant pointers and writes the state in separate pool operations. Parallel token endpoint requests can both see an unconsumed grant and both pass the check. Context7 documentation for `/luikyv/go-oidc` corroborated the library's sequence. Fix needs to make exactly-one redemption atomic without introducing false token issuance if later token work fails; inspect the pinned module source and its extension points before deciding design. Add an integration concurrency test that asserts one success only.

### Medium: device-login creation limit is declared but not enforced

`modules/devicelogin/schema.go:21` declares `maxPendingRequests = 8`; `modules/devicelogin/repository.go:139-150` provides `CountLiveForToken`, but `Service.Create` (`service.go:65-85`) does not use either. Repeated create calls can fill `device_login_requests` with pending rows until expiry. Implement a race-safe per-device cap (count-then-insert alone races; use an advisory lock or transactional locking strategy consistent with repo SQL rules) and test concurrent requests.

### Medium: SCIM upstream response validation / pagination / cost

`modules/federation/scimsync/sync.go:79-88,112-169,314-336` trusts remote SCIM list items. Missing/empty IDs can lead to unsafe delete paths; absent/malformed `itemsPerPage` can stop pagination or make progress unreliable; `findByExternalID` is repeated for each local record, causing O(local × remote) matching. Validate list records and pagination before any writes/deletes; build one externalId index per resource kind. Use bounded-memory paging or explicitly enforce remote/list limits if practical.

## Race, memory, and database notes

- Device-login pairing state uses status predicates in its `UPDATE` queries to make decision and consume single-use; tests cover sequential outcomes, but a concurrent two-exchange integration test would be useful.
- SCIM is deliberately sequential per provider. `SyncAll` reads all providers, then each `Sync` materializes full visible local snapshots and full remote user/group lists into memory. This can become a memory/latency hotspot at larger tenant sizes; pagination is remote-read but all pages are accumulated. Incremental or streaming reconcile is a future optimization, but must retain deletion safety.
- `modules/federation/oidc/protocol_storage.go:63-69,80-92` stores protocol rows with expiry but does not filter expired rows on reads; expired records remain active. A dedicated cleanup job for `oauth2_sessions` was not found in the reviewed packages. Verify migrations/current job registration before adding bounded cleanup; the table already has an `expires_at` index. Consider partial indexes only if measurements show need.
- Database state is JSONB for grant/session payloads with indexed `(kind,key)`, `expires_at`, and client/subject expressions. Consent revocation currently reads grant IDs then deletes pointers and grants. Benchmark before denormalizing further; any redesign must preserve the secret-hash pointer invariant.
- No confirmed goroutine leak was found in audited paths. SCIM request/retry flow is context-bound through the shared fetcher; device login long poll exits on request context cancellation. Retry uses `time.After`, at most two retry timers per SCIM HTTP call.

## Pocket ID parity comparison

The latest stable release found on the audit date is Pocket ID v2.14.0 (release notes: <https://github.com/pocket-id/pocket-id/releases/tag/v2.14.0>). Its release highlights multiple client secrets, RFC 8414 metadata at `/.well-known/oauth-authorization-server`, CIMD auto-grant support, and SCIM actor migration. Official SCIM docs: <https://pocket-id.org/docs/configuration/scim>. Device protocol reference: <https://datatracker.ietf.org/doc/html/rfc8628>.

Pocket ID SCIM documentation specifies all users/groups for unrestricted clients and only assigned groups/members for restricted clients, hourly sync, five-minute debounce after changes, and manual sync. Tango implements outbound SCIM with a Tango-specific ConnectRPC contract and one-time token response; its differences from Pocket ID's REST service-provider CRUD are intentional and documented in Yaak.

Tango currently exposes `/.well-known/openid-configuration`, not the RFC 8414 alias added by Pocket ID v2.14.0. It supports authorization code, refresh token, and device-code grants; scopes are `openid profile email groups`; it does not support client credentials or `offline_access`. These are feature differences, not request-shape drift.

Tango's device grant routes are `/oidc/device_authorization`, `/oidc/device`, and `/oidc/token`; user interaction must validate the user code per RFC 8628. The current Yaak device authorization, verification, and poll examples use those Tango paths and form fields. The separate Tango pairing device-login surface (`/api/device-login/...`) is not OAuth device flow.
