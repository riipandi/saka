# Plan — Hardening: enumeration, lockout, security notifications

Written 2026-10-03. Three items from the auth-design gap list the owner picked before
frontend work: strict user enumeration protection, the account lockout policy, and the
security notification emails that have triggers but no mail. The zxcvbn strength meter
comes **out** — the owner dropped it the same day. Flow references follow Clerk's
security model (`user-lockout`, `user-enumeration-protection` guides, read 2026-10-03);
the technology stays the codebase's own.

## Objective

An attacker cannot learn account existence from sign-up, forgot-password, or email
change once an operator turns strict mode on; a credential-stuffing run locks the
targeted account for a bounded or indefinite period with an admin unlock; and the
account-holder's own security events (passkey added/removed, password removed, account
locked) reach their inbox.

## Current state (verified in code 2026-10-03)

- **Password sign-in is already strict.** `ErrInvalidCredentials`
  (`modules/identity/signin/service.go:36`) covers a missing account and a wrong
  password, and `verifyDummy` (line 207) equalizes the response cost. Nothing to do
  there.
- **The enumeration holes**: `signup.ErrAccountExists` (signup/service.go:32) answers
  a taken email or username directly; `password.ErrUserNotFound` / `ErrNoPassword`
  (recovery_service.go:30,34) answer the forgot-password trigger; `verification.
  ErrEmailTaken` (verification/service.go:50) answers a taken new address during
  email change.
- **The ban mechanism** (`users.banned_at`, `ban_expires`, `ban_reason` — migration
  00002, checked in signin/service.go:437) will move into the normalized
  `account_restrictions` table (phase 4): the owner chose full normalization over
  reusing the columns, so ban and lockout become one concept — a restriction row with
  an expiry window.
- **The security-mail pattern** exists twice: `PasswordChangedNoticeTask` and
  `LoginNewDeviceTask` ride the queue (`internal/jobs/register.go:102`,
  `new_device_notifier.go`) into templates named in `internal/mailer/data.go`. New
  notices follow that path.
- **No remove-password endpoint exists** — `SetPasswordHash` serves reset and
  add-password only. The password-removed email therefore ships with the endpoint.
- **The last-credential refusal** has a house shape: the three-source chained check in
  oauthsso's `UnlinkConnection` (password + passkeys + other bindings).

## Decisions (confirmed 2026-10-03)

| Decision | Outcome | Rejected alternatives |
|---|---|---|
| Lockout storage | Normalized `account_restrictions` table unifying ban and lockout | Columns in `users` beside the ban fields (unreliable at scale: hot-row churn, lost history); reusing `rate_limits` (fixed-window, no indefinite support) |
| Strict scope | Sign-up, forgot-password, email change | One-time access stays admin-truthful; password sign-in already strict |
| Enumeration default | `bulk` (today's behaviour) until an operator flips it | Shipping strict by default (changes every deployment's sign-up/reset UX) |
| Password-removed email | Build the `RemovePassword` endpoint | Waiting for a future feature (the email would have no trigger) |
| zxcvbn | Dropped; the strength floor leaves the catalog | `Picocrypt/zxcvbn-go` (active fork, Apr 2025) — rejected: HIBP + length already cover NIST 800-63B's verifier duties |

## Phase 1 — Contract, storage, settings, audit events

Migration 00002 gains the normalized restriction storage in place: the ban columns
leave `users` (`banned_at`, `ban_expires`, `ban_reason`) and a new
`public.account_restrictions` table enters —

- `id` UUID PK, `user_id` UUID NOT NULL REFERENCES `users(id)` ON DELETE CASCADE,
- `kind` TEXT NOT NULL CHECK (`kind IN ('ban','lockout')`),
- `reason` TEXT NULL, `started_at` TIMESTAMPTZ NOT NULL DEFAULT `now()`,
- `expires_at` TIMESTAMPTZ NULL (NULL means indefinite),
- `lifted_at` TIMESTAMPTZ NULL, `lifted_by` UUID NULL REFERENCES `users(id)`.

A restriction is active while `lifted_at IS NULL AND (expires_at IS NULL OR
expires_at > now())` — the one predicate every check shares. No backfill: the project
is new and the owner forbade compatibility shims. The transient `failed_attempts`
counter stays a users column — it is hot-path mutable state that never outlives a
sign-in streak, the opposite of what the table stores. The proto gains two procedures:
`RemovePassword` under the identity Self service (request: current password or a
reauthentication proof; the house shape is session + step-up) and `UnlockUser` under
the admin user service (request: user id). `task rpc:generate` regenerates both
stacks. Settings keys enter the catalog with defaults, validation, and the schema
file: `auth.user_enumeration_protection` (`bulk|strict`, default `bulk`),
`lockout.enabled` (default true), `lockout.max_attempts` (default 100, minimum 5),
`lockout.duration` (default `1h`; empty means indefinite). Audit events join
`internal/audit`: `user_locked`, `user_unlocked`, `password_removed`. Guard rules:
`RemovePassword` Session + step-up, `UnlockUser` Admin. Yaak rows for both procedures
land here.

## Phase 2 — Drop the strength floor, close the TODO

`SettingMinStrength`, `deferredStrength`, and the `TODO(strength)` block leave
`modules/identity/password/policy.go`; the key leaves the settings catalog, the
generated schema, and the appconfig defaults. HIBP (`reject_compromised`) and
`password.min_length` stay untouched — they are the enforced posture. auth-design.md
loses the zxcvbn item, ticks HIBP as implemented, and carries the decision's reason.

## Phase 3 — Strict user enumeration protection

A mode reader (same seam shape as the blocklist checker) feeds the three features.
`bulk` changes nothing. `strict`:

- **Sign-up** with an existing email answers the success-path shape (the verification
  screen the caller already knows), sends no verification code, and instead enqueues
  the `signup_attempt_existing_email` notice to the address on file — the real
  address's owner learns someone used it. A taken username still refuses (a username
  is not a verified contact channel; there is nothing to leak past the name).
- **Forgot-password** for an unknown address or a passwordless account answers the
  same shape as a sent email and sends nothing — the notice email here would have no
  meaningful recipient.
- **Email change** to a taken address answers as if the verification step started
  (no code sent, no error that names the collision).

All three keep today's rate limits; strict mode is about the answer's shape, not
throttling. Container tests drive each feature with the mode on and off and assert
wire-shape equality between the strict path and its honest counterpart.

## Phase 4 — Unified account restrictions: ban and lockout

The restriction table replaces every ban read and write. The sign-in read answers
active restrictions through the one predicate (`lifted_at IS NULL` and unexpired);
`BanUser` / `UnbanUser` keep their wire contracts but now insert a `kind='ban'` row
and lift it respectively — the reason rides the row, the admin actor lands in
`lifted_by` through the causing transaction, and the `user-banned` email and audit
events fire as before. The webauthn reauthentication and the session checks that read
`BannedAt` move to the same predicate. When `lockout.enabled`, every refused password
verification (sign-in, and the reauthentication password path) bumps `failed_attempts`
in an in-place atomic `UPDATE` on the same tx that ran the verify; a success resets
it. The counter hitting `lockout.max_attempts` inserts a `kind='lockout'` row
(`expires_at` = the configured duration, NULL when indefinite — the insert itself is
the durable history the columns would have overwritten) and audits `user_locked`;
the lock check refuses with the existing generic credential error — the wire answer
must not distinguish locked from wrong password, or the lockout itself becomes an
enumerator. `UnlockUser` (admin) lifts the account's open lockout row and audits
`user_unlocked`. The `user_locked` notice email follows the PasswordChangedNotice
pattern. Tests: the counter's atomicity, the expiry window, the indefinite case, the
unlock, the ban round trip through the table, and the wire-shape indistinguishability.

## Phase 5 — Security notification emails + remove password

`RemovePassword` (Self, step-up) refuses when the account keeps no other live
credential — the chained check — clears the hash, audits `password_removed`, and
enqueues the `password_removed` notice. Passkey added/removed notices enqueue from
`VerifyRegistration` and `deleteCredential` (`modules/identity/webauthn/`), each
behind the mailer's notifications toggles like their password-changed sibling. Each
notice is a `.tsx` template under `email/templates/`, a data struct in
`internal/mailer/data.go`, a task type, and a processor in `internal/jobs` registered
in `register.go`. Prove them through Mailpit.
