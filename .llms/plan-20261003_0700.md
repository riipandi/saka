# Plan — Hardening: enumeration, lockout, security notifications

Written 2026-10-03. Three items from the auth-design gap list the owner picked before
frontend work: strict user enumeration protection, the account lockout policy, and the
security notification emails that have triggers but no mail. The zxcvbn strength meter
comes **out** — the owner dropped it the same day. Clerk's security model is the flow
reference (`user-lockout`, `user-enumeration-protection` guides, read 2026-10-03);
the technology stays the codebase's own.

## Objective

An attacker cannot learn account existence from sign-up, forgot-password, or email
change once an operator turns strict mode on; a credential-stuffing run locks the
targeted account for a bounded or indefinite period with an admin unlock; and the
account-holder's own security events (passkey added/removed, password removed, account
locked) reach their inbox.

## Current state (verified in code 2026-10-03)

- **Password sign-in is already strict.** `ErrInvalidCredentials`
  (`modules/identity/signin/service.go:36`) covers a missing account and a wrong
  password, and `verifyDummy` (line 207) equalizes the response cost. Nothing to do
  there.
- **The enumeration holes**: `signup.ErrAccountExists` (signup/service.go:32) answers
  a taken email or username directly; `password.ErrUserNotFound` / `ErrNoPassword`
  (recovery_service.go:30,34) answer the forgot-password trigger; `verification.
  ErrEmailTaken` (verification/service.go:50) answers a taken new address during
  email change.
- **The ban mechanism** (`users.banned_at`, `ban_expires`, `ban_reason` — migration
  00002, checked in signin/service.go:437) moves into the normalized
  `account_restrictions` table (phase 4): the owner chose full normalization over
  reusing the columns, so ban and lockout become one concept — a restriction row with
  an expiry window.
- **The security-mail pattern** exists twice: `PasswordChangedNoticeTask` and
  `LoginNewDeviceTask` ride the queue (`internal/jobs/register.go:102`,
  `new_device_notifier.go`) into templates named in `internal/mailer/data.go`. New
  notices follow that path.
- **No remove-password endpoint exists** — `SetPasswordHash` serves reset and
  add-password only. The password-removed email therefore ships with the endpoint.
- **The last-credential refusal** has a house shape: the three-source chained check in
  oauthsso's `UnlinkConnection` (password + passkeys + other bindings).
- **The session-ending seam** exists: `WithSessionEnder` on the password service
  (recovery_service.go:189) — the shape a restriction needs when it ends sessions.

## Decisions the owner made (2026-10-03, binding)

1. **Storage: a normalized `account_restrictions` table unifying ban and lockout.**
   Ban's columns leave `users`; no backfill, no compatibility shim — the project is
   new. (Rejected: columns in `users` — hot-row churn and lost history; reusing
   `rate_limits` — fixed-window, no indefinite support.)
2. **Strict scope: sign-up, forgot-password, email change.** Password sign-in is
   already strict; one-time access stays admin-truthful. Default `bulk` — today's
   behaviour until an operator flips the mode.
3. **The password-removed email ships with a real `RemovePassword` endpoint** —
   build, not wait.
4. **zxcvbn is dropped.** HIBP (`reject_compromised`, verified shipped in
   `policy.go`) plus `password.min_length` carry the NIST 800-63B verifier duties;
   the meter would add a dependency and a runtime check for a knob the posture does
   not need. (Rejected: `Picocrypt/zxcvbn-go`, the active Apr-2025 fork.)
5. **Session revocation follows Clerk, not the blanket rule**: a ban ends the
   account's active sessions; a lockout does not. The agent's recommendation (end
   sessions on any restriction) was refined against the Clerk flow — a lockout is an
   automated, temporary protection, and killing the legitimate holder's session
   serves the attacker, not the account.
6. **The attempt counter is a streak**: it resets on a successful verification, on
   the lockout's lift, and on its expiry — never a lifetime tally that locks a
   legitimate account for failures spread across months.

## Shape

- **`public.account_restrictions`** (migration 00002, edited in place):
  - `id` UUID PK (`uuidv7()`), `user_id` UUID NOT NULL REFERENCES `users(id)`
    ON DELETE CASCADE,
  - `kind` TEXT NOT NULL CHECK (`kind IN ('ban','lockout')`),
  - `reason` TEXT NULL, `started_at` TIMESTAMPTZ NOT NULL DEFAULT `now()`,
  - `expires_at` TIMESTAMPTZ NULL (NULL means indefinite),
  - `lifted_at` TIMESTAMPTZ NULL, `lifted_by` UUID NULL REFERENCES `users(id)`.
  - Active predicate, the one every check shares: `lifted_at IS NULL AND
    (expires_at IS NULL OR expires_at > now())`. An expired lockout is lifted by the
    next read that finds it.
- **`failed_attempts INT NOT NULL DEFAULT 0`** stays a users column — hot-path
  mutable state that never outlives a sign-in streak, the opposite of what the table
  stores.
- **Settings catalog** (`modules/appconfig/settings.go`, defaults + validation +
  generated schema file):
  - `auth.user_enumeration_protection` (`bulk|strict`, default `bulk`),
  - `lockout.enabled` (default true), `lockout.max_attempts` (default 100, minimum
    5; Clerk's July 2026 default dropped to 10 — 100 stays because the design doc
    names it and self-hosted operators tune their own),
  - `lockout.duration` (default `1h`; empty means indefinite).
- **Proto** (`api/connect/identity.proto`): `RemovePassword` (Self, step-up —
  session plus a reauthentication proof, the UnlinkConnection shape) and `UnlockUser`
  (admin, by user id). `BanUser` / `UnbanUser` keep their wire contracts; only their
  implementations move to the table. `task rpc:generate` regenerates both stacks.
- **Feature seam** (the established pattern — interface in the consuming package,
  wired in the identity area `Package`): a `RestrictionChecker` the sign-in and
  webauthn-reauthentication reads consult through the same query their ban check
  uses today.
- **Audit events** (`internal/audit`): `user_locked`, `user_unlocked`,
  `password_removed` — named in declaration order with the webhook mirror.
- **Notices** ride the queue like their siblings: template `.tsx` under
  `email/templates/`, data struct in `internal/mailer/data.go`, task type +
  processor in `internal/jobs`, registered in `register.go`, behind the mailer
  notifications toggles. Proved through Mailpit.

## Enforcement points

- **Sign-up** (`signup.Service.SignUp`, beside the allowlist check): under strict,
  a taken email answers the success-path shape — the verification screen the caller
  already knows — sends no verification code, and enqueues the
  `signup_attempt_existing_email` notice to the address on file: the real address's
  owner learns someone used it. A taken username still refuses: a username is not a
  verified contact channel, and there is nothing to leak past the name.
- **Forgot-password** (`password.Service`, `ForgotPassword`): under strict, an
  unknown address or a passwordless account answers the same shape as a sent email
  and sends nothing — the notice email here would have no meaningful recipient.
- **Email change** (`verification.Service`, `RequestEmailChange`): under strict, a
  taken address answers as if the verification step started — no code sent, no error
  that names the collision.
- **Sign-in / reauthentication** (`signin.Service.IssueSession` state switch beside
  `Disabled` and the ban check, mirrored in the webauthn bridge): the restriction
  predicate replaces the ban-column read. The refusal keeps the existing generic
  credential error — the wire answer must not distinguish locked from wrong
  password, or the lockout itself becomes an enumerator.
- **Failed-verification accounting**: sign-in and the reauthentication password path
  bump `failed_attempts` in an in-place atomic `UPDATE` on the tx that ran the
  verify; a success zeroes it; the counter hitting `lockout.max_attempts` inserts
  the `kind='lockout'` row (the insert is the durable history columns would have
  overwritten) and audits `user_locked`.
- **Sessions**: the ban's insert transaction ends the account's active sessions
  through the sessionEnder seam (the reset-password shape). A lockout touches no
  session (decision 5).

## Execution rules

- **Atomic commit per phase is authorized for this plan**: each phase below commits
  as it lands, limited to that phase's files, with the message the phase names.
  Never push.
- **When this plan completes, the standing rule resumes**: commits require an
  explicit ask; the agent only recommends the commit message.
- **Migration authorization**: editing `database/migrations/00002_*` in place and
  creating migration files is approved for this plan; a dev-database reset
  (`task db:reset -- --force --up`, then `task db:seed -- --force`) is approved to
  replay the edited schema.
- **Yaak requests are updated in the same change that ships a contract** — new
  procedures gain rows, changed request/response shapes update theirs; after the
  contract lands, the agent returns to only recommending the commit message.
- **Per-phase validation runs before each commit** (the phase's test matrix rows);

- **Migrations carry no `COMMENT ON`** — a second statement emits a second goose
  progress record and the progress contract's test pins one per migration;
  explanations live in the file's leading comment.
- Where a design fork appears mid-phase, the agent stops and asks with concrete
  options, one marked recommended.

### Phase 4 — Unified restrictions: ban moves in, lockout lands (commit: to carry `feat(authn): account restrictions unify ban and lockout`) — landed

The 00002 edit dropped the users ban columns; the reads that scanned them
carry the restriction predicate now:

- **Read model**: the account reads answer the ban fields from the active
  ban row joined beside them (`user` `ActiveBanJoin` — GetUser, ListUsers,
  usergroup's member list, the scimsync directory); the auth paths read the
  restriction *kind* joined beside the account (signin's three account
  reads, onetimeaccess, password recovery) and the api key's validation is
  an anti-join — a restricted owner's machine credential opens nothing.
- **Writes**: `BanUser`, `UnbanUser`, and `UpdateUser`'s ban unit write
  restriction rows through the restrictions service (wire contracts
  unchanged, reason and the replaced terms on the row, the start instant a
  re-ban keeps, the caller's own clock driving the write); the ban's
  session-ending and the audit records stay in the user feature's
  transaction.
- **Lockout**: the counter bumps in place on a failed password verify
  (sign-in and the step-up `VerifyPassword`); a success zeroes it; the
  bound writes the `kind='lockout'` row, audits `user_locked`, and mails
  the account behind `mailer.notifications.user_locked_notice_enabled`.
  The refusal keeps the generic credential error — the wire answer must
  not distinguish locked from wrong password. An expired lockout lifts on
  the read that finds it, with the streak it answered for. `UnlockUser`
  ships with its guard rule; the procedure mounts with the other UserService
  paths (the ladder caught the unmounted scaffold).
- The restrictions feature (`modules/identity/restrictions/`) owns the
  table's reads and writes: the schema, the repository, the policy, the
  locked notice's seam. The streak's arithmetic is pinned by container
  tests: bump-in-place, zero-on-success/lift/expiry, the bound's row, the
  indefinite case, the wire indistinguishability.

Validation: the full tree's tests green (`identity/…`, `internal/…`,
`database/…`, `modules/…`), `task lint` 0 issues, `rpc:stale` clean,
`db:validate` 16 files, dev DB reset + seeded on the edited migration; the

### Phase 5 — Security notices + remove password (commit: `feat(authn): security notices and the remove-password endpoint`) — landed

`RemovePassword` ships implemented (the scaffold's phase): guard rule
`Session` + step-up mirroring AddPassword's, the handler refusing the
impersonated caller the same way. The chained check rides a seam — the
password package's `AlternativeCredentials`, satisfied by the SSO
repository's `HoldsAlternativeCredential` (the bindings plus the passkey
roll, one scan) — and refuses as `failed_precondition` when the account
holds no password or keeps no other live credential. The removal deletes
the hash row, records `password_removed` in its transaction, and mails the
receipt behind `mailer.notifications.password_removed_notice_enabled`.
Sessions stay valid — the Yaak row's phase-1 draft said the removal ends
them, an overstatement corrected in this change: ending sessions would
lock out the holder the step-up proof just named.

The passkey notices enqueue best-effort from `VerifyRegistration` and
`deleteCredential` — the administrator's removal notifies the account too
— through the webauthn service's `PasskeyNotifier` seam, behind
`mailer.notifications.passkey_added_notice_enabled` and
`passkey_removed_notice_enabled`. Each notice carries its template, its
data struct, its task and processor, and its toggle, and the render of
each is pinned by the templates test.

Validation: the full tree's tests green, `task lint` 0 issues, `rpc:stale`
clean; the wire probe over the release binary proved the RemovePassword
path end to end — a real reauthentication proof spent, the removal
answered success, the receipt in Mailpit — and both passkey receipts
processed from the queue into Mailpit. The passkey ceremony trigger itself
is a browser's; the probe seeds the queue rows the ceremony would enqueue,
which proves the processor, the template, and the delivery, not the
ceremony's enqueue call.
