# Architecture

Design notes for the implemented packages. `AGENTS.md` keeps the normative
general rules and `.llms/rules.md` the detailed ones; this file keeps the
reasoning behind them, so a settled decision is not re-litigated. Read the
section for the package you are changing.

## database

### migrations/ (`database/migrations/`)

Goose SQL migrations, the single source of schema truth (16 files, `00001`–`00016`, grouped by topic — identity, authorization, multifactor, webauthn, settings, rate limits, scheduler, filestore, notification, webhook, api keys, jwks, blocklist, the federation surface, and the OAuth SSO surface last). Never embed DDL or create tables at runtime. Editing an applied migration does not re-run it — roll back with `migrate:down` and re-apply. `app_migration` also carries goose's `tstamp` (when a version was recorded), which `migrate:status` reads, so run times need no separate audit table.

### migrator.go

The engine over goose v3. `NewMigrator` loads the embedded migrations (`go:embed migrations/*.sql`) and builds a `goose.Provider` with a Postgres session locker and `app_migration` as the version table. Migrations run on the single-connection handle from `datastore.OpenMigrationDB`, never the pool. `Up`, `UpTo`, `Down`, `Status`, `Version`, `Pending`, `Applied`, `HighestVersion` return plain structs, so `cmd/` never imports goose. `Down(ctx, count)` rolls back one at a time so goose picks the next in the order it recorded; a version comparison cannot express out-of-order rollback. `MigratorOptions.Progress` receives a `ProgressEvent` per step. goose has no progress hook, so `database/progress.go` translates its verbose slog records (`executing statement` → `started`, `migration completed` → `applied`/`empty`/`rolled back`); only those two, so a goose rename costs the live per-migration line and nothing else, the caller's summary coming from the returned results. Without `Progress`, goose runs a nop logger.

### validate.go

`Validate` checks the embedded migrations without a database: unparsable file names (goose skips those silently), duplicate or non-consecutive versions, malformed annotations, unbalanced `StatementBegin`/`StatementEnd`, statements outside Up/Down, a file without a Down block. It does not parse SQL. `ValidateFS` runs the same checks over any `fs.FS` so tests use fixtures. `migrate:validate` wraps it and needs no DSN.

### create.go

`CreateMigration` writes a skeleton at the next version after the highest file on disk, and refuses a name already in use at any version, so the directory never holds two files describing the same change. Names are normalized (lowercase, non-alphanumerics collapsed to `_`), so `"Add Widgets"` and `add_widgets` collide. It creates files, never directories, and validates nothing about the SQL. `MigrationPrefixWidth` is the shared version padding.

### dump, backup, schema_dump, restore (`db:export` / `db:import`)

Design adopted from `JCoupalK/go-pgdump`, implemented here because that library hardcodes the `public` schema in ~25 queries and reads `information_schema.columns.data_type`, turning `citext` into a literal `citext` with no schema.

- `dump.go` holds the shared contract: the `public, internal, reference` schema list, `COPY` header prefix, `\.` terminator, `excludedTables` (`public.app_migration` is migrator bookkeeping, never dumped), `Connector`, `eachRow`.
- `backup.go` exports on one read-only transaction on one pooled connection, so every COPY sees one snapshot. Rows travel through `PgConn().CopyTo`, never `SELECT` + manual escaping, in `text` format not `csv`: text escapes the terminator, so a value of `\.` cannot end a block, while csv leaves it bare and truncates the table. Each table is ordered by its primary key, so the same state dumps to the same bytes.
- `schema_dump.go` renders DDL in restore order (schemas, extensions, enums, sequences, tables, constraints, indexes, functions, triggers, comments), one writer per kind, every definition from the server's own deparse helpers (`format_type`, `pg_get_constraintdef`, `pg_get_functiondef`, `pg_get_triggerdef`, `pg_indexes`), never re-derived; extension-owned objects are skipped via `pg_depend.deptype = 'e'`. Every statement is idempotent so a dump replays over an existing schema: `CREATE TABLE`/`INDEX`/`SEQUENCE`/`SCHEMA`/`EXTENSION` take `IF NOT EXISTS`, triggers become `CREATE OR REPLACE TRIGGER`, and `CREATE TYPE` / `ALTER TABLE ADD CONSTRAINT` — no such form exists — are wrapped by `guardedByTypeCheck` / `guardedByConstraintCheck` in a `DO` block that asks the catalog first; drop a guard and `TestSchemaDumpAppliesTwice` fails. Constraints must be ordered globally by type (all PK, then UNIQUE, then CHECK, then FK): per-table order puts `api_keys`' foreign key before `users`' primary key and Postgres rejects it. A catalog query must never run while another query's rows are still iterating on the same connection, or pgx reports `conn busy`; `dumpTables` reads the whole table list before any columns.
- `restore.go` reads every COPY block into memory, orders the blocks by foreign key (a dump is alphabetical, so a table can precede the table it references), then loads them. `--truncate` empties every table before any row loads, because `TRUNCATE ... CASCADE` would otherwise delete rows already restored. DDL in the file is ignored: the schema comes from `migrate:up`, so a dump cannot disagree with the migrations. A block that ends before its terminator fails rather than importing a partial table.

### compress.go

The `--compression` container and format detection behind `db:import`. `Compression` is `none|gzip|zlib|zip`, all from `klauspost/compress` — one dependency already in the module graph, so no format is hand-rolled. `pgzip` is deliberately unused: gzip-only, and its parallel writer splits the stream into independent blocks that cost ~7% of the ratio for a speed-up invisible beside the dump's own I/O. The dump is written plain first and compressed after it completes (`CompressFile`), so a failure during the dump cannot leave a half-written archive a reader would accept. A `*zip.Writer` owns its central directory, so `zipEntry` closes the archive, not the entry. Detection reads the file's own bytes (`detectCompression`), never its name: a renamed dump still loads and a name that lies is not believed. A recognized-but-unsupported container (`bzip2`, `zstd`, `xz`, `lzma`, `lz4`) is refused by name via `ErrUnsupportedCompression`; anything else is treated as plain SQL and held to the dump's own contract. zlib is told apart by a valid header (method nibble 8, first two bytes a multiple of 31). `InspectDump` counts blocks and rows for `--dry-run` without a database. **Never read the output buffer before closing the compressor** — the last block is only flushed by `Close`, and reading first yields a silently truncated file.

### seeders/

The default records a fresh database needs, behind `migrate:seed`. `Seeder` is `{Name, Apply(ctx, datastore.Querier, dryRun)}`; `Name` carries a `Seeder` suffix (e.g. `UserSeeder`, `UserSeederName`) because the report shows it beside the record it created, and a bare entity name would read as the record rather than the code writing it. `All()` returns them in dependency order — `Authorization()` (catalog + the administrator system role + the `editor`/`moderator`/`service` sample roles, additive: a role that exists is skipped and the administrator's edits survive), `User()` (default account with the administrator grant, five ban-state scenario accounts, and the scenario-role grants editor→robert_langdon, moderator→hermione_granger), `UserGroup()` (editors/moderators/archivists groups; archivists stays empty, memberships name scenario accounts and a missing account skips silently), `APIKey()` (three keys under the default account: a live one whose raw credential is printed exactly once on the report line, a one-hour expiring one, a revoked one), `Notification()` (an announcement to the global audience and a topicless system notice aimed at the editors group, each with one read receipt stamped and one left open — idempotent by title lookup, because the table carries no unique index), and `Settings()` (one row per non-sealed `appconfig.Catalog()` item at its declared default — the table is otherwise overrides-only, so the seed fills it for a fresh database's listing without inventing values; sealed items are skipped because the seeder holds no cipher, and `System()` for `initialize` carries it too). The user seeder also writes one direct permission grant (`notification:*:create` to sophie_neveu, outside her editor role), so the direct-grant path the claims union takes is exercised in development too. `Run` applies each over one querier and wraps a failure with the seeder name. The caller owns the transaction (`cmd/migrate_debug.go` passes `pool.WithTx`), so a failing seeder rolls back everything; the same `Run` works on the pool for a dry run. Every seeder is idempotent and reports the natural key of each record as created or skipped, so a second run is a no-op. `user_factory.go` creates the default account (`admin@example.com` / `@dmin123`, username `admin`, display name `Admin Sistem`); the password is hashed with `pkg/crypto`'s scrypt hasher and is not computed on a dry run. Inserts use `github.com/huandu/go-sqlbuilder` guarded by `ON CONFLICT DO NOTHING`, so a conflict on any unique column keeps the existing row. `UserSchema`/`UserPasswordSchema` and their table constants live in the owning module, not here. `config_factory.go` and `jwks_factory.go` are still empty stubs.

### modules/identity/<feature>/schema.go

The table constants and row structs for that feature, so a table rename touches one line and a repository or seeder never hardcodes a name. A table constant is the one constant worth having; a constant per column is not, and is not used anywhere: each column is named where its query is, the way `internal/queue/store.go` and `internal/storage/manifest.go` do it, because a `Column*` constant is still a string by the time Postgres sees it and each one is named in a single statement. What actually makes the columns agree with the struct is `sqlbuilder.NewStruct` — `Columns()`, `Addr()`, `Values()` read one definition — so it is the right tool for a feature with full CRUD and many columns; it cannot express `Returning`, `ForUpdate().SkipLocked()`, `Incr()`, or a CTE, which is why the queue and the storage manifests use the builder directly. `db` tags are the column names `NewStruct` reads, and a struct used that way lists only the columns the application writes, so a migration can add a column with a default without touching Go code. A row struct that is *not* built through `NewStruct` carries no tags and needs none: it is the reduced shape the feature reads, not a mirror of the table.

## cmd

### initialize.go, admin_reset_password.go, require_migrated_release.go, seed_print.go

The deployment bootstrap, carried by the release build. `initialize` applies the system seed (`seeders.System()` — the permission catalog, the system roles, and the settings catalog, deliberately narrower than the development fixtures `migrate:seed` applies) and opens the first administrator; every flag is optional (`--admin-email` defaults to `admin@example.com`, `--admin-username` to `admin`, an absent `--admin-password` is generated and printed exactly once to the command's own output), and an unattended install reads its credential from that output. The safeguard is the state itself and there is no override flag: the command counts the live accounts and refuses a database that already holds one, pointing at the recovery command instead. `admin:reset-password EMAIL` replaces an administrator's credential — the target must hold an active administrator grant (a regular account's recovery travels the forgotten-password flow, where proving the address is the proof), disabled and banned accounts are refused, an absent `--new-password` is generated and printed once, and the swap, the session revocations (the account itself recorded as the ender, the way a ban revokes), and the audit record commit in one transaction. Both commands refuse a database with pending migrations; `require_migrated_release.go` carries the rule the debug-tagged `migrate_debug.go` cannot share, and `seed_print.go` carries the seed report both commands print.

### migrate_debug.go

Debug-only commands (`migrate:create|reset|seed|validate`). The actions live here rather than in `cmd/migration.go` because a release build would otherwise compile them into `unused`. `migrate:reset` rolls back everything and, with `--up`, re-applies in one run; on a database with nothing applied, `--up` alone applies the migrations, so `reset --up` also builds a schema from scratch. `migrate:create` takes a `--dir` flag defaulting to `database/migrations` and needs no database. `migrate:seed` first proves the schema is current by asking the migrator for pending migrations, so it refuses with the count and `run migrate:up first` rather than failing halfway on a missing column. A dry run needs no confirmation; a real run asks (unless `--force` or a non-terminal stdin) and runs in one transaction.

The smoke probes (`mailer:smoke`, `logger:smoke`, `otel:smoke`) follow the same split at the registration: their command files carry no build tag, but `cli_release.go` lists no smoke command. A release binary must not hand out an unauthenticated outbound-mail primitive, inject probe lines into the production log store, or fabricate spans and a permanent `saka_otel_smoke_total` series into the production time series; the probes exist to prove wiring before a deployment depends on it, so they belong to the side that also carries `migrate:seed`.

### migration.go

DSN resolution and the migration commands. The DSN comes from `envfile.DatabaseURL`, resolved from the root `--env-file` first and the process environment second; nothing else opens a connection. `migrate:up` and `migrate:down` ask for confirmation only when stdin is a real terminal (checked with `golang.org/x/term`, because `/dev/null` is also a character device) and proceed immediately when piped, so `task db:migrate` and CI never block. `up` takes `--to`, `down` takes `--count`; both take `--dry-run` and `--force`. `migrate:status` lists every embedded migration with the time it last ran and closes with the most recent run. `migrate:version` prints the bare version number for scripts and is the only command with no target header.

### database.go, database_cmd.go (`db:export` / `db:import`)

Export defaults to `storage/backup/saka-<YYYYMMDD_hhmm>.sql` (UTC) and creates that directory when missing, with or without `--overwrite`: a first run that happens to pass `--overwrite` has nothing to overwrite, so it must not fail for an unrelated reason. A `--output` path the user typed is used as-is and its directory is never created, so a typo stays visible. The generated name is readable to the minute, so a second export inside the same minute would land on the same path; `createExportFile` fails with `ErrDumpFileExists` instead of losing the first dump, and `--overwrite` is the consent. With `--compression` set the guard is on the **final** name (`.sql.gz`), not the plain intermediate, so a stale plain file cannot block a run whose compressed output does not exist yet, and the suffix is appended exactly once. `--force` is the shared confirmation bypass. Import takes the file as a required positional argument (`cli.StringArg{Required: true}`), not a flag, because a restore always has a source. A restore is destructive even without `--truncate` — it replaces rows in the tables the dump carries — so it always confirms unless `--force` is passed; `--dry-run` reports the work and opens no database at all. `printFields` renders a report as labelled values padded to one width, and `reportLabelWidth` pins that width so the target line (before the work) and the summary (after) share one column.

### helper.go

The shared rendering every command builds on, and the one place a spinner is created. One row shape for every migration report: `printMigrationRows` over `migrationRow` (version, state, time, name, duration), so all `migrate:*` reports read alike. `migrationLabel` shortens the row name — the version has its own column and `.sql` says nothing, so `00008_create_scheduler_tables.sql` prints as `create_scheduler_tables` — dropping the prefix only when it is really digits, so `add_widgets.sql` keeps its name; `last run` still names the full file, being a sentence not a row. `migrationStateWidth` sizes the state column from the words a report uses, so `applied` is not padded to a rollback's width while two lists from one command still share a column. `migrationRow.Measured` is separate from `Duration` because a measured zero is a real answer; `migrate:status` shows no duration, the recorded time being when a migration ran, not how long it took. Every outcome line carries a `status:` label at column zero (`printStatusLine`; `printSummary` for the timed closing line), so one `grep '^status:'` finds any command's result. `reportTarget` opens with `database: host:port/name` (never the DSN), so a run against the wrong server shows before it changes anything. A running migration is shown by the spinner, not a row: a row would be overwritten on a terminal and lost in a log. `newSpinner` returns nil off a terminal, so every spinner site is a nil check and a redirected run writes no carriage returns; stop it before the first result row, or its next frame lands at the start of that row. `reporter.restart` begins a second phase in place (`migrate:reset --up`) and must not be replaced by a new reporter: the migrator holds a method value from the reporter, so a new instance would never be called and the second phase would silently keep the first phase's column width and clock. Both halves of `migrate:reset` call it, including the fresh-database path; it lives in `cmd/migrate_debug.go` because `migrate:reset` is debug-only and a release build would otherwise flag it `unused`.

### healthcheck.go

The `health` command. It needs no running server: opens the pool, runs the checker, prints the report, exits 3 when unhealthy. `--json` prints the same object the REST handler publishes, `--short` one word, `--timeout`/`--no-cache` tune the run. A database that cannot be reached is a result, not a command error. The database target is rendered from the parsed DSN host/port/database, never the DSN itself, so a report cannot leak the password; the storage check names no path on the endpoint, while the CLI report (`StorageCheckWithTarget`) shows the resolved directory, because an operator reading the terminal owns the machine.

### logger.go

How the process logger reaches a command. `initConfig` installs a `loggerState` on the context and the root `After` closes it, so a run flushes what it queued. The logger itself is built **lazily** (`loggerFrom`), not in `Before`: `config:generate` and `key:generate` run before a usable configuration exists, so building eagerly would break the two commands that bootstrap a fresh checkout. The state holds the configuration and a `sync.Once`, so the first command that logs builds one logger and every later call gets the same one. `loggerFrom` reports the failure rather than swallowing it — a command that asked for a logger and did not get one must say so, because the alternative is a run that looks healthy and writes nowhere. `observerState`/`observerFrom`/`closeObserver` live in the same file and work the same way for traces and metrics, because the two have the same lifecycle and the same reason to be lazy; they are separate state so a command that logs does not build a tracer. The root `After` closes the **observer first**, then the logger: a signal drained by the observer may be reported through the logger, and a logger closed first would drop that line. `closeObserver` **reports** a failed drain and returns nil — telemetry is a side channel, so a collector that is down at shutdown means some spans were lost, which is worth saying and is not a reason for a command to exit non-zero. The two shutdown timeouts are separate constants because the metric reader needs longer than a log batch to drain.

### loggersmoke.go

`logger:smoke`. It emits one line per level through every configured transport and prints where each one writes plus the LogsQL query that reads the line back, so the logging path can be proved end to end against a real backend before anything depends on it. It builds the logger itself rather than calling `loggerFrom`, because the command that exists to diagnose logging should not fail before it can say which transport broke. The probe field is named `probe`, not `level`: `level` is the structured transport's own key, and a field of that name would put the same key in the JSON object twice. It ships in the debug build only — the release-side split is at `### migrate_debug.go`.

### otelsmoke.go

`otel:smoke`. It records one span and one measurement through the providers the configuration enables, and prints what each signal is doing, so tracing and metrics can be proved end to end the way `logger:smoke` proves logging. It goes through `observerFrom`, the same accessor a real command uses, so the run proves the wiring rather than a pipeline assembled for the test. The counts in the closing status line are captured **before** the drain: `Shutdown` releases the providers, so checking afterwards would read every signal as off and report a run that proved nothing as if it had proved something. It ships in the debug build only, as `logger:smoke` does.

## pkg

### printext

How output is rendered for a human, shared by the CLI and `internal/health`. It owns colour and formatting. A `Style` names what text means (`StyleOK`, `StyleFail`, `StyleWarn`, `StyleLabel`, `StyleMuted`); a `Palette` decides the colour, so a renderer marks meaning without knowing a colour. `Style` is the vocabulary, `Colour` the four values a palette paints. Formatting: `Duration` (three decimals through `humanize.SIWithDigits`), `Plural`, `PadRight`. Colour is decided per destination, not per process: fatih/color reads `os.Stdout` once at start-up, which is wrong for a writer that is a buffer in a test or a file in a redirected run, so `NewPalette` asks `IsTerminal` and honours `NO_COLOR`. A buffer is never a terminal, so a test sees plain rendering without asking. Pad before colouring, never after: an escape code is invisible but not zero-width to `fmt`, so padding a painted string breaks its column. The package never decides layout — column widths, labels, and which lines a report holds belong to the caller.

### crypto

`Cipher` seals recoverable values with AES-256-GCM and the exact `enc:` prefix; `PasswordHasher` produces PHC strings (scrypt default, Argon2id opt-in). Keys are 32 bytes stored as 64 hex characters (`GenerateKeyHex`, `ParseKeyHex`, `NewCipherFromHex`). There are two seal halves and `NewAuthCipher` keeps them apart: `APP_SECRET_KEY` seals everything that is not account-authentication material (appconfig secrets, SCIM provider tokens, queue payloads), while `AUTH_SECRET_KEY` — through the SHA-256 derivation in `AuthSealKey`, so any HMAC length seals — seals what authentication rests on: the JWKS signing pairs and the multifactor TOTP secrets. Every `Cipher` also answers `Fingerprint()`, a non-secret 16-hex-char identifier of its key; sealed rows record it so a reader can tell "sealed by a key I no longer hold" apart from a corrupt row. `KeyGenerator` emits the two environment secrets: `APP_SECRET_KEY` and `AUTH_SECRET_KEY` (an HS* `--algorithm` selects the secret's algorithm; an asymmetric name is refused — the signing key pair is the database's). `GenerateKeyPair` is the separate generator the database's signing rows are stored from: private and public halves as base64 (raw, unpadded) JWK JSON with `alg` and a shared `jwk_` TypeID `kid`. `DecodeJWK` reads that encoding back; both live here rather than in a feature, because the format is this package's decision. `ParseHMACKeyHex` is a **separate** reader for `AUTH_SECRET_KEY` and must not be replaced by `ParseKeyHex`: the latter is the AES-256 reader and insists on exactly 32 bytes, while an HMAC secret is 32, 48, or 64 bytes for HS256, HS384, and HS512 — `key:generate --algorithm HS384` writes a value `ParseKeyHex` rejects. The key pair generator takes an asymmetric algorithm (default `ES256`); a passed HS* name goes to `KeyGenerator`'s secret. Passwords are hashed, never encrypted. Do not add another encryption or hashing format.

### envfile

Dotenv reader/writer that preserves comments, blank lines, and key order; new files are written `0600`. Owns the `DatabaseURL` key constant (`DATABASE_URL`); pkg/ cannot import internal/, so the config layer derives the same name through `EnvName` and a test asserts the two agree. `key:generate` declares its own `--env-file` flag (the root flag only loads config) and owns the I/O: it only prints unless that flag is given, creates a missing file, and asks before replacing the values of an existing one (`--overwrite` skips the prompt).

### responder, validate, jwtutils, testutils

`pkg/responder` — the API envelope, pagination, request IDs (documented in `docs/api-response.md`). The RPC responses carry the outcome as two flat fields (`status`, `message`) beside the payload, the same keys the REST envelope writes. `pkg/validate` — request decoding and ozzo v4 code-first validation. Handlers use these; no hand-built envelopes or ad-hoc field guards. `pkg/jwtutils` — JWT signing/verification with typed private claims. `pkg/testutils` — shared testcontainers Postgres, Mailpit, MinIO.

## internal

### datastore

The Postgres adapter. `NewPostgres` owns the single `pgxpool` of the process (sane pool defaults, connect-time ping, `Ping`/`Stats`/`Close`), `Querier` is the shared pool/transaction surface, and `WithTx` commits when the callback returns nil and rolls back otherwise (including on panic); the callback receives the `Querier`, so a transaction passes to any repository, seeder, or store written against it. `WithSavepoint` runs a callback under a savepoint when the surface it is handed is a transaction, so a side effect that is allowed to fail without failing the caller — an audit record — leaves the surrounding transaction usable; on a pool there is no surrounding transaction to poison and the callback runs directly. Every pooled connection sets `search_path` and `timezone` through `RuntimeParams` (the session zone is `app.timezone`, the one zone the deployment runs in), so a recycled connection keeps the same session defaults. `Acquire` hands out a connection for work that must stay on one backend (LISTEN, session advisory locks); callers must release it. ErrNoRows is re-exported so repositories do not import pgx. Migrations never use the pool: `OpenMigrationDB` / `(*Postgres).MigrationDB` return a `database/sql` handle pinned to one connection, because goose holds a session advisory lock and needs every statement of a run on the same backend.

**The startup probe retries, within a budget** (`connect`/`retryConnect` in `postgres.go`). A process that starts beside its database — a container whose `depends_on` only waits for a port, an orchestrator scheduling both at once — reaches the server before it accepts connections, so failing on that race turns an ordering problem into a crash loop. `database.connect_attempts` (default 5) × `database.connect_retry_interval` (default 2s) is the budget, each attempt additionally bounded by `database.connect_timeout`; `PostgresOptions` defaults `ConnectAttempts` to 1, so the wait is always something a caller asked for and a test or a one-shot command probes once. Three rules make it honest: a verdict the server gave — `28P01`/`28000` (auth) or `3D000` (unknown database), matched by SQLSTATE so no message is parsed — ends the wait immediately, because a retry reads the same answer; a cancelled context ends it and joins both reasons; and every retry writes one warning through `PostgresOptions.Logger` (nil = silent), so an operator sees a wait rather than a hang. The interval is **constant, not a backoff**: the count already bounds the wait and a startup wants a predictable worst case — an exponential backoff belongs to a client retrying live requests (`internal/fetcher`), not to a probe that runs once. `OpenMigrationDB` retries on the same terms (a migration command in a boot sequence races the database identically); `(*Postgres).MigrationDB` does not, being built from a pool that already proved the database reachable. The final error names the attempt count only when more than one attempt happened, so a single-attempt probe keeps the message it always had.

`datastore.Valkey` is the key-value backend (`internal/datastore/valkey.go`), on `valkey-io/valkey-go`: `NewValkey(ctx, ValkeyOptions{URL, DB, ApplicationName})` parses the URL with `valkey.ParseURL` (the grammar `isKVURL` mirrors), lets an `opts.DB` of zero or more outrank the index the URL carries, names the connection after the application, and verifies connectivity with a ping before returning — an unreachable backend fails the startup, and a failed construction hands out no client. The ping error carries no target: `RedactKVURL` is the one rendering, applied by the caller. The driver is opt-in: `kvstore.enable` decides availability, and nothing dials the backend while no feature selects it.

### cache

The key-value cache drivers, behind one `Cache` contract (`Get(ctx, dst, key)` appends into the caller's buffer — an API designed to be used in zero-allocation mode — plus `Set` and `Del`, each carrying the caller's context, which the remote driver owns a round trip for). `New(cfg, kv)` is the entry point a composition root calls, and Noop is the driver it hands out whenever caching does not run: the cache switched off (`cache.enable` defaults to false — a feature that has not decided to be cacheable cannot grow one by accident), the kvstore driver named while `kvstore.enable` is false (a cache that cannot reach its server is a run without caching, not a broken system — which is why the cache alone among the kvstore features is exempt from `kvStoreDrivers`), or an unknown driver. Noop answers every read with a miss, so a feature never branches on the caching question.

`cache_memory.go` is the in-process driver, adopted from `VictoriaMetrics/fastcache` without the dependency: entries are appended into 64 KiB byte chunks (nothing for the GC to scan inside a chunk), an index of `map[uint64]entry` hashes each key with the seeded stdlib `hash/maphash` (per-process seed, so no hash can be crafted offline; `cespare/xxhash` was left unused for this reason), the whole ring is cleaned when the `cache.max_memory` budget is spent while keeping the chunks it grew, and an entry carries its own TTL (`cache.ttl` is the default) measured on the monotonic clock — `cacheEpoch` is the process-start baseline, expiry deadlines are offsets from it, and `monotonicNow` reads them, so a wall-clock step can neither age an entry early nor resurrect an expired one. Collisions are handled where bigcache overwrites: every entry stores its key, a lookup verifies the bytes before answering, and a colliding entry takes a secondary slot — two keys sharing a hash keep working, only a third evicts the secondary. `Reset` is the only drain the driver takes — the budget, the TTLs, and the ring's own reset already bound what a running cache holds, so there is no flush goroutine to stop. The batch methods (`GetMany`/`SetMany`/`DelMany`) exist for the remote driver's sake — one round trip instead of one per key — and are a loop over the single-key calls here, since an in-process read has no round trip to amortize; only the batch's returned map allocates, a single hot `Get` into a roomy `dst` still allocates nothing, which `cache_memory_bench_test.go` pins.

`cache_valkey.go` drives the shared `datastore.Valkey` client: keys are namespaced under `ValkeyKeyPrefix` (`saka:cache:`) — features sharing one server are isolated by prefix, not by logical database index, which Valkey cluster does not support; the backend's memory is the server's business (`maxmemory`, `maxmemory-policy`, per-key TTL) — and any backend failure reads as a miss, because a cache may degrade and the feature behind it may not. The batch methods are where the contract earns its keep here: `GetMany` is one MGET, `SetMany` one pipeline of SETs through `DoMulti`, and `DelMany` one DEL naming every key — each a single round trip, with a nil reply element or a backend error reading as a plain miss.

### health

The health check engine, adopted in design from `alexliesenfeld/health` but implemented here (no dependency). `NewChecker` takes named checks, runs the due ones concurrently under a global timeout, caches each result for a TTL, recovers a panic into a failure, and aggregates. Two vocabularies on purpose: a component is `up`/`down` (`Status`), the system is `healthy`/`unhealthy` (`GlobalStatus`). `Check.Optional` is reported but excluded from the aggregate, so an optional backend is never an outage; `Check.Target` names what was inspected and appears in the text report. Metadata comes from `WithInfo` (static, such as the build version) and `WithInfoFunc` (computed per call, such as `Uptime`); a static key outranks a computed one. The JSON form is explicit (`marshal.go`) and byte-identical for the same state: durations in milliseconds under `took_ms`, details as an ordered array, and the info entries flattened to the top level in sorted key order (never nested under `info`), because `encoding/json/v2` does not sort map keys; an info key that shadows a wire field (`status`, `details`, `took_ms`) is refused at construction. `Result.Duration` is the length of one check run, not uptime. `WriteText`, `WriteShort`, `Message` are the only renderers, so the CLI and the REST handler cannot drift; `WriteText` takes a `printext.Styler`, pass nil for plain text. The style of a status word is mapped here, in `statusStyle`, because this package owns what `up` and `healthy` mean — `printext` only paints the meaning.

Checks (check names are generic — `database`, `kvstore`, `storage` — never the product behind them, so a published report does not advertise the engine a deployment runs):

- `check_database.go` (`DatabaseCheck`) — pings the pool, so it also fails while the pool is exhausted.
- `check_kvstore.go` (`KVStoreCheck`) — pings the shared key-value backend; wired in only while `kvstore.enable` is on, since a disabled backend is never dialled and reporting it down would describe a dependency the application does not have.
- `check_storage.go` (`StorageCheck` / `StorageCheckWithTarget`) — probes the data directory: missing, not a directory, not writable (real write-and-remove probe, mode bits alone are not enough), or world-writable (a failure, because it holds uploads and certificates). The endpoint publishes the plain check; `StorageCheckWithTarget` reports the resolved absolute path and is for the CLI report, which an operator who owns the machine reads. Error messages name the problem, never the path.
- `handler.go` — the REST endpoint (200/503, standard `pkg/responder` envelope, uncacheable).

### observability stack (docker)

`container/compose-sre.yaml` — the observability stack: **OpenObserve** (the one backend for logs, metrics, and traces, `openobserve-enterprise` per `OPENOBSERVE_VERSION`) and the **OpenTelemetry Collector Contrib** (`otel/opentelemetry-collector-contrib` per `OTEL_COLLECTOR_VERSION`), included by `container/compose-dev.yaml`. ### logger

The logging stack. One LogLayer core sits behind a `*slog.Logger` (`integrations/sloghandler`), so application code and every dependency that logs through `log/slog` emit into the same pipeline; feature code calls `slog`, never LogLayer. `New(cfg, opts...)` walks `log.transport` in order and builds each named sink: `console`, `file`, `otlp`. The list is what switches a sink on, so there is no second flag that could disagree with it; a name no sink matches fails construction rather than being skipped, and `Validate` refuses an unknown name, a repeated name, and an empty list. The console is the only sink with a rendering choice, carried by `log.format` — `pretty` (the `pretty` transport) or `structured` — because what a person reads in a terminal and what a machine reads from a log file are different questions; a file or a collector keeps JSON regardless, has no key to choose, and `Validate` reads the format only when the console is named, so asking for a colourised console cannot put escape codes in the file. Colour is decided per destination (`isTerminal`, the same rule `pkg/printext` applies), so a redirected run and a test buffer stay plain. The threshold lives on the logger (`levelFor`), not on a sink, so every destination agrees on what is worth emitting. `FlattenMetadata` is on, so fields and per-call metadata merge at the root and an entry reads the way slog's own JSON handler writes it. `New` fails rather than degrading — a deployment that asked for a file or a collector and silently got neither has lost the logs it is being trusted with — and `release` closes whatever was built before a later sink failed. `Shutdown` drains the collector first (its batch processor holds queued records nothing else can flush), then releases the file descriptor, and is idempotent. The file sink's path is derived, not configured: `LogFilePath` is `storage.local_path` + `/logs` + `saka.log`, so the process has one data directory and no second path that could disagree with it.

The OTLP sink passes **every** exporter option explicitly, including a nil `WithTLSClientConfig` on a plain http endpoint: the exporter otherwise reads `OTEL_EXPORTER_OTLP_*` for its endpoint, headers, compression, and TLS material, which would be a second configuration source deciding what a deployment logs and where, and the resource is built with `resource.NewSchemaless` rather than `resource.Default` so `OTEL_SERVICE_NAME`/`OTEL_RESOURCE_ATTRIBUTES` cannot attribute a record to a service the shell named. Every exporter is the HTTP/protobuf one — the gRPC and `http/json` legs were removed, so `otel.protocol` no longer exists and the endpoint is always the URL the exporter dials — see `internal/observer` for the full reasoning, which the two packages share. The address is `otel.endpoint` and the resource is built from `otel.service_name`/`otel.environment`, so a record, a span, and a measurement of one service carry the same identity into the same collector.

Every entry carries the calling function, file, and line **only at debug level** (`sourceGate`): slog always captures `Record.PC` and the handler forwards it, so the gate at the frontend zeroes it for every level above debug — the call site tells a reader where the code lives, which is a debug-only fact, and one wrapper covers every sink (console, file, echo, OTLP) instead of a policy each transport remembers.

**`Slog()` is the frontend and the only way feature code writes a line**; the LogLayer core is not exposed — its API is a second way to say what slog says, and using it would split the codebase into two logging idioms, the second of which skips the handler the rest of the stack is wired through. `With(...)` and `WithGroup(...)` are slog's own and work here, because the handler behind the logger implements them: a field added through `With` reaches every later record and a group nests what follows, which is the idiom for request-scoped fields (asserted in `TestSlogChainCarriesFieldsThroughThePipeline`). **Call the `*Context` methods wherever a context is in hand** (`InfoContext`, `WarnContext`, ...): the otellog sink correlates the record with the span the context carries (asserted in `TestSlogContextCorrelatesLogsWithTheActiveSpan`), and a plain `Info` writes a record with no trace ID — logging without the context is what kills log↔trace correlation. **Errors are logged as rendered text under `err`** (`"err", err.Error()`): the error slot LogLayer's serializer renders is reachable only through LogLayer's own API, which feature code does not hold — the official slog integration maps every attribute onto fields, and a raw error value there encodes as an empty object (asserted in `TestErrorsAreLoggedAsRenderedText`).

**The console and file sinks are async, zero-drop** (`internal/logger/async.go`): each sink is one worker owning a bounded queue (8192) that **blocks** its producers when full — a burst costs the response path one enqueue, never a write syscall, and overload turns into latency, never into a lost line. The console renders into a batch buffer flushed on every drain, so a burst costs one syscall instead of one per line. `Close` (which LogLayer calls to pre-flush before a `Fatal` exit, and `Shutdown` calls at the end of a run) drains the queue before releasing the inner transport, so a graceful stop and every queued entry before it are written; only a `kill -9` between enqueue and drain can lose what the queue still holds. A send that races with the close is written synchronously rather than dropped. `Logger.Flush` drains without stopping the sinks — what a test that reads its buffer after a log call uses. The OTLP sink is deliberately not wrapped: its batch processor already queues in the background.

**A run whose transports do not name the console is not blind**: `echoSink` carries warnings and errors to stderr — deliberately unconfigurable, deliberately unqueued — so an operator watching the service still hears when something is wrong, without a second copy of every routine entry; the startup and shutdown milestones for that same deployment are the two lines `serve` writes to stderr directly.

### observer

Traces and metrics, the two signals `internal/logger` does not own. It follows the logger's shape: the resolved configuration is the only source of truth, each signal is opt-in, and a signal nothing enabled dials nothing. It also owns `exporter.go`, the OTLP exporter plumbing (TLS, compression, signal routes) all four exporters of the process share — the logger's log sink imports it rather than carrying a copy, so a decision about what an exporter may read from the environment is made once. `New(ctx, cfg)` returns an `Observer` with every signal off when neither `otel.tracing.enable` nor `otel.metrics.enable` is set, so a caller never checks for nil before `Shutdown`.

**Nothing on the request path blocks**: spans go through a batch span processor and measurements through a periodic reader, so recording enqueues and returns, and a collector that is slow, unreachable, or absent costs dropped telemetry rather than a slow request — the queue is bounded by `otel.queue.max_size` and drops the oldest item when full. Metrics leave by **pull first**: the Prometheus bridge serves the exposition at `otel.metrics.prometheus_path` on the application's own port, which a Prometheus-mode scraper reads (the compose stack no longer runs one; push mode or an external scraper serves that role), and a scrape reads a snapshot the bridge already holds — so the metrics keep flowing while the collector is down, and the pipeline that carries logs and traces is not on the metrics critical path. The OTLP push leg is opt-in (`otel.metrics.push`, off by default): when it is on, a periodic reader exports beside the bridge and an instrument is exported twice, which is why it is off — the two label schemes (`service_name` pushed, `job` scraped) would store every series twice. `MetricsHandler` exposes the handler for that path; **`internal/transport` mounts it at `otel.metrics.prometheus_path`** on the router it builds, so the compose scrape job reports the service once `serve` runs — a disabled signal mounts nothing, which is why the endpoint is absent rather than empty. The bridge writes into a registry this package owns (`newRegistry`), not the Prometheus default — otherwise a scrape would attribute a dependency's metrics to this service — and the **process collectors are registered there deliberately**: the Go runtime (`go_*`) and the process (`process_*`) are what this service is, so they are registered in `newRegistry`, in one place, while nothing a dependency registered on the default registry is inherited (`TestThePrometheusExpositionIsPrivateToThisProcess` pins both sides). With push off, no exporter is built at all — `Validate` refuses `otel.metrics.push` without `otel.metrics.enable`, and the push-only settings (`interval`, `export_timeout`, `path`) are checked only when push is on. `Observer.Shutdown` stops the metric provider before the tracer provider, and `MetricsHandler` returns nil for a disabled signal rather than exposing an endpoint that reports nothing. `SetGlobals` installs only the enabled providers, so a switched-off signal keeps the SDK's no-op global.

There is one exporter per signal — `otlptracehttp`, `otlpmetrichttp`, and the logger's `otlploghttp` — all speaking `http/protobuf`; the gRPC and `http/json` legs were removed to drop the `google.golang.org/grpc` dependency tree, so there is no protocol branch and `otel.protocol` is no longer a configuration key. Like the logger, **every exporter option and every resource attribute is passed explicitly**: the SDK otherwise reads `OTEL_EXPORTER_OTLP_*`, `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, and `OTEL_SDK_DISABLED`, which would be a second configuration source deciding what this process reports and where. TLS material is closed with a nil `tls.Config` on a plain http endpoint, which stops the certificate options from being loaded. `samplerFor` maps `otel.tracing.sampler` onto the SDK samplers, including `parent_ratio` (`ParentBased(TraceIDRatioBased)`), so a service that receives an already-sampled request keeps the trace whole. A route is applied only when the configuration names one or the endpoint carries none: an address that already names a route says where the signal goes, and overriding it with the default would send it elsewhere. The `otel/log` module is pinned at v0.19.0 (see the decision records below); the trace and metric exporters are on the core version line and stay free.

### queue

The embedded task queue, ported from `mikestefanello/backlite` (MIT, SQLite) and owned here: the schema comes from migration `00008_create_scheduler_tables.sql` (the queue and the scheduler state share it), the queries from `go-sqlbuilder` (the seeders' idiom), and the logs from the process `*slog.Logger` the caller passes — the package never builds its own. A `Task` is a payload type whose `Config()` names its queue; `NewQueue[T]` pairs that type with a decoded processor, and `Client.Add(...).Save()` inserts it with a Go-generated UUIDv7, so a caller can reference the task before any commit — `Add` is variadic, which is the batch API: one statement, one transaction.

The dispatcher claims with one `UPDATE ... RETURNING` over a `FOR UPDATE SKIP LOCKED` subquery — never claimed, or claimed before `queue.release_after`, and past its `wait_until`, ordered by `priority DESC` then insertion order, so a higher priority is claimed first — so two processes sharing the database never run one task twice, and a lost worker's task is reclaimed. `release_after` must exceed every registered queue's `Timeout`, or a task still running is reclaimed while it runs: `Client.Register` refuses the pair, so the mismatch fails the run rather than executing the task twice, and the default (an hour) is twice the longest job the application runs. `TaskAddOp.Priority` ranks a task at enqueue time, negative refused; `Client.Cancel` removes a task that has not been claimed yet and reports `false` for one in flight, which finishes its lifecycle. The engine is event-driven: a save notifies it, a delayed task arms the fetcher's ticker, and when nothing is claimable the ticker falls back to one minute — the one bounded poll, which is what makes reclaim independent of traffic. A fetch that finds every worker busy waits on a one-slot idle signal the worker sends as it returns its token, and that wait ends when the run does: a worker that leaves because its context ended never returns a token, so a poll would outlive it. The signal is not a token — the fetcher recounts the free pool when it wakes, and it is the only receiver, so the count cannot shrink before those tokens are taken.

Outcomes: success deletes the task (archiving it in one transaction when the queue's `Retention` asks), a retryable failure releases it for its `Backoff`, an exhausted one archives with the error — the dead letter — and a processor panic is a failure, not a crash; `Dead` counts a queue's dead tasks and `ReplayDead` re-enqueues the ones that kept their payload under a fresh identity, so the archive is a replayable dead letter queue, not a graveyard. When `queue.encrypt` is set the client seals every payload at rest with `pkg/crypto`'s `Cipher` (the `enc:` prefix marks a sealed payload) and opens a claimed payload before the queue decodes it — an in-flight plaintext task from before the flag flipped still runs, and the archive keeps the sealed form so a replay rides the same path. A task whose queue was never registered is re-queued on its own clock and logged — it may be waiting for a deploy — and spends no attempt. `WithTx` callbacks receive the shared `Querier`, so `TaskAddOp.Executor` joins the caller's transaction, and the caller owes it a `Notify()` after the commit.

The queue instruments itself through the global meter provider (`metrics.go`, scope `github.com/riipandi/saka/internal/queue`): the client builds its `taskMetrics` at construction — real when the observer is up, the SDK's no-op when metrics are off, so recording costs a nil check — and the counters follow the engine's own contract: `saka.queue.tasks.enqueued` per queue at insert, `saka.queue.tasks.processed` by `outcome` (`success`, `retry`, `dead`, `unknown_queue`) at settle, `saka.queue.task.duration` and `saka.queue.task.attempts` as histograms, and `saka.queue.claims.failed` when a claim round cannot read the pending table. The outcome is computed where the settle branches, so a dashboard's breakdown and the engine's own behavior cannot drift apart; there is no queue-depth gauge, because a gauge over the pending table would put a `COUNT (*)` on the scrape path and the enqueued-minus-processed rates say the same thing.

### jobs

The concrete jobs the application runs on the queue: one job per `*_job.go` (task type, `QueueConfig`, processor), with `Register` the one place the queue list is spelled out and the recurring ones seeded, and `Scheduled` the list the cron scheduler enqueues — empty until a feature asks for a cron schedule, because a recurring job that runs on a fixed interval belongs with `Register`, whose self-enqueued successor is durable without a second mechanism. A recurring job keeps its own schedule: its processor **enqueues the next instance only after its own work has succeeded**, and `Register` seeds one only while none is pending, so a restart never multiplies the schedule. The order matters: a successor committed before the work fails stays committed, the queue's retry of the same attempt inserts another, and a few attempts leave several parallel chains — the `api_key_expiry_scan` did exactly that until it moved its enqueue behind the scan. `cleanup_job.go` purges the completed records their retention has expired, on `queue.cleanup_interval`; `audit_cleanup_job.go` applies `app.audit_retention_days` to `public.audit_logs`; `storage_gc_job.go` sweeps the backend; `scim_sync_job.go` runs the outbound provisioning passes — one recurring hourly queue (`scim_sync`, always seeded) and one debounced change-triggered queue (`scim_sync_debounced`, enqueued by `ScimSyncNotifier`), both driving `scimsync.Service.SyncAll` through the lazy `lazyScimSyncer` seam, which answers nil without the federation area. The engine's own goroutines know none of the jobs — jobs are application code, the queue is infrastructure.

### scheduler

The durable cron scheduler: robfig/cron v3 (zero dependencies) owns the timing, Postgres owns the claim, and the queue owns the execution — a claimed tick only enqueues a task, never runs logic. The state lives in `scheduler_jobs` (migration `00008_create_scheduler_tables.sql`, shared with the queue), one row per job: `next_due` is the claim cursor. Every replica fires the cron time; `fire` opens one transaction that locks the row `FOR UPDATE`, reads the database's own `now()` (so replica clock skew cannot double-fire), advances `next_due` from the old due — a cron spec resumes at its next mark instead of bursting, an `@every` spec catches up one slot per tick — and enqueues the task through `TaskAddOp.Executor` in the same transaction, so a tick is enqueued exactly once and never lost between claim and insert; `Notify` comes after the commit. A failed tick leaves the row untouched and retries at the next firing; the row lock replaces leader election (no elector, no leader lifecycle), and seeding is `ON CONFLICT DO NOTHING`, so a row a deploy created keeps its schedule in motion. `New` refuses a missing store or client, an empty or duplicated name, a nil task, and a spec that does not parse; `app.timezone` resolves a spec that names no zone (robfig's `WithLocation` sets the run loop's clock but not the parser's, so the `TZ=` prefix is prepended and the spec is parsed once). The scheduler instruments its ticks the same way the queue does (`metrics.go`, scope `github.com/riipandi/saka/internal/scheduler`): `saka.scheduler.ticks` by `job` and `outcome` — `claimed` (this replica advanced the row and enqueued), `skipped` (another replica's fire got there first, which is the claim design working, not a miss), `error`, `reseeded` (a state row rebuilt) — plus a per-tick duration histogram. The outcome rides out of the transaction rather than being written inside it, so a rolled-back claim never leaves a phantom tick on the counter.

### audit

The audit trail's writer and vocabulary. `internal/audit` holds what every feature needs and nothing a request reaches: the event names (`sign_in`, `account_created`, …), the `Entry` a caller fills, the `ClientInfo` the transport captures, and the `Recorder` that writes the row. The **reader** is `modules/auditlog` — a separate area, because it serves procedures and this package serves none.

The split is the same one `internal/queue` + `internal/jobs` keeps, and it is forced rather than aesthetic: `modules/auditlog` imports `modules/identity/user` (to read the account's username beside its identifier), so a recorder living there would be a package every identity feature imports and an import cycle the moment one of them did. Measured, not assumed: a probe import of `modules/auditlog` from `modules/identity/user` fails the build with `import cycle not allowed`. The second reason is the transport: `internal/transport/middleware` captures `ClientInfo` and imports no module by design, so the type has to live below it.

**A record is written in the transaction that caused it.** `Record(ctx, db, entry)` takes the query surface rather than reaching for the pool, so `pool.WithTx` passes `tx` and the account change and its record commit together or not at all. That is the property a reader trusts the log for: a rolled-back action leaves no record claiming it happened. A feature that writes outside a transaction (the verification enqueue, whose queue task is already durable) passes the pool and accepts that the record describes a committed action.

**A failed record cannot abort the change it describes.** The insert runs under a savepoint (`datastore.WithSavepoint`). Postgres poisons a transaction on any statement error until rollback (`25P02`): without the savepoint, an insert the database refused — a `user_id` the foreign key does not know, a `trigger_type` outside the enum — would make every later statement and the commit fail, so the caller's own change would roll back and the error it saw would not name the audit insert. The savepoint contains it: the record is lost, the change commits, and the recorder logs the event that went unrecorded. The helper reads the surface it is handed — a `pgx.Tx` opens a nested transaction (pgx's savepoint), a pool has no surrounding transaction to poison and runs the function directly — so one `Record` works inside and outside a transaction.

**The recorder is nil-safe.** A service built without one — the state a unit test of a feature is in — writes nothing instead of panicking, so feature constructors carry no nil check at every call site.

**Two fields come from the request, not from the caller.** `Record` fills the client facts from `audit.ClientFromContext` when the entry carries none, and the actor from `jwtutils.CallerFrom(ctx)` when the caller is impersonating. That is why a feature writes `audit.Entry{Event: …, UserID: …}` and names neither the address nor the delegation: one middleware captured the first, the token carries the second.

**The deletion record names its account differently, on purpose.** `public.audit_logs.user_id` is `REFERENCES public.users(id) ON DELETE SET NULL` — a record outlives its account — so a record written *after* the row is gone cannot name it: the foreign key refuses an identifier that names nothing, and the insert is lost. `DeleteUser` therefore writes `resource_type = "user"` and `resource_id`, and keeps the username in the payload. Measured: writing the deletion record with `user_id` set silently dropped it. The reader's list uses a **LEFT** join for the same reason — `sb.Join` is an INNER join in go-sqlbuilder and would hide exactly those records — while the facet query uses an INNER one, because an option is a selectable account and a record with no account contributes none.

The address is read back with `host(ip_address)`, never a cast: `inet::text` renders the network mask (`203.0.113.7/32`), which is not the address a client asked for.

### notification

What an administrator announces and what an account reads. `modules/notification` is an area of its own — a notification is not an account fact, and its managing surface is administrative while its reading surface is every account's. One contract (`saka.notification.v1.NotificationService`) carries both audiences, split by the guard table: the four administrative procedures (`Create`/`Get`/`ListAll`/`Cancel`) are `Admin`, the account procedures (`List`/`MarkRead`/`MarkAllRead`/`UnreadCount`/`WatchNotifications`) are `Authenticated`.

**The audience is a kind, not a fanout.** `audience_kind` is `global`, `users`, or `user_groups`; the named kinds live in junction tables and are resolved by the query at read time. Nothing is materialised per recipient at creation — a global announcement costs one row however many accounts hold. The read state is the mirror image: one receipt row per (notification, account) written the moment the account marks it read, so unread is `NOT EXISTS (receipt)` rather than a flag the create would have to seed. The visibility predicate — live, and targeted globally, by name, or through a group's membership — is one shared condition the inbox, the unread count, the mark-read gate, and the email pass's recipient walk all read, so the audience a reader sees and the audience an email goes to cannot drift apart.

**The pairs the contract cannot express live in the service.** A `system` notice is about accounts: it carries a topic never and a global audience never. `Create` validates the named accounts and groups exist (one count over the distinct identifiers) and refuses an unknown one without naming which.

**The live tail is a broker, not a log.** `WatchNotifications` is a server-streaming procedure served from an in-process broker the service owns: one publisher (the create, after its commit), one event shape, buffered channels that drop rather than block. The stream carries no history and no cursor — the durable record is the table, and a reconnecting client catches up through `ListNotifications`. Because a create publishes after its commit, a rollback can never contradict an event a reader already saw. The stream's keepalive is a `ping` event (25s cadence, one sent immediately on open, which is also what makes a client's first read deterministic), and the procedure path is listed in `rpcStreamingProcedures` — `middleware.UnboundedFor` lifts the request deadline and the `http.Server` write deadline off it while keeping client-disconnect cancellation, because a stream's whole job is to outlive the timeouts a unary call is bounded by.

**The email pass rides the seam, not the import.** The service states "this notification asked for an email pass" through the `EmailDispatcher` interface; the dispatcher (task type + gate, in the same package) turns it into a durable `NotificationEmailTask` on the `notification_email` queue, gated at the enqueue site by `mailer.notifications.announcement_email_enabled`. The processor lives in `internal/jobs` — it is the application logic the queue runs — and reads the audience through the notification package's repository, which is why the task type lives beside the notification it names: the other direction would have the area and the job package importing each other. The pass walks its audience in keyset pages, stamps `email_sent_at` only after the last page went out (a pass that dies mid-audience is retried whole), and delivers nothing for a notification cancelled meanwhile.

Retention is a job, not an endpoint: `audit_cleanup` deletes what is older than `app.audit_retention_days` (default 90, the window Pocket ID ships) and re-enqueues its own successor on `DefaultAuditCleanupInterval` (24h), seeded through `jobs.Seeder` like the other recurring jobs. The window rides in the task payload, so a changed configuration takes effect at the next run. There is deliberately no procedure to write, edit, or delete a record: a log its subject can rewrite is not a log.

### storage

The file storage engine and its two backends — the local filesystem under `storage.local_path` and an S3-compatible store (`storage.driver` selects; `New` builds only the selected one, so a local deployment never opens an object-store client). A **bucket** is a row in `storage_buckets` (migration `00009` — name TEXT UNIQUE ≤ 100 characters validated in Go, NULL-able `file_size_limit` and `allowed_mime_types`, seeded `devbucket`), resolved by name at every entry point, and the name is the container the backend addresses the file by: a directory under the local data directory's `uploads/` subtree (`storage.local_path/uploads/{bucket}/{key}` — the engine's own subtrees `staging/`, `logs/`, `backup/`, `config/` sit beside `uploads/` at the top level, and the store's listing walks one bucket's subtree only, so it can never name them), and the physical bucket of the same name on the object store (`{endpoint}/{bucket}/{key}`, path-style; the S3 section carries no bucket key — the rows are the bucket list, and `EnsureBucket` provisions the container at creation, idempotently). A file is stored **whole** under the key its feature composed inside its bucket: the sync hashes the staging file (SHA-256 of the whole file — the content hash) and hands the bytes to one PUT, so both drivers keep the same `/{bucket}/{key}` tree. There is no chunk store. The earlier design cut a file into content-addressed chunks the backend held individually, buying cross-file dedup and per-chunk resume at the cost of a bucket of hash-named objects no final file ever appeared in — a whole-file PUT answers the same durability (the staging file and the manifest row are the resume points), so the chunk layer is gone rather than kept as a second representation. The manifest — one `storage_objects` row (`bucket_id` FK ON DELETE RESTRICT, `UNIQUE (bucket_id, key)`, `is_private` boolean default false) — lives in Postgres, the durable place a read and a garbage collection start from; the content hash is the one-value fast path that says a sync has nothing to upload. A private row is read only over a signed link (`storage.Signer`, HMAC over `app.secret_key`, the expiry inside the payload, default ttl the `storage.signed_url_expires` setting); a plain read answers the 404 a missing object gets, and a private response carries `private, no-store`. Object ids travel as `file_` TypeIDs and bucket ids as `bkt_` (the columns stay UUID; the conversion lives at one boundary per package — the manifest scan and the management module's schema).

Keys are the feature's naming, made safe at the door: `Key(parts...)` composes a multi-purpose key (`avatars/usr_1.png`, `user-files/…`) by mapping each part onto one path segment, `ValidateKey` refuses any key with a traversal, absolute, or hidden segment, `ValidateBucketName` refuses a bucket name that is not one path segment, and every manager entry point validates both before it builds a path — a reference cannot walk out of the staging directory. A reference on the queue and in logs is the composite `bucket/key` (`SplitRef` splits it; `Stage`'s callers and the tus completion both enqueue with one). Metadata is the feature's free-form record (content type, original file name, owner) in a JSONB column: written at `Stage` time, rewritten by `UpdateMetadata`, carried but never interpreted by the engine — except the tus session's own `tus_upload_length` marker, which the protocol state reads and completion strips.

The request path is a local disk write and nothing else: `Manager.Stage` writes the file into `storage.local_path/staging/{bucket}/{key}` through a temp file and a rename (no reader ever sees a half-written name) and commits the intent row — metadata plus the staging fingerprint — then **the caller enqueues the upload itself**: the write that finished is the fact the queue carries, so there is no watcher to notice it a second time. Everything else happens on the durable queue. `storage_upload` (`StorageUploadTask`) runs `Manager.Sync`: a pending manifest whose staging fingerprint (size + mtime) matches the staging file is **trusted for its content hash** — the checkpoint that keeps a retry from re-hashing a large file (a Stage row a sync never reached carries no hash and is hashed as if new) — otherwise the sync streams the file once for the hash, rewinds, and PUTs it whole. Two details keep that trust honest. A re-stage **clears** the stored content hash, because the fingerprint it writes is the new file's and the row's hash belongs to the previous version: without the clear a sync that matched the fingerprint would skip hashing and store the new bytes under the old digest. The fingerprint is truncated to **microseconds** on the way in (`micros`), the precision `timestamptz` keeps, so the value a retry compares against is the value the database can hand back — a nanosecond file system would otherwise make every honest retry re-hash, and a rounded store could make the reuse path trust a fingerprint the column never held. The pending checkpoint lands before the bytes travel; the ready manifest commits in one transaction after the PUT returns, and the staging copy is removed only if its fingerprint still matches what the sync read — a file re-staged underneath a running sync is left for its own round, not destroyed. A change to a key replaces its object whole: there is no per-chunk diff to apply, and the content-hash check is what keeps an unchanged replay from re-uploading.

The upload's deadline is real on both legs that can run long. The task times out at 30 minutes so it stays strictly under `queue.release_after`; the hash pass (`sha256` over the whole staging file) and the local `FS.Put` copy are plain `io.Copy` calls that no context reaches on their own, so each wraps its source in `ctxReader` — a per-read context check that stops the copy when the task's context ends. Without it a copy that outlasted the release window would leave the row claimed while the first worker was still inside `io.Copy`, and the next claim could overlap it. A cancelled local write removes its temp file, so a dead context never leaves a half object or a stray temp name.

Nothing polls the staging tree. The settle mechanisms are deterministic (the fsnotify watcher was removed with its `storage.watch` config section — two settle mechanisms over one staging tree would race, and the deterministic enqueue does not need a debounce): a `Stage` caller enqueues when `Stage` returns, the tus completion enqueues on the final chunk, and the **startup sweep** (`jobs.SweepUploads`, a serve-run runner that runs once and ends) re-enqueues the manifest rows a dead run left pending with no session marker. The interrupted tus sessions are the **expiry job's**: `storage_upload_expiry` (recurring, re-enqueues its own successor) reclaims every session whose last activity rests past `TusSessionExpiry` (24 h) — the staging file and the row go together. Deletion removes the manifest row first and the object second — a crash between the two leaves an unreferenced object — and `storage_gc` (a recurring job on the cleanup pattern, re-enqueuing its own successor at `DefaultStorageGCInterval`) sweeps each bucket's container against the manifest's key set: an object the set does not name is the drain of the paths a crash can leave, and a bucket the table does not name is never walked. `Manager.Open` reads a file back as one stream the backend serves on demand; no whole-file buffer exists on the read path either. The S3 driver holds the one AWS client of its own (static credentials from `storage.s3.*`, path style for MinIO/Silo), translates the protocol's not-found shape into `ErrNotFound` at its edge, and pays the single-PUT ceiling (5 GiB on the services this targets) as a deployment ceiling, not a code path.

The manifest travels with the database and the objects do not, so the two can disagree: a deployment that switched drivers reads a `ready` row whose object the new backend never held. The engine answers `ErrNotFound` from `Open` for exactly that — the row is not consulted as proof the bytes exist — and it is the **feature's** call what that means: an avatar falls back to the bundled default and logs, because the account has no picture either way and a 500 would tell the client its request was wrong. The rule the split follows: a read names what is missing, the feature decides whether missing is an error.

The upload round has two feature extension points, both nil by default and wired in the registry (`WithBeforeSync` / `WithAfterSync`). `BeforeSyncHook` is the gate: it runs before the staging file's fingerprint is read, so a hook that rewrites the file (sanitize, re-encode) is hashed from its own output, and an error refuses the file — the queue retries, and a hook that keeps refusing walks it to the dead letters. `AfterSyncHook` is the post-processing point: it runs once the manifest is ready and the object is durable, before the staging copy is removed — thumbnails, metadata enrichment, notifications (the upload-finished notice rides this hook: it enqueues an `upload_finished_notice` task naming the owner the staging caller recorded in the metadata, and the processor delivers it through the notification area's own create; a file staged with no owner produces no task). Both run on the queue's retry path, so **idempotence is their contract**: a retry replays them (a failed after-hook leaves the staging file, and the retry reaches the hook through the finished-manifest fast path without re-hashing). A hook must also stay quick — long work belongs in a job the hook enqueues, not in the upload worker's slot.

The engine instruments its rounds the same way the queue does (`metrics.go`, scope `github.com/riipandi/saka/internal/storage`; the manager builds one): `saka.storage.files.staged` at `Stage`, `saka.storage.staging.settled` when a completion enqueues its upload, and one counter set per sync round — `saka.storage.uploads` by `outcome` (`success`, `skipped` for the retry that found nothing to do, `error`), a duration histogram, and on success the bytes that reached the backend. `Sync` is a thin wrapper over the private `sync`, and the outcome travels **beside** the error on purpose: a failed staging cleanup is not a failed upload (the manifest is ready), so the counter counts what the round actually achieved while the caller still sees the error.

**The resumable-upload protocol is the engine's client surface.** `internal/storage/tus.go` and `tus_handler.go` speak tus 1.0.0 in-house (see the library decision record) at `/api/uploads`: a creation (`POST`, the `Upload-Metadata` naming bucket and key, the `Upload-Length` declaring the size) opens a session — an empty staging file under `staging/{bucket}/{key}` and a pending manifest row carrying the declared length as the `tus_upload_length` metadata marker — and its body, when there is one, is the first chunk. `HEAD` answers the staging file's size as the `Upload-Offset` a resuming client continues from; `PATCH` appends one chunk of `application/offset+octet-stream` at the offset the client claims, refusing a claim the file's size does not name (409) and refusing a file that has already reached its declared length or a row no session owns — the refusal is also what keeps a completion from firing twice. When an append reaches the declared length the **completion fires inside the same request**: the marker is stripped (the row becomes an ordinary staged upload the sweep can recover, the expiry stops claiming it) and the queue takes the file through the `UploadEnqueuer` seam the registry wires over the queue client. `DELETE` terminates: the staging file and the row go together. The expiry job reclaims the interrupted sessions; the bucket's existence, `file_size_limit`, and `allowed_mime_types` are checked at creation, before any byte travels. Authentication is the transport's bearer middleware (creation and the session methods are `Authenticated`; the `OPTIONS` discovery is `Public` — it names the version and extensions a client may rely on), and the paths are lifted off the request deadlines (`middleware.UnboundedForPrefix`) because a chunk's travel time no unary deadline can bound. There is no per-upload authorization model yet: any signed-in account may upload into any bucket. The client integration is `tus-js-client`; the debug build's `/debug/file-upload` probe page drives the whole flow against a running server.

### authorization

Who may act, beyond "an administrator". `internal/authz` is the vocabulary and `modules/identity/authorization` is the managing surface over it; `internal/guard` is the enforcement point. The model is Unkey's, flattened on purpose: a **permission is a string** — `resource:id:action`, the id position carrying `*` for every instance of the kind (`user:*:read`) — a **role is a named set** of those strings, and an account's effective grants are its roles' permissions plus the ones granted to it directly. There is no role inheritance: a hierarchy's answer is always reconstructible from the flat set, and its cost (cycle detection, closure tables, recursive checks) is not.

**The catalog is code, and that is the security boundary.** The slugs an application enforces are declared once in `internal/authz` (`Resource` table → `Catalog()`), seeded into `public.permissions` so roles can reference them by key, and served read-only by `ListPermissions`. An administrator manages the layer above the catalog — roles, each role's set, each account's grants — never the slugs themselves: a permission the runtime could invent is a permission nobody audited, and a slug the table held but the code stopped enforcing would authorize nothing and lie on every screen that showed it. `SetRolePermissions` and `SetUserPermissions` refuse a slug the permissions table does not hold for exactly that reason.

**The token is the snapshot; the row is the truth.** `user.LoadGrants` is the one door every token mint walks through — sign-in, the session refresh, the delegation, the API-key credential — and the access token carries what it read as two claims, `roles` and `permissions`. A grant that changes lands in the next token, which is why the access token's life is short and the renewal re-reads the account. `jwtutils.Caller` answers the questions the claims can: `HasRole`, `IsAdministrator`, and `HasPermission` (wildcard-aware, `authz.Match` — the wildcard is legal in the instance position only, and `ValidSlug` refuses it anywhere else).

**`users.is_admin` is gone; the administrator role is the elevation.** The boolean the users table carried could not be granted, audited, or narrowed, and it answered a question the role set now answers — so `guard.Admin` reads the role claim (`caller.IsAdministrator()`), the impersonation refusal ("an administrator may not wear another administrator") reads the target's roles, and the seeder grants the default account the administrator role the moment it creates it. A fresh database without a seed has no administrator by construction; `saka initialize` is the bootstrap that applies the system seed and names the first administrator — it refuses a database that already holds an account, and `saka admin:reset-password` recovers an administrator's access with the account's sessions revoked around the swap.

**The managing surface is administrative end to end.** Every `AuthorizationService` procedure is `Admin`, deliberately: a surface that granted its own management could raise anything to itself. System roles (`type = 'system'`, seeded) refuse rename and delete and keep the seed's permission set; a custom role cannot be deleted while accounts actively hold it — the grants must be lifted first, so a deletion strips nothing silently. Role grants and direct grants carry their own life (`assigned_at`/`revoked_at`/`granted_by`/`revoked_by`): a revoke is a stamp, not a delete, so an assignment's history survives, and a re-grant opens a fresh row — the composite primary key plus the partial unique index on the active rows is what makes both true at once.

**For the frontend, the claims are the API.** A signed-in caller's abilities are the token's `roles` and `permissions` — the strings map one-to-one onto a casl `can(action, subject)` — and `ListPermissions` answers the catalog rows (the `perm_…` id, the slug, the description; search, resource filter, and sort) so an admin UI renders the checkboxes the server will actually enforce. `ListRoles` narrows by search and `RoleType`. An admin managing another account's grants reads them from `ListUserRoles`/`ListUserPermissions` and writes them with the `SetUser*` pair; both write procedures replace the whole set, because a grant set is a fact about the account, not a delta to apply.

## Implemented modules

### modules/identity

The identity **area**: the unit the composition root loads. `identity.Module` holds the feature list and mounts every feature on one router, so `internal/registry` names one module per area rather than one per feature, and a new identity feature is added inside the area without the transport or the registry learning about it.

`NewModule(Deps)` takes the resolved services (`Deps.KeySet` today) and builds the features from them; `features(deps)` is the one place an identity feature is named, and each feature names its own routes — a protocol endpoint (`/.well-known/…`) mounts on the router's root, an application-API feature mounts itself under `/api`. Adding a feature therefore touches its own package and one line in `features`.

The area also owns the wiring of its own services, which is what makes it composable rather than merely separate: `identity.Package` registers the services the area owns, and `identity.Mount(i)` resolves what its features need — the cached `jwtutils.KeyProvider`, then the `*jwks.Service` beside it, reporting `service.Err()` so a broken key pair fails the run — and returns the `kernel.Module`. The composition root used to hold both, which is what made it a per-area registration list: it knew that this area wants a key provider and that its service has an `Err()` to check. Adding a dependency now touches `Deps` and this file, never `internal/registry`. The same shape applies to every area (`modules/federation` holds `discovery`, `oidc`, `scimsync` the same way).

**Route claims are policed between modules.** `chi`'s registration is last-wins (`node.setEndpoint` overwrites unconditionally), which is why `kernel.Mount` reads each module's routes back from a scratch router and fails the run when two modules claim the same method/pattern pair — see the kernel section above. Within one module's own registration, last-wins holds and is the module's own defect. `kernel.Mount`'s doc and `internal/kernel`'s tests pin the detection.

### modules/identity/blocklist

The access-restriction feature: the blocklist CRUD and the pure address logic
both gate readers share. `public.blocklist_entries` (migration `00015`) holds
one email address or one `@domain` entry per row — the grammar is the column's
CHECK constraint read twice, `ValidatePattern` in Go mirroring it so a refusal
is `invalid_argument` before the write, never the database's error. The match
(`Matches`) is exact, `@domain` **equality** (a subdomain is a different
domain, unlike the allowlist's suffix reading), and the subaddress carry-over:
a blocked exact address also blocks its `+`/`=`/`#`/Yahoo-hyphen variants. The
provider table (`yahooDomains` on exact domains only, `gmailDomains`) and the
folds live in `address.go` as pure functions — `SubaddressBase` (the
blocklist's cut, dots kept) and `CollisionBase` (the subaddress blocker's cut,
Gmail dots folded) are two different answers to "one mailbox?" and both are
imported by the features that ask.

The admin CRUD is `saka.identity.v1.BlocklistService` (`Admin` in the guard
table), idempotent on add: the insert is `ON CONFLICT (pattern) DO NOTHING`
returning whether it fired, the audit event `blocklist_entry_added` /
`blocklist_entry_removed` writing only on a state change, inside the caller's
transaction.

**The gates ride seams, not imports.** Signup defines `BlocklistChecker`
(`Blocked`, `CollisionTaken`) and signin defines `BlocklistChecker`
(`Blocked`) — consuming-side interfaces, satisfied with
`signup.WithBlocklist` / `signin.WithBlocklist` in the area's `Package`. The
verification feature defines `SubaddressGuard` (`CollisionTaken`) for the
email-change check. The decisions the gates share: the allowlist wins over
the blocklist at both surfaces; every settings or list read that fails lets
the request pass (fail-open, warn log) — the lists are an anti-abuse control,
not an availability one, and a broken read must not lock accounts out. The
sign-up refusal is the generic `not_found` "sign-up is not available"; the
sign-in refusal (`ErrSigninRestricted`, read inside `IssueSession`'s state
switch behind `access.blocklist_applies_to_signins`) is `permission_denied`
"sign-in is not permitted" and answers only a proven credential — a wrong
password still answers `invalid credentials`. The subaddress blocker refuses
an email change with `failed_precondition` without naming the collided
account.

### modules/identity/jwks

The published key set, at `GET /.well-known/jwks.json`. The database is the one signing authority: `public.jwks` (migration `00013`) holds every asymmetric key pair, its private half sealed `enc:` with the auth secret (derived from `AUTH_SECRET_KEY`, not the application secret). Each row carries `seal_fp`, the fingerprint of the key that sealed it. When the process's fingerprint no longer matches a row's — an `AUTH_SECRET_KEY` rotation — the signing read retires the stale rows in place and provisions a replacement pair (the `Sealer` seam, audit event `jwks_invalidated`), so the rotation recovers on the next sign-in; tokens minted under the retired key fail verification until they expire. Rotating the application secret leaves the signing keys untouched. `saka initialize` provisions the first pair in the seed transaction (the `JWKSKeyPairSeeder`, audit event `jwks_provisioned`); `jwks:generate` stages a further pair for rotation; both seal with the auth cipher and record its fingerprint. The environment carries no key-pair material. `Service` implements `jwtutils.KeyProvider`, so the endpoint that publishes the set and the code that verifies a token read one source — a key that is not published is not accepted, and a key that is published is accepted with no second list to keep in step.

**The cache lives at the provider seam, not inside the service.** The registry wraps the service in `jwtutils.NewCachedKeyProvider(service, jwks.KeyCacheTTL)`, and both the endpoint and any future verifier take the `jwtutils.KeyProvider` interface rather than the concrete service — so the cache is invisible to the feature, and how long a set is reused is a deployment decision instead of a property of the set. `KeyCacheTTL` is a minute: the value is cheap to rebuild and a rotation must be picked up promptly, while a client that verifies many tokens must not turn each verification into a query (`TestTheCachedProviderReadsTheSourceOncePerTTL` pins five fetches inside the TTL at one source read). The HTTP `max-age` a client honours is a separate, longer window.

`VerifyKeySet` returns every row that is `is_active`, `use_for = 'sig'`, and either without an expiry or not yet expired. Two behaviors are deliberate and pinned by tests: a **stored row that cannot be parsed is skipped, not fatal** (one bad row must not take the keyset down for every client), and **a duplicate `kid` appears once** (a set naming one key twice is a set a client cannot index). A source that cannot be read fails the call rather than answering a partial set — the set is the source of truth for what verifies, and silently dropping it would refuse valid tokens without a visible cause. `SignKey` unseals the first active row's private key and adopts the row's `kid`, so a minted token's header names a key the published set carries; the rows are ordered by `key_id`, so the first row is stable. The generated pair's `kid` is a `jwk_` TypeID, stamped by `crypto.GenerateKeyPair`, so every key in the set names itself the same way.

The published document is a bare JWK Set (the RFC 7517 `{"keys":[...]}`), **not** the API envelope: every standard JWKS client parses that shape, and wrapping it would make the endpoint unreadable to them. A failure still goes through the responder envelope, and the request id travels in its header either way. The `Repository` never selects `private_key`, and each key is marshalled by jwx after `jwk.PublicKeyOf`, so a private half cannot reach the document by either path — both are pinned by tests, including one that inserts a row with a sealed private key. A module mounted with no provider **fails closed** with a 500 rather than answering an empty set, which a client would read as "no key is valid".

**Algorithm handling.** Signing is **dual stack**: the database's key pair (asymmetric) and `auth.secret_key` (HMAC) are independent halves, and either can sign. `auth.jwt_algorithm` names which one signs when both are configured; it is **optional and omitted from the generated sample**, because a deployment with one stack never needs it — the answer is derived, from the active signing row's `algorithm` column or from the HMAC secret's length. It is validated against `config.JWTAlgorithms`, and a test in this module asserts that list equals `jwa.SignatureAlgorithms()`, so a library that grows an algorithm fails there instead of silently rejecting a valid name.

`Service` exposes the resolved material: `SignKey` (asymmetric), `HMACKey` + `HMACAlgorithm` (symmetric), and `SigningAlgorithm` for the answer a caller signs with. The HMAC algorithm follows the secret's length — 32/48/64 bytes for HS256/HS384/HS512 — which is the same rule `key:generate` follows when it sizes the value, so the two agree without a second config key. The secret is read with `crypto.ParseHMACKeyHex`, **not** `ParseKeyHex`: the latter is the AES-256 reader and insists on exactly 32 bytes, so it would have rejected the 48- and 64-byte secrets `key:generate --algorithm HS384|HS512` writes.

Two properties are relied on and pinned by tests. **`kty` bounds `alg`**, so the classic RS256→HS256 confusion is rejected by jwx itself: a published RSA key with `alg=RS256` (or with no `alg`) cannot verify an HS256 token, because the candidate algorithms come from the key type (`jws.key_provider` `selectKey`), not from the token header. **A symmetric key is refused, not published**: `rejectSymmetric` rejects `kty=oct` on both paths into the set, because a symmetric key's "public" form *is* the secret — verified before the guard existed, `{"kty":"oct","k":"…"}` published the HMAC secret verbatim. HMAC signing stays supported through `auth.secret_key`, which is never published; the guard rejects publication, not the algorithm.

**The dual stack's cost, stated plainly:** the HMAC secret is *not* in the published set and never can be, because publishing it would let every reader mint tokens. An HS* token therefore verifies only in a process that holds the secret, and cannot be verified from the JWKS endpoint. That is inherent to symmetric signing, not a gap in this module.

Closed for the tokens the process signs itself, open for a foreign key set: the own-token verification path is `jwtutils.AccessVerifier`, which resolves the key and algorithm per call and builds the verifier with that exact pair — the accepted algorithm is pinned by construction, no `WithAllowedAlgorithms` needed. What stays open is `jwtutils.Verifier.WithKeySet` (it sets `jws.WithRequireKid(true)`, so a token without `kid` is refused even for a single-key set, but it cannot pin `alg`): a verifier over a *foreign* key set — the OIDC federation case — would accept an algorithm-confused token, and when that path exists the pin has to be a check on the parsed header against the set's declared algorithms, in the verifier wrapper. The signed key's `kid` is always present (verified: `jwt.Sign` copies it into the header), so `WithRequireKid(true)` matches what this module signs.

### modules/identity/signin

The sign-in feature, the first password credential on the RPC surface: `saka.authn.v1.AuthService/SignIn` (the contract lives in `api/connect/authn.proto`, not `saka.identity.v1` — authentication is its own package, the area is the implementation). The identity is one field, matched as CITEXT username or exact email; the failure for an unknown identity and a wrong password is one error, and a miss runs the verifier against a lazily computed dummy hash, so the two failures cost the same work and the endpoint is not an account enumerator.

The answer is the token pair the protocol section settles: a stateless access token (signed through the area's `jwks.Service`, so the dual stack is the deployment's decision — the service resolves algorithm and key per call, symmetric to `HMACKey`, asymmetric to `SignKey`) and a refresh token whose only server-side trace is a hashed row in `public.sessions` (SHA-256, 256 bits of base64url randomness). The session window reads the settings database, not the configuration file: `session.max_lifetime` is the one bound — the remembered and the non-remembered path share it, read fresh at every mint (`signin.Service.sessionLifetime`, bounds 5 minutes–10 years, an unreadable value falls back to the catalog default) — and the renewal refuses a session whose last activity rests older than `session.inactivity_timeout` (bounds 5 minutes–1 year), revoking the row on the spot so a stolen refresh token cannot wait the gate out. The `remember` flag selects only a lifetime, not a kind of token. The session row is the feature's one write-side coupling: the table constants live in the `session` package (`session.SessionTable`, `session.SessionID`), the row is written where the credential is verified, and the id leaves the server as a TypeID (`sess_…`) — the UUID column stores the typed id's UUID, the prefixed form is for clients and log lines. `sid` in the access claims is the same id, so a later rotation or revocation names exactly the row.

Account state is refused after the credential verifies: `disabled` and a live ban window are `permission_denied` details, not `unauthenticated`, so the caller who owns the password learns the real reason; the ban reason text never leaves the database. An account inside a lockout window is the exception, and deliberately: the lockout's refusal is the same generic credential error a wrong password earns, so the lockout never becomes an account enumerator — the bound's row is the database's answer, the wire's shape unchanged. The failed-password streak is the account's in-place counter, the lockout write and its audit the restrictions feature's (see that section). The `last_login_at` touch commits with the session row, both through the shared `Querier`. The caller's address, agent, and fingerprint are the transport's capture: one middleware read them from the request before the procedure ran, and the handler carries them into the session and the audit record through `audit.ClientFromContext`, so every record of a sign-in names the same address the rate limit keyed on.

Opening the session is `IssueSession`, the issuer the one-time access exchange and the MFA bridge share: it takes the query surface its writes run on, so a caller holding a transaction passes its tx and the session and whatever caused it commit together, and it carries the account-state checks every issuer owes. When the verified account keeps a confirmed TOTP factor, the sign-in forks before any issue: the `mfaGate` (see multifactor) is asked whether a challenge is owed and mints the pending bridge, and the response carries the challenge instead of the pair. The password verification stays here; the session's shape and the audit record do not.

### modules/identity/session

The session lifecycle: what happens to the row a sign-in wrote once the caller walks away from it.
The surface is `saka.authn.v1.SessionService` beside the issuing `AuthService`, because the two
halves are one story — the opening and the ending — carried by one contract.

The access token stays stateless by decision, and the lifecycle is what makes that honest. A
sign-out stamps `revoked_at` and `revoked_by` on the row in the transaction the audit record
commits in, and the refresh token dies with the stamp — but the access token keeps authenticating
until its own expiry, because a logout that required a round trip per request would turn every
token into a lookup, which is the statelessness the protocol settled. The consequence is a
semantic the surface states rather than hides: after a sign-out, `GetSession` answers
`unauthenticated` — the token verified, the session behind it did not survive — and that is the
signal a resuming client needs. The two failures the service defines are deliberately different:
an **ended session of your own** is an authentication state (`unauthenticated`), while a **session
you cannot name** is a target that does not exist (`not_found`), because the owner's list is the
only way to learn which sessions exist and the answer discloses nothing about any other account's.

The renewal rotates **in place**: the row keeps its identifier while the token hash and the window
are replaced, so a client's session keeps its identity across renewals and the old access token's
`sid` still names a live row. The read, the reuse judgement, and the rotation run in **one
transaction over a row lock** (`SELECT … FOR UPDATE`), because two in-flight renewals of one token
must not both pass a stale read: the second waits, then finds a `token_hash` that is no longer the
one it presented, which is the reuse the session dies for. The rotation's write carries both the
identifier and the hash it is replacing in its WHERE clause, so a rotation that lost the row to a
concurrent renewal matches nothing and costs the new secret rather than overwriting the winner's.
The presented hash is looked up against `token_hash` and `rotated_token_hash` together: a live row
reached through a spent hash is the duplicated credential, and the session is revoked outright — in
the transaction the audit record commits in — rather than merely refused. No audit record is
written for an ordinary renewal: it is the session continuing, not a happening an operator audits
for, and one line per heartbeat would drown the log in the very renewals it exists to see past.

The issuer is a **seam, not an import**. The opening and the renewal must not drift apart — they
sign the same claims shape for the same session identifier, and they write the session window from
the same two configuration keys — but the sign-in feature reads this package's schema, so a direct
import would cycle. `session.Issuer` is the interface the lifecycle defines and `*signin.Service`
satisfies structurally: `SignSessionToken` signs the claims the caller assembled (the account-level
`SignAccessToken` is its thin wrapper), `SessionLifetime` is the window a renewal writes, and
`AccessTokenTTL` is the `access_expires_in` a renewal answers, and the session window it writes
is the `refresh_expires_in` the pair answers beside it. The refresh token's draw lives in
`pkg/crypto.NewRefreshTokenPair` for the same reason: two issuers draw it, and a token's entropy
must not depend on which procedure issued it.

The guard's `Session` rule carries the surface's whole policy: a machine credential is refused
because it has no session behind it, and a caller whose claims carry no `sid` is refused because a
token without one is not a session — whatever signed it. The audit events name the happening:
`sign_out` ends the current session, `session_revoked` ends one the holder named, and the record
names the session it ended so an operator can pair it with the sign-in line.

### modules/identity/signup

The sign-up feature: `saka.identity.v1.SignupService/Signup`, the contract in `api/connect/identity.proto` (the identity package, unlike sign-in's `saka.authn.v1` — authentication is its own package, account creation is identity's). RPC only: there is no REST route and none is planned for it. The account carries its primary credential from the first call — the password is required and hashed with the shared `crypto.PasswordHasher` — so the account can sign in immediately; it is created unverified, and email verification is a later procedure (`public.auth_tokens` with purpose `email_verification` already exists for it).

Signup serves the mode the catalog names: `access.mode` reads `open` or
`invite` fresh per request — open, anyone may create an account (the
allowlist and the blocklist gate it; see the blocklist section), invite, the
request must carry a raw signup token, stored server-side only as its SHA-256
hash in `public.signup_tokens`. An unknown, expired, and spent token answer one failure (`permission_denied`), so the endpoint does not disclose which half was wrong; the spend is a conditional `usage_count` bump inside the transaction that also writes the user and the password, so a single-use token cannot create two accounts under a race and a refused duplicate spends nothing. The username grammar and the email check the users table enforces live in the contract — `SignupRequest` carries them as protovalidate constraints the transport's validate interceptor enforces before any handler runs, answering `invalid_argument` with typed violation details — and the names are mandatory on the same terms, so a duplicate answers `already_exists` and a malformed field never reaches the database. The answer is the canonical account view the account procedures share — `user.UserView` read back from the row the transaction wrote, mapped to the wire once in `user.WireView` — so sign-up describes the account exactly the way the administration CRUD does: the names, the creation instant the database stamped, and the unverified state. The service carries no shape checks of its own; `pkg/validate`'s ozzo vocabulary stays the REST body seam.

The signup-token administration is the feature's second half, and the first consumer of the Bearer seam: `CreateSignupToken` draws the raw value (256 bits of base64url, the refresh token's shape), shows it once in the answer, and stores the hash with the requested window and budget — `ttl_seconds` between one hour and thirty days, a `usage_limit` that defaults to the single invitation and caps at a thousand, both validated through the same ozzo vocabulary. `ListSignupTokens` answers the counters and window through the shared `ListMetadata` block, never the raw values; `DeleteSignupToken` revokes an issued token, answering `not_found` for an id that names nothing. The three procedures are administrative: the transport-wide bearer middleware authenticated the caller, and the handler reads `jwtutils.AccessClaims` out of the context and refuses a non-admin with `permission_denied` — authorization lives at the feature because only it knows which procedures are administrative, while authentication is the transport's uniform default. The raw token's lifetime is request-driven, not configuration: an invitation's window is the operator's decision per issue.

The strict enumeration mode (`auth.user_enumeration_protection` = `strict`, `bulk` the default) rewrites the taken-email answer: a signup whose email another account holds answers the same success shape an honest creation earns — the account id a freshly minted decoy TypeID (`user.FormatID(uuid.NewV7())`, so a zero id cannot oracle the real one), the caller's own field values, the gate's stamps — and writes nothing. The address on file learns of the attempt through the `signup-attempt-existing-email` notice behind `mailer.notifications.signup_attempt_notice_enabled`; the token count the response carries is the honest path's only, so the shape comparison holds. The username refusal stays honest under strict — the username is not a verified contact channel, so a decoy would tell nobody anything true.

### modules/identity/user

The account administration feature: the CRUD surface over `public.users` an operator drives. Every procedure is administrative, and the handler holds no check of its own: the procedure is declared `Admin` in `internal/guard`'s table and a caller without the role is refused there with `not_found`, so the account never learns the endpoint exists. The shape follows the upstream it ports: **CreateUser** creates an account without a signup token, its password optional (absent, the account carries no credential row until a later procedure sets one, so an invitation-less account is not silently signable); **UpdateUser** is a *full replace*, every field specified and an empty name part or locale clearing its value, because the upstream endpoint is a `PUT`; **DeleteUser** refuses the account the caller is signed in with (`failed_precondition`) — the caller's username travels from the claims and compares case-insensitively, the way the CITEXT column matches — and the removal is soft by construction — the `fn_soft_delete` trigger archives the row, never a flag the service writes. The same archive answers every operator delete: the account, its group, the OIDC client, the custom claim, the webhook endpoint, and the signup token each carry the trigger, so `public.deleted_records` is the one place a deleted row is readable (the deleted-record insert — the row is moved, not flagged; see the archive's own section under initialization).

The ban fields are the one place the shape leaves the upstream: the upstream carries no ban, and saka's ban is a row in `public.account_restrictions` (the restrictions feature's table; see that section) — the `User` wire message keeps its `banned_at`/`ban_expires`/`ban_reason` fields, answered by the active-ban join the reads carry (`user.ActiveBanJoin`, the same join the group directory and the scimsync directory reuse). `UpdateUser` still treats the ban as a unit — a `ban_expires` timestamp present applies the ban (writing the row through the restrictions service, the start instant answering *since when*, so a re-ban does not move it), an absent expiry lifts it — and answers with a re-read row so the join populates the ban fields. The contract expresses the format through the wire type itself: `ban_expires` is a `google.protobuf.Timestamp`, so a malformed instant is refused at decode, not by a duplicated rule.

The `User` wire message is the canonical account view the account procedures answer with, mapped once in `user.WireView`: sign-up and the CRUD fill the same shape. The nullable columns are optional on the wire, so an account without a name part or a ban reads as absent rather than as an empty string, and the account's preferences travel as one typed block — `User.metadata`, the `UserMetadata` message — instead of loose fields. `DisplayName` — the given and family names joined — lives here because both creators share it; the list's search term matches the username, the email, and the display name through ILIKE, the columns the trigram indexes exist for.

Timezone is a presentation preference, never a storage format: every instant the server answers is UTC, and the preference — default `UTC`, an IANA zone name validated with `time.LoadLocation` at the service boundary, because the proto constraint can only bound the length — is the hint the client formats its timestamps against. An empty presented value resolves to the default, so a cleared field means UTC rather than an unparseable zone, and `Local` is refused: "wherever this server happens to run" is never what a client-side preference means. Both preferences — the timezone and the locale — rest in the account's `users.metadata` JSONB document, typed in Go as the closed `user.UserMetadata` struct and answered on the wire as the `User.metadata` block; an absent document or key answers the default, so a corrupt document degrades the presentation instead of failing the account read, and a new preference is a struct field, not a migration. The requests keep their flat, validated fields. The SPA's profile surface, not yet built, is to render the timezone over the browser's own detection.

The account views carry the account's group memberships (`user_groups`, the full group view the group procedures answer with, ordered by display name): the shape the upstream user DTO sets, and the data a client renders beside the account — the group names are what a deployment's clients match a group-based claim against. The memberships read through a seam, `user.GroupDirectory`: the group feature's repository implements it, and the area wires it post-construction, because `usergroup` imports `user` and the import may not run the other way. The list fills its page in one batch read; a creation that names groups attaches them inside the account's own transaction, so an unknown group id rolls the whole creation back. The profile picture is the account's one file: the write is a REST route — a raw-body `PUT`, because a file upload is a browser's form job, not a protocol procedure — that stages the bytes into the storage engine, sniffed off their magic bytes, never a declared type, and syncs in the request, so the read that follows sees them; the reset is an RPC procedure (it carries no file) that deletes the file and clears the row. Both doors are the account owner's.

The picture's key is `avatars/<account-id>.<ext>`: the extension comes from the sniffed bytes, so the object names what it holds wherever it is listed — a bucket browser, a presigned URL, the local deployment's file tree — with no lookup and no dependence on the file name the client sent. That makes the kind part of the identity: an upload of another kind lands under another key, so the replaced picture is deleted **before** the new one is stored. The other order is the one that cannot be repaired — the replaced file would keep its manifest row, and the row is exactly what the garbage collection keeps an object for, so the orphan would never be swept — while losing the race the first order can lose costs nothing visible: the row names the key it always named, and a picture whose object is missing already answers the bundled default, the state a reset produces. The key is recomposed on every update, so no path migration exists and none is needed. The read is the feature's other REST route, because an `<img>` tag fetches a URL rather than speaking the protocol: a stored picture streams with the content type the update recorded, an account without one answers the bundled default by redirect to `/images/default-avatar.png` — a frontend asset under `public/images/`, shipped in the compiled SPA — and the row naming a key the engine has lost lands on the same default rather than an error. The self-service profile edit (`/users/me`) and the group join stay planned: they need the self-service shape; the passkey procedures shipped as `saka.authn.v1.WebAuthnService` (see the endpoint reference).

### modules/identity/restrictions

The account-restriction feature: the one table both kinds of barred access read and write —
`public.account_restrictions`, a row per restriction with a `kind` CHECK (`ban` | `lockout`), an
open-row predicate of `lifted_at IS NULL AND (expires_at IS NULL OR expires_at > now())`, and
`lifted_by` naming the account that lifted it. The normalization is the design: a ban and a lockout
answer the same questions (since when, until when, why), so they share one schema, one expiry
rule, and one read, and a new kind is a CHECK value plus its policy, not a second table.

The reads are the feature's other half. The auth paths do not ask the feature whether an account
is barred — they join the active row beside the account they already read (the sign-in issuer's
three account reads, the one-time access exchange, the password recovery's reads, each selecting
`coalesce(ar.kind,'') AS restriction_kind`) and switch on the kind. The account reads that surface
ban fields join the active ban row (`user.ActiveBanJoin`), and the API key's validation is an
anti-join — a restricted owner's machine credential opens nothing. An expired lockout lifts on the
read that finds it: `Active` runs `ExpireLifted` first, so the row is lifted and the streak it
answered for starts fresh.

The writes are the feature's own: the failed-password streak lives on `users.failed_attempts` in
place (the hot path's counter, one `UPDATE ... RETURNING`), and it is a **streak, never a tally** —
a successful sign-in zeroes it, a lift zeroes it, an expiry's read zeroes it. The lockout lands
when the streak reaches `lockout.max_attempts` (floor 5, default 100): the row, the `user_locked`
audit, and the locked notice behind `mailer.notifications.user_locked_notice_enabled`. The policy
reads the settings catalog at call time; an unreadable key keeps its default. `Unlock` (the
`UnlockUser` procedure, guard `Admin`) lifts the open lockout rows, zeroes the streak, and audits
`user_unlocked`. A ban's write stays the user feature's (`BanUser`/`UnbanUser`/`UpdateUser`'s ban
unit) because its side effects — the session revocation, the audit, the notices — run in that
feature's transaction; the row write itself is this feature's `ApplyBanAndLift`, taking the
caller's own clock as an argument so a test's frozen time stays the truth.

The lockout's refusal keeps the generic credential error on the wire — a locked account and a
wrong password are indistinguishable to the caller, because a distinct answer would make the
lockout an account enumerator. The lockout does not end the holder's sessions: ending the session
of a legitimate holder serves only the attacker who guessed the password; the ban, whose subject
earned it, does end them.

### modules/identity/usergroup

The groups accounts belong to: an organizing unit that carries no permission of its own. Upstream
hangs custom claims on groups, gates OIDC clients on them, and syncs them from LDAP; saka's group
is the membership alone until those features land, which is why the surface holds six procedures
and nothing about claims, clients, or directory sources. The `signup_tokens_user_groups` junction
is the one upstream purpose already reserved in the schema — a signup token names the groups its
account joins — and it waits for the signup feature to grow it.

The member count every answer carries is what the query computes, never a column. The list's LEFT
join is spelled with the option for the reason the audit trail's is: an INNER join would drop
every group whose membership is empty — exactly the group an administrator just created and is
about to fill — while the GROUP BY turns the joined rows into one row per group and the aggregate
into the count. The count is sortable, which no column is: the ORDER BY is the aggregate the query
computed. The name columns sort case-insensitively, because a group named `aardvark` and one named
`Zebra` read in dictionary order, not in byte order.

The name's uniqueness is the unique index's job, and the create and update read the write's
failure — the duplicate is answered from the write, not from a SELECT that would only narrow the
race. The membership update is a **replace**: the request names the whole set, an empty list
empties the group, and the replacement is a delete and a batched insert inside the caller's
transaction, so a group read mid-replacement sees one set or the other, never a half of each.
Every identifier must name an account before the replace runs — a member that does not exist
would make the group wrong rather than merely empty, so the replacement is refused whole and the
group keeps the set it held. Upstream instead drops unknown identifiers silently, which makes an
answered request a lie about what was asked.

The audit events follow saka's convention rather than upstream's silence:
`group_created`, `group_updated`, `group_deleted`, and `group_members_updated` — the membership
change is its own event, because the log's one filter cannot see inside a payload. The records
name the group in `resource_type`/`resource_id` and leave `user_id` empty: a group is not an
account. The deletion's payload carries the member count the removal took away, the one fact
about the deleted group a later reader cannot reconstruct. The members travel through the user
package's exported view — the account wire view is written once — and the feature defines no
shape of its own for an account.

### modules/identity/onetimeaccess

The one-time access codes: a credential an administrator or an emailed message puts in one
account holder's hands, exchanged for a session without the password. The surface is
`saka.authn.v1.OneTimeAccessService` — the contract names it under authentication, because the
exchange is the sign-in a caller makes with a code instead of a password.

The codes live in `public.auth_tokens` under the `one_time_access` purpose, beside the
email-verification rows the table was created for. The hash-only rule is the same — the raw code
is shown once and its SHA-256 is the only thing stored — and the unique index on
`(user_id, purpose)` is the reason the table never needs a cleanup job: one row per account, a
new code replaces the old, and an expired one sits until then. The exchange deliberately runs
one factor, not two: the code is the recovery path an account walks when its password is the
thing it cannot produce, and demanding the second factor beside it would turn a forgotten
password into a locked-out account. The compensating controls are the code's shape — bound to
the device pair it was issued beside, spendable once, ended by a wrong-device budget
(`wrong_attempts` on the row) — and the exchange's device comparison is constant-time. The spend
is a conditional delete carrying the hash the caller resolved, so an exchange that read the row
before a re-issue committed removes nothing and answers the unknown-code refusal instead of
opening a session off the stale read; the delete the wrong-device budget runs carries the same
guard. The whole exchange is one transaction, so a refusal rolls the spend back and a code whose
sign-in failed halfway is still spendable within its window.

The exchange is one transaction end to end: the code's spend (a guarded delete whose
affected-row count is what a second caller loses the race with), the account read, the session
row, the last-login stamp, and the audit record commit together. Upstream consumes the token
first in its actor store and compensates with a best-effort restore when the rest fails; a
database transaction makes the compensation unnecessary — a rollback returns the code, so a
holder whose sign-in failed halfway tries again inside the window instead of re-requesting.

The session the exchange opens comes from `signin.IssueSession`, the issuer the password
sign-in itself calls. That method is the seam: it carries the checks every issuer owes the
account (disabled, banned), the session row's shape, and the access token's signing, and it
takes the query surface its writes run on, so a caller holding a transaction passes its tx and
the code's spend and the session's opening are one fact. The audit event the opening is recorded
under is the caller's decision — a password sign-in and a code exchange describe different
happenings — which is why the vocabulary holds `one_time_access_sign_in` beside `sign_in`.

The public email request answers the same success for an address no account holds, and carries a
16-character device token either way: the shape of the answer is the only thing the caller reads,
so the response cannot become an address oracle. The device token is the second half of the
email path's pair — the requester holds it, the mailbox holds the code, and the exchange demands
both — stored beside the code's hash in the column the migration reserved for it. The
administrative email send pairs none: its caller is an operator, not a browser, and a device
token it cannot hold would only lock the code.

The two email paths switch separately
(`auth.one_time_access_email_as_admin_enabled`,
`auth.one_time_access_email_as_unauthenticated_enabled`, both off by default), and the refusal is
`permission_denied` rather than the endpoint pretending the account does not exist: the switch is
the deployment's own answer about itself. The email rides the `one_time_access_email` queue task
with a retry schedule tighter than the verification email's — three attempts inside a minute and
a half — because a code that outlives its own delivery is not a convenience, it is a hole.

### modules/identity/verification

The email-verification flow: `saka.identity.v1.EmailVerificationService/SendEmail` and `.../VerifyEmail`, the contract beside the other identity services. `SendEmail` is the signed-in user's own door — any authenticated caller, the account named by the claims' identifier and never by the request — and refuses an already-verified account with `failed_precondition`, so the caller learns the state rather than receiving a pointless message; an unconfigured mailer refuses with `unavailable`, because enqueuing into a queue whose processor cannot ever succeed would only dead-letter a task. The message goes out through the **durable queue**, not inline: the procedure draws the raw token (256 bits, the signup token's shape), upserts its hash into `public.auth_tokens` under the `email_verification` purpose — the `(user_id, purpose)` unique index means a re-request replaces the hash and moves the window rather than piling up rows — and enqueues `jobs.EmailVerificationTask`, whose processor renders the compiled `email-verification` template with the single-use code — typed on the verify screen, never a link — and submits through the mailer. The token lives in the queue payload, which is the flow's one disclosure boundary: the queue's optional payload encryption is the control for it, and a worker that dies mid-send retries the whole task, so the template render and the submission are idempotent by design. A resend is the same procedure re-issued — the upsert is what replaces the token — but a request inside the cooldown the last send opened refuses with `resource_exhausted`: the row's `last_sent_at` is the clock, a minute is the window, and without it the procedure is the loop a mailbomb script runs.

`VerifyEmail` is public and the token is the whole credential: the procedure hashes the presented value, reads the row under the verification purpose, and an unknown, expired, and spent token answer one failure (`permission_denied`) — the disclosure rule the signup token applies. The stamp and the delete run in one transaction, so a token cannot verify twice under a race: the delete is what a second caller loses, and the conditional update (`email_verified_at IS NULL`) keeps an earlier verification instant. The delete carries the hash the read resolved, so a re-request that replaced the row between the two makes the consume fail and rolls the stamp back, rather than verifying the account off a stale read. The endpoint carries no caller: the token identifies the account, so the frontend the message links to can forward it from a browser that holds no session — this is why the flow has no REST twin, per the upstream shape's `/api/users/me/verify-email` being folded into the RPC surface.

### modules/identity/multifactor

The TOTP second factor: `saka.authn.v1.MultifactorService` beside the issuing `AuthService`, because enrollment and the sign-in bridge are one story with it. Pocket ID has no MFA at all (passkey-only — no passwords, no TOTP), so this surface is saka-only and the design reference is Better Auth's twoFactor plugin; the schema in migration `00003` was pre-authored for it.

Enrollment is a two-step ceremony on purpose: `BeginTotpEnrollment` writes an **unconfirmed** authenticator (sealed secret — the auth cipher, `AUTH_SECRET_KEY`, because the secret is account-authentication material — 15-minute window, answered once — the secret never leaves the server again) and `ConfirmTotpEnrollment` activates it only after a code the app rendered verifies. The account's **first** confirmation writes its recovery set, because an account that holds no confirmed factor holds no codes and the ceremony's one clear answer is where they belong. Enrollments are **per device** — up to ten rows per account, each a `totp_` TypeID with its own name, `confirmed_at`, and `last_used_at` — so a user registers a phone and a tablet and either answers the challenge.

The sign-in bridge is the state-handling core. A password success over an account keeping a confirmed factor mints a pending row (`public.mfa_pending`, 5-minute TTL, SHA-256 hash only) instead of a session: `SignIn` answers `mfa_required` + the pending token, and `CompleteSignIn` spends it — with a TOTP code or a recovery code — on the token pair `signin.Result` answers with, so a client treats the two alike. While the `mfa.required` catalog setting stands, a password success over an account keeping **no** confirmed factor answers the same no-token shape with `mfa_enrollment_required`: the bridge's `purpose` column reads `enroll`, the pair admits the enrollment endpoints through their optional `pending_token` (the guard carries the session-or-bridge rule the tables cannot express), and the sign-in completes through the same `CompleteSignIn` once a factor is confirmed. The bridge dies at its success, its expiry, or its **three-wrong-codes budget** (in-process, keyed by row id — a fresh bridge costs a verified password, so guessing the factor means re-running the first factor for every three guesses). The bridge is deleted **in the transaction that opens the session**, so a rollback returns it and one code cannot open two sessions; the TOTP replay guard is a separate line of defense — `last_used_step` compare-and-set means two concurrent challenges with one code answer exactly one winner.

Recovery codes are **one set per account, not per device** — ten codes, alphabet without `0/O/1/I`, SHA-256 hashed, single-use guaranteed by the UPDATE's `used_at IS NULL` clause (a race answers one winner). Every destructive procedure — regenerate, disable, the last authenticator's removal — demands the second-factor proof, because a stolen session alone must not switch the protection off. The proofs consume recovery codes but not TOTP steps: a proof that rotates under a double-clicked button is a support ticket.

The sign-in fork runs through the `mfaGate` interface (`GateSignIn`, `KeepsConfirmedFactor`) that the multifactor service satisfies and the area's provider wires post-construction (`issuer.WithMFAGate(service)`) — the sign-in package cannot import multifactor back without a cycle, the same seam the ban's side effects use. Guard rules: `CompleteSignIn` is `Public` (the pending token is the credential), the rest are `Session`; the impersonated caller is refused everywhere, because an administrator must not enroll a factor onto the account they are wearing. The `enc:`-sealed secrets use the deployment's one cipher; a nil cipher (a consumer area without `app.secret_key`) is answered at the ceremony rather than failing a run that never touches the feature.

### modules/identity/oauthsso

Sign in with a provider: `saka.authn.v1.OAuthSSOService`, saka-only (Pocket ID is passkey-only and has no SSO surface). The client stack is `golang.org/x/oauth2` + `coreos/go-oidc/v3`; the outbound flow rides two REST routes (`/oauth/{provider}/start` and `/oauth/{provider}/callback`, guard `Public`, answers 302 redirects only — never a JSON envelope, because the browser is mid-redirect) and the completion procedures answer over ConnectRPC.

Three tables (`00016`): `oauth_connections` (one per provider slug, `builtin` kinds carry their endpoints in code and store none), `oauth_linked_accounts` (one binding per connection + provider account id — `UNIQUE`), and `oauth_flows` (one authorization-code ceremony, `pending → resolved → verify_email | require_names → completed`). The client secret, the PKCE verifier, and the provider's tokens rest sealed `enc:` with the **application** cipher (`crypto.NewCipherFromHex(c.App.SecretKey)`) — connection credentials are operator configuration, not account-authentication material. A nil cipher refuses the sealed write at the call site.

The **flow token is minted at the callback**, not at the begin: the begin returns only the authorize URL, and the guarded consume (`WHERE … stage='pending' AND flow_token_hash IS NULL`) writes the identity, the sealed tokens, and the fresh token's hash — a replayed callback answers `not_found` whichever half failed. The provider adapters live beside the feature root (`builtin/google.go` — id_token claims only; `builtin/github.go` — the user API plus the primary verified email; `custom/` — mapping-aware claims where the userinfo document overrides the id_token, and `SkipIssuerCheck` when manual endpoints carry no issuer). The root cannot import the adapters without a cycle: the root defines the `Provider` interface and the `IdentityFetcher` seam, and the area wiring builds the adapters and calls `WithProviders` post-construction — the cross-feature seam shape the multifactor gate uses.

The resolution (`resolution.go`) runs at `ContinueSignIn` and picks the account in one settled order: the binding for (connection, provider account id) first; then a **verified** provider address that matches an account (the link rides the `oauthsso.account_linking_enabled` toggle — off, the match answers `failed_precondition` rather than signing in silently); then JIT creation under `access.mode = open` (allowlist wins over blocklist, blocklist fails open, an unreadable settings source closes the door — the sign-up feature's own answers; the username derives from the address's local part with a suffix on a taken name). An unverified address pauses the flow at `verify_email` for a 12-character code (hash on the row, queue-delivered template, three strikes end the flow by compare-and-set); a provider that named no names pauses at `require_names`. The MFA fork is the password path's: a confirmed factor answers `ContinueOAuthSignInResponse` with the `mfaGate` bridge, never a session — the sign-in completes through the same `CompleteSignIn`. Sessions mint through `signin.IssueSession` with `ProviderOAuthSSO`, inside the transaction that binds the identity — and the JIT path hands the issuer the account shape the insert carried, because a read back through the pool cannot see its own uncommitted row.

The holder's surface is `ListLinkedConnections` (oldest first) and `UnlinkConnection` (`Session` + `StepUp`): the stranding check is one scan over the three other ways in — a second binding, the password row, a passkey — and the last-credential unlink answers `failed_precondition` with the set-a-password-first message. A foreign binding answers the same `not_found` a missing one does. The hourly `oauth_cleanup` job sweeps expired flows. Audit: connection CRUD (`oauthsso_connection_*`), the sign-in (`oauthsso_sign_in`), and the account's three (`oauthsso_account_created/linked/unlinked`) — the unlink's record commits with the removal, and the soft-delete trigger captures the row.

### modules/identity/webauthn

The passkey surface: `saka.authn.v1.WebAuthnService` — one credential in three roles (the
passwordless first factor, the MFA bridge's second factor, the step-up proof), over
`go-webauthn` v0.18.2 with the ceremonies as opaque JSON. The contract's `credential` field is
a **string carrying the browser's `PublicKeyCredential` JSON verbatim** — `@simplewebauthn/browser`
answers objects, so the client stringifies; the client passes the JSON through untouched in both
directions.

The traps the ladder bought:

- **The signature counter is the clone alarm.** A rewound counter answers `failed_precondition`
  silently ("contact the operator") — and a virtual authenticator re-seeded from captured
  material asserts with counter 0, which IS a rewind against a row that already advanced. The
  Playwright suite runs the whole ladder on one context so the counter advances naturally; an
  E2E that re-seeds credentials between acts will watch the server refuse correct behavior.
- **The discoverable sign-in resolves the account by the assertion's userHandle** — the raw 16
  bytes of the account's UUID. `user.UUIDFromWire` is the conversion; `uuid.Parse` on the wire
  form is the runtime 500.
- **The account reads are two.** `FindAccountByID` inner-joins the password table (the question
  "is there a way back in" — the stranding check's read); `FindAccountByIDAny` left-joins it
  (the question "is there an account" — the enrollment, sign-in, and step-up resolutions). An
  account that signs in by one-time code alone was invisible to the passkey surfaces until the
  left join existed; the ladder's passwordless scenario is what pins it.
- **The stranding refusal lives in the service, not the guard** — the contract cannot express
  "the last credential of an account whose password row is gone", so every delete door
  (holder's, administrator's) runs the same check: held ≤ 1 and the inner-join account read
  answers not-found → `failed_precondition`.
- **The security receipts ride the `PasskeyNotifier` seam**: an enrollment
  (`VerifyRegistration`) and a removal (`deleteCredential`, the administrator's door included)
  enqueue their receipt through it after the commit, best-effort — a lost notice must not fail
  a ceremony that succeeded. The toggles are `mailer.notifications.passkey_added_notice_enabled`
  and `passkey_removed_notice_enabled`; a nil notifier keeps the ceremonies working.
- **Each procedure registers at its own path** in the module's `MountRPC` — a handler added to
  the generated service without an `r.Handle` line answers the router's `unimplemented` 501, and
  no Go compile error names it. The area's forwarding test pins the claims.
- **The step-up proof is interceptor-level.** `Reauthenticate` answers a hashed, single-use
  token whose window is the `session.reverification_window` setting (default 30 minutes, read
  fresh at grant, bounds 1 minute–24 hours); a procedure whose guard rule carries `StepUp: true` consumes the
  `X-Saka-Reauthentication` header through the `guard.ReauthConsumer` interface the webauthn
  feature implements. A nil consumer fails closed.
- **The AAGUID catalog** ships embedded (`aaguid.json`, ~398 entries, names only, lazy
  `sync.Once`); `get-aaguid.sh` re-trims it from the upstream combined payload. An unnamed
  credential answers the model's name; a zero AAGUID answers "Passkey".
- **The browser ladder is `tools/e2e-passkey`** (wire-level, the soft authenticator answering)
  plus `e2e-tests/` on Playwright's virtual authenticator against the debug build's
  `/debug/passkey/*` pages — a release binary refuses those paths with the 404 envelope and
  carries none of the page.

Guard: `BeginLogin`/`VerifyLogin` are `Public`; the management side is `Session` (the
impersonated caller refused, so an administrator cannot plant a credential on the account they
are wearing); `DeleteCredential` carries `StepUp`; the administrative roll doors ride `Admin`, the
way the UserService's doors do. Expired ceremony rows and spent proofs are swept hourly by the
`webauthn_cleanup` job.

### modules/apikey

The machine credentials: an API key is a personal access token an account issues for its own
scripting, and the surface is `saka.apikey.v1.ApiKeyService` — its own area, because the
credential is not an account fact but a transport-authenticated one, the way a session is.

The credential answers as its owner, and the owner is read **live on every request**: the hash
lookup joins the account, so a role change or a disablement takes effect on the key's next request
rather than at a token mint. That is the difference between this credential and a JWT, whose claims
are a sign-in-time snapshot — and it is the reason the key can be trusted with the administrative
surface its owner holds. The authwall's refusal never says which half failed: an unknown, expired,
revoked, or disabled-owner key is one answer, because each is the fact a probing caller would want
to distinguish. The `last_used_at` the lookup touches is written beside the read rather than folded
into it — the query builder's UPDATE carries no RETURNING, and a metric that loses its write is not
a decision — so the touch is best-effort by construction.

The key itself is drawn as `<prefix>.<secret>` — an eight-character prefix an operator reads, a
thirty-two character secret a client sends, both from the full alphanumeric alphabet with the
crypto source — and the row stores the SHA-256 of the presented string and nothing else. The
prefix is what makes a leaked key identifiable without the key: it travels in every view, so an
operator can find the row a leaked credential belongs to and revoke it. The name is unique per
owner by the `(name, owner)` index, and the duplicate is answered from the write's failure, the
way the group's name is.

The management surface refuses the credential it manages. `Session` is the guard rule that reads
the caller's credential kind — the field `jwtutils.Caller` now carries beside its claims, because
the kind is how the caller arrived, not something a token asserts — and a machine credential is
refused on the four procedures that create, list, renew, and revoke keys, with the not_found shape
every other refusal takes. The upstream it ports spells the same refusal with a middleware switch
on its own routes; here it is one rule against the one caller type, which is why the surface can
grow a second machine credential without a second middleware. The refusal exists for a reason a
credential cannot fix itself: a key that could issue and revoke keys would outlive its owner's
intent, surviving every revocation by minting its successor first.

Revocation is soft: the `revoked_at` stamp the schema reserved is the write, the row survives it,
and the view carries the instant — a reader can still tell what a revoked key had access to, which
a deletion would have erased. A second revocation is the same success and records nothing, because
the caller's intent is the state the key is already in. Renewal is the mirror of the refusal: an
unexpired key is refused (`failed_precondition`), because renewal is how a key lives past its
expiry, not how it escapes one — and the reminder stamp the old window earned dies with it, so the
new window earns a fresh reminder.

The authwall's halves stay in their own layers. The header is the transport's: `middleware.APIKeyAuth` wraps the bearer authenticator, reads `X-API-Key`, and delegates to the key service through the `KeyAuthenticator` interface the middleware defines — the middleware imports no module, the bearer authenticator stays in the identity area bearer-only, and the caller a validated key answers as is the service's `AuthenticateAPIKey`, which builds the machine caller from the owner row it just read. The precedence when both headers arrive is the bearer's: an explicit token is the credential the caller named first, and a key that rode along silently must not rescue a bad one.

The expiry reminder is the area's one background job: a recurring queue task reads the seven-day
window, enqueues one reminder per unreminded key, and marks the row so the next pass does not
repeat itself — the mark is written when the reminder is **enqueued**, not when it is delivered,
because a durable queue's promise is the delivery attempt, and an unmarked row is exactly what a
failed enqueue needs to retry. A key whose owner has no address is skipped unmarked, so an address
that appears later still earns its reminder. The switch is `auth.expiry_email_enabled`, off by
default: a mailer that writes to account holders on a schedule is a deployment's decision.

### modules/federation

The federation **area**: the surfaces a deployment serves to applications that
federate identities to it. Sub-phase a of the OIDC provider — client
management — is implemented here; the protocol phases (authorize, token,
userinfo, end-session, introspect, PAR, device flow, discovery) and the
customclaim scaffold join as they land. The transport split the
protocol section settles is the area's shape: **management is ConnectRPC**
(`saka.federation.v1.OidcClientService`, the backoffice's generated client),
**the protocol endpoints are REST** — the shapes the specifications define,
the third naming exception beside SCIM and WebAuthn.

**SCIM is outbound provisioning** (`modules/federation/scimsync`, ported from
Pocket ID): saka is the SCIM client, not the server. The visibility roll is
the client's own — one fail-closed rule everywhere: a client is restricted
when its `is_group_restricted` flag is set or its allowed-groups roll carries
rows, and restricted clients admit only their allowed groups' members, a
flag with an empty roll admitting nobody. The listings the sync reads are
validated before any write — a body that is not a well-formed SCIM list,
contradictory counts, a cursor that never advances, a listing beyond the
100-page/100,000-resource bounds, or a row without `id`/`externalId` fails
the pass without deletes, so a malformed snapshot can never read as an
empty one and wipe the remote; a restriction with no groups is the one
legitimate empty snapshot, and it deprovisions the remote whole. Matching
is indexed by `externalId`, and resource URLs are joined by concatenation,
so an escaped id is never re-encoded. One
`scim_service_providers` row per OIDC client names a remote base URL and the
bearer token the sync presents — sealed `enc:` at rest, shown once in the
Create answer, never read back. One pass (`ScimProviderService/Sync`, the
hourly `scim_sync` job, or the five-minute debounced notifier) pushes the
client's visible accounts and groups out until the remote matches the local
snapshot. The visibility roll follows the fail-closed restriction rule the
protocol and the catalogue share, so provisioning cannot admit an account
the sign-in would refuse; banned and disabled
accounts push `active: false`. Users go before groups, so the members'
remote ids exist when the groups reference them, and a member the remote
refuses skips the group rather than writing it half-blind. The SCIM JSON
field names (`externalId`, `displayName`, RFC 7644's title-case
`Resources`) are the specification's, the naming exception above — they
never cross the RPC wire, which speaks the proto's snake_case.

The `client_id` is the one wire identifier that is not a TypeID: it is the
credential a foreign client presents, the operator's word (letters, digits,
`_`, `-`) or a generated one. The identifiers it names on saka's own wire —
`created_by_id` as `usr_…`, the restriction's groups as `ugrp_…` — travel in
their TypeID forms.

**Secrets are hashes in a JSONB document.** The `credentials` column carries
`{secrets: [...]}`, one entry per secret: a SHA-256 hex hash, a four-character
prefix, and the window. The raw value exists in exactly one response (the
creation), the way the API keys and the reset tokens run — a database leak
cannot replay it. **Several live secrets per client are legitimate**: a
rotation is an addition followed by a deletion, never a swap, so the document
rewrite runs under the row lock (`SELECT … FOR UPDATE`) and filters by secret
id rather than overwriting.

**PKCE follows the kind.** A public client cannot keep a secret, so the write
forces `pkce_enabled` on when `is_public` is set — the operator does not
choose it. `pkce_supported` is not a capability the write derives: it is the
**observed** capability, set by the authorization endpoint when a client
presents a code challenge the requirement did not demand, and reset when the
requirement is switched off. This is upstream Pocket ID's own semantics.

**The logo rides the storage engine** the profile pictures ride: the bytes
sniffed for their kind (PNG/JPEG/WebP — an SVG is refused, because a publicly
served SVG is a script host), the key `oidc-logos/<client_id>.<ext>` carrying
the extension the bytes earn, staged then synced in-request, the replaced file
deleted before its replacement is stored. The staging metadata names no owner,
so no upload-finished notice mails an operator about their own administrative
write. The read is the one REST route the feature claims:
`GET /oidc/clients/{id}/logo`, public on the guard's books, 404 for an
unknown client or an absent logo — never a substitute image.

**The preview is a pure function of the account's own views.** PreviewClient
answers the id-token, access-token, and userinfo claim maps the client would
receive, built through the `UserDirectory` seam the user feature's `GetUser`
satisfies — no token is minted, and the custom claims join when the
customclaim feature does. The seam pattern is the account view's: the
consuming package names the interface, the area wires it post-construction,
and a typed-nil dependency is dropped at the seam rather than held in an
interface the first call would panic through.

CIMD (client-id metadata document) is **implemented on the management side**:
`client_type = 'cimd'` materializes from a fetched document whose URL is the
client's own identifier, gated by the `oidc.cimd_url_allowlist` config
patterns (an empty list is the feature off), and `RefreshClient` forces the
re-fetch. The protocol-time materialization — an authorize request carrying
a CIMD id that has not been seen yet — lands with the protocol core, where
the client lookup consults the same materializer.

**The consent ledger and the token cascade.** `OidcConsentService` reads and
undoes what the authorization flow records in `user_authorized_oidc_clients`:
the self-service procedures (`ListMyAuthorizedClients`,
`RevokeMyAuthorizedClient`, `ListMyClients`) ride `Authenticated` — the
account is the token's subject — and the two administrative reads
(`ListUserAuthorizedClients`, `ListAllAuthorizedClients`) ride `Admin`.
`ListMyClients` answers the catalogue the consent page offers, under the
fail-closed restriction rule the protocol and SCIM share: a client is
restricted when its `is_group_restricted` flag is set **or** its
allowed-groups roll carries rows, restricted clients appear only for
accounts in one of those groups, and a flag with an empty roll admits
nobody (the `is_group_restricted` column is upstream's explicit flag and
carries no write in saka yet — the roll alone restricts). A revocation is
one transaction: the ledger row dies,
the account's grants for the client die with it (the grant document's
`sub` names the account), and every code and refresh pointer riding those
grants dies too — a revoked consent is a consent the client cannot use.

**Client authentication admits both spellings.** The stored secret hashes
are plain SHA-256 hex digests, so the protocol's secret verifier matches by
the algorithm each entry names (a 64-char hex entry is a digest, anything
else a PHC string the password hasher reads). The library binds one
authentication method per client — `client_secret_post` is the one saka's
confidential clients declare — so a flattening middleware on the token,
introspect, and PAR routes copies the `Authorization: Basic` pair onto the
form when the form carries none, body bounded to 1 MiB before the parse:
RFC 6749 §2.3.1's two spellings of the same credential.

**Introspection is client-scoped** (RFC 7662): a client reads only the
tokens minted to it — the `TokenIntrospectionIsClientAllowed` callback
answers `info.ClientID == client.ID`, and a stranger's introspection
answers `access_denied`. **PAR** (RFC 9126) rides the same
`oauth_sessions` rows: a pushed request creates an authorization session
whose pointer row resolves by the PAR id, the request URI is
`urn:ietf:params:oauth:request_uri:…`, the lifetime 5 minutes, and a client
whose `requires_pushed_authorization_requests` is set is refused at the
plain authorize endpoint. `/oidc/token` and `/oidc/par` ride the
credential bucket; introspection is exempt — the client already paid with
its secret. **Revocation** (RFC 7009) rides the credential bucket too:
any registered client may call `/oidc/revoke`, the library's own
client-scoped check refuses a token minted to another client (403
`access_denied`), and the grant-revocation switch is on because saka's
access tokens are JWTs the store never sees by themselves — a
revocation names its grant instead, the grant carries `revoked_at`, and
the next refresh redemption answers `invalid_grant`. An unknown token is
the same empty 200 as a known one. **Back-channel logout** is a
delivery, not an endpoint: a client that registered
`backchannel_logout_uri` receives a logout token — signed by the same
material the provider signs with (`typ: logout+jwt`, the
back-channel-logout events member, `aud` the client, `sub` the account,
`sid` only when the hint named one, never a `nonce`) — through the
`backchannel_logout` queue, a form POST expecting an empty 200, five
attempts. The enqueue rides the committed end of `EndSession`, a
preparation failure is a logged loss and never a failed logout, and the
whole feature rides the `oidc.backchannel_logout_enabled` setting,
read per call. **The refresh windows ride settings too**: every grant's
refresh token lives the `oidc.refresh_token_hours` window (zero: never
expiring, the historical behavior), a grant carrying `offline_access`
rides the `oidc.offline_refresh_token_hours` long one, and both are
read at every issuance and rotation through the grant handler — an
operator's change lands on the next issuance, never waiting for a
restart, and an unreadable setting fails open to the never-expiring
token.

**The device grant (RFC 8628) and the prefix.** The provider registers
its routes under `WithPathPrefix("/oidc")` — the v0.25.0 API exposes no
setter for the device endpoints, and the prefix is the one mechanism
that renames them: every `With*Endpoint` value is the bare name, the
full path is always `protocolPrefix +` the endpoint, and discovery
builds its advertised URLs from issuer + prefix + bare name. The RFC
8414 alias `/.well-known/oauth-authorization-server` is saka's own
mount: the provider registers the discovery handler on the
openid-configuration path alone, so the alias re-points the request's
path at it — one document, both faces, and every AS member an RFC 8414
client reads (revocation and introspection endpoints with their
authentication methods included) already rides the discovery document.
The device
code and the user code ride the same pointer pattern as the
authorization code — session rows kind `device`, hashed pointer rows
kinds `devicecode` and `usercode`, a re-entered user code moving the
pointer to the newest session holding it. Every registered client may
use the grant; the approval walks the SPA interaction the authorize
flow walks, and `oidc_device_authorized` is the approval's own audit
record. One-time redemption is atomic without a library seam: the token
endpoint's request carries a snapshot cache (`grant_cas.go`), the grant
store remembers the document each read produced, and `SaveGrant` runs a
compare-and-swap against it — of the requests racing on one code,
exactly one saves and issues; a loser's save is refused, and the same
rule protects the authorization code's consumption and the refresh
rotation's rewrite.

**Device login is a second feature, not the device grant.**
`modules/devicelogin` is the passkey-less pairing sign-in: a browser
that cannot sign itself in creates a request, another browser approves
it, and the creating browser's long poll answers the decision. The
device side is REST (`/api/device-login/requests`, the exchange riding
an http-only pairing cookie); the approval is
`saka.authn.v1.DeviceApprovalService` guarded `Session` with the
impersonated caller refused — the approval names the account whose
browser will sign in, and a token acting for another must not mint
sessions for a third device. Codes are drawn from
`23456789ABCDEFGHJKMNPQRSTUVWXYZ` and rendered `XXXX-XXXX`; the code
and the pairing secret live only as SHA-256 hashes; decisions are
single-use in the UPDATE's WHERE, and the exchange's consumption is
first-writer-wins. One creating browser holds at most
`maxPendingRequests` (8) live requests, enforced inside an advisory
lock on the token's hash so concurrent creations cannot race past the
cap; expiry frees the room, and a refused creation answers 429.

**Protocol state expires twice and is swept once.** Every `oauth_sessions`
row carries the expiry of the object it holds — the grant's refresh window,
the session's timeout, the pointer's code lifetime — and a lookup refuses a
row the column judges dead, within a two-minute clock-skew allowance
(`loadDocument`), so an expired credential fails closed even before the
sweep reaches it; a NULL expiry — a logout session without a client, a
grant without a refresh window — is never judged by the column. The
`protocol_cleanup` job (`internal/jobs`, hourly, seeded like the other
recurring jobs) reaps the rows past a one-hour grace in bounded batches of
ten thousand, a hundred thousand per run: the grace is wider than the
lookup allowance, so nothing is deleted while a lookup could still accept
it, and the batches keep a backlog from a stopped deployment off one
long-running statement. The consent cascade deletes what revocation kills
at once; the sweep is for the rows nothing revokes — the codes never
exchanged, the sessions abandoned, the grants left to age out. The sweep
also reaps `oauth_jtis`, whose rows are the JTI claims the replay
protection holds: `provider.WithJTIConsumer` claims every jti a
client-presented JWT carries (a DPoP proof, a client assertion) with a
fifteen-minute window, the INSERT's unique index makes the second
presentation lose, and the sweep frees the id once its window passes.
`interaction_sessions` remains a scaffold table with no writer.

### modules/webhook

The webhook area is saka-only: the outbound event surface Pocket ID never had. It is an area of
its own rather than a feature of identity because a delivery endpoint is not an account fact —
it is a destination the deployment streams its events to. Every procedure is administrative
(`guard.Admin` on all ten, `ListEventTypes` included).

The emission seam rides the audit recorder: `internal/audit`'s `Recorder` carries a sink, and
this area's service is that sink, wired after construction (`recorder.WithSink(service)` inside
the area's provider) so `internal/audit` never learns the package exists. `AuditRecorded` runs
inside the savepoint the record rode — a rollback takes its deliveries with it, so a receiver is
never told about a change that did not happen — and it never fails the caller: an emission
failure costs the delivery, not the change, and the failure is logged. The tasks ride the
caller's transaction (`TaskAddOp.Executor`), which commits after the sink returns, so the sink
calls `queue.Client.Notify()` when it is done: the queue contract requires the notification from
an executor-bound save, and the dispatcher can wake ahead of the outer commit. That wake-ahead
is why `RunDelivery` answers a delivery row it cannot see with a retry instead of a quiet end —
the row appears with the commit and the next attempt delivers it.

The event catalog (`events.go`) is the single source of the wire vocabulary. Each entry carries
the dot name (`user.created`), the audit event it maps from, and a description; the catalog is
also the emission filter (an unmapped audit event is never delivered) and the subscription
boundary (`checkEvents` refuses names outside it). The names are curated by hand — the audit
vocabulary's snake_case cannot say where the first dot belongs — and never rename once shipped;
a mapping added later is a new subscription choice. `internal/audit/catalog.go` holds the audit
vocabulary's own catalog (name + description beside the constants), and a source-level test in
each package holds the two lists to one set: `internal/audit`'s test parses `audit.go`'s const
block, `modules/webhook`'s test maps every `audit.Catalog()` entry.

Delivery rows store the exact canonical body bytes; every attempt re-signs the stored bytes, so
a signature survives retries. The signing secret is sealed `enc:` with the application cipher
(`crypto.NewCipherFromHex(c.App.SecretKey)` — an `AUTH_SECRET_KEY` rotation does not touch it)
and exists in plaintext in the create and rotate responses alone. The delivery engine is a queue
task (`webhook_deliver`, 5 attempts × 30 s backoff, 30 s receiver deadline) whose processor lives
in `internal/jobs` and resolves the service through the `WebhookRunner` seam — a container
without the area answers `no delivery runner is wired`. Retention is the recurring
`webhook_prune` task: attempts age out at 7 days, terminal deliveries at 30 (their attempts
cascade; a pending delivery is never a candidate). Identifiers are TypeIDs on the wire — `whk_`
endpoints, `whd_` deliveries, `wha_` attempts — while the columns stay UUIDs.

The runner's outcome rules: an attempt record and the delivery's status change ride one
transaction, and the status write carries `WHERE status = 'pending'`, so a replayed task — a
lost worker's reclaim, a dead-task replay — re-records the try but cannot re-send a delivery a
receiver already answered. A delivery whose endpoint is gone, disabled, unsigned, or refused by
the destination policy is marked failed on the spot; a redirect or a 4xx (but a 408 and a 429)
is the same kind of fact and fails on the first answer, so the retry budget is spent only on
failures a second try can save.

The destination policy is the deployment's SSRF stance: `webhook.allow_private_network` (default
`false`) refuses a delivery whose host resolves to a loopback, private, link-local, or
unspecified address, judged per attempt from the resolver's answer. Deliveries never follow a
redirect — `fetcher.Request.NoRedirect` marks the request, and the fetcher's redirect policy
answers the 3xx as the response — so the signature headers never travel to a redirect target,
and a public URL cannot lead the request into the deployment's own network by way of one. The
residual risk the policy carries is the resolver answering differently between the check and
the dial; closing that needs a dial-time policy, which is a fetcher transport change.

## Notice emails and their switches (settled 2026-09-27)

The application sends two kinds of email, and only one of them is configurable. **Transactional**
emails carry the flow itself — a verification code, a password-reset code, a one-time access code,
an email-change confirm code, each single-use and typed on its screen — so no switch exists for them: turning one off would break the flow,
not save the cost. **Notices** are receipts a committed fact sends — a new-device sign-in, a changed
password, a removed password, an added passkey and a removed one, an administrative MFA removal, a
ban and its lift, an account lockout, a sign-up attempt against a taken address, an expiring API
key, the email-change pending notice and its success confirmation — and every one of them is gated
per flow under `mailer.notifications.*` (default on). The gate sits at the **enqueue** site, in the
jobs adapter, not in the queue processor: a switched-off flow is a no-op before the task exists, so
the queue never carries mail nobody asked for.

The new-device notice is the one notice with state of its own: `public.known_devices` remembers
every browser fingerprint an account has signed in from, and the first-seen judgement rides the
session's transaction (`INSERT ... ON CONFLICT ... RETURNING (xmax = 0)`), so a rolled-back sign-in
leaves no device row and a concurrent sign-in cannot double-notice. A fingerprint-less client is
never a device — it cannot be told apart from any other fingerprint-less client, so noticing it
would mail every sign-in. The judgement runs in `IssueSession`, so every way of opening a session —
password, one-time access, MFA bridge — feeds it.

The email-change flow lives beside email verification (`modules/identity/verification`), sharing the
`auth_tokens` table under the `email_change` purpose with the pending address bound in the row's
`payload` column. The confirm token is the flow's whole credential: generated, shown once in the
message, stored only as a hash; the confirmation moves the account to the row's payload, never to an
address the confirm request could name, and re-judges uniqueness inside its transaction — a lost
race leaves the token unconsumed. The delete that consumes the token carries the hash the read
resolved, so a re-request that replaced the row between the two makes the confirmation abort rather
than applying the payload it read from a superseded row. A confirmed change stamps the account
verified: the token proved control of the new address.

## Protocol and authentication (settled 2026-09-24)

The two transports serve different audiences, and the split decides where each fact lives. **ConnectRPC is the primary protocol** — internal communication and the backoffice client, whose generated clients read response headers natively and think in `connect.Code`. **REST serves external integrations**, and the OAuth2/OIDC identity-provider features are planned on the REST surface, where third-party tooling expects conventional shapes.

**One contract, per-transport mapping — not one wire shape.** The contract the two surfaces share is semantic: snake_case field naming (the shared codec), the pagination rules (`pkg/responder` enforces them once), and error semantics. The wire form is each protocol's idiom:

| Fact | ConnectRPC | REST |
| --- | --- | --- |
| Status | `connect.Code` | `status` + HTTP code in the envelope |
| Request/trace id | Header (`X-Request-Id`) | `metadata` + header |
| Rate limit | Header (`X-RateLimit-*`) | `metadata.rate_limit` + header |
| Pagination | Fields on the list message | `metadata` block |
| Error | `connect.Error` with typed detail messages | Envelope error document |
| Links | Not modelled (a page token when a list needs one) | The `links` map |

`ResponseMetadata` in `api/connect/common.proto` carried `status_code`, `request_id`, and `rate_limit` once, mirroring the REST envelope; it is now **`ListMetadata`**, the pagination block alone, and `CheckResponse` carries no metadata field — status, the correlation id, and the rate-limit window travel with the protocol (connect codes, the request middleware's `X-Request-Id` header written before any handler runs, the limiter's `X-RateLimit-*` headers), and a structured failure is a typed message attached as a connect error detail. Envelope-in-body is right where the data is domain (pagination) and an anti-pattern where the protocol already carries it — a Connect client raises on error and cannot read a body envelope, so an error envelope inside RPC is unusable exactly where it would matter. `docs/api-response.md` is the human-facing contract.

**Authentication is stateless: Bearer Token (JWT) and `X-API-Key`.** No server-side auth sessions. ConnectRPC answers a Bearer token verified against the `jwks` key set. **Which stack signs is a deployment decision, not an audience decision**: `auth.jwt_algorithm` names the algorithm when both halves are configured, and the material decides when it does not — derived from the key pair's `alg` or the HMAC secret's length. The audience only constrains verifiability: an HS* token verifies only in a process that holds `auth.secret_key`, while a verifier outside the process reads the published asymmetric set. `X-API-Key` targets external REST integration and is stored hashed, following the token-row convention. The session lifecycle is that server-side state: refresh-token rotation and named revocations landed in `modules/identity/session`, so a feature needing more state joins it rather than repurposing anything.

**The Bearer seam landed (settled 2026-09-25).** `connectrpc.com/authn` (v0.2.0) is the seam: an HTTP middleware the RPC router is wrapped in — not a connect interceptor, as the earlier note imagined; it authenticates before a request is decoded, so an unauthenticated call costs no unmarshal, and it receives the handler options so a refusal is marshaled in the caller's protocol. The mechanism lives in `internal/transport/middleware/bearer.go` (`BearerAuth`); the policy — `rpcPublicProcedures`, the set answered without a caller — lives beside the rate-limit exclusion lists in `internal/transport/server.go`, and encodes the same default in the opposite direction: a procedure is throttled and protected unless named. **The REST surface joined the same seam**: the modules' REST routes are wrapped in `RESTBearer` (same file), guarded by a public-path list (`restPublicRoutes`) beside the RPC one, and the refusal is the REST envelope. The authenticator is a resolvable service (`middleware.Authenticator` in the registry, stubbed in the consumer test the way the limiter is). Claims travel as `authn.GetInfo` context values on both transports, so a feature's caller-reading helper is one function; a REST write never verifies a token itself. The `apikey.go` scaffold stays for machine credentials. Verification is `jwtutils.AccessVerifier` over the `SigningKeySource` the area's `jwks.Service` satisfies: key and algorithm resolve per call (a rotation is picked up without a restart) and the verifier is built with that exact pair, so the accepted algorithm is pinned by construction — the open `alg`-pinning note is closed for the tokens the process signs itself; verifying a foreign key set (OIDC federation) would reopen it, since `WithKeySet` cannot pin. The claims (`jwtutils.AccessClaims`, promoted from `signin` now that the seam is the second consumer) travel as `authn.GetInfo` context values; authorization is the guard below. `identity.Authenticate(keys, cfg)` is the area's authenticator; the composition root's `newRouter` is the one place a transport need names an area's service, and the transport itself receives only the function through `Options.Authenticator`.

**The guard: authorization is declared, not checked at each handler (settled 2026-09-26).** Authentication answers *who* the caller is; `internal/guard` answers *whether* they may run this. The policy is two tables — `ProcedureRules` keyed by the generated procedure path, `RestRules` a list of method + chi pattern — and a request the tables do not name is **administrative**, which is the safe default: forgetting to declare a new procedure refuses it, while an undeclared procedure answered openly is a breach nobody notices. The rule is per-request, so it is an interceptor (`middleware.Guard`, registered in `rpcHandlerOptions`) on the RPC surface and one chi middleware (`RESTBearer`, which now authenticates *and* applies the route's rule) on REST; both read the same tables, so a procedure cannot be public for the authenticator and guarded for the guard.

Four rules, in `guard.go`:

- **`Public`** — answered without a caller: the health probe, sign-in, sign-up, email verification by token, the JWKS document, the picture read.
- **`Authenticated`** — any verified caller, whatever the role. It is for a request that is the caller's own *by construction*: the account comes from the claims and the request names no target (`SendEmail`). Upstream reaches the same shape with a separate `/users/me` route; here the subject is the target, so no second route is needed.
- **`Self(field)`** — the account the request names must be the caller's own. `field` is the proto field name (RPC) or the path parameter (REST), read through `Target.ID`, which consults the path params then the message field under the same name — one rule serves both transports. **An administrator does not pass by virtue of the role**: that is upstream's `/users/me` beside `/users/{id}` expressed as one rule, and the administrative procedures are where an administrator acts on someone else. A caller that is **impersonating** is refused outright (`ErrImpersonated`): a delegated session is an administrator's tool for the administrative surface, never a way to use the requests that belong to the account.
- **`Admin`** — the default.

**The order is authorization, then validation, then the procedure** — and that order is a disclosure rule, not a detail. `connect.WithInterceptors` composes first-listed-outermost, so the guard sits above the validate interceptor: a caller who may not run a procedure gets the same `not_found` whatever their body looked like, and cannot tell an administrative procedure from an absent one by sending a malformed request. The consequence is deliberate: `ResetProfilePicture` is no longer in the protovalidate test table, because a non-owner is refused before the identifier is judged.

**A refusal is `not_found`, not `permission_denied`.** The guard maps `ErrUnauthenticated` to `unauthenticated` (401 on REST — the caller can present a credential) and *every other* refusal to `not_found` (404), the shape that discloses least: a caller who may not act on an account learns nothing about whether it exists, and a caller without the role learns nothing about which procedures exist. The distinction between "not yours", "not allowed", and "not there" survives in the audit record and the server log, which an operator reads. A rule must never reach a database — it runs on every call, and a decision that needs a round trip belongs in the service where the transaction already is.

**The caller is one type.** `jwtutils.Caller` carries the token's subject (`UserID`) beside its claims —
the subject travels in the wire form, `pkg/userid`'s `user_` TypeID encoded from the row's UUID, and
the seams that need the key decode it at the boundary — and is what the authenticator puts on the context and every seam reads (`jwtutils.CallerFrom`). It exists for two reasons. First, a self rule compares identifiers, and the subject is a *registered* claim while `AccessClaims` holds only the private ones — reading it from the claims alone is impossible. Second, **delegation**: `AccessClaims.ActorID`/`ActorUsername` name the account a token acts on behalf of (this application's spelling of the OAuth token exchange's `act` claim), so `IsImpersonating()` is answered from one field rather than reconstructed per seam. Impersonation is planned, and the guard already enforces its rule: an impersonated caller is refused on `Self` and admitted on `Admin`/`Authenticated`, which is the shape `stop-impersonating` needs (it must be callable *while* impersonating, so it is `Authenticated`, not `Self`). The durable record of a delegation belongs in the session row (`public.sessions`), not only in the token: a token cannot be revoked, and Better Auth's admin plugin — the reference for this feature — records `impersonatedBy` on the session for exactly that reason.

**Impersonation is implemented.** `SessionService/ImpersonateUser` (Admin rule) opens a delegated session: the row carries `impersonated_by`, the token carries the `actor_id`/`actor_username` pair, the window is `ImpersonationTTL` (one hour, a hard bound the renewal cannot extend — `Refresh` caps a delegated row's expiry at `created_at + TTL` and refuses once it has passed), and the audit records `impersonation_started` with the actor named. `StopImpersonating` (`StopImpersonating` rule — the one that requires the delegation) revokes the row and re-signs the actor's own pair. `Authenticated`, `Session`, and `Self` refuse an impersonated caller outright: the delegation reaches only the administrative and permission-gated surfaces plus its own way out. A delegated row's renewal re-signs the actor pair from the row, inside the renewal's own transaction and **before** the rotation: the provider is what makes the row a delegation, and `impersonated_by` is `ON DELETE SET NULL`, so an administrator deleted while their delegation lived leaves a row that would otherwise read as the target's own session — both shapes (a null actor, an unreadable one) fail the renewal with `ErrSessionEnded` rather than mint a token for the target with nobody behind it. The read sits before the write, so the refusal does not spend the refresh token. Replay of a spent refresh token revokes the session it names — the reuse signal the `rotated_token_hash` column exists for.

**Machine credentials (`X-API-Key`) are the `modules/apikey` area.** The credential acts as its owner through the same guard table — an administrator’s key administers — and the one surface that refuses it is the keys’ own, by the guard’s `Session` rule reading the credential kind `jwtutils.Caller` now carries. The transport’s half is `middleware.APIKeyAuth`, which owns the header and delegates the validation to the key service through the `KeyAuthenticator` interface it defines; the bearer authenticator stays in the identity area, bearer-only, and the composition root joins the two. See `### modules/apikey` above.

The OIDC surface, when built, is specification-driven and becomes the third naming exception beside SCIM and WebAuthn (`docs/api-response.md` carries the list): its endpoints answer the shapes the specification defines, not the envelope.

## Planned layout

Design records for packages that were planned before they landed — `internal/config` and `internal/fetcher` are implemented as described below; read them as the rationale, the code as truth. The still-unbuilt scaffolds are named where they are.

### modules/storage

The storage **management area** (`AreaName "storage"`, feature `bucket`): the administrative surface over the buckets the engine namespaces by. `saka.storage.v1.BucketService` (`CreateBucket`, `UpdateBucket`, `DeleteBucket`, `ListBuckets`, `GetBucket`) is Admin-gated end to end — a bucket is infrastructure policy, not an account fact — with audit events `storage_bucket_created` / `_updated` / `_deleted` mapped into the webhook catalog.

The service refuses deleting a **non-empty** bucket (the caller empties it first; cascade delete would make an administrator misfire a restore-from-backup job) and the bucket the `storage.default_bucket` appconfig setting names. A creation provisions the bucket's physical container **before** the row is written — the name is the object store's own bucket, and the engine's `EnsureBucket` seam (an interface this package defines, wired post-construction over the resolved `*storage.Manager` the way the settings reader is) is idempotent. Update is partial (an absent field keeps its stored value) with the mime-type list wrapped in an optional `MimeTypeSet`, so absent and empty stay distinct. The area's `Package` resolves `*appconfig.Settings` post-construction (the same lazy seam notification uses for the queue) and hands the engine a `settingsReader` interface instead of importing the appconfig area — a consumer defines the interface it needs, the wiring joins them in the container. Wire ids are `bkt_` TypeIDs; the audit record keeps the raw UUID.

### internal/config (planned)

The configuration layer, on koanf. The JSON config file is the single source of truth: `Load` merges three layers in fixed precedence — built-in defaults, the config file, then the command-line flags. Merge is last-wins per key, not per section, so a source that sets one leaf leaves its siblings alone. **The environment is deliberately not a layer.** A variable reaches a config key only where the file references it, with `env:NAME` as a whole value or `${NAME}` inline, so a user names variables whatever they like, the file decides which key each fills, and a stray export in a shell can never change a value nobody referenced. A directive naming a missing variable is **deferred**, not a load failure: the key keeps its default, `Config.Unresolved` records the variable, and `Validate` reports it only where the missing value leaves the key unusable — so `migrate:status`, which reads only `database.url`, is never blocked by an unset JWT key, and an unset `APP_MODE` falls back to development without an error. The file is **required**: a missing one is `ErrNoConfigFile`, not a fallback to the defaults, so `config:generate` is the first command a fresh checkout runs. `Load` resolves but does not validate, so a command that needs one key is not blocked by a key it never reads; `cmd/config.go` exposes `configFrom(ctx)` for that case and `fullConfigFrom(ctx)` for a command that needs the whole configuration. A duration key is written as a plain number of seconds (`"access_ttl": 900`), never as a duration string: koanf hands a JSON number to mapstructure as a `float64`, which would set a `time.Duration`'s nanoseconds, so `900` would silently mean `900ns`. `internal/config/duration.go` holds `durationKeys`, the list of keys read as seconds; `normalizeDurations` converts a numeric value on those keys only, before each layer is merged. A duration string (`"15m"`) is still accepted, so a hook on the Go type is wrong: a duration is an `int64` and so is an ordinary number. A test asserts `durationKeys` is exactly the set of `time.Duration` fields on `Config`. `app.mode` (not `app.env`) names the runtime mode. The struct is the schema: a field with a koanf and json tag, a default in `Default`, and a rule in `Validate` makes a key work in every source at once. Keys are dotted (`database.max_conns`); `EnvName` is the *convention* the generated file and `.env.example` spell a key as (`DATABASE_URL`), not a loader mapping — deriving it would turn `AUTH_SECRET_KEY` into `auth.secret.key`. A file key that names no config key is dropped, so a stray entry cannot replace a section with a scalar and break the decode.

`Sample()` renders the starter file: every key with its default, every key in `secretKeys` as an `env:` directive rather than a literal, and every key in `envKeys` (`app.mode`, `app.base_url`, `app.assets_url`, the `otel.*` deployment keys, the five `mailer.smtp_*` keys, the `kvstore` and `storage.s3` deployment keys) as a directive naming the variable a deployment sets — the name is written out because it does not always match the key upper-cased (`app.base_url` is `PUBLIC_BASE_URL`, and `app.assets_url` is `PUBLIC_ASSETS_URL`). `app.assets_url` names where the browser fetches assets from: the built-in `/storage` mount by default, and an S3 bucket or a CDN origin once a deployment points the variable there — one URL, no driver switch of its own. `log.transport` and `otel.endpoint` are directives, because a deployment is the one that decides whether it keeps the terminal, ships to a collector, or both, and where that collector listens; `log.file.filename` does not exist at all, so there is nothing to pin. A list key written as a directive arrives as one string, because that is all an environment variable can carry, so `internal/config/lists.go` holds `listKeys` and `normalizeLists` splits it (`LOG_TRANSPORT=console,file,otlp`); without that step koanf would decode the string into a one-element list holding "console,file,otlp", which names no sink. A test asserts `listKeys` is exactly the set of slice-valued fields on `Config`, the way the duration test asserts `durationKeys`. The same file holds `mapKeys` and `normalizeMaps` for a key whose value is a map (`otel.headers`), split from the specification's own `name=value,...` form, and the same test asserts it against the map-valued fields. A map key is also kept whole by `flattenNested`, so a **file** writes it as a JSON object rather than as a section: walking it would produce `otel.headers.authorization`, a key that is not part of Config, which `filterKnown` would drop — leaving the header silently unset instead of reported. Space is not a separator: `console file otlp` stays one name and is then refused by name, rather than being read as three sinks nobody asked for. An entry with no `=` is dropped rather than sent as a nameless header, while an empty value (`x-empty=`) is a header with no value, which is legal.

`mailer` is the optional email section: an empty `mailer.smtp_host` means the mailer is not configured and is **not** a configuration error, so a local checkout needs no mail server. `Validate` checks only what a set host needs — a usable port, an address in `from_email`, and a username whenever a password is given (`mailer.smtp_password` is a secret, so `Redacted` hides it and `Sample` writes it as a directive). An unset variable is reported only where it leaves the key unusable (`Config.unsetNote`), never for every key that references one: an unset `APP_MODE` falls back to development and `auth.jwt_algorithm` to the material's own answer, so reporting those would flag a deliberate choice. Driver and format values are `memory`/`kvstore` (cache), `database`/`kvstore` (rate limit, session), `pretty`/`structured` (log), `local`/`s3` (storage); a key-value backend is named `kvstore` rather than after the product behind it. `storage.s3` holds the object-storage settings, nested rather than flattened because its eight keys cover credentials, the bucket, the endpoint, the addressing style, a prefix, a region, and a link lifetime — a common prefix on each would be noise the nesting already carries. The section is validated **only when `storage.driver` is `s3`**, so a local deployment that keeps credentials in the file for a later switch still runs. `storage.s3.region` has a concrete default (`DefaultS3Region`, `us-east-1`) rather than an empty one because the S3 client refuses to resolve an endpoint without a region and every request fails — even against a service that ignores the region such as MinIO — so an unset `STORAGE_S3_REGION` variable must leave a usable value; an explicitly empty region is still an error. `signed_url_expires` is a duration key, and Validate holds it inside `1s..7d`: the protocol caps a signed link at seven days, and the client reads a zero as "use my own fifteen-minute default" rather than as a lifetime. `force_path_style` defaults to true because MinIO and Silo need it and the client does not fall back on its own (`bucket.localhost` does not resolve). The credentials are in `secretKeys`; their variable names are what `EnvName` derives, so they are deliberately **not** in `envKeys` — that map is for a name that differs from the derived one. `path_prefix` is in `nullKeys`, so a generated file writes `null` rather than `""`; the two resolve alike, so this is about what the file reads like.

`log` holds the console format plus the two optional sinks, selected by `log.transport` — a list of `console`, `file`, `otlp` — which is the one place a sink is switched on. The default is `[console]`, so a fresh checkout and a container that logs to stdout need no volume and no collector. `Validate` refuses a name no sink matches, a repeated name, and an empty list, and checks a section **only when its transport is named**: the rotation keys of `log.file` are read then, and `log.format` likewise (the way `storage.s3` is read only on the `s3` driver), including the one combination that never deletes a rotated file (`max_backups` and `max_age` both zero, which would fill a disk quietly), and `log.otlp.path` is held to a path then. `log.file` has no filename key: the sink writes to `storage.local_path + /logs` + `saka.log`, so the process has one data directory.

`otel` is the section the three signals share, and its shape follows from one decision: **one collector address serves logs, traces, and metrics**, because that is what a collector is, so `otel.endpoint` is the only place a collector is named. A signal that needs a different route on that collector sets its own path (`log.otlp.path`, `otel.tracing.path`, `otel.metrics.path`), never its own address — a second address would be a second configuration source deciding where telemetry goes. `otel.endpoint` has a concrete default (`DefaultOTLPEndpoint`, `http://localhost:4318`, the protocol's own port) rather than an empty one, so an unset `OTEL_ENDPOINT` leaves a usable address instead of blocking a deployment whose collector is local, and its scheme is what decides TLS, so there is no second setting to keep in step with it. `otel.service_name` defaults to the application identifier rather than to an empty string, because a record with no service name cannot be attributed at all. There is **no `otel.protocol` key**: the exporters speak `http/protobuf` only — the one protocol the Go SDK implements for all three signals, over the transport an HTTP deployment can put behind the same proxy and TLS terminator as the rest of its traffic — so the endpoint is always the URL the exporter dials, and a gRPC or `http/json` value in an old file is an unknown key koanf carries and Config ignores. The gRPC exporter packages and the `google.golang.org/grpc` tree behind them are gone from `go.mod`. `otel.headers` is a map and therefore in `mapKeys`, so it is kept whole at load time rather than walked into dotted keys `filterKnown` would drop — a JSON object in the file, and the specification's own `name=value,...` string behind a directive. Every header **value** is a secret (in `secretKeys`) because an authorization token is why the key exists and the names inside are chosen by the user; the names are kept in a rendering, since a name says which credential is missing without revealing it. `otel.tracing.*` is read only when `enable` is true, and `otel.metrics.*` likewise, the way `storage.s3` is read only on the `s3` driver: a signal nothing switched on is not held to a sampler or an interval it never runs. `otel.tracing.ratio` is read only by the two ratio samplers, so a ratio outside `0..1` is refused by name rather than silently ignored, and `otel.metrics.prometheus_path` is a **path** rather than a second enable flag: the exposition is always served when metrics are on, and where it is served is the one decision a scrape job needs. `otel.queue.max_size` bounds the in-memory buffer each signal exports from, which is the setting that keeps export off the request path.

`kvstore` is the optional Valkey/Redis section: `Enable` gates availability, while the per-feature driver fields still choose what each feature uses, so switching the backend on moves nothing by itself. `Validate` reports the one combination that cannot work — a driver set to `kvstore` while `Enable` is false — naming every offending driver in one message (`Config.kvStoreDrivers`), and checks `kvstore.url` **only when enabled**, since a disabled backend is never dialled. `isKVURL` mirrors the URL grammar the client accepts (`redis.ParseURL` in `redis/go-redis`: schemes `redis`/`rediss`/`unix`, a missing host defaulted to `localhost:6379`, a path that is empty or one integer database index, a unix socket carrying its path) — validation stricter than the client would reject a URL that connects, and mirroring the query-parameter list is not done because it is a second copy to keep in step. `RedactKVURL` reduces the URL to `host:port/database`; it does **not** reuse `RedactDSN`, whose parse is pgx's and rejects a `redis://` URL outright, which would replace the whole target with the placeholder. There is one data directory, `storage.local_path` — `app.data_dir` was removed rather than kept as a second path that could disagree with it. `secretKeys` is one list, asserted against both `Sample` and `Redacted`, so a secret cannot be written literally or reach a log line. `Config.Origin` reports which layer last set a key (`default` / `config-file` / `flag`).

Two secret renderings, deliberately kept apart, both built on `withSecrets`: `Redacted` replaces every secret with `[redacted]` and is the **fail-safe** behind `Config.String()`, so a log line never carries a fragment of a key; `Masked` keeps the first and last four characters with `****` between them, which is what `config:print` renders so a value can be traced to the key that produced it. A secret shorter than `maskMinLength` (16) is redacted in full even by `Masked`, because keeping eight characters of a short password would leave most of it readable; an empty secret stays empty so an unset key reads as unset. Neither renders the DSN: `RedactDSN` reduces it to `host:port/database`, the one rendering the CLI and the health check both use, because a connection string is a composite value where revealing part of the string says nothing. `config:print` renders the resolved configuration as a table (`github.com/rodaine/table`, coloured through `printext.Palette`): the values come from `config.Values(cfg.Masked())`, so a secret cannot reach the table even by mistake, and `--source` adds the layer from `Config.Origin`. It resolves with `configFrom`, **not** `fullConfigFrom`: a configuration being inspected is often one that does not validate yet, so an unset key prints empty rather than stopping the report. The table writes through `trimmedWriter` because rodaine/table pads the last column too, and the header is trimmed **before** it is painted — a colour reset is invisible but not zero-width, so trimming after it would leave the padding inside the escape where it survives into a redirected file. `cmd/config.go` resolves once in the root `Before` and puts the result on the context as a `configState` — the result *and* the failure, because resolution is **deferred**: a broken or absent config file must not stop `config:generate` (writes the file) or `key:generate` (runs before a referenced variable exists), so the command that needs the configuration is the one that reports the error.

### internal/fetcher

The outbound HTTP client. One `*fetcher.Client` is built in `internal/registry` from `config.Fetcher` and the process `*slog.Logger`, resolved when `serve` starts, and closed by the injector's shutdown. Features call `Do` with an absolute URL; they do not construct a client and there is no configured base URL — an upstream address is hardcoded at the call site. Hosts share one connection pool and each host owns a Resty client, because Resty's breaker is per client and `Allow` does not receive the request, so one breaker cannot tell hosts apart. Resty (`resty.dev/v3`, v3.0.0-rc.4) is the transport. Its debug log stays off, because that log includes bodies. A cookie jar is not installed, so one upstream's cookies are not replayed to the next. `RedirectHeaderStripSensitivePolicy` drops `Authorization` and `Cookie` on a redirect to another host. Each call starts a client span and injects W3C `traceparent` (and baggage) from `otel.GetTextMapPropagator`, falling back to trace-context plus baggage when the global propagator has no fields — that is the SDK default until `observer.SetGlobals` installs the same pair.

`Do` returns the response for an HTTP status of 400 or above and an `*fetcher.Error` a caller matches with `errors.Is`: `ErrNetwork`, `ErrTimeout`, `ErrCanceled`, `ErrCircuitOpen`, `ErrStatus` (the code is `Error.Status`), and `ErrRetryExhausted` alongside the class when every configured retry ran. The error text is method, scheme, host, and path. The query and the userinfo are omitted, and the transport error is not unwrapped into the text, because `url.Error.Error` contains the full URL. The response body is returned to the caller and is not logged. Resty's own lines go through an `slog` adapter that redacts bearer and basic tokens, `password`/`token`/`secret` query parameters, URL userinfo, and the query string.

The client instruments every call (`metrics.go`, scope `github.com/riipandi/saka/internal/fetcher`; the client builds its metrics at construction): `saka.fetch.requests` by `host` and `outcome`, where the outcome is the same taxonomy `errors.Is` matches — `success`, `http_status`, `network`, `timeout`, `canceled`, `circuit_open`, `retry_exhausted` — so a dashboard's breakdown and a caller's error handling cannot drift apart; plus a duration histogram (retries included), an attempts histogram, and `saka.fetch.breaker.opens` from Resty's state-change hook. The host label is `scheme://host`, the breaker's own key, and never a full URL — a path or query on it would make every distinct upstream request its own time series.

Timeout, retry, and the breaker are one policy so they do not trip each other. `fetcher.timeout` is the budget of a single attempt (Resty's `SetTimeout`, which applies only when the caller's context has no deadline) and also the dial and handshake budget. The caller's context cancels the attempt and the backoff wait. Retries use Resty's capped exponential backoff with jitter between `fetcher.retry_wait` and `fetcher.retry_max_wait`. Resty's default conditions retry only a `url.Error` whose `Temporary` method is true and do not look at status codes, so the client adds a condition: network failures and per-attempt deadlines, HTTP 408 and 429, and 5xx except 501. Other 4xx are not retried. POST and PATCH are not retried either — Resty refuses non-idempotent methods unless told to, and this client does not tell it to. `fetcher.retry_count` is capped at 5. The count-based breaker (`NewCircuitBreakerCount`) opens on the same statuses, and only after more failed attempts than one call's retries (`circuit_failure_threshold` must exceed `retry_count`), so the retries of a single call cannot open it. It stays open for at least one attempt budget (`circuit_reset_timeout` is at least `fetcher.timeout`) and then allows one probe at a time. `fetcher.user_agent` defaults to `saka/<version> (+https://github.com/riipandi/saka)`: a product token, not a browser token. The generated file omits the key (`omittedKeys`), so a checkout keeps that token by absence. `fetcher.max_body_bytes` defaults to 16 MiB and is refused above 32 MiB. A relative URL is refused.

### internal/mailer

The outbound email path: `*Mailer` submits over SMTP and `*Templates` renders the React Email output embedded in the binary. One `*mailer.Service` pairs the two; `internal/registry` builds it from `config.Mailer` and the process `*slog.Logger`, and `serve` resolves it before the listener opens so a broken template fails the run rather than the first send. The mailer is optional and stays so: an empty `mailer.smtp_host` builds a mailer whose `Send` reports `ErrNotConfigured`, which is not a deployment failure. `github.com/emersion/go-smtp` is the protocol and `github.com/emersion/go-sasl` the mechanisms; both are dependencies of each other, so adopting one adopts the pair.

A session is opened per `Send` and closed by it — no pool, because an SMTP session is stateful and a pooled one would have to be verified before reuse anyway. Encryption is decided once: `mailer.smtp_secure` selects implicit TLS (the port-465 shape, `tls.Dialer`), otherwise the connection is upgraded with STARTTLS when the server advertises it and sent in the clear when it does not — the local Mailpit server is the second case, and it is reported as a warning rather than refused, so a development checkout needs no certificate. The certificate is verified against the configured host, and TLS 1.2 is the floor. Credentials are presented with PLAIN where the server offers it and LOGIN otherwise; a server offering neither is `ErrAuth`, not a silent unauthenticated session. `mailer.timeout` bounds the dial, the handshake, every command, and the message body — the library's own defaults are RFC 5321's five and twelve minutes, far longer than a submission this process makes should take. A cancellation closes the connection through `context.AfterFunc`, so a blocked read fails instead of waiting out the server.

**A credential is never offered on an unencrypted connection that leaves the machine.** `go-sasl` sends the password as soon as the server asks, with no opinion about the transport; the stdlib's `net/smtp` refuses that case inside `PlainAuth`, and `go-sasl` has no equivalent, so `Mailer.authenticate` refuses it itself with `ErrInsecureAuth` before any mechanism is chosen. Three things make a session safe: it is over TLS (`TLSConnectionState` is the authority, not the configured intent — a `smtp_secure` run that failed to negotiate never reaches the check), the host is loopback (`localhost`, an `IsLoopback` IP literal, so a local Mailpit needs no certificate), or `mailer.smtp_allow_plaintext_auth` is set. The class is `ErrAuth` and the cause is kept on `Error.cause`, so `errors.Is` answers both "authentication failed" and "and the reason is the transport" — the actionable half, since the fix is TLS or the opt-in rather than a different password. It is deliberately **not** a `Validate` rule: whether a server offers STARTTLS is only known once it has been asked, and a configuration check would reject the ordinary submission server. `ErrInsecureAuth` is exported for the same reason it exists — a caller acts on it, and it must not be retried as a rejected credential.

The library exports no sentinel for "this server has no STARTTLS", so the plaintext fallback matches its message text (`startTLSUnsupported`); a test runs that message against a Mailpit container, so a library change fails a test rather than quietly moving a session to plaintext. A failed STARTTLS attempt closes its own connection, so the fallback dials again — only a server without TLS pays for the second dial.

`Message` is what the caller supplies and the envelope what the session needs: the sender, every recipient including the blind ones, the header block, and a **body that is written on demand**. `envelope.writeTo` takes an `io.Writer` — on the send path that is the `DATA` command's writer — and `bodySource` is either the two strings the caller passed or a closure that renders one template into it. The send path therefore never holds a rendered message: `Service.Send` resolves the template name, then `Mailer.submit` issues `MAIL`/`RCPT`/`DATA` and streams the message through `envelope.writeTo`. `SendMail` is not used, because it takes an `io.Reader` and a body produced on demand cannot be given as one. A message with both bodies is `multipart/alternative` with the text part first, so a client that cannot show the HTML falls back to the plain one; a message with one body is sent as that body alone, because a wrapper around a single part is boilerplate some readers display. Headers and bodies are quoted-printable, the subject and the sender name are RFC 2047 encoded words, and every line is CRLF terminated. `Bcc` is an envelope recipient only — it is never written into the headers, which is what keeps it blind. An address or header value carrying a line break is refused, because the envelope is written line by line and that is the injection. A `Message-ID` is generated per message from a random identifier at the sender's domain. A failure while writing the body aborts the transaction with `RSET` rather than closing `DATA`, so the server never accepts a half-written message as a complete one.

`Templates` parses the compiled files (`web/email/*.tmpl`, embedded through `web.EmailTemplates`) at construction, as pairs: a name with only one rendering fails construction, and an unknown name is refused by `Render`/`RenderTo` rather than producing an empty body. The two renderings are separate template sets on purpose — `html/template` escapes what it writes and `text/template` does not, so the HTML body is safe against a template field carrying markup while the plain-text body keeps the characters as written. `Render` (both renderings as strings) and `RenderTo` (one rendering into a writer) produce identical bytes, which a test pins; `Render` is the convenience for a test or a preview, `RenderTo` is what the send path uses. Every template's field set is a struct in `data.go` (`PasswordResetData`, `LoginNewDeviceData`, …): a template naming a field the struct lacks fails the render, so a renamed field is caught by a test rather than printed as nothing. A struct is used rather than a map because the field name is then checked at the call site too. `LoginNewDeviceData.DateTime` is the one `time.Time`, because that template formats it itself; every other date is a string, because these values travel the queue as JSON. `SenderFrom` resolves the sender identity from `app.base_url` (falling back to `app.assets_url`), so a template's logo follows the deployment's public origin and the URL is a real asset rather than a `{{.LogoURL}}` that nobody filled in.

**The parsed templates are the cache, and no second one is worth having.** Parsing every template is ~177 µs and happens once per process; rendering one rendering is ~4.5 µs (58 allocs, 1.5 KB) and both is ~10.4 µs (73 allocs, 20 KB), against 60–100 ms for the submission itself — under 0.01%. `internal/mailer/bench_test.go` pins those numbers. Memoizing by template data would retain reset tokens past their use, and putting templates in `internal/cache` would add a network round trip for content that is already in the binary.

`cmd/mailersmoke.go` is `mailer:smoke`: it renders one template and submits it through a real server, printing the server, sender, auth, TLS mode, template, and recipient — the same shape as `logger:smoke` and `otel:smoke`, so the three prove their paths the same way. It builds the mailer itself rather than reaching for the registry, because a command that exists to diagnose mail should not fail before it can say which part broke. It ships in the debug build only, as its siblings do.

### internal/kernel

The module contract. A `Module` is `{Name, Mount(chi.Router)}`: it owns its package and registers its endpoints through `Mount`, so no route list outside the module can drift from its handlers. `kernel.Mount` walks the modules a composition root passes; the transport serves what it is given, so a new module needs no change outside `internal/registry`.

A module that also serves procedures implements **`RPCModule`** (`Module` plus `MountRPC(chi.Router, ...connect.HandlerOption)`), and `kernel.MountRPC` registers the procedures of the modules that do. It is a second interface rather than a third method on `Module`, so a module with no procedure says so by not implementing it and the transport asks with a type assertion instead of calling a method that would have to do nothing. The RPC router is mounted with its prefix stripped, so a module registers the procedure paths a generated Connect handler answers.

**The handler options travel with the call, and that is the point of the signature.** They carry the shared JSON codec — the one that serializes snake_case, so a procedure answers in the same field names its REST twin writes — plus the panic boundary and the correlation-id interceptor. A module that registers a generated handler with them answers like the transport's own services; one that ignores them silently falls back to protobuf's default camelCase mapping, which is the drift the shared codec exists to prevent (`internal/transport.TestModuleProcedureGetsTheSnakeCaseCodec` pins both sides, including a negative control on a handler registered without the options).

**A route claimed twice fails the mount.** `kernel.Mount` reads each module's routes back from a scratch router before registering them, so two modules claiming one method/pattern pair fail the run naming both — chi's own registration is last-wins and would hand the route to whichever mounted later, silently. `kernel.MountRPC` does the same for procedure paths, which are claimed by path alone. Mounting twice is safe (Mount is registration only); a conflict *inside* one module's own registration is still chi's last-wins and is that module's defect. The boundary policed is between modules.

### internal/transport

The HTTP surface, on chi, split by role so a reader looking for one thing opens one file. `http.go` registers the HTTP surface and `rpc.go` the ConnectRPC one; `handler.go` and `handler_rpc.go` hold only the handlers those routers mount — no routing, no mount order — and `server.go` binds the listener. `transport.go` holds the package-wide constants, `middleware/` the pipeline pieces, `storage/` the serving mount.

`NewRouter` (in `http.go`) composes the pipeline: request id first (every response and envelope metadata names its request), then the request logger and panic recovery (one line per request at the status's level — 5xx error, 4xx warn; a panic becomes a 500 envelope plus a logged stack), CORS (a policy question is answered before a route runs), and the request timeout (a context deadline the handler honours), then the endpoints — the `/api` landing endpoint, `/api/healthz` from `internal/health`, the metrics exposition at `otel.metrics.prometheus_path` when the signal is on, the throttled group (the API's own routes, the `/rpc` surface, and every feature module's), the uploads mount, and the SPA mount (`web.SetupStatic`, debug/release variants) last, because its handler answers whatever the routes above it did not claim and its own not-found rule keeps API and protocol paths from being answered with the SPA document.

The SPA document is Go-rendered (`web/shell.go`), following the Vite backend integration guide: there is no `index.html` — the build's input is the application entry (`app/main.tsx`; the multi-page input map in `vite.config.ts` names one entry per page) — and every unclaimed GET renders the shell. The head tags come from the olivere/vite port (`web/vite_*.go`, MIT, owned here): the debug build emits same-origin paths and its surface proxies the compiler behind the port (the Vite dev server is a loopback-only constant, `viteDevServer`, `http://127.0.0.1:5173` — development-only, deliberately not config): a navigation, told by its `Accept: text/html`, renders the shell, and everything else — modules, public assets, the HMR socket, which is an Upgrade the reverse proxy pipes through — is the compiler's to answer, so the browser holds one origin. The release build skips the proxy entirely: it resolves the tags from the embedded build manifest, one fragment per entry, so a second page carries its own assets. A page (`web.Page`) names its entry plus the title, description, and noindex the shell renders; `DefaultPage` is the application document, and a later phase registers further pages and turns noindex off where the surface is public. The shell escapes every value a page carries; the fragment is the one trusted-markup input, built from the manifest and never request data. Request ids are TypeIDs with the `req_` prefix (`go.jetify.com/typeid`), honoured from the incoming `X-Request-Id` header and stored through `responder.WithRequestID`, so middleware, envelope metadata, and a later trace agree on one idiom. CORS is `rs/cors` driven by the `server.cors` section; an empty origin list is a passthrough, and `Validate` refuses `*` with credentials because the browser does.

**The ConnectRPC surface is `rpc.go`** (`RPCPath`, `/rpc`), and `http.go` names it with one `mountRPC` call so the router reads as a list of mounts. `rpcRouter` builds a chi router holding the transport's own services (today `saka.system.v1.HealthService`) and every module's procedures through `kernel.MountRPC`; `mountRPC` adds it with `http.StripPrefix`, because chi's `Mount` shifts only its own route context and a generated Connect handler matches its procedure path exactly. The throttled group wraps the mount, so a procedure call is held to the same rate policy as a REST route, and the mount runs before the modules so a module that claimed a path under the prefix is reported at startup instead of silently answering for the same path.

`NewServer` stays here, beside the router: the `server` section it reads is the same one the router's request deadline comes from, so a timeout is decided in one place on both sides of the boundary. `internal/logger/transport.go` is not a candidate for it — that file holds the log *sinks* (console, structured, echo), a different meaning of the word, and an HTTP server has nothing to do with them.

**`handler_rpc.go` holds the RPC handlers** and nothing else: `rpcHealthService` answers the readiness procedure from the same `*health.Checker` the REST endpoint runs, so the two surfaces share one check set, one cache, and one aggregate. A healthy system answers the readiness document (aggregate status, per-check details in check-name order, `took_ms`); an unhealthy one fails with `unavailable` — 503, the status a probe acts on — and the message names the checks that are down. The correlation id travels on every answer because the request middleware writes the `X-Request-Id` header on the writer before any handler runs — the one writer on purpose: connect merges handler-set headers by appending (`mergeHeaders`), so a second writer, a handler or an interceptor, answers with the id twice. A test pins the single value on the success and the failure path.

Three decisions in `rpc.go` hold the two transports to one contract:

- **A codec, not the default mapping.** `rpcJSONCodec` registers under connect's own JSON names (`json`, `json; charset=utf-8`) and marshals with `protojson.UseProtoNames`, so a response writes the declared proto field names — `status_code`, `request_id` — instead of protobuf's default lowerCamelCase. Without it an RPC field and its REST twin would be two spellings of one contract. Requests stay tolerant: protojson accepts either spelling on the way in and `DiscardUnknown` keeps a client off the server's schema version. One camelCase survives the codec and is connect's own: the `debug` echo connect attaches to each `details` entry of a failure body, rendered with protobuf's default mapping (`ruleId`) beside the authoritative `value`. Left alone on purpose — the codec cannot reach it, and `value` decodes to the proto field names. Field names a specification owns (JWKS now; SCIM, WebAuthn, OIDC when they ship) keep the spelling that specification defines.
- **Procedures are registered by path, not by service prefix.** The generated handler answers a path under its service prefix it does not know with a plain-text 404, which a Connect client cannot read. Registering each procedure keeps the not-found boundary in one place, where `connect.NewErrorWriter` answers in the protocol the caller used (unknown procedure → `unimplemented`, 501). The path is registered for every method on purpose: the generated handler is what refuses a wrong method with `405` and `Allow: POST`.
- **A panic is answered in the caller's protocol.** `connect.WithRecover` turns a panicking procedure into `internal`, because the recovery middleware above answers with the REST envelope, which a Connect client cannot parse. The panic value is not published — it is an internal detail — and the middleware still logs it with the stack and the request id.

**The telemetry is part of the surface, and it lives in two seams.** `otelconnect` is adopted: every procedure is served behind `otelInterceptor()` — one of `rpcHandlerOptions`, so a module's handler reports the `rpc_server_*` histograms and the server span exactly like the transport's own — and `NewServer` wraps the whole router in `otelhttp`, so every API request (REST and RPC, the `/api` and `/rpc` prefixes; the scrape and the SPA assets are filtered out) carries a server span and the `http_server_*` metrics. Both read the global providers the observer installs, so a switched-off signal costs a no-op. OpenObserve's own dashboards read them; the Perses provisioning tree is gone (see the observability stack section).

**Candidates for this surface, not yet adopted.** `connectrpc/authn-go` and `connectrpc/validate-go` are the two extensions the first-party surface still wants. Each plugs in as a Connect interceptor or handler option beside `rpcHandlerOptions`, so no route, codec, or mount changes to gain one — an interceptor wraps the procedure call, which is exactly the seam `rpcHandlerOptions` already occupies (where `otelconnect` now lives). `authn-go` needs a token-verifying function and `validate-go` needs a `protovalidate` constraint on the request messages; neither should be added before the module that needs it exists, because a credential check with no protected procedure and a validator with no constraint both pass trivially.

**The throttled surface is two chi groups, one per transport.** A module mounts its own routes on the router it is handed — a feature under `/api`, a protocol endpoint at `/.well-known` — and middleware attached to the `/api` subrouter never reaches them, so the limiter used to leave every feature route exempt from the policy the API's own routes were held to. The two groups — REST routes and modules in one, the `/rpc` mount in the other — cover every mounted route without also covering the SPA or a metrics scrape, and they exist so a limited request is refused in the protocol the caller used: the middleware takes a `Refuse` the mount site passes, the responder envelope on REST (`restRefuse`) and a connect `resource_exhausted` error serialized under the shared codec on RPC (`rpcRefuse`). Both groups share one limiter and one policy; the exclusion lists are per transport — `httpRateLimitExclusions` and `rpcRateLimitExclusions` in `internal/transport/server.go` — because the namespaces the surfaces answer are disjoint, so an exclusion on one surface must not silently spare the other's paths. Both health endpoints are excluded, so the same readiness a monitor watches is never refused. The limiter's driver is chosen in the registry: `database` runs `fn_check_rate_limit` (the fixed window is synchronized under advisory locks in migration `00007`, and the raised `42901` SQLSTATE is read as the result, its detail carrying the retry hint), `kvstore` runs one Lua script on the shared backend (`saka:ratelimit:` prefix); the key is the client address sanitized to the alphabet the `rate_limits.key` check allows. Behind a proxy every key is the proxy's address — a trusted-proxy setting is a later decision, not a spoofable `X-Forwarded-For` read. `NewServer` binds the timeouts; the listener and the graceful drain stay with `serve`. `middleware.RateLimit` takes the surface's name ("rest" or "rpc") as its first argument and counts every check (`metrics.go` in the middleware package): `saka.http.ratelimit.requests` by `surface` and `outcome` — `allowed`, `limited`, `excluded`, and `degraded`, the last being the pass-through a failed limiter is allowed and **must never do silently**, which is exactly why it is counted. There is no key label: the key is a client address, and per-address series is the cardinality blowup the counter exists to observe, not to amplify.

**The devtool is a build-tag pair, not a route with a mode flag.** `devtool_debug.go` (`debug` tag) mounts, outside the throttled and bearer-guarded groups, the samber/do web UI at `/debug/do` (`dohttp` pages over the injector `Options` carries in) and two POST codecs, `/debug/encode-id` and `/debug/decode-id`, that convert between a TypeID and the prefix + UUID pair it decodes from — unauthenticated, because a release build serves none of it: `devtool_release.go` claims the same paths and answers with the 404 envelope, so a release refuses in the API's protocol instead of letting the SPA answer. No auth middleware is added, because the guard is the build tag — an authenticated debug surface would suggest the release one exists. The injector reaches the router through `Options.Injector`, the one field a release build ignores.

### internal/transport/storage

The serving mount, at `/storage`. It lives under `transport` because it is part of the HTTP surface — a mount the router composes, beside `middleware` — not a service a module owns; nothing outside `transport` imports it. It serves the engine's finals: the first path segment is resolved against `storage_buckets` (a directory that exists on disk but names no bucket is a 404, never a listing), the rest is a `ValidateKey`-checked object key, and the bytes stream from the active backend through the engine — a local file or the S3 read — under `/storage/{bucket}/{key}`.

The mount keeps the policy, so every driver answers alike: the response headers, and the translation of `ErrNotFound` into a 404 — a driver says a key is missing, not how to say it. The mount also refuses to list a directory, which the standard file server does by default: a key naming a directory answers with the names of the files under it, and those are the names of files a client was never given. The driver returns the miss, so the enumeration boundary holds for every driver rather than for the one that remembered it.

A missing object is a 404 and never the SPA document, which is the reason it mounts before the SPA and stays out of the SPA's fallback: an `<img>` pointing at a page is a broken image rather than a visible error. It also sits outside the throttled group, because a page loading an asset spends no rate-limit check, and outside the bearer-guarded group, because serving is the bucket's public read. A missing directory is not an error — a run that never stored an object has none, and the first write creates it — and every response for a file carries `Cache-Control: public, max-age=31536000, immutable` with `X-Content-Type-Options: nosniff`, the content being named by its path so a replacement lands under a new name. A miss carries neither, so a client does not keep the 404 and miss the file a later write stores. The URL a feature builds for a file is `app.assets_url + /{bucket}/{key}` — the default `/storage`, or a CDN origin whose path layout mirrors the bucket tree.

### internal/registry

The composition root, split along the infrastructure/module boundary. `New(ctx, cfg, metrics, logger, extra ...Area)` builds the container from four `do.Package` values — the config and logger as `do.Eager` values, `infrastructure(ctx)`, the areas' own packages, and the router and server that join them — so `do.New` reads as the composition list itself rather than as a sequence of `do.Provide` calls. `do.Lazy` is the package form of `do.Provide` (it calls it), so nothing about the lazy behavior changed: resolving the server is still what opens the pool, and an unreachable database still fails the run before the listener opens.

`infrastructure.go` registers what the process runs on — the pool, the Valkey client, the cache, the health checker over them, the mailer, the storage store and manager, the queue client with `internal/jobs` registered on it, the scheduler, the rate limiter, the outbound client. It names no module: a module reaches these services by invoking them from the container, so the two halves meet only in the container, not in an import.

`modules.go` holds the seam and nothing else. An **area** is `{Name, Package, Mount}`: `Package` registers the services the area owns, `Mount` resolves what its features need and returns the `kernel.Module` the router mounts. The composition root therefore knows an area provides services and produces a module, and knows nothing about which services those are — no area's internals appear in this package. `Areas()` is the one place an area of this application is named, and `New` takes further areas as a variadic, so a consumer outside this repository serves its own area by passing one in: `registry.New(ctx, cfg, metrics, log, myArea)`. `TestAConsumerServesItsOwnArea` mounts an area defined in the test package and asserts its route answers 200, which is the property that failed before the seam existed.

The wiring inside an area lives in the area: `modules/identity/module.go` owns `identity.Package` (the JWKS service and the cached `jwtutils.KeyProvider`) and `identity.Mount` (which resolves the provider, then the service beside it, and reports `service.Err()` so a broken key pair fails the run before the listener opens). The composition root used to hold both of those, which is what made it a per-area registration list rather than a composition root.

`registry.go` is the join point and the only file that names both halves: the router resolves the health checker and the limiter from infrastructure and the module list from the areas, and the server wraps the router. It is also where the run's own context is captured rather than registered — a context that the command cancels on a signal is a property of the run, not a service anything could resolve and replace.

`do.Scope` is deliberately not used. The docs present it as the way to organize services by module, and it becomes the right tool when an area needs its own instance of a service or needs to hide one from a sibling area — neither is true today, and `kernel.Module` is already the contract that gives a module its own package and route ownership. Adding scopes now would be a third abstraction for a concept that already has two. Add them when a second area needs a service instance the first must not share.

The metrics handler and the logger are built and closed by the command lifecycle, not by the container. Both are registered as values, so the services below resolve them like any other dependency — the metrics handler included, since a module that later needs it resolves `http.Handler` instead of receiving it through another parameter.

**A service must not carry a hidden side effect in its provider.** The queue's construction wires its processors (pure — no connection is touched); the recurring seeding is its own service, `*jobs.Seeder`, whose `Seed` the prewarm walk calls against the client it resolves. A provider that reads or writes a database hides a dependency the container cannot see; construction must be resumable and side-effect-free. `Register` in `internal/jobs` stays idempotent through the pending-count guard, so seeding twice across a restart adds nothing.

**Every service the container holds is either resolved by the prewarm walk or listed as a cold exception with its reason.** `TestPrewarmResolvesEveryBlockingService` compares `ListProvidedServices` against `ListInvokedServices` after the walk, so a service registered in `infrastructure.go` and forgotten there fails at test time instead of surfacing as a 500 on the first request. The exceptions today: the Valkey client (opt-in, disabled in the test run) and the cache (module-facing, cold until a feature resolves it).

**The run's lifecycle is the registry's, not the command's.** `Prewarm(ctx, i)` resolves every service a serve run blocks on — the fetcher, the mailer, the queue, the scheduler, the seeding of the recurring jobs, the router, the server — so the command makes one call after `New` and a configuration or dependency a service cannot work with fails the run before the listener opens, instead of the command resolving six services by hand. `Runners(i)` returns the long-running components as `{Name, Start, Stop}` in start order: the queue first (the scheduler's first tick claims into a running dispatcher), the scheduler second, the upload sweep last — `jobs.SweepUploads`, the boot-time recovery that re-enqueues the staged uploads a dead run left behind; it runs once, synchronously, and a failure fails the run. The stop order is the reverse, and the drain ownership travels with the entry: the queue's `Stop` is nil because it outlives the listener and the container's shutdown walk drains it, the scheduler's `Stop` runs inside the shutdown window before the HTTP drain. `cmd/serve.go` starts the list, stops it in reverse inside the drain window, and resolves only the listener by name — adding a long-running component is a registration in `infrastructure.go` plus one entry in `Runners`, never a second orchestration in the command. `TestRunnersAreTheLongRunningComponentsInStartOrder` pins the order and the drain ownership.

**Every query against application tables is built with `go-sqlbuilder`** (PostgreSQL flavor), not written as a raw string: the queue store, the scheduler, the storage manifests, and the seeders all follow the same shape — builder → `Build()` → the shared `Querier` — so one place owns the placeholder dialect and a query can never smuggle a value into the statement by hand. Raw SQL is the exception in two places only: tests (assertions and fixtures may write plain `$1` strings) and `database/`'s maintenance tooling, whose statements are the migrator's own bookkeeping or the server's deparse output. A `SELECT` of a database function is still a query — `fn_check_rate_limit` is built with `sb.Var(...)` like any other argument.

## Library decision records

Outcomes of library comparisons, kept so the comparison does not get re-run. Record a new outcome here when it settles a decision.

- **Look up before writing against a third-party package**: Context7 MCP (`mcp_context7__resolve_library_id`, then `mcp_context7__query_docs`) for API usage and options, DeepWiki MCP (`mcp_deepwiki__ask_question` with `owner/repo`) for design intent and behavior. Use them when the answer depends on a version, when the README is thin, or when comparing two candidate libraries. Do not use them for this repo's own code — read the source. The pinned source of truth is the module cache (`go env GOMODCACHE`); when docs and code disagree, the code wins — say so and follow the code.
- **In-memory cache**: deliberately avoids both cache libraries it was weighed against. `allegro/bigcache` does not handle hash collisions — the new item overwrites the previously stored one, a documented data loss — and `VictoriaMetrics/fastcache` would add `golang/snappy`, `golang.org/x/sys`, and `allegro/bigcache` (its benchmark peer) as runtime dependencies. The design was adopted instead: chunked byte ring, append-style `Get(dst)`, collision handling via full-key verification and a secondary slot. The hash is the stdlib `hash/maphash`, seeded per process; `cespare/xxhash/v2` is already in the module graph (goose, Prometheus) and stays indirect.
- **samber/hot** (studied 2026-09 as an improvement source for `internal/cache`): not adopted as a dependency — its generic `HotCache[K, V]` layer sits above per-value maps, which gives the garbage collector every entry to scan and loses the byte-ring zero-allocation property the in-memory driver is built around; its collision story is no stronger than the full-key verification already in place. Four ideas were adopted in design instead: the monotonic-clock expiry (an entry stores its deadline as an offset from a process-start baseline, read via `time.Since` — a wall-clock step can neither age an entry early nor resurrect it), batch operations on the `Cache` contract (`GetMany`/`SetMany`/`DelMany`, where the remote driver answers in one round trip — MGET, a pipeline of SETs, one DEL — while the in-memory driver loops over Get), and benchmarks pinning the zero-allocation claim (`cache_memory_bench_test.go`). Declined with reasons: lock-free reads (an in-place overwrite breaks concurrent readers; 64 sharded RWMutexes keep contention low already), TTL jitter and janitor (a janitor contradicts the settled "no flush goroutine to stop" decision; jitter stays an option if synchronized expiry ever bites in practice), cache hit/miss metrics (belongs in `internal/observer`'s bridge when a real dashboard needs it), and stale-while-revalidate / loader chains / missing-key caching (these need a typed layer above the byte contract and goroutine lifecycle — a feature-layer concern to build over the queue/scheduler when a feature asks for it, not a driver property).
- **Key-value client**: `valkey-io/valkey-go` over `redis/go-redis/v9` for the same economy: valkey-go brings no runtime dependency beyond `golang.org/x/sys` (already in the graph), parses the `redis://` URL scheme itself via `valkey.ParseURL`, and the `isKVURL` validation mirrors its grammar.
- **Scheduling and concurrency libraries** (`go-co-op/gocron/v2` — runtime deps `jonboulle/clockwork` + `robfig/cron/v3`; `alitto/pond/v2` — zero deps): left out. Neither is a queue — both hold everything in memory, so neither can replace `internal/queue`'s durable claim/retry/archive over Postgres, and a process death loses every in-flight task. Recurring jobs need no gocron either: a job that enqueues its own next instance is durable, multi-process safe through the queue's atomic claim, and inherits retries, backoff, and archive — what an in-process scheduler provides only behind an elector or locker that has to be implemented and run somewhere. Revisit gocron only when cron-expression schedules (daily at a time, monthly) become a real requirement, and even then the durable shape is a cron parser that computes the next run and enqueues it as a task, never business logic running in-process.
- **River** (`riverqueue/river`): a mature Postgres queue, evaluated and left out — adopting it would replace `internal/queue` wholesale — its own schema (`river_job`, `river_job_state` enum, `river_leader` election, `river_migration` versioning), its own client/worker idiom, and a dependency set beyond pgx (`pgerrcode`, `puddle`, `tidwall/gjson`+`sjson`, `x/sync`) — for features saka has not asked for. The parts that would tempt later are a paid Pro subscription ($125/mo, private module): workflows, batching, sequences, concurrency limits, dead letter queue, durable periodic jobs (`Pilot` persistence), encrypted jobs, ephemeral jobs. Its periodic-job shape validated the `internal/scheduler` design instead: a `Next(time)` schedule interface with robfig/cron plugged in as the implementation, an atomic claim so exactly one replica triggers a tick (River runs the enqueuer on an elected leader; a CAS claim on `scheduler_jobs` needs no election), and claim + enqueue in one transaction. Worth porting when a real need appears: unique jobs via a partial unique index, and queued-task cancellation.
- **Outbound HTTP client** (`resty.dev/v3` v3.0.0-rc.4): adopted for `internal/fetcher` because the integration client needs attempt timeouts, capped exponential backoff with jitter, a count-based circuit breaker, and a logger hook in one library. It is a release candidate; the pin stays on the rc that was read against (`SetTimeout` does not use `http.Client.Timeout` and does not apply when the caller already set a deadline; default retry conditions do not include 5xx or non-temporary network errors, so those conditions live in this repo). The cookie jar and the debug body log are left off. Revisit the pin when v3 leaves release candidate.
- **SMTP client** (`github.com/emersion/go-smtp` v0.25.0 + `github.com/emersion/go-sasl`): adopted for `internal/mailer` because it is the maintained Go SMTP client with STARTTLS and implicit TLS, a `Client` whose timeouts are settable, a `DATA` command that is an `io.WriteCloser` (so a body can be streamed), and `*SMTPError` with a reply code and a `Temporary()` method. It pulls in only `go-sasl` (which it uses for the mechanisms). `net/smtp` was weighed and left out: it is frozen ("not accepting new features"), has **no timeout of any kind** (`Dial` uses `net.Dial` with no deadline and no `context.Context` anywhere in the API), no implicit-TLS helper (port 465 needs a hand-rolled `tls.Dial` + `NewClient`), and no typed error — so it would need the deadline wrapper and the error classification written on top of it, which is most of what `go-smtp` provides. Its one advantage is that `PlainAuth` refuses to send a credential over an unencrypted non-localhost connection; `go-sasl` has no such guard, so `internal/mailer` implements it (`ErrInsecureAuth`). Two of `go-smtp`'s behaviors are load-bearing here: `NewClientStartTLS` returns an unexported error for "this server has no STARTTLS", so the plaintext fallback matches the message text and a test pins it against a container; and the STARTTLS handshake sends its own greeting, so a STARTTLS session introduces itself with the client's default name rather than the sender's domain (a plaintext session is greeted explicitly with `Hello`).
- **Authorization as a declared table, not a per-handler check** (settled 2026-09-26): the alternative was a helper each handler calls at its top (`authz.RequireAdmin(ctx)`). The table wins because the policy of the whole surface is readable in one file, a new procedure is protected by default, and the public list is *derived* from it rather than kept beside it — the two-list drift is what the old `rpcPublicProcedures`/`restPublicRoutes` pair invited. The cost is that a rule is named per procedure, and a renamed contract breaks the build (which is the point). Upstream Pocket ID declares the same policy per route (`authMiddleware.Add()` vs `WithAdminNotRequired().Add()`), so the table is a port of that idea into Connect's shape.
- **Connect authentication middleware** (`connectrpc.com/authn` v0.2.0): adopted as the RPC surface's bearer-auth seam. It is an HTTP middleware, not a connect interceptor — the earlier note imagined an interceptor beside `rpcHandlerOptions`, and the library's actual shape is better: it authenticates before the request is decoded (an unauthenticated call costs no unmarshal) and takes the same handler options so refusals are marshaled in the caller's protocol across Connect, gRPC, and gRPC-Web. Its `InferProcedure`/`BearerToken` helpers cover the public-procedure exclusion model. A hand-rolled interceptor (~80 lines) was the alternative and loses on all three counts; the cost is the **Unstable** status (v0.x, so breaking changes are possible) on a small, core-shaped API (`AuthFunc`, `Middleware`, `Wrap`) — revisit the pin when it reaches 1.x. The REST twin and machine credentials (`X-API-Key`) stay with the `middleware/apikey.go` scaffold.
- **Request validation** (`connectrpc.com/validate` v0.7.0 + `buf.build/go/protovalidate`): adopted as the RPC surface's declarative validation. The constraints live in the contracts as `buf.validate.field` options (mirroring what the database enforces), the interceptor sits in `rpcHandlerOptions` beside the codec and the panic boundary, and a refusal is `invalid_argument` with a typed `buf.validate.ErrorInfo` detail. Evaluated against keeping the hand-written ozzo rules (`pkg/validate`): ozzo stays for the REST JSON bodies only — two systems enforcing the same rule on one surface is the drift this removes, not a pairing to grow. The well-known constraint options come from the `buf.build/bufbuild/protovalidate` buf module dependency. Costs, stated plainly: the interceptor is **Unstable** (v0.x — two breaking changes in its history: `WithValidator` at v0.2, `NewInterceptor` at v0.5) while protovalidate-go underneath is stable; and CEL brings a dependency chain (`cel-go`) that is not small. The proto rules are not a test substitute — the transport test pins each violated contract case against the real router.
- **OIDC protocol engine** (compared 2026-09-28, decision pending the user's pick — binds sub-phases b–d only; sub-phase a is engine-independent): `ory/fosite` (v0.46.1, last release Dec 2024 — OAuth2 core incl. PKCE, refresh, introspect, revocation, PAR, device flow, OIDC id_token flows; discovery, userinfo, and end-session are hand-built; schema `00004` is fosite-shaped because upstream Pocket ID uses it), `zitadel/oidc` (v3/v4, active, full OP incl. end-session and device auth; the RP half is OpenID Certified, the OP half is not), and `luikyv/go-oidc` (v0.25.0, MIT, 2024, single maintainer — full OP incl. PAR, JAR, DCR, CIBA, and the **only candidate already OpenID Certified**: Basic, Implicit, Hybrid, Config, Dynamic OP, FAPI 1.0/2.0 on openid.net's certified list, with the conformance suite in its CI). The user's target is OpenID certification for saka in the future, which weighs toward `luikyv/go-oidc`; the fallback is `zitadel/oidc`. Whichever lands, the protocol handlers mount as REST routes on chi and the storage adapter maps onto the `00004` tables.
- **tus, protocol-only, implemented in-house** (settled 2026-10-04): the resumable-upload protocol is adopted as a specification (tus 1.0.0 core + `creation-with-upload`, `termination`, `expiration`), never as the `tusd/pkg/handler` library. The library's filestore holds session state in `.info` files beside the bytes (a second manifest the engine cannot see), its S3 layout is a vocabulary the GC's key set cannot name, and embedding it would run a second auth surface beside the guard — the protocol's own headers carry all the state the engine needs, so the handler over the engine is the smaller system. The client side is `tus-js-client` (the debug probe page loads its UMD bundle from the CDN); the server holds no client dependency.
- **LogLayer transport pins**: `go.loglayer.dev/transports/otellog/v3` v3.0.0 was built against `go.opentelemetry.io/otel/log` v0.19.0, where `Record.Body()` returns `otellog.Value` and attributes are `otellog.KeyValue`. OTel moved `KeyValue` and `Value` into `go.opentelemetry.io/otel/attribute` in `otel/log` v0.20.0, so the transport does not compile above v0.19.0 (`undefined: otellog.StringValue`). `go.opentelemetry.io/otel/exporters/otlp/otlplog/otlploghttp` and `go.opentelemetry.io/otel/sdk/log` are held at v0.19.0 for the same reason: their `otel/log` floor has to agree with the transport's. (The `otlploggrpc` exporter was removed with the gRPC leg.) The core module (`go.opentelemetry.io/otel`, and `otel/sdk` with it) is on its own version line and stays free, and so are the trace and metric exporters (`otlptracehttp`, `otlpmetrichttp`, `exporters/prometheus`), which depend on the core module rather than on `otel/log`. Before bumping any of the three pinned modules, check that the transport still compiles; the failure is at the type level and shows up only when `otellog` is built. **`go get` on an unrelated OTel package will silently raise `otel/log` past the pin** — it happened while adding the metric exporter — so after any `go get`, re-check the three versions and `go mod edit -require` them back.
